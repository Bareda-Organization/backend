## 1. 배경 · 목표

노선 최적화와 배차 규칙은 앞으로 **지속 변경**이 예정된 영역. 현재 구조는 "알고리즘 통째 교체" 는 지원하나 **"제약 하나 추가" · "계산 단계 추가"** 에 취약.

목표는 셋.

1. 변경의 성격을 **정책(값) · 전략(구현체) · 단계(협력자)** 세 축으로 분리
2. 확정된 요구 5건(§3)을 담을 수 있게 **도메인 모델 확장**
3. 알고리즘 교체 시 **과거 노선의 재현 가능성**과 **품질 회귀 판정 수단** 확보

비목표 — 외부 솔버(OR-Tools 등) 도입, 실시간 재최적화, 다중 인스턴스 대응.

## 5. 도메인 모델 — 정차지 단위 전환 (D-1)

### 5.1 변경 전후

```
[현재]  route_plan 1 ── N route_plan_stop(seq, student_id NOT NULL, lat, lng, eta_s)

[변경]  route_plan 1 ── N route_plan_stop(seq, lat, lng, eta_s, kind, label, pinned)
                                  └── N route_plan_stop_rider(student_id)
```

### 5.2 `route_plan_stop` 신규 · 변경 컬럼

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `student_id` | **삭제** | `route_plan_stop_rider` 로 이관 |
| `kind` | varchar | `STUDENT_POINT`(학생 좌표) · `MERGED_POINT`(병합 지점) · `MANUAL_POINT`(관리자 임의 지점) |
| `label` | varchar null | 화면 표기명. 병합·수동 지점의 식별 수단 |
| `pinned` | boolean | true 면 재계산 시 `seq` 고정(§10) |

`kind` 를 두는 이유 — 병합 지점과 수동 지점은 **재계산 시 처리 규칙이 다름**. 병합 지점은 다음 계산에서 다시 산출되나, 수동 지점은 관리자가 지우기 전까지 보존.

### 5.3 `route_plan_stop_rider` 신설

| 컬럼 | 설명 |
|---|---|
| `route_plan_stop_id` | 부모 정차지 |
| `student_id` | 탑승·하차 학생 |
| `origin_lat` · `origin_lng` | **병합 전 원래 좌표** |

`origin_lat/lng` 보존 이유 — 병합으로 학생이 실제 집 앞이 아닌 지점에서 타게 되므로, 학부모 화면이 "원래 위치에서 N m 떨어진 공통 정차지" 를 설명할 근거가 필요. 이 값이 없으면 병합 후 원좌표 복원 불가.

### 5.4 엔티티 스케치

```java
// 정차지 — 학생 0명도 성립(관리자 임의 지점)
public class RoutePlanStop {
    private int seq;
    private double lat, lng;
    private long etaSeconds;
    private StopKind kind;
    private String label;
    private boolean pinned;
    @OneToMany(mappedBy = "stop", cascade = ALL, orphanRemoval = true)
    private List<RoutePlanStopRider> riders = new ArrayList<>();
}
```

### 5.5 소비처 동반 수정 (§2.2)

| 소비처 | 수정 방향 |
|---|---|
| `BusQueryService:100` | 정차 DTO 를 `students: [...]` 배열 보유 형태로 변경. **API 응답 구조 변경 — `API_SPEC.md` 갱신 필요** |
| `DriveSessionCommandService:153` | `boarded.contains(stop.getStudentId())` → 정차지의 **전원 승차 여부**로 판정 |
| `DriveSessionCommandService:162~169` | 접근·노쇼 알림을 정차지의 **탑승 학생 전원**에게 발송 |

## 6. 계산 파이프라인 (D-4)

### 6.1 계약

```java
public record RoutingContext(
        RoutingRequest request,
        Map<Long, LatLng> points,        // 1단계 산출
        List<StopGroup> groups,          // 2단계 산출
        List<StopGroup> ordered,         // 3단계 산출
        RouteResult road,                // 4단계 산출
        PlannedRoute planned) {          // 5단계 산출
    // 단계는 with...() 로 새 컨텍스트를 반환. 필드 재할당 부재
}

public interface RoutingStage {
    RoutingContext apply(RoutingContext ctx);
    default boolean supports(RoutingContext ctx) { return true; }
}
```

### 6.2 단계 구성

| 순서 | 단계 | 역할 | 교체 축 |
|---|---|---|---|
| 1 | `ResolvePointsStage` | 방향별 좌표 해석(`pointOf` 이관). 좌표 없는 학생 분리 | 단계 |
| 2 | `MergeStopsStage` | 반경 `mergeRadiusM` 내 좌표를 `StopGroup` 으로 병합 | 정책값 + 단계 |
| 3 | `OrderStopsStage` | `RouteEngine` 호출. 고정 정차(§10) 위치 보존 | 전략 |
| 4 | `ResolveRoadRouteStage` | `MapRouteClient` 호출 + 경유지 상한 구간 분할(현행 `resolveRoute` 이관) | 전략 |
| 5 | `ComputeEtaStage` | 누적 ETA 산출 · `PlannedRoute` 조립 | 단계 |

조립 위치는 설정 클래스 1곳.

```java
@Bean
List<RoutingStage> routePlanPipeline(ResolvePointsStage s1, MergeStopsStage s2, OrderStopsStage s3,
                                     ResolveRoadRouteStage s4, ComputeEtaStage s5) {
    return List.of(s1, s2, s3, s4, s5);
}
```

`@Order` 애너테이션 대신 명시적 목록을 쓰는 이유 — 순서가 **한 파일에서 읽힘**. 애너테이션 방식은 순서가 여러 파일에 흩어져 파이프라인 전체 형태를 추적 불가.

### 6.3 배차(assignment)는 파이프라인 밖 (D-2)

배차는 "테넌트 전체 → 버스별 학생 묶음", 노선 계산은 "버스 1대 → 정차 순서" 로 **입출력 차원이 다름**. 하나의 파이프라인에 억지로 합치면 컨텍스트 절반이 항상 비는 형태가 됨.

```
autoAssign(테넌트)
  ├ 좌표 해석
  ├ BusAssigner.assign(...)          ← 전략 포트 (파이프라인 밖)
  └ 버스마다 → routePlanPipeline 실행 ← 병합·순서·도로·ETA
```

병합이 배정 뒤에 오는 이유 — 다른 버스에 배정된 두 학생은 물리적으로 한 정차지에서 태우기 불가. 배정 전 사전 클러스터링이 필요해지면 `PreClusterStage` 를 배차 흐름 앞에 추가.

## 7. 전략 레지스트리 (D-5)

## 8. 정책 객체 (D-3 · D-7)

```java
public record RoutingPolicy(
        int mergeRadiusM,          // 기본 500 — 0 이면 병합 미수행
        int cutoffHours,           // 기본 6
        LocalTime pickupDepartAt,  // 기본 08:00 (D-7)
        LocalTime dropoffDepartAt, // 기본 17:00 (D-7)
        String engineName,         // 기본 "heuristic"
        String assignerName,       // 기본 "sweep"
        boolean autoPublishDaily   // 기본 true
) {}

public interface RoutingPolicyProvider {   // spec
    RoutingPolicy forTenant(Long tenantId);
}
```

- 초기 구현체는 `application.yml` 기본값을 전 테넌트에 반환. **테넌트별 정책 테이블은 실물 요구 발생 시 구현체 교체로 대응**(D-10) — 호출부는 이미 `forTenant(tenantId)` 로 받으므로 무수정
- `RoutingRequest` 는 로스터 · depot · 방향 · 서비스일 · 고정 정차 · 정책을 한 덩어리로 보유. 향후 제약은 **이 record 의 필드 추가**로 흡수

### 8.1 출발 예정 시각의 한계 (D-7)

정책의 방향별 고정 시각은 **버스마다 출발 시각이 다른 학원을 표현 불가**. 이번 범위에서는 수용하고, 버스별 시간표 요구가 확인되면 `BusSchedule` 엔티티로 승격 후 정책은 기본값 역할로 후퇴. 컷오프 계산이 `RoutingPolicy` 한 곳만 보도록 격리해 두면 이 승격이 국소 변경으로 끝남.

## 9. 컷오프 · 자동 배포 (조건 1·2)

### 9.1 컷오프 판정

```
변경 가능 여부 = now < (serviceDate + 방향별 출발시각) - cutoffHours
```

적용 지점 — 학부모 위치변경 승인 흐름(`schedule/command/LocationChangeCommandService`) · 관리자 시뮬레이션 채택(`RoutingCommandService.applySimulation`).

⚠️ **컷오프 통과 여부와 무관하게 관리자 수동 삽입(§10)은 허용** — 조건 3 이 명시.

### 9.2 자동 배포 스케줄러

- `routing/scheduler/DailyRoutePlanScheduler` 신설. cron 은 설정값
- 테넌트별 전 버스 · 양방향 계획 생성 → 정책 `autoPublishDaily` 가 true 면 승인·배포까지 수행
- 실패는 **버스 단위로 격리**하고 다음 버스로 진행(현행 `replanDirection` 의 예외 처리 관례 계승)
- 인스턴스 1개 전제(D-9) — 다중화 시 분산 락 필요. **문서에 명시하고 미구현**

| 항목 | 규칙 |
|---|---|
| 삽입 | 관리자가 버스 · 좌표 · **삽입 위치(seq)** · 학생(선택) 지정 |
| 저장 | `kind=MANUAL_POINT` · `pinned=true` · 지정 seq |
| 재최적화 시 | `pinned` 정차는 seq 유지. 나머지 정차만 순서 최적화 대상 |
| 도로·ETA | 순서 재계산은 미수행하되 **`MapRouteClient` 는 재조회** — 거리·ETA 가 갱신되지 않으면 기사·학부모에게 잘못된 도착 예정이 노출 |

`RouteEngine` 계약 변경 — `optimizeOrder(RoutingRequest)` 가 고정 위치를 인지해 **자유 정차만 재배열**. `HeuristicRouteEngine` 의 2-opt 는 고정 인덱스를 넘는 구간 반전을 후보에서 제외.

---

## 11. 계산 이력 · 재현성 (D-8)

`route_plan` 에 4개 컬럼 추가.

| 컬럼 | 값 예시 | 용도 |
|---|---|---|
| `engine_name` | `heuristic` | 어떤 알고리즘 산출물인지 |
| `assigner_name` | `sweep` | 상동 |
| `policy_snapshot` | `{"mergeRadiusM":500,"cutoffHours":6}` | 당시 정책값. 정책이 바뀌어도 과거 설명 가능 |
| `trigger` | `SCHEDULER` · `ADMIN` · `PARENT_CHANGE` · `REPLAN_EVENT` | 누가 촉발했는지 |

`version` 기반 이력은 이미 존재(재계산이 새 행 생성)하므로 컬럼 추가만으로 재현성 확보.

## 12. 품질 회귀 판정 (조건 5)

알고리즘 교체가 상시화되면 **"새 것이 나은가" 를 숫자로 판정할 수단**이 필수.

- 고정 좌표 세트(도심 밀집 · 교외 분산 · 혼합) 3종을 테스트 리소스로 보유
- 지표 — 총 주행거리 · 최대 학생 탑승시간 · 정차 수
- 기존 `HeuristicRouteEngineTest`("지그재그보다 나쁘지 않음") 는 유지하고, 상한 기준 회귀 테스트를 추가
- 지도 API 미호출(Haversine 기준)로 구성 — 외부 의존·비용 회피
