# 2026-08-21 · 운영 관제 대시보드 설계 (Prometheus + Grafana)

> **문서 성격.** 관측 스택 도입의 **설계 근거**. 실행 순서·체크리스트는 별도 구현 계획서가 담당하며,
> 이 문서는 "왜 이 구성인가 / 무엇을 넣고 무엇을 뺐는가 / 어디가 함정인가"를 기록.
>
> **상위 추적.** `backend/docs/plans/2026-08-21-모니터링-구현계획.md` 의 **2차 운영 모니터링**(MON-8~13) 이 대상이며,
> 이 설계가 그중 MON-8·MON-9·MON-10·MON-11 을 흡수.

## 1. 배경 — 현재 관측 수단의 실측

| 항목 | 현재 상태 | 근거 |
|---|---|---|
| actuator | 의존성 존재, **`health` 하나만 노출** · `show-details: never` | `backend/build.gradle:55` · `application.yml:94~101` |
| 외부 접근 | nginx 가 `/actuator` 를 **404 로 차단** | `infra/proxy/nginx.prod.conf:149` |
| 메트릭 저장소 | **부재** — `micrometer-registry-*` 의존성 0건 | `build.gradle` |
| 로그 | CloudWatch Logs 수집(6개 서비스), **평문** | `docker-compose.prod.yml:21~26` |
| 알람·APM | **부재. 장애 인지는 수동** | `docs/DEPLOYMENT.md:591` |

**조용히 고장 나는 지점이 실재.** `@Scheduled` 4개가 예외를 잡아 `log.warn` 만 남기고 진행하므로,
판정 로직이 통째로 실패해도 앱은 정상 기동 상태를 유지하며 **알림 미발송으로만 뒤늦게 발현**
(`location/scheduler/ConnectionLossScheduler.java:29~33`, 나머지 3개 동일 패턴).
그중 `SosEscalationScheduler` 는 안전 기능이라 정지 시 3분 미확인 SOS 가 에스컬레이션되지 않으며 **관측 수단이 전무**.

| 결정 | 값 | 대안 대비 근거 |
|---|---|---|

## 3. 구성

### 3.1 컨테이너

| 컨테이너 | 역할 | 메모리(개략) |
|---|---|---|
| `prometheus` | 지표 수집·시계열 저장 | ~300MB |
| `grafana` | 대시보드 | ~200MB |
| `postgres-exporter` | 커넥션·트랜잭션·락·DB 크기 | ~20MB |
| `redis-exporter` | 메모리·키 수·명령·축출 | ~15MB |
| `node-exporter` | 호스트 CPU·메모리·디스크 | ~20MB |
| **합계** | | **약 550MB** |

Kafka 브로커 지표는 **JMX exporter 를 두지 않음** — 브로커 내부보다 **애플리케이션의 소비 지연·실패**가 관측 목적에 부합하며,
그 값은 Spring 측 Micrometer Kafka 컨슈머 지표로 확보 가능. 컨테이너 1개와 JMX 설정 부담을 회피.

### 3.2 스크레이프 경로 — 기존 차단 정책 유지

```
prometheus ──(compose 내부 네트워크)──> backend:8080/actuator/prometheus     노출 부재
   nginx ──> /actuator                                                      404 (현행 유지)
```

`management.endpoints.web.exposure.include` 에 `prometheus` 를 추가하되 **외부 도달은 불가**.
`show-details: never` 도 유지 — `application.yml:91~92` 의 판단(상세 노출 시 DB URL·Redis 호스트 노출)은 그대로 유효.

### 3.3 Grafana 설정의 코드화

datasource·대시보드를 **파일 프로비저닝**으로 주입. 수동 생성은 컨테이너 재생성 시 소실되고 재현이 불가.
대시보드 JSON 은 저장소에 두어 리뷰·이력 추적 대상에 포함.

## 4. 범위 경계 — Grafana vs 관리자 웹

> **Grafana = "시스템이 살아 있는가" · 관리자 웹 = "운영이 잘 되고 있는가"**

### 4.1 Grafana 대상 (파이프라인 생존·처리량)

| 지표 | 형태 | 관측 목적 |
|---|---|---|
| 스케줄러 4종 마지막 성공 후 경과 | Gauge | 조용한 정지 감지 (MON-8) |
| 스케줄러 실패 누적 | Counter | 반복 실패 |
| Kafka 소비 실패 건수·소비 지연 | Counter·Gauge | 컨슈머 예외 삼킴 (MON-9) |
| 버스 위치 수신 건수 (`origin` 태그) | Counter | 보고 중단 여부 |
| STOMP 세션 수 | Gauge | 실시간 연결 생존 |
| 알림 발송 건수 (`type` 태그) | Counter | 알림 파이프라인 생존 |

### 4.2 Grafana 제외 (관리자 웹 소관)

승하차 기록·운행 세션 현황 · SOS 발생과 처리 상태 · 결석·시간변경 신고 현황 · 버스별·학생별 세부.

**부수 효과:** 이 경계를 지키면 지표에 **버스 id·학생 id 같은 식별자 태그가 미포함**.
cardinality 폭증 회피와 개인 식별 정보 미유입이 동시에 성립.

> ⚠ **현재는 관리자 웹에 해당 화면이 부재.** SOS 확인·결석 승인·승하차 조회 화면이 미구현이며
> (`docs/PRODUCT_SPEC.md` §12 의 O2·O3·O4), 백엔드 API 만 존재. 이 경계 확정은 **Grafana 에 넣지 않는다는 결정**이고,
> 실제 열람 가능성은 **관리자 웹 화면 구현이라는 별도 작업**에 의존. 이 설계의 범위 밖.

## 5. 지표 — 자동 확보 vs 계측 필요

### 5.1 의존성 추가만으로 확보 (`micrometer-registry-prometheus`)

| 지표군 | 내용 | 대시보드 용도 |
|---|---|---|
| `http.server.requests` | **URI 패턴·메서드·상태코드별** 요청 수·응답시간 히스토그램 | **API별 p95·p99·에러율의 근거** |
| JVM | heap·non-heap·GC·스레드·클래스 | 서버 상태 |
| HikariCP | 활성·대기·타임아웃 커넥션 | DB 커넥션 고갈 감지 |
| Tomcat | 스레드 풀·큐 | 요청 적체 |
| Kafka 컨슈머 | 레코드 지연·처리량 | 소비 지연 |

**히스토그램 활성화 필요.** 백분위수는 기본 비활성이며 `management.metrics.distribution.percentiles-histogram` 설정 필요.

### 5.2 계측 필요 (커스텀 Meter)

§4.1 의 6종. **별도 모듈 `src.backend.observability` 에 격리하고 도메인 코드는 수정하지 않음**(사용자 확정, 2026-08-21).

### 5.3 결합도 — 도메인 수정 0줄

계측을 도메인 메서드 안에서 호출하면 `observability` 와 도메인이 서로를 참조해 **양방향 의존**이 성립.
기존 확장점만 쓰면 **단방향(`observability` → 도메인)** 으로 유지 가능하며, 도메인 파일 수정이 **부재**.

| 지표 | 사용하는 확장점 | 도메인 수정 |
|---|---|---|
| 스케줄러 생존·실패 | `@Aspect` 가 `@Scheduled` 메서드를 감쌈 | **0줄** |
| Kafka 소비 실패 | `@Aspect` 가 `@KafkaListener` 메서드를 감쌈 | **0줄** |
| 버스 위치 수신 | `@EventListener(BusLocationUpdatedEvent)` — **이미 발행 중**(`BusLocationCommandService:55`) | **0줄** |
| 알림 발송 | `NotificationSender` 포트 구현체 추가 — **이미 `List<NotificationSender>` 주입**(`NotificationCommandServiceImpl:29`) | **0줄** |
| STOMP 세션 | `@EventListener(SessionConnectedEvent·SessionDisconnectEvent)` | **0줄** |

**대가:** `spring-boot-starter-aspectj` 의존성 1개 추가.
⚠ **Boot 4.0.0-M3 에서 `spring-boot-starter-aop` 에서 개명한 이름.** 구 좌표는 4.x BOM 에 부재해 버전 해석부터 실패 — `spring-boot-starter-web`→`webmvc`, `webflux`→`webclient` 와 같은 계열.

**이 격리가 성립하는 조건:** 위 확장점 5개가 **이미 존재**한다는 실측. 이벤트를 새로 발행하게 만들거나
포트를 새로 뚫어야 했다면 도메인 수정이 발생해 격리가 무너짐.

⚠ **AOP 로 감싸면 실패 시 계측만 하고 예외는 그대로 다시 던져야 함** — 삼키면 스케줄러 재시도·Kafka 재처리 동작이 변경됨.

## 6. 대시보드 4장

| # | 이름 | 내용 |
|---|---|---|
| 1 | **API 개요** | 엔드포인트별 요청 수·p95·p99·에러율, 느린 API 상위, 4xx/5xx 분리 |
| 2 | **서버 / JVM** | 스레드·커넥션풀·부하·메모리 — 상세는 §6.1 |
| 3 | **데이터 계층** | Postgres·Redis·Kafka — 상세는 §6.2 |
| 4 | **파이프라인 생존** | 스케줄러 4종 경과·실패, Kafka 소비 실패, 위치 수신 건수, STOMP 세션, 알림 발송 |

### 6.1 대시보드 2 — 서버 자체 상태 (패널 단위)

**스레드** — 요청 처리 능력의 포화를 직접 관측.

| 패널 | 지표 | 읽는 법 |
|---|---|---|
| JVM 스레드 수 | `jvm.threads.live` · `daemon` · `peak` | 지속 증가는 스레드 누수 |
| **스레드 상태 분해** | `jvm.threads.states{state=runnable\|blocked\|waiting\|timed-waiting}` | `blocked` 증가는 락 경합, `waiting` 급증은 외부 호출 대기 |
| Tomcat 스레드 풀 | `tomcat.threads.busy` / `tomcat.threads.current` / `tomcat.threads.config.max` | busy 가 max 에 근접하면 요청 적체 시작 |
| 요청 큐 대기 | Tomcat 큐 길이 | 0 이 아니면 이미 포화 |

⚠ **Redis 지연과 직결.** `spring.data.redis.timeout` 미설정(Lettuce 기본 60초, MON-14)이라
Redis 응답이 지연되면 요청 스레드가 최대 60초 점유. `blocked`·`waiting` 증가와 `tomcat.threads.busy` 포화가
**동시에 나타나는 형태**가 그 신호이며, 이 패널 조합이 MON-14 의 발현을 관측 가능하게 함.

**데이터베이스 커넥션** — HikariCP.

| 패널 | 지표 | 읽는 법 |
|---|---|---|
| 커넥션 상태 | `hikaricp.connections.active` · `idle` · `pending` | `pending` 이 0 을 넘으면 풀 부족 |
| 커넥션 획득 대기시간 | `hikaricp.connections.acquire` (백분위수) | 증가는 풀 고갈의 선행 신호 |
| 커넥션 타임아웃 | `hikaricp.connections.timeout` | 발생 자체가 장애 |
| 커넥션 사용시간 | `hikaricp.connections.usage` | 긴 트랜잭션 탐지 |
| 풀 크기 대비 사용률 | `active / max` | 상시 80% 초과면 풀 증설 검토 |

**부하·자원** — 호스트와 프로세스를 분리해서 봄.

| 패널 | 지표 | 읽는 법 |
|---|---|---|
| 시스템 load average | `node_load1` · `load5` · `load15` | vCPU 수(t3.medium=2) 대비 해석 |
| CPU 사용률 | 프로세스(`process.cpu.usage`) · 시스템(`system.cpu.usage`) | 둘의 격차로 "우리 앱인가 이웃 컨테이너인가" 판별 |
| 메모리 | heap 사용/최대 · non-heap · 호스트 가용 · 스왑 | **§7 예산 초과 여부를 여기서 확인** |
| GC | 수집 횟수 · **일시정지 시간 합** | 일시정지 급증은 p99 응답시간 악화로 직결 |
| 디스크 | 사용률 · I/O 대기 | EBS 30GB 대비 |
| 파일 디스크립터 | `process.files.open` / `max` | 소켓 누수 탐지 |

### 6.2 대시보드 3 — 데이터 계층 (패널 단위)

| 대상 | 패널 |
|---|---|
| Postgres | 활성 커넥션 수 / `max_connections` 대비 · 커밋·롤백률 · **락 대기 수** · 데드락 누적 · DB 크기 · 캐시 적중률 |
| Redis | 사용 메모리 / `maxmemory`(128MB) 대비 · **축출(evicted) 건수** · 키 수 · 초당 명령 수 · 연결 클라이언트 수 |
| Kafka | 컨슈머 그룹별 **소비 지연(lag)** · 처리량 · 소비 실패 |

⚠ **Redis 축출은 이 프로젝트에서 특별한 의미.** `maxmemory 128mb` + `allkeys-lru` 설정(`docker-compose.prod.yml:56`)이라
메모리가 차면 **위치 좌표가 TTL 만료 전에 축출**됨. 그 경우 관제 지도에서 버스가 사라지는데 원인이 TTL 이 아니라 메모리 압박이며,
축출 패널이 없으면 두 원인을 구분 불가.

**HikariCP 와 Postgres 커넥션을 함께 보는 이유:** 앱이 보는 풀 상태와 DB 가 보는 실제 세션 수가 어긋나면
커넥션 누수 또는 풀 설정 오류. 한쪽만으로는 판별 불가.

## 8. 단계

**1단계 — 로컬 완성.** `docker-compose.yml` 에 5개 컨테이너 추가, `localhost:3000` 에서 4장 검증.
**2단계 — 운영 노출(후속).** `docker-compose.prod.yml` + nginx 서브도메인 + IP 허용 목록.

2단계를 1단계와 동시에 만들지 않는 근거: IP 허용 목록은 실제 접속 IP 확정이 선행 조건이고,
`nginx.prod.conf` 가 환경변수를 미지원해 값이 파일에 직접 기재됨(`DEPLOYMENT.md` 의 도메인 자리표시자와 동일한 제약).

## 9. 보안

- **Prometheus·exporter 포트를 호스트에 미개방.** compose 내부 네트워크에서만 접근.
- **`/actuator` 외부 차단 유지.** 이번 변경으로 완화 부재.
- **Grafana 기본 계정 변경 필수.** `admin/admin` 유지 시 2단계 노출 시점에 즉시 문제.
- **지표에 개인 식별자 미포함** (§4.2).

## 11. 검증 방법

**측정으로만 완료를 판정.** 아래를 실제로 재현.

1. `GET /actuator/prometheus` 가 컨테이너 내부에서 200, **외부에서 404**
2. Prometheus targets 5개 전부 `UP`
3. `/api/buses/{id}` 를 서로 다른 id 로 여러 번 호출 후, 시계열이 **id 별로 분리되지 않음**(R1 음성 대조)
4. 스케줄러를 인위적으로 실패시켰을 때 해당 Gauge 가 증가하고 대시보드에 발현 (MON-8 의 완료 조건)
5. 버스 위치 보고 중단 시 수신 Counter 증가 정지
6. 컨테이너 재생성 후 대시보드 4장이 **프로비저닝으로 자동 복원**
7. 관측 스택 기동 전후 `docker stats` 로 실사용 메모리 비교 — §7 예산과 대조
8. 부하를 걸어 `tomcat.threads.busy`·`hikaricp.connections.active` 가 **실제로 증가**하는지 확인 —
   값이 0 에 고정되면 해당 MeterBinder 미등록이며, 패널만 있고 지표가 부재한 상태가 됨
