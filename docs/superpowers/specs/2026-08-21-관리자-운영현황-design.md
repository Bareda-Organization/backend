# 2026-08-21 · 관리자 운영 현황 API 설계 (BG-21 · BG-22)

> **문서 성격.** 관리자 웹이 운영 상황을 보기 위한 **백엔드 API 설계**. 실행 순서는 별도 구현 계획서가 담당.
> **상위 추적:** `backend/docs/plans/2026-08-21-백엔드-MVP-갭-보완.md` **T7**.

**경계.** 관제 대시보드 작업(`2026-08-21-관제-대시보드-design.md`)에서 그은 선의 반대쪽이다 —
**Grafana = "시스템이 살아 있는가" · 관리자 웹 = "운영이 잘 되고 있는가".**

---

## 1. 배경 — 이미 있는 것과 없는 것

**있는 것 (재구현 금지)**

| 요소 | 기존 수단 |
|---|---|
| 버스 실시간 위치 | `GET /api/locations/buses` · STOMP `/topic/tenant/{id}/bus-locations` |
| 버스 경로 | `RoutePlan`(polyline·정차·누적 ETA) · `GET /api/route-plans/{id}` |
| 명단 | `GET /api/buses/{id}` 의 `RosterEntry` · `GET /api/drive-sessions/{id}/roster` |
| 승하차 기록 | `GET /api/ride-events/bus/{busId}` |
| 미승차 임계 | `NotificationThresholds` (미승차 10분·근접 5분·SOS 3분) |

**없는 것 — 이 설계의 실체**

1. **탑승 상태가 명단에 부재.** `BusDetailResponse.RosterEntry`(`bus/dto/BusDetailResponse.java:28`)는 학생 정보·보호자·승하차 지점만 담고 **탑승 여부를 담지 않음.** 프론트가 승하차 기록을 따로 받아 대조하는 구조.
2. **"누락 학생" 조회 수단 부재.** 미승차는 `NO_SHOW` 알림으로만 나가고 조회 API 미존재.
3. **운영 이상 징후를 모아 보는 수단 부재.** 정원 초과·좌표 미설정·미배정은 각각 다른 조회를 조합해야 확인 가능.

## 2. 확정 사항 (2026-08-21)

| 결정 | 값 | 근거 |
|---|---|---|
| API 형태 | **운영 현황 전용 엔드포인트 신설**(`/api/operations/*`) | 프론트가 4개 조회를 화면에서 조립 중(`PRODUCT_SPEC` §11.2). 조각을 늘리는 대신 합침 |
| 상태 판정 | 5단계 — `ALIGHTED`·`BOARDED`·`PENDING`·`UPCOMING`·`MISSED` (§3) | 누락 임계는 `NotificationThresholds` 재사용. 새 규칙 미도입 |
| 실시간 갱신 | **폴링 유지** | STOMP 전환은 `MON-6` 과 함께 별도 처리 |
| 선행 | **`BG-7`(진행 중 세션 조회) 포함** | 없으면 전체 이력을 받아 앱이 골라야 함 |
| BG-22 범위 | 4개 영역 전부(사용자 확정) — 운행 요약·미처리·배차 이상·지연 | §5 |

## 3. 탑승 상태 판정 규칙

**5단계.** 한 학생의 상태는 승하차 기록과 정차 도달 여부로 결정.

| 상태 | 조건 | 화면 의미 |
|---|---|---|
| `ALIGHTED` | 하차(`ALIGHT`) 또는 인계(`HANDOVER`) 기록 존재 | 내림 |
| `BOARDED` | 승차(`BOARD`) 기록 존재, 하차 기록 부재 | 타고 있음 |
| `UPCOMING` | 기록 부재 + 해당 정차 **미도달** | 탑승 예정 |
| `PENDING` | 기록 부재 + 정차 **도달**, 도달 후 경과 < 임계 | 아직 안 탐 |
| `MISSED` | 기록 부재 + 정차 도달 후 경과 ≥ **미승차 임계(10분)** | 누락 |

**정차 도달 판정.** `세션 시작 시각 + 계획 ETA(누적 초)` 로 **추정**.

⚠ **추정임을 응답과 문서에 명시.** 실제 정차 도달 시각을 기록하는 수단이 부재해(`RideEvent` 는 승하차 시점만 기록)
계획 ETA 를 근거로 삼는다. 지연 운행 시 실제보다 이르게 "도달"로 판정되어 `MISSED` 가 조기 발생할 가능성.
정확도를 올리려면 정차 도달 이벤트 기록이 선행 조건이며 이 설계의 범위 밖.

**세션 미시작 시.** 전원 `UPCOMING`. 판정 기준 시각이 부재하므로 도달 계산을 하지 않음.

## 4. BG-21 — 운행 현황 API 2종

### 4.1 `GET /api/operations/buses` — 학원 전체 요약

관제 화면의 **목록·지도 마커**용. 버스마다 한 줄.

```
busId · busName · direction · sessionStatus(NOT_STARTED|IN_PROGRESS|COMPLETED)
location { lat · lng · recordedAt · origin · stale }
counts   { total · boarded · alighted · pending · upcoming · missed }
```

- `location.stale` — 좌표 TTL(15초) 만료로 조회 불가한 상태. **좌표 부재와 "보고 중단"을 구분**(관제 대시보드에서 확인한 구분과 같은 취지).
- `counts.missed` 가 0 보다 크면 화면이 즉시 강조하는 값.

### 4.2 `GET /api/operations/buses/{busId}` — 버스 1대 상세

선택한 버스의 **학생별 상태 + 경로**.

```
bus · session { id · direction · status · startedAt }
routePlan { version · polyline · stops[ seq · name · lat · lng · etaSeconds · reachedAt(추정) ] }
students[ studentId · name · status(§3) · stopSeq · stopName · recordedAt · guardians[] ]
```

⚠ **정류장 이름을 응답에 포함.** 기존 `RoutePlanResponse` 는 정류장명을 담지 않아 화면이 "N번 정차"로만 표시하는 갭이 있음(`PRODUCT_SPEC` §12 F10). 이 API 가 그 갭을 함께 해소.

## 5. BG-22 — 운영 현황 요약 API

`GET /api/operations/summary` — 관리자 첫 화면용. 사용자가 확정한 4개 영역.

```
today        { busesTotal · running · completed · notStarted · byDirection{PICKUP,DROPOFF} }
pending      { sosOpen · attendancePending · scheduleChangePending }
dispatch     { overCapacityBuses[] · studentsWithoutCoords[] · busesWithoutCrew[] · unpublishedPlans[] }
anomalies    { staleLocationBuses[] · longRunningSessions[] · delayedBuses[] }
```

**각 항목의 근거와 한계**

| 항목 | 판정 | 한계 |
|---|---|---|
| `pending.sosOpen` | `SosStatus.OPEN` 건수 | 없음 — `findByStatus` 계열 이미 존재 |
| `pending.*Pending` | 결석·시간변경의 `PENDING` 건수 | 없음 |
| `dispatch.studentsWithoutCoords` | `dropoffLat/Lng` 또는 승차 정류장 미설정 학생 | **자동배차에서 조용히 제외되는 원인** — 지금은 배차 실행 시에만 드러남 |
| `dispatch.overCapacityBuses` | 배정 인원 > 좌석 정원 | `RouteResponse.overCapacity` 로 이미 계산되나 모아 보는 수단이 부재 |
| `dispatch.busesWithoutCrew` | 기사 또는 선탑자 미배정 | 승하차 기록은 **선탑자만** 가능하므로 선탑자 부재는 운행 불가 |
| `dispatch.unpublishedPlans` | 당일 계획이 `PUBLISHED` 미도달 | 배포 전에는 기사 앱에 노선이 안 보임 |
| `anomalies.staleLocationBuses` | 좌표 TTL 만료 + 세션 진행 중 | 운행 중인데 위치가 안 오는 상태 |
| `anomalies.longRunningSessions` | 세션 시작 후 과다 경과 | 임계값 결정 필요 — 종료 처리를 잊은 경우 탐지 |
| `anomalies.delayedBuses` | 계획 ETA 대비 지연 | ⚠ **정확도 낮음.** §3 과 같은 이유(실적 기록 부재)로 추정치. 응답에 추정임을 명시 |

### 5.1 추가 항목 (사용자 요청, 2026-08-21) — 운영자가 실제로 확인해야 하는 것

§5 의 4개 영역 외에, **관리자가 운영 중 확인해야 하나 지금은 볼 수단이 전무한 것**을 더한다.
전부 **기존 필드로 뒷받침되는 것만** 넣는다 — 근거 없는 항목은 만들 수 없는 API 가 된다.

| 항목 | 응답 위치 | 근거 필드·메서드 | 왜 필요한가 |
|---|---|---|---|
| **보험 만료·임박 차량** | `compliance.insuranceExpiring[]` | `Bus.insuranceExpiry`(`bus/entity/Bus.java:62`) | 만료 차량 운행은 법적 문제. **실측(2026-08-21): 1호차가 2026-08-15 만료로 6일째 만료 상태이나 어디에도 노출 부재** |
| **오늘 발송된 알림 이력** | `notifications.today[]` | `NotificationLogRepository.findByTenantIdOrderByCreatedAtDesc` | 학부모 문의 응대에 필수 — 무엇이 나갔는지 모르면 답변 불가 |
| **누락 학생의 보호자 연락처** | `BG-21` 상세 응답의 `students[].guardians[]` | 기존 roster 의 보호자 정보 | **누락을 발견해도 연락 수단이 화면에 없으면 그 화면은 무용** |
| **기사·선탑자 배정 현황** | `dispatch.crewAssignment[]` | `Bus.driver` · `Bus.attendant` | **선탑자 미배정이면 승하차 기록 자체가 불가**(불변조건 I-1) |

**임계값**
- 보험: **만료됨** / **30일 이내 임박** 두 단계로 나눈다. 만료는 즉시 조치 대상, 임박은 갱신 준비 대상이라 성격이 다르다.
- 알림 이력: **당일분**만. 전체 이력은 기존 `GET /api/notifications` 가 담당하므로 중복 부재.

⚠ **알림 이력에 개인 식별 정보가 포함된다.** 관제 대시보드(Grafana)에는 식별자를 넣지 않기로 했으나(§4.2 경계),
관리자 웹은 **원래 개인정보를 다루는 화면**이라 기준이 다르다. 다만 `@CanMonitorOperations` + `TenantGuard` 로
소속 학원 범위를 벗어나지 않게 한다.

---

## 6. 인가

전부 **관리자 전용**. 기존 `@CanMonitorOperations` 를 재사용하고 `TenantGuard` 로 학원 격리.
학원 관리자는 `tenantId` 생략 가능, 플랫폼 관리자는 필수 — 기존 관제 API 와 동일 규약.

---

## 7. 성능

- 버스 N대 × 학생 M명을 조회하므로 **N+1 회피가 필수.** `bus/query/BusQueryService.java:53` 의 배치 조회(`findByAssignedBusIdIn`) 패턴을 따름.
- 승하차 기록은 **당일·해당 버스로 좁혀 한 번에** 조회하고 메모리에서 학생별로 분배.
- ⚠ **페이지네이션 미도입**(`BG-11`). 버스 수가 학원당 수십 대 규모라 당장은 문제 부재하나, 전면 도입 시 함께 처리.

---

## 8. 범위 밖

- **프론트 화면 구현** — 이 설계는 API 까지. 화면은 별도.
- **STOMP 실시간 전환** — `MON-6`.
- **정차 도달 이벤트 기록** — §3 의 추정을 실측으로 바꾸려면 필요하나 별도 항목.
- **관리자 CRUD 화면**(`PRODUCT_SPEC` §12 O4) — 별개.
- **알림 발송** — 이 API 는 조회 수단이며 통지 수단이 아님.
