## 2. 공통 — 가입 · 승인 · 로그인 · 차단 · 설정

### UF-X-01. form 회원가입 · 학원 선택

`[회원가입 폼 입력 — 아이디·비밀번호·이름·연락처]` → `[역할 선택 — 학부모/학생/기사/동승자/관계자]` → `[학원 검색 — 학원명 또는 학원 코드]` → 결과 `{학원명} · {지역} · {학원 코드}` 확인 → `[선택]` → `POST /auth/signup` → `SignupRequest` 생성 · 계정 `pending` → 승인 대기 화면

**분기 · 예외**

- (아이디 중복) → ✕ 인라인 유효성 에러 — 다음 단계 진행 불가
- (학원 미선택) → ✕ 제출 버튼 비활성
- (검색 결과 부재) → "학원을 찾을 수 없습니다 — 학원에 문의해 주세요". 사용자가 학원을 생성하는 경로 부재
- (비활성 학원) → 검색 결과에서 제외 — 신규 가입 차단 (O-01)
- (역할 = 관계자) → 승인 대기열이 **메인 관리자** 콘솔로 전달 (C-01 · O-02)
- (역할 = 관계자 · 해당 학원에 관계자 1명 존재) → 메인 관리자 승인 단계에서 ✕ 초과 승인 차단 (학원당 1명)
- (메인 관리자) → 가입 경로 자체가 부재 — 내부 발급

### UF-X-02. 승인 대기 · 거절 · 재신청

`pending` → 승인 대기 화면(`GET /auth/signup-status`) — 신청 학원 · 신청 일시 · 현재 상태 · 학원 문의처 · `로그아웃` → 관계자(또는 메인 관리자) 수락 + 레코드 연결 → `active` → 역할별 홈

**분기 · 예외**

- (`pending` 상태로 타 화면 접근) → ✕ 서버 인가 계층 403 — 홈 · 명단 · 노선 · 실시간 위치 · 알림 목록 · 설정 전부 차단
- (`pending` 로그인 직후) → **푸시 단말 등록·해지 가능** — 승인·거절 결과를 받을 단말이 필요해 허용 API 에 포함 (FEATURE_SPEC NTF-12 · §3.6)
- (`pending` 수신 알림) → 승인·거절 결과만. 운행 알림은 대상 밖
- (거절 `rejected`) → 같은 화면에 거절 사유 표시 + `[학원 재선택 · 재신청]` 진입점 → `POST /auth/signup/reapply`
- (수락 시 레코드 연결 누락) → ✕ 서버가 승인 처리를 거부 — 연결 부재 계정은 로그인은 되나 데이터 조회 불가 (AUTH-11)

### UF-X-03. 로그인 · 자동 로그인

`[아이디·비밀번호 입력]` → `POST /auth/login` → access(단기) + refresh(장기) 발급 → 계정 상태 판정 → `active` 면 역할별 홈

**분기 · 예외**

- (앱 재실행) → 기기 보안 저장소의 refresh 로 access 자동 재발급 — 자동 로그인 기본 (C-14)
- (웹 새로고침 · 탭 재개) → 브라우저가 보관한 HttpOnly 쿠키로 access 자동 재발급. 웹은 access 를 메모리에만 두므로 **새로고침마다 이 경로를 거치는 것이 정상** (C-14 · API_SPEC §1.2.1)
- (refresh 만료 · 로그아웃 · 계정 차단) → 토큰 무효화 → 로그인 화면으로 이동 후 재로그인 요구
- (로그아웃 진입점 — 앱) → **두 앱 모두 홈 머리말 오른쪽 `[로그아웃]`** → 확인 대화 1회 → `POST /auth/logout`. 학부모 앱은 설정 화면 맨 아래에도 둔다(2026-09-29 `Ruling 362` — 설정 안에만 있어 찾지 못했다)
- (`pending` · `rejected`) → 로그인은 성공하되 승인 대기 화면으로 고정 (UF-X-02)
- (`blocked`) → ✕ 로그인 실패 — 해제는 메인 관리자만 (UF-O-03)

### UF-X-04. 로그인 실패 누적 · 계정 차단

`[비밀번호 오입력]` → 실패 횟수 누적 → **5회** 도달 → 계정 상태 `blocked` → ✕ 이후 모든 로그인 실패

**분기 · 예외**

- (차단 단위) → **계정 단위**. IP 차단 부재 — 학원 와이파이·가정 공용 회선의 무관한 사용자까지 잠기는 것을 방지 (C-11)
- (사용자 자력 해제) → 경로 부재. 메인 관리자만 해제 (UF-O-03)
- (아이디·비밀번호 분실) → `[전화번호 인증]` 또는 `[관리자 경유 복구]` (AUTH-08). **SMS 연동(`PRD` F-05) 전까지 전화번호 인증은 `503`** — 학부모·학생·매니저는 학원에 요청해 관계자가 초기화(`API_SPEC §5.22`), 관계자는 메인 관리자(`§6.7`) (2026-09-25 `Ruling 329`)

### UF-X-09. 설정 — 비밀번호 변경 · 단말 등록

**2026-09-13 신설 · 2026-09-14 번호 정정(`UF-X-05` → `UF-X-09`).** 화면은 이미 구현돼 있는데 이 문서에
대응 절이 없어 `AUTH-07`·`NTF-12` 의 조작 순서가 정본에 부재했다(`FE-R2` 이월 4).
**새 기능 ID 를 만들지 않는다** — `FEATURE_SPEC` 의 것을 참조.

⚠ **신설 당시 `UF-X-05` 로 붙였는데 그 번호는 아래 `§8` 의 "일일 배차 · 확정 노선 산출" 이 이미
쓰고 있었다** — 한 문서에 같은 ID 가 둘이라 `defines UF-X-05` 가 어느 절을 가리키는지 갈리지 않았다.
**옛 절 쪽이 이기고 이 절이 옮겼다** — 옛 절은 `ERD.md §3.3` 과 `ConfirmedRoute.java:18` 을 포함해
9곳이 참조하는데 이 절은 계획서만 참조했다. `FE-R3` 의 `DOC` 좌석이 다른 항목을 판정하다 발견.

#### 비밀번호 변경 (AUTH-07)

`[설정 진입]` → `[현재 비밀번호 · 새 비밀번호 입력]` → `POST /auth/password` →
**기존 refresh 토큰 전량 무효화** → `[다시 로그인]`

매니저 앱(기사·동승자)은 설정 화면이 없어 **홈 머리말의 `[비밀번호 변경]` 아이콘**이 진입점이다 (R32 M13).

**분기 · 예외**

- (현재 비밀번호 불일치) → ✕ `401 INVALID_CREDENTIALS` — **계정 존재 여부는 드러내지 않는다**(로그인 상태이므로 해당 없음)
- (새 비밀번호 규칙 위반) → ✕ `422 VALIDATION_FAILED`
- (로그인 상태 요구) → 비로그인 진입 경로 부재. 분실은 `UF-X-04` 의 복구 경로(AUTH-08)
- ⚠ (성공 후) → **다른 기기의 세션도 함께 끊긴다.** 웹이면 쿠키 삭제 지시가 함께 온다(`§2.7` 과 같은 형태)
- (제출 중) → 중복 제출은 막힌다 — 진행 표시는 `FE-R2` 목표 10 대상

#### 단말 등록 · 해지 (NTF-12)

`[앱 진입]` → `[푸시 토큰 획득]` → `POST /me/devices` → `201` → **이후 알림 수신 대상**
`[알림 끄기]` → `DELETE /me/devices/{token}`

**분기 · 예외**

- ⚠ (`pending` 계정) → **등록 가능하다. 대기 화면 안에서 한다** — `PendingApprovalScreen` 에
  등록 패널을 직접 둔다(Ruling 267, 옵션 A). **설정 화면을 거치지 않는다** — `§1.4` 가
  `pending` 의 호출 가능 목록을 4개로 제한해 설정 화면이 그 밖이기 때문
- (같은 기기 재등록) → 토큰을 덮어쓴다. **행이 늘지 않는다**(`(account_id, device_id)` 기준)
- ⚠ (등록이 없으면) → **알림 전 종류가 도달하지 않는다.** 서버가 발송 대상 단말을 특정하지 못한다 —
  승인 결과 푸시도 여기에 걸린다

## 3. 학부모 플로우

### UF-P-01. 자녀 연결 — 인증 코드 (P-02 · S-05, Ruling 324)

**2026-09-22 개정 — 학부모의 사전 연결 요청 단계를 없앴다.** 학생 앱에서 `[연결 코드 생성]`(`POST
/me/link-code`, 선행 조건 없음) → 학생이 코드를 학부모에게 구두·메시지로 전달 → 학부모 앱
`[코드 입력]` → `POST /me/students/link` → 서버 인증 → `GuardianStudent` 생성 → 홈에 자녀 반영

**분기 · 예외**

- (다자녀) → 자녀 1명당 같은 프로세스 반복 — 학부모 재가입 부재
- (코드 만료 · 불일치) → ✕ 연결 실패 → 학생이 `[코드 재생성]`
- (학생 계정 미보유) → ✕ 연결 불가 — 서비스 대상은 휴대전화(학생 계정) 보유 학생 (C-13)
- (동생 신규 등록) → 관계자가 기존 학부모 계정에 연결만 추가하지 않는다 — **가입 승인은 계정 활성화만
  하고(AUTH-11 예외), 연결은 이 화면의 코드 절차로 별도 진행** (Ruling 324)
- (퇴원) → 연결 해제, 과거 이력은 보존
- (연결된 자녀 0명) → 오류가 아니다. 홈 화면이 "연결된 자녀가 없습니다" 안내와 이 화면 진입 버튼을 노출

### UF-P-02. 다자녀 화면 전환

홈 → (자녀 2명 이상) 자녀 선택 UI 노출 → `[자녀 선택]` → 실시간 위치 · 상세 노선 · 탑승 토글 · 변경 신청이 선택 자녀 기준으로 전환

**분기 · 예외**

- (자녀 1명) → 선택 UI 비노출
- (알림) → **자녀 선택과 무관하게 전 자녀 알림 수신**. 모든 문구에 자녀 이름 포함 (ATT-03)
- (자녀별 독립성) → 자녀마다 호차·노선·승하차지·탑승 여부가 각각 다름 — 형제의 동일 호차 보장 부재

### UF-P-03. 요일별 등하원 주소 설정 (P-05)

홈 → `[설정 · 요일별 주소]` → 요일(월~일) × 등원/하원별 주소 직접 기입 → `PATCH /students/{id}/weekly-address` → 서버 정상 처리 확인 → "처리되었습니다" 표시 → 저장 완료

**분기 · 예외**

- (기본 주소) → 개념 부재. 노선 산출은 요일별 주소가 유일 기준 (C-12)
- (미변경 요일) → 매주 같은 요일의 주소가 반복 적용
- (같은 날 일일 변경 존재) → **일일 변경 > 요일별 주소** — 해당 일만 일일 변경 적용, 이후 요일별 주소로 복귀 (P-06)
- (서버 처리 실패) → "처리되지 않았습니다" 명시 · 기존 값 유지 (C-10)

### UF-P-04. 회차별 탑승 토글 — ①구간 (P-03 · ATT-01)

홈 → (자녀 2명 이상) 자녀 선택 → `[등원/하원 스위치 OFF]` → **확인 창**(끌 때만 — 켤 때는 바로 · 구간별 문구: ①구간 "바로 반영" · ②구간 "관리자 승인 필요 · 이 회차에서 1번" · ③구간 "되돌릴 수 없음", 취소하면 요청 부재) → `PATCH /students/{id}/runs/{runId}/intent` → 서버 확인 → 즉시 저장 · `RunRider.status` = `absent` → 매니저 앱 명단에서 개인 행 제외(집계는 "미등원 N명" 유지) → **재최적화 호출 부재** — ①구간 동안 회차는 `idle` 이라 확정 노선 자체가 부재, 출발 30분 전 확정 배치(UF-X-05 4단계)가 최신 입력을 읽어 노선에 반영 → 관계자 통지 (FEATURE_SPEC C-04 ① 각주 · RTE-03 · ATT-02, Ruling 198)

**분기 · 예외**

- (기본값) → 등원·하원 스위치 모두 ON
- (학부모 알림) → **발송 부재** — 학부모가 스스로 설정한 값 (C-02)
- (승하차지 잔여 탑승자 0명) → **①구간은 재최적화 대상 부재 — 확정 배치 산출 시 노선에서 제거**(Ruling 198). ①구간에는 `skipped` 가 성립하지 않음. `skipped` 발생 경로는 **③구간 미등원**과 **운행 중 미승차** 둘뿐 (C-05)
- (OFF → ON 되돌리기 · ①구간) → 가능 — 재최적화 대상
- (②구간 진입) → UF-P-05 로 분기
- (③구간 = `Run.status` = `moving` 이후 · OFF) → **승인 없이 즉시 수용** — `absent` 기록. **노선 변경 부재**, 해당 승하차지는 **경로상 경유하되 정차하지 않음**(`skipped`) + 기사·동승자 즉시 푸시 (C-04 ③ · C-05)
- (③구간 · OFF → ON 되돌리기 · 위치 변경) → ✕ 불가 — 이미 배포된 노선에 승하차지를 되살릴 경로가 부재
- (서버 처리 실패) → 기존 상태 복구 · "처리되지 않았습니다" (C-10)
- (학생 계정) → 이 기능 비노출 — 학부모 전용

### UF-P-05. 회차별 탑승 토글 — ②구간 승인 경유 (C-04)

출발 **30분 전** 도달 → 토글 화면에 남은 시간 카운트다운 노출(확정 전에는 "확정까지 N시간 M분") → `[스위치 OFF]` → 확인 창("승인 요청은 이 회차에서 1번만") → 승인 대기로 접수(즉시 반영 부재) → 관계자에 푸시 (REQ-05) → 학부모 화면 상태 `pending` → 관계자가 **전/후 노선 대조 확인 후 승인** → `absent` 처리 + **노선 재최적화·재배포** → 기사·동승자 푸시 + 학부모 통보

**분기 · 예외**

- (승인 효과) → **재최적화 후 재배포** — 빠진 승하차지가 노선에서 제거되고 순서·소요시간이 갱신. 관리자가 승인 화면에서 전/후 대조를 보고 선택 (A-05)
- (거절 효과) → **기존 경로 유지** — 재최적화 부재
- (한도) → **회차당 1회** — 단위는 회차(`Run`). 등원 회차와 하원 회차가 각각 1회씩이며 서로 한도를 공유하지 않음. 소진 후 재신청은 ✕ "금일은 변경할 수 없습니다" 안내
- (거절) → 사유와 함께 학부모 통지 · 현상 유지
- (출발 시각 도달 또는 운행 시작 · 관계자 미응답) → ✕ **자동 거절** — 둘 중 먼저 오는 시점에 마감, **기존 노선 그대로 유지** + 학부모 통지 · **횟수 미소진** (X-02)
- (서버 처리 실패) → 기존 상태 복구 · **횟수 미소진** — 재신청 가능 (C-10)
- (②구간 추가) → ✕ 불가. ②구간에 수용되는 요청은 **미등원(제외)** 뿐이며 관계자의 강제 추가도 예외 부재 (A-06)

### UF-P-06. 일일 스케줄 변경 · 탑승 위치 변경 신청 (P-06 · REQ-01·02)

홈 → `[일정]`(항상 노출) → `[날짜 선택]`(**오늘 · 내일** 두 가지, 한국 시간 기준 — 고른 날짜로 `GET /students/{id}/runs?date=` 조회, 그날 회차가 없으면 "그날 운행이 아직 없습니다" 안내 · Ruling 366) → `[대상 회차 선택]`(그날 회차 중 하나) → `[변경 승하차 주소 입력]` → `[사유 입력(선택)]` → `[확인]` → `POST /students/{id}/change-requests` → **신청 완료**(변경 완료 아님) → **홈에 처리 대기 배지(N건)** + 신청 목록에 상태 뱃지 → `pending`(처리중) → `approved`(반영 완료) 또는 `rejected`(사유 표시)

**분기 · 예외**

- (①구간 · 출발 30분 전까지) → 승인 없이 즉시 저장 — **재최적화 호출 부재, 확정 배치(UF-X-05 4단계)가 최신 입력을 읽어 반영**(Ruling 198) → 상태 바로 `approved`
- (②구간 · 30분 안쪽~출발 전) → 관리자 승인을 통해서만 반영. 승인 시 **재최적화·재배포**, 거절 시 기존 경로 유지 — 같은 회차의 탑승 토글과 **한도를 공유**(회차당 1회, UF-P-05)
- (③구간 · 운행 시작 후) → ✕ 위치 변경 불가 — "운행이 시작되어 변경할 수 없습니다". **탑승 취소(미등원)만** 별도 경로로 접수 (UF-P-04)
- (입력 주소가 기존 노선 범위 밖) → 접수는 성립하되 "학원 확인 후 반영" 안내 → 관계자가 강제 방문지로 처리 (UF-M-03)
- (대기 중 안내) → `pending` 동안에는 기존 승하차지 탑승 안내 유지 + **처리중 뱃지 상시 노출** — 신청 사실이 화면에서 사라지지 않음
- (종료 상태 오인) → 이 플로우의 종료는 **신청 완료**. 반영 여부는 상태 표시로만 확인

### UF-P-07. 실시간 버스 위치 · 노선 자세히 보기 (P-07 · P-08)

홈 · 실시간 운행 정보 → `[지도 진입]` → `GET /students/{id}/bus-position` + WS 구독 → 버스 현재 위치 + 노선 표시 → `[노선 자세히 보기]` → 승차지 이전 2개 · 승차지 · 하차지 요약 + 동승자 연락 버튼

**분기 · 예외**

- (ETA · 탑승 인원) → **비노출** — 노선에서 위치만 (C-08). 메인 관리자 관제 ETA 는 별개 (O-05)
- (확정 전) → 고정 노선 기준 표시 + "확정 전" 배지
- (변경분) → `added` 초록 · `removed` 빨강 · `skipped` 빨강 취소선 (C-09)
- (위치 신호 유실) → "마지막 확인 위치 · N분 전" 표기
- (운행 시간 아님) → 지도 대신 "운행 예정 시간" 안내
- (당일 `absent`) → 진입은 허용, "오늘은 버스를 이용하지 않습니다" 안내
- (기사 직접 연락) → 버튼 부재 — 스코프 제외

### UF-P-08. 알림 목록 · 알림 설정 (P-09)

홈 → `[알림]` → `GET /notifications` — 최근 **14일** 보관, 미읽음 배지 → `[알림 항목 선택]` → 읽음 처리 → 관련 화면 이동 / 설정 → `[알림 설정]` → `PATCH /me/notification-settings` — 도착(`arrive`) · 등하원(`boarding`) · 미승차(`no_show`) on/off, **토글 3개뿐** — 승차 취소 · 하차 취소 · 운행 시작 알림은 전부 `boarding` 에 귀속(`alighting` 토글은 부재) (FEATURE_SPEC NTF-05·07, Ruling 223 ①)

**분기 · 예외**

- (지연 알림) → 설정 항목 자체가 부재 — 항상 발송
- (off 동작) → **푸시만 차단**. 레코드는 항상 생성되어 목록·관계자 알림 로그에 존치
- (다자녀) → 자녀 선택과 무관하게 전 자녀 알림 수신, 문구에 자녀 이름 포함

### UF-D-01. 담당 회차 확인 (M-02 · M-07)

### UF-D-02. 승하차지 리스트 · 명단 조회 · 변경 확인 응답 (M-03 · M-04 · M-09)

운행 카드 `[클릭]` → `GET /runs/{runId}/roster` → 승하차지 리스트(운행 순서 정렬) → `[승하차지 클릭]` → 명단 — 이름 · 사진 · 반 · 연락처(마스킹) · 특이사항 · 혼자 귀가 가능 여부 · 상태 → 확정 후 변경 발생 시 푸시 수신 → `[변경 목록 확인]` → `POST /runs/{runId}/ack-changes`(기사는 운행 화면, 동승자는 명단 화면에 같은 확인 띠가 뜸 — R32 M4)

**분기 · 예외**

- (`absent` 학생) → 개인 행 제외. 집계에 "미등원 N명"만 유지 (RST-04)
- (`added` 승하차지·탑승자) → 초록 하이라이트
- (`skipped` 승하차지) → 빨강 취소선 + "이 승하차지는 오늘 탑승자가 없어 정차 부재" 안내. 목록에서 제거 부재, 순번 재부여 부재
- (상태 변경 버튼) → 기사 화면에 비노출 — 조회 전용 (C-06)
- (외부 내비게이션 연동) → `[내비 안내]` → `다음 목적지 1개` 또는 `남은 전 구간` 선택 → `GET /runs/{runId}/navigation` → 서버가 활성 공급자(MVP 카카오내비 단독, 서버 설정 `app.navigation.provider`)와 그 앱 상한(승하차지 4곳 = 경유지 3 + 목적지 1)에 맞춰 승하차지를 잘라 응답(`truncated`) → 앱이 딥링크 조립·실행. **`confirmed` 시점부터 가능** — 별도 화면이 아니라 이 흐름이 출발 전 경로 확인 수단 (RUN-08 · M-09, Ruling 201·204·202)
- (확인 응답 미수행) → 관계자 대시보드에 미확인으로 표시 (MON-05)

### UF-D-03. 운행모드 시작 (M-08 · M-10 · RUN-02)

`[운행 시작]`(출발 시각 **±10분** 에만 활성) → **확인 창**("운행을 시작할까요?" — 취소하면 요청 부재, R32 M6) → `POST /runs/{runId}/start` → `Run.status` = `moving` → ✕ 노선 전면 잠금 → 위치 송신 시작(**2초** 주기, `POST /runs/{runId}/position`) → 운행모드 화면(항상 다크) — 현재/다음 승하차지 대형 텍스트 + **가운데 지도**(확정 노선의 도로 경로 · 승하차지 순번 핀 · 현재 버스 위치. 버스 위치는 기사 단말이 스스로 잰 좌표, 카메라는 노선·버스가 전부 보이게 맞춤, 도착·종료 대형 버튼은 화면 아래에 고정 — R32 M1)

**분기 · 예외**

- (출발 시각 ±10분 밖) → ✕ 버튼 비활성 — 오조작 방지. 창 시작 전이면 "HH:mm 부터 시작할 수 있습니다", 지났으면 지났다는 문구(R32 M10). 창을 ±10분으로 넓혀 지연 대응을 흡수했다 (X-01 해소, Ruling 202)
- (하원 회차) → 시작과 동시에 전원 자동 `boarded` (C-07)
- (등원 회차) → 승하차지별 승차 처리를 동승자가 수행 (UF-E-02)
- (운행모드 버튼 성격) → 전부 보고용(도착·지연·종료). 노선을 바꾸는 버튼 부재
- (운행 중 뒤로가기) → 확인 창("운행 화면을 나갈까요?" — 나가면 이 화면의 위치 송신이 멈춘다고 알림, `계속 운행`이 기본). 운행 중이 아니면 바로 나감 (R32 M15·M16)
- (남은 승하차지) → 운행 화면에 **남은 승하차지 목록**(도착 전·미경유 아닌 곳, 눌러 펼치면 학생 이름). **조회 전용** — 승하차 처리 버튼 부재(M-12, R32 M5)
- (알림) → 학부모·학생·관계자에 운행 시작 알림 (RUN-05)

### UF-D-04. 승하차지 도착 처리 (M-11 · RUN-04)

승하차지 진입 직전 → `[도착 처리]`(**마지막 승하차지는 확인 창** — 도착 처리가 곧 운행 종료라 되돌릴 수 없음, 취소하면 요청 부재. 그 앞 승하차지는 운전 중 조작이라 확인 부재 — R32 M6) → `POST /runs/{runId}/stops/{stopId}/arrive` → 도착 타임스탬프 서버 기록 → 현재/다음 승하차지 포인터 전진 → (최종 지점이면) **운행 종료 겸함** (C-15)

**분기 · 예외**

- ("곧 도착합니다" 예고 알림) → 이 조작이 트리거가 **아님**. 서버가 **다음 미도착 승하차지까지 직선거리 300m 이내 진입을 최초 1회만** 감지해 자동 발송, `absent` 학생은 대상에서 제외 (NTF-04 · §2.1 정책 상수, Ruling 207). 도착 처리는 기록·포인터 전진 전용
- (동승자 명단) → 포인터가 전진해도 해당 승하차지 처리 명단은 **별개로 계속 열림** — 두 값을 묶으면 미처리 학생의 명단이 동승자 화면에서 사라짐
- (중복 처리) → ✕ 동일 승하차지 재처리 차단
- (다음이 `skipped`) → 미경유 안내 라인 + 그 다음 실제 경유지를 표시. 경로 안내·ETA 재계산 부재 — 최단거리 주행은 기사 판단 (C-05)
- (최종 지점 · 등원) → 학원 도착 처리 즉시 `Run.status` = `finished` + 전원 자동 `alighted` + 위치 송신 중단 (C-07 · C-15)
- (최종 지점 · 하원 · 전원 하차 완료) → 도착 처리 즉시 `finished`
- (최종 지점 · 하원 · 미하차 학생 존재) → 도착은 기록되고 **종료 보류** — `moving` 유지 + 미하차 목록 표시. 동승자가 마지막 학생을 `alighted` 처리하는 순간 서버가 자동으로 `finished` 전이 (RUN-06)
- (별도 종료 버튼) → 부재. 기사가 따로 누를 것이 없음 (C-15)
- (통신 두절) → 큐에 적재 후 복구 시 재전송, 서버 멱등 처리 (M-06)

### UF-D-05. 운행 종료 — 별도 조작 부재 (M-11 · RUN-05·06 · C-15)

최종 지점 도착 처리(UF-D-04) → 서버가 종료 판정 → `Run.status` = `finished` → 위치 송신 중단 → 관계자에 운행 종료 통지 · `run_ended` 발행

**기사가 누르는 종료 버튼은 부재.** 도착 처리 하나가 종료를 겸함.

| 구분 | 종료 시점 | 부수 효과 |
|---|---|---|
| 등원 | 학원(도착지) **도착 처리 즉시** | 전원 자동 `alighted` (C-07) |
| 하원 · 전원 하차 완료 | 마지막 승하차지 **도착 처리 즉시** | — |
| 하원 · 미하차 잔류 | **보류** — 마지막 탑승자가 `alighted` 되는 순간 서버 자동 전이 | 보류 중 `moving` 유지 · 미하차 목록 표시 (RUN-06) |

**분기 · 예외**

- (미하차 상태로 종료) → ✕ 성립 불가. 잔류가 0명이 되기 전에는 `finished` 미전이 — 기사 조작으로 우회할 경로가 부재
- (보류 중 위치 송신) → 계속 유지. `moving` 이므로 관제·학부모 화면에 버스가 계속 표시

## 6. 동승자 플로우

### UF-E-01. 담당 회차 · 명단 진입 (M-02 · M-03)

로그인 → 담당 회차 → `[회차 클릭]` → 승하차지 리스트 → `[승하차지 클릭]` → `GET /runs/{runId}/roster` → 탑승자 명단 — 사진 · 이름 · 반 · 연락처(마스킹) · 특이사항 · 혼자 귀가 가능 여부 · 상태 · 비고

**분기 · 예외**

- (지도 화면) → 동승자 앱에 부재 — 명단 중심 구성
- (`absent`) → 개인 행 제외, 집계에 "미등원 N명"
- (집계 표시) → 탑승 완료 / 대기 / 미승차 카운트

### UF-E-02. 등원 승차 처리 (M-12 · BRD-01)

명단 → `[학생 선택]` → **사진 + 명단 육안 확인** → `[탑승]` → `PATCH /runs/{runId}/riders/{riderId}` → 서버 확인 → `waiting` → `boarded` → **5초 이내** 3곳 동시 반영: 학부모 승차 푸시 · 관계자 실시간 현황 · 알림 로그

**분기 · 예외**

- (확인 수단) → 사진 + 명단 육안. 태그(NFC/QR) 미사용
- (일괄 처리) → 부재 — 개인별로만 (C-06)
- (기사 조작) → ✕ 403 — 동승자 전용
- (하원 회차) → 승차는 운행 시작 시 전원 자동 처리, 동승자는 하차만 담당 (UF-E-04)
- (서버 처리 실패) → "처리되지 않았습니다" 명시 · 상태 미변경 — 낙관적 UI 부재 (C-10)

### UF-E-03. 미승차 처리 · 에스컬레이션 (M-13 · EXC-01)

`[학생 선택]` → `[미승차]` → **확인 창**("○○ 학생을 미승차로 처리할까요?" — 취소하면 요청 부재, R32 M7) → `no_show` → **T+0**: 학부모 즉시 알림 + 관계자 동시 통지 + **3분** 카운트다운 시작(학원별 설정) → T+0~3분 대기 → 무응답 시 `[보호자 전화 시도]`(시도 이력 저장) → **T+3분** 무응답 확정 → 관계자 에스컬레이션 보고 → 관계자 판단에 따라 출발

**분기 · 예외**

- (`absent` 와의 구분) → `absent` 는 학부모 사전 OFF 로 명단에 부재. 동승자가 누르는 것은 나올 예정이던 학생의 `no_show` (C-02)
- (학부모 응답 도착 — 전화·앱) → 카운트다운 중단 → 현장 판단으로 처리
- (`no_show` 전이) → 종결 상태 — 이후 `boarded` 로 진행 부재. 오조작은 되돌리기로 처리 (UF-E-06)
- (알림 off 설정 학부모) → 푸시만 차단, 목록·로그에는 존치
- (기록) → 대기 시작·종료 시각, 연락 시도 이력, 최종 판단(출발/재시도) 저장
- (최종 판단 선택 시점) → 연락 기록 시트의 `출발 확정`·`재시도` 는 대기 시간(학원 설정 A-17 — 명단 응답 `no_show_case.expires_at`)이 끝난 뒤에만 켜지고, 그 전에는 남은 시간을 셈 (R32 M12)

### UF-E-04. 하원 하차 처리 · 보호자 부재 (M-12 · M-14 · EXC-02)

운행 시작 시 전원 자동 `boarded` → 승하차지 도착 → `[학생 선택]` → 혼자 귀가 가능 여부 확인 → `[하차]` → `alighted` → 학부모 하차 푸시 + 관계자 현황 + 로그

**분기 · 예외**

- (혼자 귀가 불가 · 보호자 부재) → 명단 화면 머리말 `[예외 보고]` → `[보호자 부재 보고]`(대상 = 탑승 중이면서 혼자 귀가할 수 없는 학생) → `POST /runs/{runId}/reports` → 관계자 즉시 통지 → 관계자 판단. 기사는 운행 화면의 종료 보고서에서 같은 보고를 낸다 (R32 M3)
- (최종 상태) → `alighted` 가 최종 — 보호자 인계 정책은 부재 (A-10)
- (미하차 상태) → 운행이 `finished` 로 전이하지 않고 보류 — 마지막 학생 하차 시 서버가 자동 종료 (UF-D-05)

### UF-E-05. 지연 알림 전송 — **동승자 전용** (M-05 · NTF-06)

명단 → `[지연 알림]` → `[사유 프리셋 선택]`(도로 정체 / 기상 악화 / 차량 점검 / 앞 승하차지 대기) → `[메시지 수정]` → `[지연 시간 선택 — 5분 단위]` → `[미리보기 확인]` → `[전송]` → `POST /runs/{runId}/delay` → **관계자 + 아직 탑승하지 않은 학생·학부모**에게 발송 → 명단 복귀

**분기 · 예외**

- (발신 권한) → ✕ **기사는 발신 불가** — 운전 중 문구를 고르고 다듬는 조작 자체가 위험. 승하차를 동승자에게 맡긴 것(C-06)과 같은 근거
- (수신 범위) → **관계자**(학부모 문의가 학원으로 먼저 오므로) + **현재 승하차지 이후** 승하차지의 학생·학부모. 이미 탑승한 학생은 대상 밖
- (수신 설정) → 지연 알림은 설정 항목 자체가 부재 — 대상자 전원 수신 (NTF-07)
- (`absent` 학생) → 발송 대상에서 제외 (C-02)
- (기발송 후 추가 지연) → 누적/갱신 규칙 미확정 (PRD §10.1 오픈 이슈 I)

### UF-E-06. 상태 되돌리기 (BRD-05)

`[오처리 학생 선택]` → `[되돌리기]` → `POST /runs/{runId}/riders/{riderId}/revert` → 이전 상태 복구 · **변경 이력 보존** · **승차 취소 · 하차 취소 알림 신규 발행**

**분기 · 예외**

- (기발송 알림) → **정정하지 않음** — 승차 취소 · 하차 취소는 **새 알림**으로 발행(오픈 이슈 J 잔여 ② 확정, Ruling 219). 두 알림 모두 **`boarding` 설정 토글**에 귀속, `alighting` 토글은 부재 (Ruling 223 ①)
- (`no_show` 되돌리기의 정정 알림) → **미정** — 미승차 알림이 그대로 남는 오통지 문제, 구현 이월 (Ruling 223 ②)
- (이력) → 원 상태 · 정정 상태 · 처리자 · 시각 저장

### UF-E-07. 오프라인 처리 · 동기화 (M-06 · BRD-06)

통신 두절 감지 → 명단은 로컬 캐시로 계속 조회 → `[승하차 처리]` → 단말 큐에 적재 + 화면에 "미전송" 표기 → 통신 복구 → 자동 재전송 → 서버 멱등 처리 → "처리되었습니다" 전환

**분기 · 예외**

- (멱등) → 재전송분 중복 무시 — 큐 항목별 멱등키 기준
- (미전송 상태 오인) → 전송 완료 표기는 서버 확인 후에만 (C-10)
- (발생 구간) → 터널·지하주차장에서 상시 발생 — 유실 시 학부모 알림 누락으로 직결

## 6.5 크로스롤 — 비상 알림

### UF-X-08. 비상 알림 — 발신부터 확인까지 (M-15 · A-16 · O-07 · EXC-04)

**기사·동승자 공통.** 승하차와 달리 역할을 제한하지 않음 — 안전 사안.

홈·운행·명단 화면 머리말 `[비상]`(홈에서는 확정 이후·종료 전 회차가 여럿이면 회차를 먼저 고름 — R32 M2) → `[유형 선택]`(사고 · 차량 고장 · 학생 응급 · 기타) → `[메모 입력]`(선택) → `POST /runs/{runId}/emergency` → 현재 위치(**측정 시각 포함**)·회차·호차·인력 연락처 자동 첨부 → 서버가 **수신 시각을 `raised_at`으로 기록** → **학원 관계자 + 메인 관리자에 동시 발송**(팝업 · on/off 부재) — 관계자 화면에 **배치 기사·동승자 연락처(`contacts[]`)** 표시 → 관계자 `[확인]` → 발신자 앱에 "학원이 확인했습니다" 표시 (Ruling 236)

**분기 · 예외**

- (수신 범위) → 학원 관계자 · 메인 관리자. **학부모·학생은 대상 밖** — 안내 시점·문구는 사실을 파악한 관계자가 판단 (C-17)
- (발신 가능 시점) → 회차가 `confirmed` 이후면 가능. **운행 중이 아니어도 발신 가능** — 출발 전 차량 이상이 대상
- (오발신) → 발신 후 **1분 이내** 취소 가능. 취소 사실도 수신자에게 통지되고 **이력은 존치** — 발신 기록 자체를 지우지 않음
- (관계자 미확인) → 메인 관리자 콘솔에 **미확인 상태와 경과 시간** 노출. 관계자 1명 체제라 그의 부재가 곧 공백
- (통신 두절) → 오프라인 큐 적재 후 복구 시 전송. **전송 시각과 발신 시각을 함께 기록** — 사고 시점 판정 근거
- (중복 발신) → 차단 부재. 같은 회차에 여러 건이 쌓이면 목록으로 표시 — 상황이 바뀔 때마다 다시 알리는 것이 정상
- **2026-09-30 보완**(`R32-W5`) — 관계자 웹은 **`(staff)` 레이아웃 전 화면**에서 수신한다. 미확인 비상 알림은 화면 우측 상단 팝업으로 **`[확인]` 전까지 유지**되고(다른 알림이 와도 덮이지 않음 · 여러 건이면 쌓임), `[비상 알림 목록]` 링크와 사이드바 '비상 알림' 건수(`unacked_count` 기준)가 함께 보인다. 새로고침·재접속 뒤에도 서버의 미확인 목록으로 다시 뜬다
- **2026-09-14 보완**(`FE-R3` 이월 ⓑ) — 위 흐름은 실시간 수신·확인 1건을 서술한다. **접속이 끊겼다 돌아온 관계자가 밀린 알림을 따라잡는 경로**는 `GET /staff/emergencies`(`status`·`date` 조회, 응답에 `unacked_count`)이다 — 배지 숫자가 이 값이고, 목록 화면 진입 시 호출한다. 새 기능 ID 를 만들지 않는다 — `A-16`(`API_SPEC §5.16`)의 조회 측면

## 7. 학원 관계자 플로우

### UF-M-01. 가입 요청 승인 · 레코드 연결 (A-02 · AUTH-10·11)

사이드 내비 미처리 배지 → `[가입·변경 승인]` → `GET /staff/signup-requests` — 이름 · 역할 · 연락처 · 신청 일시 → `[요청 선택]` → `[수락]` + (학생·기사·동승자는 **레코드 연결 필수** — ID 를 직접 입력하지 않고 **이름 검색 목록에서 고른다**(학생은 여러 명 가능), 학부모는 **연결 없이 승인만**) → `POST /staff/signup-requests/{id}/decide` → 계정 `active` → 신청자에 결과 알림

**분기 · 예외**

- (레코드 연결 누락 — 학생·기사·동승자) → ✕ 저장 차단 — 연결 부재 계정은 로그인만 되고 데이터 조회 불가
- (학부모 승인) → **레코드 연결 입력 자리가 없다**(Ruling 324) — 자녀 연결은 이 화면과 분리된 학부모·학생 앱의 코드 절차(UF-P-01)로 진행. 승인 직후 자녀 0명인 채 `active` 가 되는 것이 정상
- (거절) → `[거절 사유 입력]` → 계정 `rejected` → 신청자 화면에 사유 표시 + 재신청 진입점
- (관계자 본인 가입) → 이 화면 대상 밖 — 메인 관리자가 처리 (UF-O-01)

### UF-M-02. ②구간 변경 승인 · 거절 (A-05 · REQ-04·05)

푸시 즉시 수신 → `[승인 대기 목록]` → `GET /staff/approvals` → `[요청 선택]` → 승인 화면 — 출발까지 **남은 시간 카운트다운** · 요청 학생·승하차지 · 잔여 인원 · 영향 학생 · 정원 · **기존 노선 vs 재최적화 결과 대조**(순서 변경 · 제거되는 승하차지 · 전/후 예상 소요시간·거리) → `[차이 확인]` → `[승인]` → `POST /staff/approvals/{id}/decide` → `absent` 처리 + **재최적화 노선 배포** → 기사·동승자 푸시(확인 응답 대상) + 학부모 통보 → 처리 이력 저장(누가·언제·무엇·자동 거절 여부·배포 노선 버전)

**분기 · 예외**

- (승인 효과 범위) → `absent` 처리 + **노선 재최적화·재배포**. 출발 전이라 주행 중 위험이 부재하고 기사·동승자가 확인 응답을 다시 함 (C-04 ② · A-05)
- (잔여 인원 0명) → 해당 승하차지가 **재최적화로 노선에서 제거** — 출발 전이라 `skipped` 표시가 아니라 노선 자체가 갱신 (C-05 대비 지점)
- (거절) → 사유와 함께 학부모 통보 · **기존 경로 유지**, 재최적화 부재
- (출발 시각 도달 또는 운행 시작 · 미처리) → ✕ 서버가 자동 거절 — **기존 노선 유지**(재최적화 부재) + 학부모 통지 · 횟수 미소진
- (승인 조작이 마감 이후 도달) → ✕ 반영 부재 — 이미 자동 거절로 종결, 기존 노선 유지
- (책임 소재) → 승인한 관리자 — 이력 저장이 전제
- (이른 아침 미접속) → 요청이 `pending` 으로 잔류하다 자동 거절로 종결 (X-02 미해결)

### UF-M-03. 노선 강제 추가 — ①구간 한정 (A-06 · RTE-06)

학부모 전화 접수 "오늘만 B 승하차지" → `[운행 관리 · 강제 추가]` → `[기존 학생 검색·연동]`(신규만 직접 입력) → `[주소 입력]` → 주소 검증(좌표 변환) → 승하차지 매칭 또는 신규 생성 → `[추가할 호차 선택]` → `POST /staff/runs/{runId}/forced-add` → **대기 저장(`run_forced_addition`) — 즉시 재최적화 부재** → 확정 배치(UF-X-05 4단계) 산출 시 노선에 반영 → 기사·동승자 배포 + 푸시 → 반영 상태 확인 화면(대기 중 표시 포함, Ruling 198)

**분기 · 예외**

- (②구간 진입 = 출발 30분 안쪽) → ✕ 추가 차단 — **관계자도 예외 부재**
- (주소 검증 실패) → ✕ 저장 보류 + 재입력 요구
- (정원 초과) → ✕ 저장 차단 — 학생 탑승 가능 인원 = 정원 − 기사 − 동승자 (BUS-04)
- (기존 학생을 이름으로 직접 입력) → 중복 레코드 생성 위험 — 검색·연동 경로가 기본
- (적용 범위) → 당일 운행에만. 고정 노선 불변

### UF-M-04. 수동 조정 · 버스 간 이동 (A-07 · RTE-07)

`[학생 선택]` → `[출발 버스 명단에서 제외]` → `[도착 버스에 강제 방문지 추가]` 또는 `[근처 기존 승하차지 명단에 추가]` → `POST /staff/students/{id}/transfer` → **대기 저장 — 즉시 재최적화 부재**, 확정 배치 산출 시 양쪽 노선 모두 반영 → 양쪽 영향 표시 → 양쪽 기사·동승자에 배포 + 푸시(Ruling 198)

**분기 · 예외**

- (파급 범위) → 학생 1명 이동으로 출발 버스·도착 버스 노선이 둘 다 변경 — 양쪽 영향을 한 화면에 표시
- (정원 초과) → ✕ 저장 차단 + 현재 인원·정원 병기
- (구간 제약) → ①구간에서만(전 구간이 대기 저장 대상이라는 뜻) — ②구간 이후는 추가에 해당하여 차단

### UF-M-05. 일상 모니터링 (A-03 · A-04 · MON)

`GET /staff/dashboard` → 운행 대시보드 — 지표 카드 + 금일 회차 표(호차 · 구분 · 출발 · 인력 · 탑승 현재/전체 · 상태) → `[회차 행 클릭]` → 호차별 일일 명단 — 학생 · 반 · 승하차지 · 연락처 · 변경 구분 · 상태 · 비고 → WS 구독으로 실시간 탑승 현황 · 미승차 에스컬레이션 진행 표시

**분기 · 예외**

- (`absent` 표시) → 관계자 웹에서는 **빨강으로 계속 표시** — 매니저 앱의 행 제외와 정반대 (RST-03)
- (변경분) → `added` 초록 · `removed` 빨강 · `skipped` 빨강 취소선
- (기사·동승자 확인 응답) → 미확인 건을 대시보드에 표시 (MON-05)
- (운행 종료 후) → 금일 현황에서 미승차 인원·처리 이력 확인
- (실시간 위치 지도) → `GET /staff/runs/live` — **`moving` 회차만** 표시. 위치 신호가 **2분 이상 유실**되면 `position` = `null` + "마지막 확인 N분 전" — 계획값 재계산은 부재 (MON-07 · A-14, Ruling 232·233)
- (예외 보고 조회) → 비상 알림과 별개 — `[예외 보고 목록]` → `GET /staff/reports` — 유형 · 메모 · 회차 · 호차 · 대상 학생 · 보고자 · 시각 · 처리 여부, `type`·`date`·`run_id` 필터 → 상세 `GET /staff/reports/{id}` (A-18, Ruling 213)

### UF-M-06. 기초 데이터 관리 (A-08~A-12)

**학생 등록** — `[학생 정보 관리]` → `[추가]` → 이름 · **사진** · 성별 · 나이(학년) · 반 · **특이사항** · 혼자 귀가 가능 여부 · 좌석 → `[저장]`

- (**보호자 연락처는 입력하지 않음**) → 학부모 계정이 연결되면 그 계정의 연락처를 표시. 중복 입력이 없으므로 보호자가 번호를 바꾸면 자동 반영
- (**승하차 주소도 입력하지 않음**) → 학부모가 요일별 주소(P-05)·일일 승하차지(P-06)로 등록하고 그 시점에 검증·매칭. 관계자는 조회만
- (계정 미연결 상태) → 학생 레코드만 존재하고 **연락처·주소가 비어 있음** — 학부모 가입 승인으로 연결돼야 명단이 완성 (UF-M-01)
- (퇴원) → soft delete — 오늘 명단은 유지, 과거 이력 보존

**차량 등록** — `[차량 관리]` → `[추가]` → **호차명 · 차량번호 · 정원** → `[저장]`

- (**학생 탑승 가능 인원은 입력하지 않음**) → **배차 시 자동 계산** — 정원 − 배치된 기사 − 배치된 동승자
- (배정이 계산값 초과) → ✕ 차단 (BUS-04)

**매니저 관리 · 배치** — `[매니저 관리]` → `[추가]` → 이름 · 연락처 · 근무 시간 · 역할(기사/동승자) → `[저장]` → `[운행 관리 · 회차 선택]` → `[기사 배치]` → `PATCH /staff/runs/{runId}/assignment`

- (근무 시간과 운행 시간 불일치) → 경고 표시
- (동일 매니저 시간 중복 배치) → 충돌 검출·경고 (MGR-06)
- (배치 중인 매니저 삭제) → ✕ 차단 — 배치 해제 후 삭제
- (당일 배치 변경) → 해당 매니저 앱에 즉시 반영 + 푸시

**운행 스케줄** — `[운행 스케줄]` → 요일·시간별 운행 계획 등록 → 일일 회차 자동 생성 (SCH-01·02)

- (휴원·특강) → 회차 임시 추가·취소로 처리 — **정규 스케줄은 불변** (SCH-03)

**고정 노선 관리** — `[고정 노선]` → 학생 요일별 주소 기반 노선 편성·최적화 → 배치 매니저 표시 (RTE-01)

- (확정 노선과의 관계) → 별개. 확정 노선은 출발 30분 전 배치가 산출 (UF-X-05)

### UF-M-07. 알림 로그 · 수신 확인 (A-13 · NTF-10·11)

`[알림 로그]` → `GET /staff/notifications` — 시각 · 호차 · 대상 · 종류 · 확인 여부 → `[종류 필터]` → 미확인 배지 확인 → 중요 통지는 수신 확인까지 추적(범위는 §10.2 규칙4·5 의 그 3종, 정의는 FEATURE_SPEC NTF-10 참조)

- (미확인 지속) → 배지로 잔류 — 관계자가 별도 연락

### UF-M-08. 경유 지점 지정 (A-15 · RTE-10)

⚠ **웹 화면 부재(2026-09-23 `Ruling 325`, 2026-09-30 정정)** — 고정 노선 편성 화면에서 회차별 경유 지점 지정 칸을 **제거**했다(편성 화면은 한 노선으로 들어와 작업하는 곳). 아래 흐름은 **사양(API·백엔드 `§5.15`)의 흐름**이고, 지금 관계자 웹에는 이 절차를 밟는 화면이 없다. 웹 진입점을 다시 만드는 것은 별도 사양 판정이 필요하다.

확정 노선 배포 후·출발 전 → `[운행 관리]` → `[회차 선택]` → `[경유 지점 지정]` → `[주소 입력 또는 지도에서 선택]` → 주소 검증 (STU-05) → `POST /staff/runs/{runId}/waypoints` → 그 지점을 포함해 재최적화 → **기존 노선 vs 결과 대조 제시**(순서 변경 · 전/후 예상 소요시간·거리) → `[배포]` → 기사·동승자 푸시 + 확인 응답 대상 (RUN-07)

**분기 · 예외**

### UF-O-07. 회차 강제 확정 (권한 `RUN_FORCE_CONFIRM` — 기능 ID 부재, `FEATURE_SPEC §6.2` 판정)

**2026-09-17 신설** — `API_SPEC §6.14`(Ruling 254)는 이미 정의돼 있는데 이 문서에 대응 절이
없었다(`r5-fedoc` 목표 10). 기능 ID 는 **부재** — `RUN` 도메인 전 항목이 기사·동승자 스코프이고,

만들 근거가 없다는 판정이 `FEATURE_SPEC §6.2`에 있다(2026-09-14 확인, `r5-fedoc` 목표 11 로 재확인).

`(확정이 계속 실패하는 회차 — 연속 실패 시 관계자 경보, `TECH_DECISIONS §14.2`)` →
관제 화면에서 대상 회차 확인 → `[강제 확정]` → **사유 입력**(필수) →
`POST /admin/runs/{runId}/force-confirm` → 폴백(직선거리) 계산으로 `idle` → `confirmed` 전이 —
`route_version` 신규 생성 + 통상 확정과 동일한 후속(관계자·기사·동승자 통지 · `RunRouteConfirmedEvent`)
발생 → `audit_log` 1행 기록(누가·언제·왜·`fallback_used`)

**분기 · 예외**

- (전제) → 회차가 `idle` 상태 + `confirm_at` 경과. 아니면 ✕ `409 RUN_NOT_IDLE` · `409 RUN_NOT_DUE`
- (사유 공백) → ✕ `422 VALIDATION_FAILED`
- (대상 부재) → ✕ `404 RUN_NOT_FOUND`
- ("강제 종료" 아님) → 미하차 상태로 회차를 끝내는 경로는 두지 않는다 — 잔류 학생 검증(RUN-06)은
  그대로 적용된다(`TECH_DECISIONS §14.3` ⚠)
- (정본 공백) → **어떤 화면·신호로 "이 회차가 강제 확정 대상" 이라고 식별해 이 흐름에 진입하는지는
  `API_SPEC`·`TECH_DECISIONS` 어디에도 명시가 없다.** 근거는 `TECH_DECISIONS §14.2` 의 "연속 실패
  시 관계자에 경보" 뿐이고, 그 경보의 수신 채널·화면은 정본에 없다 — 지어내지 않고 비워 둔다
  - **식별 재료는 `consecutive_failures`**(2026-09-25, BR-047) — §5.10 회차 응답과 §6.8 관제 응답에 실린다. 비워 둔 것은
    경보 **채널**(푸시·알림 종류)뿐이다

| 하차 취소 | 되돌리기로 `alighted` → `waiting` (UF-E-06) | 학부모 | ● (`boarding`) |
| 운행 종료 | `Run.status` → `finished` (최종 도착 처리 · C-15) | 관계자 | — |
| **비상 알림** | 매니저 앱 `[비상]` 발신 (EXC-04) | **관계자 + 메인 관리자** | **✕ (설정 항목 부재)** — 팝업 병행 (C-17) |
| 비상 알림 취소 | 발신 **1분 이내** 취소 (EXC-04) | 위와 동일 | ✕ |
| 예외 보고 접수 | `POST /runs/{runId}/reports` (A-18) | 재직 관계자 전원 | ✕ 설정 항목 부재 |
| 가입 승인 · 거절 | 관계자(또는 메인 관리자) 처리 | 신청자 | — |
| 자녀 연결 요청 | 학부모 연결 요청 | 학생 | — |
| ②구간 변경 요청 접수 | 학부모 ②구간 신청 (REQ-05) | 관계자 — 푸시 즉시 | ✕ |
| ②구간 승인 · 거절 · 자동 거절 | 관계자 처리, 또는 출발 시각 도달·운행 시작 중 먼저 오는 시점 | 학부모 | — |

| 확정 노선 변경 | ②구간 승인 재최적화 · **경유 지점 지정**(RTE-10) | 기사 · 동승자 — 확인 응답 요구 (RUN-07) | ✕ |

| 당일 배치 변경 | 관계자 배치 변경 | 해당 매니저 | ✕ |
| 미승차 에스컬레이션 보고 | `no_show` 후 3분 무응답 | 관계자 | ✕ |

| # | 규칙 |
|---|---|
| 1 | 알림 off 는 **푸시만 차단**. 레코드는 항상 생성되어 앱 목록 · 관계자 알림 로그에 존치 |
| 2 | 보관 기간 **14일** |
| 3 | `absent` 학생은 도착 · 지연 알림 대상에서 제외 |

| 7 | `pending` 계정 수신 알림은 승인 · 거절 결과만 — 운행 알림은 대상 밖 |

## 12. 실패 · 예외 경로 모음

### 12.1 서버 처리 실패 (C-10)

| 발생 지점 | 처리 |
|---|---|
| 탑승 토글 · 변경 신청 | 기존 상태 복구 · "처리되지 않았습니다" 명시 · ②구간 **횟수 미소진** — 재신청 가능 |
| 승하차 처리 | 상태 미변경 · 알림 미발송 · 재시도 유도. 낙관적 UI 부재 |
| 요일별 주소 저장 | 기존 값 유지 · 실패 명시 |
| 공통 원칙 | 서버 2xx 확인 후에만 "처리되었습니다" 표시 — 실패가 조용히 넘어가는 경로 부재 |

### 12.2 통신 두절

| 대상 | 처리 |
|---|---|
| 동승자 승하차 처리 | 로컬 큐 적재 → 복구 시 자동 재전송 → 서버 멱등 처리 (UF-E-07) |
| 기사 도착 처리 · 위치 송신 | 큐 적재 후 재전송. 학부모 화면은 "마지막 확인 위치 · N분 전" |
| 명단 조회 | 로컬 캐시로 계속 조회 가능 |
| 학부모 실시간 위치 | 신호 유실 표기 — 위치 갱신 중단이 오류 화면으로 이어지는 경로 부재 |

### 12.3 승인 무응답 · 한도 소진

| 상황 | 처리 |
|---|---|
| ②구간 요청이 마감(출발 시각 · 운행 시작 중 먼저) 까지 `pending` | 서버가 **자동 거절** + **기존 노선 유지** + 학부모 통지 · 횟수 미소진 (X-02) |
| 같은 회차에 ②구간 변경 2회째 시도 | ✕ "금일은 변경할 수 없습니다" — 회차당 1회 (다른 회차의 한도는 미소진) |
| 가입 요청 장기 미처리 | 계정 `pending` 잔류 — 승인 대기 화면 고정, 학원 문의처 안내 |

### 12.4 정원 · 중복 · 잔류

| 상황 | 처리 |
|---|---|
| 강제 추가 · 버스 간 이동 시 정원 초과 | ✕ 저장 차단 + 현재 인원·정원 병기 (BUS-04) |
| 차량 등록 시 배치 인원 초과 | ✕ 저장 차단 — 학생 탑승 가능 인원 = 정원 − 기사 − 동승자 |
| 동일 승하차지 도착 재처리 | ✕ 중복 차단 |
| 오프라인 큐 재전송 중복 | 멱등키로 중복 무시 |
| 하원 최종 도착 시 미하차 학생 존재 | 도착은 기록, **종료 보류** + 미하차 목록 표시. 잔류 0명 시 서버 자동 종료 (RUN-06 · C-15) |
| 승하차 오처리 | 되돌리기로 정정 · 이력 보존, **기발송 알림은 정정하지 않고 승차·하차 취소 알림을 새로 발행**. `no_show` 되돌리기의 정정 알림은 미정(UF-E-06, Ruling 219·223 ②) |

### 12.5 권한 · 구간 차단

| 상황 | 처리 |
|---|---|
| `pending` 계정의 일반 API 호출 | ✕ 서버 인가 계층 403 — 허용 API 는 승인 대기 화면 조회 · 로그아웃 · 본인 프로필 조회 · 푸시 단말 등록·해지 뿐(전체 목록은 FEATURE_SPEC §3.6 참조) |
| `blocked` 계정 로그인 | ✕ 실패 — 해제는 메인 관리자 (UF-O-03) |
| 기사의 승하차 상태 변경 시도 | ✕ 403 — 동승자 전용 (C-06) |
| 동승자의 운행 시작 · 종료 · 도착 처리 시도 | ✕ 403 — 기사 전용 |
| 출발 시각 ±10분 밖의 운행 시작 | ✕ 버튼 비활성 — 대체 수단은 두지 않는다. 창 자체를 ±10분으로 넓혀 흡수 (X-01 해소, Ruling 202) |
| ③구간(운행 시작 후) 변경 시도 | ✕ 전면 불가 — 학부모·관계자 모두 |
| ②구간 추가 시도 | ✕ 차단 — 관계자도 예외 부재 |
| 타 학원 회차 명단 조회(`§5.4 roster`) | ✕ `403 ACADEMY_SCOPE_VIOLATION` — 정본 `§1.5` 와 동일(2026-09-03 사용자 판정 ② 로 코드 정정, X-08 해소 · Ruling 240). 존재하지 않는 회차는 `404 RUN_NOT_FOUND` |
| 동승자 당일 결근 | **동승자 없는 회차는 없다고 가정** — 결근은 운영에서 대체 배치로 흡수(X-03 해소, Ruling 203) |
