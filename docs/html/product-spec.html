학원 통학버스 통합관리 — 제품 사양서

서비스 목적 · 도메인 규칙 · 정책 임계값 · MVP 구현 범위 · 갭 목록 · 코드 실측 기준 2026-08-01

학원 통학버스의 노선 편성·배차·학생 승하차·예외 대응·법정 운행기록을 하나로 묶는 멀티 테넌트 플랫폼(모바일 앱 + 관리자 화면)의 제품 사양이다. 이 문서는 “무엇을 만드는가(요구사항)”와 “지금 실제로 무엇이 있는가(실측 구현 범위)”를 한 곳에 담는다. 1~10장은 목표 요구사항, 11~12장은 코드 실측 결과다.

1. 서비스 개요 & 목적

학원 통학버스 운영에서 전화·수기로 흩어져 있던 정보를 하나의 데이터 흐름으로 연결해 안전성 + 운영 효율을 올린다.

  • 6대 서비스: ① 노선표·배차 ② 학생 승하차 ③ 학원·기사·학부모 커뮤니케이션 ④ 차량·운행인력 관리 ⑤ 운행 모니터링·사고 대응 ⑥ 통계·법정 운행기록
  • 핵심 가치: 지도에 버스를 표시하는 것이 아니라, 승하차 기록 · 명단 · 배차 · 예외 대응 · 법정 기록이 끊기지 않고 연결되는 것. 실시간 위치는 그 위에 얹히는 한 조각이다.
  • 해결하는 문제: 학부모가 자녀 탑승 여부를 알려고 전화한다 / 기사가 종이 명단으로 승하차를 확인한다 / 결석·시간변경이 구두로 전달돼 명단에 반영되지 않는다 / 사고·미승차 시 누가 언제 무엇을 했는지 기록이 남지 않는다.

2. 사용자 계층 & 권한

하나의 승하차 기록(RideEvent)을 여러 계층이 각자 권한 범위 안에서만 조회한다 — “계층별 조회 권한 분리”가 설계의 핵심이다.

기획 원본(docx)은 운영 4역할(학원관리자·기사·동승보호자·학부모)을 정의하지만, 코드의 Role enum은 여기에 학생·플랫폼 관리자를 더한 5계층이다. 동승보호자는 MVP에서 별도 역할로 분리하지 않고 기사 앱의 승하차 확인 흐름에 흡수했다(추후 역할 승격 가능).

계층(Role)조회 범위MVP 화면백엔드 API

  • 학원관리자 ≠ 플랫폼관리자. 권한 범위가 완전히 별개다.
  • 두 관리자 역할은 화면이 완전히 동일하고, 차이는 tenant 결정 방식뿐이다 — 학원관리자는 JWT의 소속 학원 고정, 플랫폼관리자는 GET /api/tenants 목록에서 드롭다운 선택.
  • 멀티테넌시는 N:M. User에 tenant_id를 직접 박지 않고 UserTenantRole(user_id, tenant_id, role) 연결 테이블로 표현한다. 학부모 1명이 서로 다른 학원에 자녀를 둘 수 있고, 기사가 복수 학원에 소속될 수 있기 때문이다. 플랫폼관리자는 tenant_id가 NULL인 전역 역할로 저장된다.
  • 학생(Student)은 단일 학원 종속이다(student.tenant_id NOT NULL).
⚠ 흔한 오해

“학생·학부모 API가 없다”가 아니다. 백엔드에는 학생·학부모 전용 엔드포인트가 이미 다 구현돼 있고, 그것을 호출하는 프론트 화면이 없을 뿐이다. 두 역할은 로그인은 성공하지만 “준비 중” 배너만 본다(→ 12장 O1).

3.1 엔티티 전체 (16개)

마스터 데이터 — Tenant(학원, depot 좌표 보유) · User(app_user 테이블, user가 예약어라 개명) · UserTenantRole · Student · StudentGuardian · Bus · Route · Stop

운영 데이터 — RideEvent(승하차 허브) · DriveSession(운행 세션) · RoutePlan + RoutePlanStop(당일 노선 계획) · AttendanceException(결석·휴원) · ScheduleChangeRequest(시간 변경) · SosEvent · NotificationLog

⚠ 기존 문서 오류 정정 2건

1. PROJECT_MASTER_PLAN.md §3의 엔티티 목록에 있는 AuditLog는 실제로 존재하지 않는다. 감사 로그 테이블·엔티티가 없으므로 “민감 조작 이력”은 현재 남지 않는다.

2. 같은 목록에 DriveSession · RoutePlan · RoutePlanStop 3개가 빠져 있다. 이 셋은 실제 구현·사용 중인 핵심 엔티티다.

3.2 설계 결정

  • RideEvent가 허브다. Student·Bus·Stop·Route와 연결되고, 4계층이 각자 범위로 조회한다.
  • 정정은 덮어쓰기가 아니라 append-only. 원본을 남기고 source=CORRECTION · corrected_by · corrected_at · original_ref를 채운 새 행을 만든다.
  • 대용량·이벤트성 테이블은 JPA 연관 대신 평문 Long 참조를 쓴다(RideEvent · DriveSession · RoutePlan · SosEvent · NotificationLog · AttendanceException · ScheduleChangeRequest). 그래서 DB FK 제약은 13개뿐이고 나머지 참조 무결성은 애플리케이션이 책임진다.
  • tenant_id 보유 엔티티 11개 / 16개. Stop은 Route 경유, StudentGuardian은 Student 경유, RoutePlanStop은 RoutePlan 경유로 간접 격리한다.
  • 정원 개념이 두 갈래다. Bus.seatCapacity(물리 좌석 수)와 Route.assignCapacity(노선 배정 정원)는 별개 값이고 서로 동기화되지 않는다. 자동 배차의 실제 판단은 seatCapacity만 쓰고, assignCapacity는 화면의 “정원 초과” 경고 표시에만 쓰인다.
  • 스키마는 Flyway가 관리한다(ddl-auto: validate). 마이그레이션 5개(V1 베이스라인 + V3~V5는 CHECK 제약 확장, V2는 로컬 전용 데모 시드).
⚠ 흔한 오해

“정류소 = 주소”가 아니다. 주소와 별개로 실제 승하차 지점(동 앞·출입구, 진행 방향, 유턴 여부, 대기 안전장소, 지오펜스)을 따로 관리해야 한다. 현재 Stop은 이름·순서·좌표만 갖고 있어 이 요구사항을 아직 만족하지 못한다.

4. 노선 · 배차 관리

노선은 최단거리가 아니라 정원·안전·시간 제약을 만족하는 “운행 가능한” 경로다. 변경은 덮어쓰지 않고 버전 관리한다.

4.1 요구사항

  • 관리 단위: 요일별 / 등원·하원 / 수업시간별 / 차량별 / 학기·방학별 + 적용 시작·종료일
  • 최적화 제약(기획 목표): 차량 정원, 학생별 승하차 가능 시간, 학원 도착 마감, 교통량, 정차 소요시간, 아파트 진입·회차, 일방통행·유턴·높이 제한, 어린 학생 최대 도보거리, 학생별 최대 탑승시간, 형제자매 동일 차량, 진행방향 반대편 하차 방지, 위험 횡단 방지
  • 임시 변동 절차: ① 학부모 신청 → ② 시스템이 정원·노선 영향 자동확인 → ③ 관리자 승인/거절 → ④ 기사·동승보호자 전달·확인 → ⑤ 학부모 최종 안내
  • 정책: 기사·학부모가 직접 합의한 변경도 학원 승인을 거쳐야 효력이 생긴다. 정규 노선은 관리자 최종 승인 후에만 적용된다.

4.2 계획 생명주기 (구현됨)

DRAFT / RECOMMENDED  —approve→  APPROVED  —publish→  PUBLISHED

  • PUBLISHED가 되어야 기사 앱 조회 API에 노출된다.
  • 재계산은 기존 행 수정이 아니라 version + 1인 새 행 생성이다. 이력이 보존되고, 기사 앱은 같은 버스·방향에서 최신 version을 골라 쓴다.
  • 배포 후 취소·철회 전이는 존재하지 않는다.
  • 결석 승인·시간변경 처리·학생 배정 변경·하차지 변경 4가지 이벤트가 발생하면, 해당 버스의 당일 계획만 국소 재계산(replan)된다. 실패하면 기존 계획을 그대로 두고 경고 로그만 남긴다.

4.3 자동 배차 알고리즘 (실측)

2단계다. ① 학생을 버스에 나눠 담고 → ② 버스별 정차 순서를 최적화한다.

  1. 버스 배정 — sweep 방식: 학원(depot) 기준으로 학생 좌표를 방위각 순으로 정렬한 뒤, 버스를 id 오름차순으로 순회하며 seatCapacity만큼 순차로 잘라 담는다.
  2. 정차 순서 — 휴리스틱 3단계: sweep 정렬(결정적 초기 순서) → nearest-neighbor(그리디) → 2-opt(구간 반전 개선, 최대 1000 pass). 거리 함수는 Haversine 직선거리라 이 단계에서 외부 API 호출이 없다.
  3. 실제 도로거리·ETA: 순서가 확정된 뒤 외부 경로 API를 1회 호출해 얻는다. 기본 제공자는 Naver Directions(키 필요), 미설정 시 OSRM 공개 데모 서버로 폴백한다.
  4. 방향 처리: DROPOFF는 [depot, …], PICKUP은 최적 순서를 뒤집어 […역순, depot]. “대칭거리에서는 depot 고정 최적경로를 뒤집어도 총거리가 같다”는 성질에 기대 최적화를 1회만 수행한다.
⬜ 반영되지 않은 제약

4.1의 최적화 제약 중 실제로 반영되는 것은 좌석 정원 하나뿐이다. 시간창(등원 도착 마감·하원 출발 시각), 버스 간 부하 분산, 정차 소요시간, 형제자매 동일 차량, 도로 통행제한, 기사 배정 여부·보험 만료 필터는 전부 미반영이다. 구조적으로 앞 버스부터 정원까지 꽉 채우므로 마지막 버스가 비는 편향이 생긴다.

⚠ 흔한 오해

“노선이 하나”가 아니다. 시스템에는 고정 노선(Route + Stop)과 당일 계획(RoutePlan + RoutePlanStop)이 별개로 존재하고, 자동 배차는 고정 노선의 정류장 순서(Stop.seq)를 전혀 보지 않고 매번 새로 계산한다. 한 버스가 서로 다른 두 순서를 동시에 가질 수 있으며, 둘의 정합성을 맞추는 코드는 없다. Route/Stop은 사실상 “정류장 마스터 데이터 + 정원 경고 표시” 용도로만 남아 있다.

5. 승하차 관리 & 학생 상태머신

승차·하차를 하나로 묶지 않고 각각 기록한다.

5.1 학생 운행 상태 전이 (기획 목표)

📊 학생 운행 상태머신 — 기획 목표 8단계 중 코드가 기록하는 것은 3개뿐
“정류소 대기”, “하차예정” 같은 중간 상태는 저장되지 않는다 — 기록되는 지점은 BOARD·ALIGHT·HANDOVER 3개다.

현재 코드가 실제로 기록하는 것은 이 중 BOARD(승차완료) · ALIGHT(하차완료) · HANDOVER(보호자 인계완료) 3개 지점이다. “정류소 대기”, “하차예정” 같은 중간 상태는 저장되지 않는다.

5.2 확인 방식

기획상 초기에는 명단 + 사진 육안 + NFC/RFID + QR + 실패 시 수동 + 탑승 인원·좌석 자동 대조를 병행하기로 했다.

  • 실제 구현된 경로는 기사 수동 기록 하나뿐이다. RideSource enum에 QR·NFC가 정의돼 있으나 이를 생성하는 코드 경로가 없어 기록의 source는 항상 MANUAL로 고정된다.
  • 기록 시각(occurredAt)도 서버의 now()로 고정된다 — 과거 시각으로 남기려면 정정 API를 써야 한다.
  • 사진 육안 확인은 Student에 사진 필드가 없어 불가능하다.

5.3 운행 세션과 차내 잔류 방지

승하차 기록은 운행 세션(DriveSession) 안에서 이뤄진다. 기사가 방향(등원/하원)을 골라 시작하고, 명단을 처리한 뒤 종료한다.

  • 같은 (버스, 방향, 운행일)에 진행 중 세션이 이미 있으면 시작이 거부된다.
  • 명단은 당일 승인된 결석자를 자동으로 제외한 실제 명단이다.
  • 차내 잔류 방지: 구현됨. 종료 시 세션 구간의 승하차 기록을 학생별로 훑어 마지막 기록이 BOARD인 학생이 하나라도 남아 있으면 종료를 차단한다.
  • 세션 구간 판별에 drive_session_id 컬럼이 아니라 busId + 시간창을 쓴다 — “버스당 진행 중 세션은 1개”라는 전제에 의존한다.
⚠ 흔한 오해 2건

1. 태그(QR/NFC)만으로 확정하면 오확정 위험이 있다. 명단·실제 학생을 함께 확인하는 이중 구조가 원래 요구사항이며, 현재는 기사 수동 확인이 그 역할을 대신하고 있다.

2. 하차완료 ≠ 보호자 인계완료. 저학년은 단순 하차 버튼만으로 운행을 끝내면 안 된다. 그래서 HANDOVER 타입을 별도로 두었다.

6. 예외상황 · 에스컬레이션

각 예외를 대기 → 연락 → 관리자 보고 → 후속조치의 정해진 순서·임계시간으로 처리한다.

⚠ 법적 근거

도로교통법상 어린이 하차확인장치 작동, 좌석안전띠·보호자 동승, 안전운행기록 작성·보관·분기 제출이 의무다. 즉 위 확인·기록은 편의 기능이 아니라 법정 요건이다. 현재 운행 기록은 DB에 남지만 법정 서식 출력·제출 기능은 없다.

7. 실시간 위치 · 알림 정책

학부모에게 전체 노선이 아니라 자녀 관련 제한 위치만 제공한다. 알림은 “이벤트 1건 = 발송 1건”이 되도록 멱등(중복 억제) 처리한다.

7.1 위치 데이터 경로 (실측)

구간방식상태
기사 앱 → 서버 (버스 위치)5초 주기 POST /api/locations/bus구현 단, 기본 좌표원이 Mock
서버 → 관리자 (관제)3초 REST 폴링 GET /api/locations/buses부분 실시간 push 아님
학생 앱 → 서버 (학생 위치)REST 또는 STOMP /app/location백엔드만 학생 앱 없음
서버 → 학생·학부모·기사 (학생 위치 push)Kafka → STOMP /user/queue/location백엔드만 구독 화면 없음
서버 → 관리자 (알림 push)STOMP /topic/tenant/{tenantId}/notifications구현·사용 중
  • 버스 위치는 저장은 되지만 이벤트를 발행하지 않아 실시간 push로 이어지지 않는다. 그래서 관제 화면이 폴링에 의존한다.
  • 학생 위치는 Redis에 최신 1건만 약 9초 TTL로 보관한다 — 위치 이력 조회 API는 존재하지 않는다.
  • 버스 위치는 인메모리 맵에 최신 1건만 저장되며 서버 재시작 시 휘발된다.

7.2 알림 파이프라인

📊 알림 파이프라인 + 멱등 2단 방어
같은 dedup_key가 재감지돼도 발송은 1회뿐이다. UNIQUE 위반 예외는 삼키고 무시한다.

흐름은 이벤트 감지 → dedup_key 계산 → 이미 발송됐나? → YES 무시 / NO 저장 + 발송이며, dedup_key = (유형 + 학생 + 대상일자 + 정류장/단계)다.

멱등은 2단 방어로 구현돼 있다 — ① 애플리케이션의 existsByDedupKey 선(先) 체크, ② notification_log.dedup_key UNIQUE 제약이 동시 틱 경쟁을 최종 차단(위반 예외는 삼키고 무시).

7.3 임계값 (문서·코드 공통 상수)

아래 값은 코드의 NotificationThresholds 상수로 실제 존재하며 스케줄러가 참조한다.

알림임계대상NotificationType구현
미승차 판정정류소 도착 +10분학부모+관리자NO_SHOW구현
근접 알림도착 예상 5분 전학생+학부모APPROACH구현
SOS 에스컬레이션관리자 미확인 3분플랫폼관리자SOS구현
위치 연결 끊김heartbeat 끊김 +30초관리자CONNECTION_LOST구현
승차/하차/인계 완료즉시학부모BOARD_DONE/ALIGHT_DONE/HANDOVER_DONE구현
시간변경 결과처리 시학부모SCHEDULE_RESULT구현
노선 추천·배포처리 시기사ROUTE_RECOMMENDED/ROUTE_PUBLISHED구현
⬜ 정책상 목표값이나 미구현

“GPS 단발 이상치 오탐을 막기 위해 위치 기반 판정은 연속 N회(예: 3회) 관측이 모두 조건을 만족할 때만 발송한다”는 규칙은 코드에 없다. 현재는 dedup_key 멱등만으로 중복을 막고 있어, 단발 이상치가 곧바로 판정으로 이어질 수 있다. 마찬가지로 푸시 실패 시 지수 백오프 재시도도 미구현이다(발송 실패 결과가 NotificationLog에 기록되지 않는다).

⚠ 흔한 오해

미승차를 매 틱 알리면 알림 폭탄이 된다. 같은 dedup_key가 재감지돼도 1회만 발송하는 것이 핵심이다. 스케줄러 주기(15초·30초)는 “얼마나 자주 다시 훑느냐”일 뿐 임계값이 아니다 — 임계값은 10분·5분·3분이다.

8. 개인정보 · 위치정보 · 법

학생 사진·주소·연락처·위치는 민감 개인정보다. 수집목적·보유기간·접근권한을 설계 단계에서 확정해야 한다.

  • 동의: 학부모 수집·이용 동의 + 만 14세 미만 법정대리인 동의 + 사진 별도 안내
  • 보호: 암호화, 계층별 접근권한, 조회·수정 이력, 캡처·다운로드 제한, 퇴사·노선변경 시 권한 즉시 회수
  • 위치정보: 차량 위치가 학생·기사와 연결되면 개인위치정보에 해당할 수 있어 위치정보사업 신고 여부에 대한 법률 검토가 필요하다. 보유기간 최대 1년.

현재 구현 상태: 위 항목 전부 미구현. 동의 UI·동의 저장 스키마·보유기간 정책·접근 이력(AuditLog)이 모두 없다.

⚠ 실서비스 전환 선행조건

MVP(Mock)는 실 위치를 수집하지 않아 유예 가능하지만, 동의 UI와 저장 스키마는 실 GPS 전환 전에 반드시 구현해야 한다. 미루면 Mock→실 GPS 전환이 법적으로 막힌다.

⚠ 흔한 오해 3건

1. “백엔드가 덜 됐다”가 아니다. SOS·결석·일정변경·버스/학생/회원/학원 관리·승하차 정정은 백엔드가 다 구현돼 있고 프론트 화면만 없다. 남은 일의 성격은 “API 구현”이 아니라 “화면 구현”이다.

2. 관제는 실시간 push가 아니다. STOMP 연결은 있지만 알림 전용이고, 버스 위치는 3초 REST 폴링이다.

3. 기사 앱이 보내는 좌표는 기본값이 가짜다. 스위치를 켜면 노선 polyline을 따라 왕복하는 Mock 좌표(≈43km/h)가 서버로 전송된다. 게다가 서버는 좌표 출처를 항상 GPS로 기록해서, 관제 화면의 “출처” 표기가 실제 Mock 여부를 반영하지 못한다.

12. 미구현 · 갭 목록

11장의 매트릭스를 “무엇이 안 되는가 / 사용자에게 어떤 결과인가 / 어디를 고쳐야 하는가” 관점으로 재정리했다. 총 28건 — 운영불가 5 · 기능누락 15 · 사소 8.

심각도 정의:

  • 운영불가 — 이 상태로 서비스를 열면 해당 기능이 성립하지 않는다
  • 기능누락 — 화면은 동작하나 기능·정확성에 구멍이 있다
  • 사소 — 죽은 코드·하드코딩 등 품질 항목

12.1 운영불가 (5건)

O1. 학생·학부모가 쓸 화면이 하나도 없다

5계층 중 2계층이 로그인 직후 “준비 중” 배너에서 멈춘다. 자녀 위치·승하차 기록·알림함·결석 신고·시간 변경·SOS를 앱에서 할 수 없다. 서비스의 핵심 사용자가 서비스를 못 쓰는 상태다.

→ 고칠 곳: 프론트엔드 전용. 백엔드 엔드포인트(/me·/children 계열)는 이미 다 구현돼 있다.

O2. SOS 기능이 화면에 전혀 없다

학생이 긴급 상황을 알릴 수단이 없고, 관리자가 확인·종료할 화면도 없다. 백엔드 6개 엔드포인트와 3분 에스컬레이션 스케줄러가 아무도 호출하지 않는 상태로 돌고 있다. 안전이 제품 가치의 중심인데 그 기능이 도달 불가하다.

→ 고칠 곳: 프론트 SOS 발신 화면(학생) + 관제 화면의 SOS 확인·종료 UI.

O3. 결석 신고·시간 변경을 넣을 화면이 없다

기사 명단 화면은 “결석 신고된 학생은 자동으로 빠진다”고 안내하지만, 신고를 넣는 화면도 승인하는 화면도 없다. 결과적으로 명단 자동 제외 기능이 동작할 조건 자체가 만들어지지 않는다.

→ 고칠 곳: 프론트 학부모 신고 화면 + 관리자 승인·반려 화면.

O4. 버스·학생·회원·학원을 등록할 화면이 없다

관제 화면의 빈 상태 문구가 “버스 관리에서 버스를 먼저 등록하면…”이라고 안내하지만 그 화면이 존재하지 않는다. 프론트의 HTTP 클라이언트에는 put·delete 메서드조차 없고 쓰기 호출은 7종(로그인·재발급·위치보고·승하차·운행 시작/종료·배차)뿐이다. 데이터는 오직 DB 시드나 Swagger로만 들어간다.

→ 고칠 곳: 프론트 관리자 CRUD 화면 + HTTP 클라이언트에 쓰기 메서드 보강. 백엔드는 수정·삭제 API 보강 필요(→ F12).

O5. 기사 앱의 위치 출처 기본값이 Mock이다

기사가 전송 스위치를 켜면 기본으로 가상 좌표가 서버에 저장되고, 관리자는 그것을 실제 위치로 본다. 실 GPS를 쓰려면 매번 수동 전환해야 한다. 또한 Mock 소스는 노선이 없으면 예외를 던져 전송이 통째로 멈춘다.

→ 고칠 곳: 기본값을 실 GPS로 바꾸고 Mock은 개발 빌드 플래그 뒤로. 노선 부재 시 폴백 경로 필요.

12.2 기능누락 (15건)

번호내용 · 결과고칠 곳
F1 기사에게 알림 화면이 없다 — 개인 큐(/user/queue/notifications) 구독 코드는 준비돼 있으나 이를 쓰는 화면이 없어 도달 불가능한 코드다. 노선 배포·미승차 알림이 기사에게 닿지 않는다. 기사 셸에 알림 탭 추가
F2 플랫폼관리자의 관제 화면이 다른 화면과 다른 학원을 본다 — 지도·목록은 항상 1번 학원 고정인데, 같은 화면의 상세 패널·노선 조회는 드롭다운 선택값을 따른다. 배차·노선 화면에서 다른 학원을 골라도 관제 지도만 계속 1번 학원을 보여준다. 관제 화면도 공통 tenant 선택 상태를 쓰도록 통일
F3 “학원 1번” 폴백이 3곳에 중복 하드코딩 — 관제·공통 tenant·알림 세 군데에 같은 상수가 흩어져 있어 알림 화면도 플랫폼관리자면 무조건 1번 학원으로 고정된다. 단일 출처로 합치기(F2와 같은 뿌리)
F4 “현재 진행 중인 운행” 전용 API가 없다 — 기사·관리자 모두 버스/학원의 전체 운행 이력을 받아 앱에서 진행 중인 것을 골라낸다. 이력이 쌓일수록 응답이 계속 커지고 느려진다. 백엔드에 상태 필터 또는 /active 엔드포인트 추가
F5 승하차 기록 조회에 버스·기간 필터가 없다 — 관리자 화면이 학원 전체 기록을 받아 앱에서 버스별로 거른다. 날짜 단위라 등원·하원이 섞여 오고 세션 구간 분리도 클라이언트 몫이다. 쿼리 파라미터에 busId·세션 범위 추가. 목록 조회 6건 전부 페이지네이션이 없다는 문제도 같이 해결
F6 기사 노선 조회의 정렬을 서버가 보장하지 않는다 — 재배차로 version이 올라간 새 계획이 생겨도 서버는 방향으로만 정렬해 주므로 앱이 직접 최신 version을 골라낸다. 다른 클라이언트가 붙으면 옛 노선을 볼 수 있다. 서버가 버스·방향별 최신 version만 반환하도록 수정
F7 기록 시각에 타임존이 없어 절대 시각을 표시할 수 없다 — 서버가 LocalDateTime을 그대로 내려보내 9시간 어긋난다. 관제 화면은 “몇 초 전 갱신”을 클라이언트 수신 시각으로 대체 계산하고 있고, 서버가 실제로 기록한 시각은 화면에 쓸 수 없다. API 응답을 타임존 포함 형식으로 전환
F8 위치 출처(origin)가 실제와 다르다 — 기사 앱이 Mock을 보내도 서버는 전부 GPS로 기록한다. 상세 패널의 “단말/시뮬레이터” 표기가 거짓을 표시한다. 보고 요청에 출처를 실어 보내고 서버가 그대로 저장
F9 버스 위치에 실시간 push가 없다 — STOMP 인프라가 있는데도 버스 위치만 3초 폴링이다. 관제 지연·서버 부하가 모두 불리하다. 버스 위치 보고 시 이벤트를 발행해 기존 push 파이프라인에 연결
F10 노선 계획 응답에 정류장 이름과 학원 좌표가 없다 — 화면이 polyline의 첫 점을 학원으로 간주하고, 운행 시작 전에는 정류장을 “N번 정차”로만 표시한다. 기사가 어디에 서는지 이름으로 알 수 없다. 계획 응답에 정류장명·depot 좌표 포함
F11 승하차 순서를 서버가 검증하지 않는다 — 승차 기록 없이 하차를 보내도 서버가 200을 준다. 앱이 버튼을 하나만 노출해 막고 있을 뿐이라 다른 클라이언트나 직접 호출은 막히지 않는다. 서버에 순서·중복 검증 추가
F12 마스터 데이터의 수정·삭제 API가 없다 — 구성원은 생성·조회만 있어 퇴사 처리·기사 교체가 불가능하고, 버스·학생의 배정은 null로 보내도 “변경 없음”으로 해석돼 배정 해제 수단이 없다. 수정·삭제 엔드포인트와 명시적 해제 표현 추가
F13 승하차 기록 정정을 앱에서 할 수 없다 — 백엔드 정정 API는 있으나 프론트가 호출하지 않아, 기사가 잘못 기록하면 되돌릴 방법이 전혀 없다(“되돌릴 수 없다”고 안내만 한다). 명단 화면에 정정 UI 추가
F14 노선 계획의 개별 승인·배포·수동 생성 UI가 없다 — 프론트는 자동배차 제안 + 확정 경로만 쓴다. 확정 한 번에 승인·배포가 함께 일어나므로 “승인은 하되 배포는 나중에” 같은 운영 판단을 할 수 없다. 노선 상세 화면에 승인·배포 액션 추가
F15 계정을 만들 경로가 앱 안에 전혀 없다 — 회원가입 화면을 두지 않은 것은 “계정은 관리자가 생성한다”는 의도적 결정인데, 그 관리자용 생성 화면도 없다. 결과적으로 어느 쪽으로도 계정을 만들 수 없다. O4와 함께 해결

12.3 사소 (8건)

  • M1. 사용되지 않는 PendingScreen 죽은 코드
  • M2. 호출부 없는 AuthController.attachBusId() 죽은 코드
  • M3. 노선 상세 경로 상수가 선언만 되고 라우터는 문자열 리터럴을 씀 — 경로 변경 시 어긋날 위험
  • M4. 빠른 로그인 패널이 시드 계정 4개(비밀번호 password)를 하드코딩. 빌드 플래그로 가려져 있으나 운영 빌드에서 반드시 꺼져 있어야 한다
  • M5. 지도 기본 중심 좌표 하드코딩(한빛학원 근처) — 다른 지역 학원은 첫 화면이 엉뚱한 곳을 본다
  • M6. 다크 테마 코드가 있으나 라이트 모드로 고정
  • M7. 운행 방향 enum이 모듈별로 둘(DriveDirection / RouteDirection)이라 화면이 문자열로 비교
  • M8. 운행 종료 요약에서 “거리”를 의도적으로 제외(계획값과 실적이 다르기 때문 — 9장 참조)

12.4 백엔드 측 리스크 (프론트 갭과 별개)

화면 유무와 무관하게 API 자체에 남아 있는 문제다. 학생·학부모 앱을 붙이기 전에 처리해야 한다.

구분내용
권한 상승 가능회원가입이 누구나 호출 가능하고 요청 body의 학원·역할을 그대로 신뢰한다 → 임의의 학원에 학원관리자로 self-signup이 가능하다. 최우선 차단 대상.
테넌트 격리 누락 1건정류장 목록 조회가 인증 주체를 아예 받지 않아, 인증된 아무나 다른 학원의 정류장 이름·좌표를 읽을 수 있다.
WebSocket 역할 검사 누락학생 위치 보고 STOMP 채널에는 역할 검사가 없다(REST 대응 엔드포인트는 학생만 허용).
정정 권한이 넓다승하차 정정 인가가 “같은 학원 소속”만 확인해서, 담당이 아닌 버스의 기록도 같은 학원이면 기사가 정정할 수 있다.
참조 무결성 미검증버스에 담당 기사를 지정할 때 역할·소속을 확인하지 않는다(학부모 계정을 기사로 지정 가능). 학생 등록 시 연결 계정은 존재 확인조차 하지 않는다.
입력 검증 느슨좌표에 위경도 범위 검증이 없고, 비밀번호에 길이·복잡도 제약이 없다(1글자 통과).
성능버스·노선 목록의 배정 인원 계산이 N+1 쿼리이고, 목록 조회 전반에 페이지네이션이 없다.

12.5 MVP 완성에 필요한 최소 항목

위 28건 전부가 MVP 조건은 아니다. “기획한 서비스가 시연 이상으로 성립하려면 반드시 있어야 하는 것”만 추리면 다음과 같다.

순위항목이유
1O4/F15 관리자 데이터 관리 화면(버스·학생·회원 등록)이게 없으면 새 학원을 온보딩할 방법이 없다. 다른 모든 기능의 전제
212.4 회원가입 권한 상승 차단보안 결함. 외부에 노출되는 순간 문제가 된다
3O1 학부모 화면(자녀 위치·승하차 기록·알림함)제품의 존재 이유. 백엔드가 다 돼 있어 비용 대비 효과가 가장 크다
4O5/F8 위치 출처 실 GPS 기본화 + 출처 정직하게 기록관제 데이터가 진짜여야 나머지 판단이 의미를 갖는다
5O2 SOS 발신·확인 화면안전 기능. 백엔드·스케줄러가 이미 대기 중
6F13 승하차 정정 UI오기록을 되돌릴 수 없는 것은 운영상 치명적
7F11 서버 측 승하차 순서 검증기록 신뢰성의 최소 보장
8F7 시각 타임존 정상화법정 운행기록·KPI의 전제

MVP 범위에서 미루어도 되는 것: 도보 경로 안내, 학부모 통합 실시간 추적, QR·NFC 태그, 외부 발송 채널(알림톡·SMS), 통계·리포트, 계약·과금, 차량 점검 체크리스트, 법정 서식 출력 — 전부 로드맵 2·3단계 항목이다.

단, 실 GPS 전환 전에는 미룰 수 없는 것

8장의 개인정보·위치정보 동의 UI와 저장 스키마. 이것은 기능이 아니라 전환의 전제 조건이다.
