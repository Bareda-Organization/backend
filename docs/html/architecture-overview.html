1. 런타임 구성 — 컨테이너 하나하나가 무엇을 맡는가

바깥에서 닿는 포트는 nginx 의 80 하나. 백엔드·프론트엔드 컨테이너는 호스트에 포트를 열지 않고 compose 내부망에서만 서로 부름. 프론트 빌드가 API_BASE_URL="" 상대경로를 쓰므로 같은 번들이 localhost 든 배포 도메인이든 그대로 동작하고, 출처가 같아 브라우저 CORS 자체가 발생하지 않음.

📊 런타임 구성도 — Docker 구역 경계와 클라이언트 2종 (로컬·개발 기준)
파란 상자 = 요청 경로 위의 처리 주체, 초록 = 영속·경계, 보라 = 휘발성 저장, 노랑 = 비동기 전달·외부 의존. 웹 브라우저와 모바일 기기는 Docker 경계 밖이고, 컨테이너로 띄울 수 있는 프론트 타깃은 Web 뿐 — 컨테이너 안에서 Android·iOS 앱을 실행할 방법이 없어 모바일은 항상 경계 밖에서 flutter run 으로 붙는다. frontend 컨테이너가 서빙하는 것은 소스가 아니라 빌드된 정적 번들이며, 그래서 UI 를 반복 수정할 때는 재빌드가 느려 로컬 실행이 권장됨.
백엔드 인스턴스를 늘리면 깨지는 것 @Scheduled 작업 4개가 중복 실행되고, WebSocket 세션 레지스트리(LocationSessionRegistry)와 InMemory 위치 저장소가 프로세스 로컬이라 인스턴스마다 다른 답을 냄. 수평 확장 전에 스케줄러 리더 선출과 STOMP 브로커 릴레이가 선행 조건.

같은 코드가 로컬과 운영에서 서로 다르게 묶인다. 특히 웹이 어디에 놓이는지가 갈리고, 그 차이가 CORS 설정까지 이어진다.

📊 로컬 vs 운영 — 웹이 놓이는 위치와 Docker 구역의 범위
두 패널의 점선 구역 넓이가 다른 것이 요점 — 로컬은 화면까지 Docker 안에 있어 같은 출처(:80) 가 되고 CORS 가 아예 발생하지 않지만, 운영은 화면이 Vercel 로 빠져 출처가 갈리므로 허용 목록 주입이 필수 조건이 됨. 로컬에서 CORS 를 한 번도 만나지 않다가 운영에서 처음 겪게 되는 구조이므로, 배포 전에 이 두 설정값을 반드시 확인.

2. 요청 3갈래 — 같은 앱이 세 경로를 동시에 사용

📊 데이터 플로우 — REST · WebSocket push · 폴링
붉은 계열(③)은 정상 설계가 아니라 전환이 남은 구간을 뜻함. ①과 ②의 차이는 방향 — ①은 화면이 필요할 때 끌어오고, ②는 사건이 났을 때 서버가 밀어냄. ②의 중간에 Kafka 를 끼운 이유는 발행 모듈이 알림 모듈을 직접 부르지 않게 하려는 것이고, 실제로 RideEventCommandService 는 NotificationService 를 모름.

3. 백엔드 모듈 지도 — 업무 단위 16개 + 공통 인프라

패키지 최상위를 controller/ · service/ 같은 기술 단위가 아니라 업무 단위로 가름. 기능 하나를 고칠 때 폴더 하나만 열면 되게 하려는 의도이며, 각 모듈 안에서 다시 controller · command · query · repository · entity · event 로 나뉨.

📊 모듈 지도 — 책임군별 배치
색은 책임군 구분일 뿐 호출 방향이 아님. 판정 기준은 "이 모듈이 답하는 질문" — 기준정보는 존재, 계획은 예정, 실행은 현재, 예외는 이탈, 조회·전달은 표현. location 과 operations 에만 엔티티가 없는 이유도 여기서 나옴: 하나는 휘발성 좌표만 다루고, 하나는 다른 모듈의 데이터를 조합해 읽기만 함.

4. 요청 1건이 통과하는 계층 — Controller · Service · Repository

Spring 의 기본 3계층 위에 이 저장소가 얹은 규칙이 둘. 하나는 서비스를 command 와 query 로 가르는 것(쓰기 트랜잭션과 읽기 전용 조회를 섞지 않음), 다른 하나는 응답을 ApiResponse<T> 로 통일하는 것(성공·실패 형태가 같아 프론트가 한 번만 언랩).

📊 요청 → 처리 → 응답 경로와 예외 우회로
위아래로 갈라진 두 초록 상자가 CQRS 분리 지점 — 같은 도메인이라도 쓰기 트랜잭션과 읽기 조회가 다른 클래스에 있음. 점선 회신 화살표가 Repository 에서 출발하는 이유는 반환 경로에서 추가 처리가 없기 때문이며, 컨트롤러는 DTO 를 ApiResponse 로 감싸기만 함.

5. 인증 · 인가 — 세 층이 서로 다른 질문에 답변

세 층이 각각 누구인가 · 무엇을 할 수 있는가 · 그 데이터에 닿아도 되는가 를 나눠 맡음. 특히 세 번째가 이 시스템의 핵심 제약인데, 멀티 테넌시 격리를 DB 레벨(RLS)이 아니라 애플리케이션 코드에서 강제하기 때문.

📊 인가 3층 구조와 STOMP 우회로
2층에서 역할 문자열이 컨트롤러에 등장하지 않는 것이 이 구조의 핵심 — 컨트롤러는 "버스를 관리할 권한"만 요구하고, 그 권한을 어떤 역할이 갖는지는 부여표 파일 하나가 결정. 노란 패널은 예외 경로이며 정상 설계에 포함되나, 2층을 우회하므로 역할 변경 시 별도 점검 대상. 3층이 없으면 A 학원 관리자가 B 학원 학생을 조회 가능 — 격리가 코드에만 있는 만큼 이 층의 누락이 곧 보안 결함. 누락 여부를 사람 눈에 맡기지 않도록 ControllerAuthorizationConventionTest 가 매핑 메서드 단위로 2층 부재를 검출 — 의도적으로 여는 매핑은 근거와 함께 METHOD_LEVEL_EXEMPT 에 등록해야 통과(2026-08-23 기준 2건: RouteController#stops · LocationSocketController#report, 둘 다 3층을 서비스 계층이 담당).

@Target({ElementType.METHOD, ElementType.TYPE})

6. 도메인 이벤트 — 커밋 이후에만 나가는 2단 릴레이

발행 측은 Kafka 를 모름. 도메인 서비스는 Spring 의 ApplicationEventPublisher.publishEvent() 만 부르고, 커밋 이후에 동작하는 리스너가 Kafka 로 옮김. 이렇게 가른 이유는 DB 롤백과 메시지 발행이 어긋나는 상황을 막기 위해서.

📊 이벤트 릴레이 — 트랜잭션 경계와 소비자 fan-out
보라 점선은 트랜잭션 경계이고, 릴레이 상자가 그 바깥에 있는 것이 이 그림의 핵심 — 경계 안에서 Kafka 를 부르면 롤백된 사건의 알림이 이미 나간 뒤가 됨. 소비자 4종은 같은 토픽 집합을 나눠 듣고 서로를 모름. BusLocationPushConsumer 만 회색 없이 "미구독"이라 표기한 이유는 서버 측 경로가 완성돼 있고 클라이언트 전환만 남았기 때문.
Java · global/event/TransactionalDomainEventRelay.java 
@Component
public class TransactionalDomainEventRelay {

    private final DomainEventPublisher domainEventPublisher;

    public TransactionalDomainEventRelay(DomainEventPublisher domainEventPublisher) {
        this.domainEventPublisher = domainEventPublisher;
    }

    // 커밋 이후에만 호출된다. 롤백되면 이 메서드 자체가 실행되지 않는다.
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void relay(DomainEvent event) {
        domainEventPublisher.publish(event);
    }
}

7. 실시간 위치 — 학생과 버스, 두 파이프라인

이 시스템에는 위치 경로가 둘이고 진행 상태가 서로 다름. 설계 제약은 "MVP 는 Mock 으로 하되 데이터 소스만 갈아끼우면 실 GPS 로 넘어갈 것" 이었고, 실제 구현은 LocationSource 포트 + 설정 플래그 조합.

📊 위치 파이프라인 두 갈래 — 생성부터 화면까지
두 줄이 같은 모양인데 끝만 다른 것이 요점 — 위쪽은 전달까지 갔으나 수신자 화면이 없고, 아래쪽은 화면이 있으나 수신 방식이 폴링. 붉은 상자는 결함이 아니라 전환 잔여분이며, 초록 상자가 Mock↔실GPS 교체가 실제로 가능한 근거(진입점 이후 경로가 공유됨).
폴링이 남아 만드는 두 가지 부작용 기사 앱이 5초마다 보내는데 관제는 3초마다 읽으므로 같은 좌표를 여러 번 읽음 — 화면 갱신 주기가 실제 데이터 신선도보다 짧음. 또한 응답의 recordedAt 에 타임존이 없어 프론트가 절대 시각 대신 "클라이언트 수신 시각"으로 신선도를 계산 중.
