1. 런타임 구성 — 무엇이 몇 개인가

제품 4종이 공유하는 서버는 Spring Boot 인스턴스 1개. 앞단의 nginx 가 TLS 종단과 리버스 프록시를 맡고 /ws 경로에 WebSocket 업그레이드를 허용. 뒤로는 PostgreSQL·Redis·Kafka 를 용도별로 분담시키고, 경로·거리·ETA 산출과 주소 → 좌표 변환은 네이버 API 에 위임(C-18).

📊 런타임 구성도 — 제품 4종 · API 1인스턴스 · 인프라 4종
인스턴스 1개는 용량 판단이 아니라 세 가지가 동시에 요구하는 전제 — 확정 배치의 단일 실행 · 인메모리 WebSocket 세션 · 위치 캐시 지역성. 붉은 점선 상자 하나만 경계 밖이며, 노선 계산 ③단계(도로 경로)가 그 장애에 직결.

증설은 인스턴스 수를 늘리는 것만으로 성립하지 않음. 아래 네 항목이 동시에 필요.

2. 요청 네 갈래 — 같은 계산, 다른 실행 정책

서버로 들어오는 일을 넷으로 가른 기준은 화면이 아니라 실행 정책. 노선 계산이 배치와 사용자 대기 경로 양쪽에서 호출되므로, 코드는 1벌로 두고 타임아웃·동시성·실패 처리만 호출자가 주입.

📊 데이터 플로우 — 요청 네 갈래와 공유 계산부
가운데 상자가 ②·③ 두 갈래에 걸쳐 있는 것은 계산 코드가 1벌이라는 뜻이며, 상자 안 분홍·보라 두 줄이 호출자별 실행 정책의 차이. 배치용 정책(긴 타임아웃·재시도)을 온디맨드에 그대로 쓰면 관리자가 승인 화면에서 수십 초를 대기.
승인 대기 목록에서 항목마다 재최적화를 돌리면 N배 계산이 발생 목록 조회는 요약만 반환하고 전/후 대조는 상세 조회에서 1건만 계산. 목록에 N건이 쌓인 시각이 곧 응답 지연. 계산 결과는 요청 단위로 캐시하고 입력(명단·승하차지·경유 지점)이 바뀌면 무효화 — 미리보기와 실제 배포본이 달라지는 것을 막는 장치.

3. 백엔드 모듈 지도 — 도메인 15 + global

기능 도메인 코드(AUTH·RTE 등 17종)와 모듈을 1:1 로 맞추지 않음. 도메인 코드는 기능 분류이고 모듈은 함께 바뀌는 것의 묶음.

📊 모듈 배치와 의존 방향
붉은 점선 상자는 그려지지 않은 화살표의 뜻 — 아래 밴드에서 위 밴드로 향하는 호출이 부재. 이 방향을 허용하면 주소 수정이 노선 계산을 직접 호출해 트랜잭션이 비대해짐. 굵은 테두리의 routing 은 계산·배치·경유 지점·버전을 모두 담아 모듈 중 가장 무거움. 상자 안에 적힌 것이 그 모듈이 소유하는 대상이며, 아래 세 건은 상자 하나에 담기지 않는 소유 규칙.

4. 인가 3층 — 세 층을 모두 통과해야 접근이 성립

화면 숨김은 UX 이고 차단은 서버 책임이며 서로 대체 불가(C-01). 판정은 계정 상태 · 권한 상수 · 자원 소속 세 층으로 구성되고, 한 층만 두면 각각 다른 구멍이 열림.

②층이 보는 것은 역할이 아니라 권한 상수 — if (role == DRIVER || role == ESCORT) 를 호출 지점마다 복제하면 역할이 하나 늘 때 전수 수정이 필요. 역할↔권한 매핑을 한 파일에 모으고 컨트롤러는 BOARDING_WRITE · EMERGENCY_RAISE 같은 상수만 봄. 카탈로그 정본은 FEATURE_SPEC §6.2, 그림은 §9.

📊 인가 3층 통과와 각 층이 막는 구멍
왼쪽 세로 줄기는 통과 순서가 아니라 누적 조건 — 세 층 중 하나라도 빠지면 오른쪽 붉은 상자의 접근이 성립. 붉은 점선은 그 층을 제거했을 때 열리는 경로. 아래 초록 상자가 "접근 성립"이 아니라 "자원까지만"인 이유는 마지막 줄 — 같은 자원 안에서도 필드가 등급으로 다시 갈리므로 3층 통과가 전 필드 노출을 뜻하지 않음. 메인 관리자 예외는 조회 범위에만 적용되고 변경 권한에는 미적용.

PENDING 에도 토큰을 발급하는 이유 — 대기 화면이 서버 조회를 필요로 함(학원명 · 신청 일시 · 상태). 토큰을 안 주면 그 화면을 비인증 API 로 열어야 하고, 그러면 신청 정보가 인증 없이 노출.

가장 흔한 사고 지점 — 목록 조회의 academy_id 누락 단건 조회는 대조가 눈에 보이지만 목록은 조건 하나가 빠져도 동작해서 테스트를 통과. 서비스가 빠뜨려도 새지 않도록 저장소 계층에 강제하고 회귀 테스트로 고정. 로그인 실패 5회 누적 차단은 계정 단위이며 IP 단위 차단은 부재 — 학원 와이파이·가정 공용 회선의 무관한 사용자까지 잠기는 것을 피함.

5. 노선 계산 파이프라인 — 입력은 회차 1건

노선 산출의 입력은 그날의 일일 승하차지(C-16). 요일별 주소(P-05)를 기본값으로 하고 그날의 일일 변경(P-06)이 있으면 그것이 우선. 여기에 금일 탑승 의사(ATT-01)를 반영해 대상 명단을 확정.

학생↔버스 대응은 계산이 아니라 편성이 결정. 고정 노선(RTE-01 · A-08)이 버스별 요일·방향 묶음을 이미 갖고 있고 회차가 그 버스를 물려받음(run.bus_id ← schedule.bus_id). 확정 배치는 회차 1건 = 버스 1대를 입력으로 받으므로 파이프라인에 학생을 버스에 배정하는 단계가 부재.

📊 노선 계산 5단계와 파이프라인에 들어오지 않는 둘
회색 점선 상자 둘은 흐름이 아니라 이 파이프라인에 들어오지 않는 것 — 위는 계산 이전에 편성이 끝내는 대응, 아래는 계산 이전에 주소 검증이 끝내는 병합이며, 둘 다 화살표가 닿지 않는 이유가 그것. 분홍 상자가 계산의 입력 단위이고 그 앞의 초록 상자는 명단, 뒤의 다섯 칸은 그 입력 1건을 순서로 바꾸는 과정. 보라 배지 둘은 알고리즘 교체가 예정된 전략 포트(최적화는 가중치 기준 미확정, 동승자 배정은 충돌 규칙이 학원마다 달라질 축), 붉은 배지는 외부 호출이라 타임아웃·폴백이 필수인 단계이며 폴백으로 계산된 결과는 그 사실을 화면에 표시.

경유 지점(RTE-10)은 ②에서 위치를 고정하고 나머지 승하차지만 재배열. 관리자가 지정한 순번을 최적화가 뒤집으면 지정의 의미가 소멸.

⑤ 가 계산 뒤에 오는 이유 — 동승자 배정은 소요 시간이 확정된 뒤라야 근무 시간 충돌을 판정 가능(MGR-05·06 · PRD §5.1 2단계). 기사 배치는 그 전에 관계자가 수동으로 끝냄.

배포와 버전

계산 결과를 곧바로 반영하지 않고 미리보기 → 관리자 확인 → 배포 단계를 둠(A-05 · A-15). 배포 전까지 확정 노선은 불변이며, 경유 지점 지정 API 의 apply 플래그가 그 경계. 배포마다 버전을 올리고 기사 단말이 보고 있는 버전을 기록해 어느 판을 보고 운행 중인지 관계자 화면에서 확인 가능(MON-05).

6. 시간 기반 배치 — 이 시스템의 중심축 ★

회차의 idle → confirmed 전이는 사용자 조작이 아니라 출발 30분 전 도달이 일으킴(C-04 · RTE-02). 회차마다 출발 시각이 다르므로 "출발 30분 전"도 회차별로 서로 다른 시각이고, 고정 시각 cron 으로는 표현 불가. 30초 폴링으로 도래분을 집는 방식을 채택.

📊 도래 폴링 루프와 조건부 UPDATE 멱등
왼쪽 위 세 줄은 confirm_at 이 회차마다 다른 값이라는 뜻 — 고정 시각 cron 이 표현하지 못하는 근거. 오른쪽 아래 두 상자의 색 차이는 갱신 행 수 판정이며, 0행이 곧 다른 실행의 선점. 분홍 점선은 처리 완료 여부와 무관하게 도는 고정 주기. 두 파란 상자에 적힌 것은 JPQL 이지 네이티브 SQL 이 아님 — 데이터 접근은 전 구간 JPA(§9).
Java · 도래분 조회 (JPQL) 
// 30초마다 실행. 회차별 confirmAt(출발 - 30분)이 지난 건만 집는다
// 상한(LIMIT)은 Pageable 로 전달 — 네이티브 쿼리를 쓰지 않는다
@Query("""
    select r from Run r
     where r.status = :idle and r.confirmAt <= :now
     order by r.confirmAt
    """)
List<Run> findDue(@Param("idle") RunStatus idle,
                  @Param("now") Instant now,
                  Pageable pageable);

선점 판정을 맡는 조건부 UPDATE 도 같은 JPQL @Modifying 이며 실물 코드는 §9 에 둠. 애플리케이션 락이나 인메모리 플래그에 의존하지 않는 이유 — 인스턴스를 늘리는 순간 무효. DB 가 단일 진입을 보장하면 증설이 이 조건부 UPDATE 하나로 성립.

두 시계를 분리 — 실행 시각 vs 판정 시각

배치는 출발 30분 전 실행이 원칙이나 큐 적체·재시작으로 늦게 돌 가능성이 존재. 이때 읽는 값과 판정 기준을 서로 다른 시계로 둠.

📊 타임라인 — 실행 시각과 판정 시각의 분리
분홍 세로선은 배치가 몇 시에 돌든 고정, 청록 점선은 실행 지연에 따라 이동 — 두 선이 성질이 다르다는 것이 이 그림의 요지. 초록·붉은 두 패널은 같은 07:32 요청을 어느 시계로 판정했는지의 차이이며, 아래쪽 붉은 패널이 두 시계를 하나로 합쳤을 때의 결과.
흔한 오해 "최신값을 읽는다"와 "구간 판정 기준"을 한 값으로 합치는 것. 두 값은 별개이며, 배치는 판정 결과를 읽어 노선을 만들 뿐 마감을 이동시키지 않음. 30분 전 스냅샷을 만들지 않는 이유도 같은 축 — 스냅샷을 쓰면 "30분 전 ~ 실행 시각" 사이에 승인된 삭제가 확정 노선에 미반영되어, 미탑승 학생을 태우러 가는 경로가 그대로 배포.

동시 도래 폭주 — 가장 현실적인 장애 시나리오

학원 N곳 × 호차 M대가 같은 출발 시각(08:00)을 쓰면 07:30 한 틱에 수십 건이 동시 도래. 회차당 계산은 외부 지도 API 호출을 포함해 수백ms~수초.

대응내용
배치 크기 제한한 틱에 처리할 회차 수 상한(LIMIT N). 남은 건은 다음 틱
동시 실행 제한계산 워커 풀 크기를 외부 지도 API 레이트리밋에 맞춤
회차 단위 격리한 회차의 실패가 나머지를 막지 않도록 try/catch 로 감쌈
실패 재시도상태를 idle 로 되돌려 다음 틱에 재시도. 연속 실패 횟수를 기록해 관계자에 경보
관측도래 후 확정까지의 지연을 지표로 노출 — 이 값이 늘면 증설 신호

처리 시간이 폴링 주기를 넘기면 밀림이 누적. 지연 지표가 임계를 넘으면 배치 크기가 아니라 워커 수나 인스턴스를 늘리는 것이 대응.

7. 3구간 규칙 — 출발 시각이 기준선

노선 변경의 허용 범위는 회차 출발 시각을 기준으로 셋으로 갈림(C-04). 추가는 노선을 늘려 다른 학생의 도착 시각에 영향하고 삭제는 노선을 줄이기만 하므로, 구간별 비대칭은 의도된 설계.

📊 타임라인 — 3구간과 구간별 허용 동작
빗금 구간은 운행 시작 버튼이 활성인 출발 시각 ±3분 — 버스가 출발 시각보다 먼저 떠날 수 있어 ②구간 마감이 출발 시각과 일치하지 않는 원인. 상단 회색 점선은 상태 전이 지점과 구간 경계가 같은 시각이라는 대응 관계. 자동 승인이 아니라 자동 거절인 이유는 관계자 미확인 상태에서 노선이 바뀌면 책임 소재가 소멸하기 때문.
구간승인재최적화한도
① 출발 30분 전까지부재 — 즉시 반영수행부재
② 30분 안쪽 ~ 출발 전관리자 승인 필요승인 시 수행 후 재배포(버전 +1)회차당 1회 (등원/하원 불문)
③ 운행 시작 후부재 — 미등원 요청만 즉시 수용부재 — skipped 표시만추가·위치 변경 불가

마감을 두 경로가 나눠 맡음 — 운행 시작으로 닫히는 분은 POST /runs/{runId}/start 트랜잭션 안에서 동기 종결하고, 출발 시각 도달로 닫히는 분만 30초 폴링이 집음. 폴링 하나로 두 조건을 다 처리하면 운행 시작 직후 최대 30초 동안 ②구간 승인이 통과해 잠긴 노선이 바뀜.

③구간에서 노선을 다시 계산하지 않는 이유 주행 중 경로 재계산·재배포는 기사가 이미 인지한 경로와 어긋나 주행 위험이 증가. "이 승하차지는 미정차" 한 줄은 경로를 건드리지 않아 안전하게 전달 가능. 출발 전인 ②구간은 이 위험이 부재하므로 재최적화를 허용 — 같은 요청이라도 구간에 따라 처리가 달라지는 근거.

8. 실시간 · 알림

위치는 매니저 앱이 5~10초 주기로, moving 상태에서만 송신. 한 번의 수신이 최신 좌표 갱신 · 근접 판정 · WebSocket 팬아웃 세 갈래로 갈림.

📊 위치 파이프라인과 WebSocket 4채널
가운데 세 갈래는 순차가 아니라 같은 수신 1건에서 갈라지는 병렬 처리. "곧 도착합니다" 알림의 트리거가 기사 조작이 아니라 서버의 좌표 판정이라는 점이 두 번째 갈래의 요지 — 기사 조작을 트리거로 두면 조작 누락·지연이 그대로 알림 누락. 근접 판정을 계획 ETA 근사가 아니라 실제 좌표로 하는 이유는 지연 운행에서 값이 어긋나기 때문.
관제는 폴링이 아니라 WebSocket 관제 화면이 전 학원 버스를 동시에 보므로 폴링은 학원 수에 비례해 부하가 증가. 승하차 상태 반영 5초 이내(NFR-02)를 3초 폴링으로 맞추면 대부분의 요청이 변화 없는 응답.

알림 — 트랜잭셔널 아웃박스

알림은 이벤트를 받아 바로 쏘는 구조가 아님. 상태 변경과 같은 트랜잭션에서 notification_log 에 push_state='pending' 으로 적재하고, 발송은 커밋 후 즉시 시도 + 워커 회수 2단으로 분리. 아래는 위치·상태 변경에서 단말까지의 큰 흐름이며 2단 구조의 기제·유실 창·재시도 상한은 §9 에서 따로 다룸.

📊 상태 변경 → 아웃박스 적재 → 발송 → 단말, 그리고 두 알림의 수신자 차이
분홍 세로선이 커밋 경계 — 그 왼쪽은 상태 변경과 한 트랜잭션이라 둘 다 커밋되거나 둘 다 롤백되고, 오른쪽은 전부 트랜잭션 밖이라 실패해도 승하차 기록이 사라지지 않음. 초록·주황 두 발송 경로는 순서가 아니라 정상 경로와 안전망의 관계이며, 둘이 같은 건을 동시에 집어도 dedup_key UNIQUE 가 한쪽만 통과시킴. 아래 왼쪽 두 상자의 조건이 서로 다르다는 것이 요지 — 레코드는 무조건, 푸시만 설정 대상. 맨 아래 두 상자를 갈라 놓은 기준은 발신 역할과 수신자 범위이며, 색은 붉은 쪽이 안전 사안이라는 표시. absent 학생은 도착·지연 알림 대상 밖(C-02).
device_token 이 없으면 푸시가 전부 미발송 (NTF-12) 등록·해지는 알림 전 종류의 전제. 서버가 발송 대상 단말을 특정하는 유일한 수단이라, 이 등록이 빠지면 아웃박스가 정상 동작해도 레코드만 쌓이고 단말에는 아무것도 도달하지 않음. 증상이 "알림 실패"가 아니라 "조용함"이라 발견이 늦음 — 계정당 등록 단말 수를 지표로 노출할 것.
비상 알림만 다른 취급을 받는 두 지점 (EXC-04 · C-17) 발신 역할 — 승하차(C-06)·도착 처리와 달리 역할을 제한하지 않는 유일한 쓰기 경로. 사고 현장에서 누가 먼저 인지하는지 정할 수 없으므로 기사 앱·동승자 앱 양쪽에 비상 버튼이 존재.
발송 시점 — 아웃박스에 적재하되 워커를 기다리지 않고 커밋 직후 즉시 발송하고 재시도 간격도 다른 알림보다 짧음. 유실은 사고 대응 실패이고 지연도 곤란하다는 두 요구가 겹친 유일한 알림.

알림 문구에 자녀 이름이 필수(P-02) — 다자녀 가정에서 어느 아이 얘기인지 화면 상태와 무관하게 식별이 되어야 함. 문구 생성은 NotificationComposer 뒤에 두어 다국어·표현 변경이 발송 경로를 건드리지 않게 함.

9. 기술 선택이 각 구간에서 어떻게 쓰이는가

구간마다 무엇을 쓰고 무엇을 쓰지 않는가를 그림으로 옮긴 절. 서술 원문과 판단 근거는 TECH_DECISIONS.md.

이 시스템의 성격은 대용량 데이터 가공이 아니라 정해진 시각에 소량을 정확히 한 번 처리. 무거운 프레임워크를 넣으면 개념만 증가하고 얻는 것이 부재. 투자 대상은 동시성 제어 · 시각 주입 · 외부 호출 보호 셋.

요청 1건이 지나는 기술 스택

📊 데이터 플로우 — 구간별로 담당하는 기술
보라 상자의 테두리가 Spring Security 의 경계 — 안쪽 3단은 "누구이고 어떤 역할인가"까지이고, 오른쪽 붉은 점선 패널은 그 경계 밖으로 밀어낸 항목. ③ 자원 소속을 Security 로 하지 않는 근거는 둘 — @PreAuthorize 로 학원 격리를 걸면 인가와 서비스가 같은 데이터를 두 번 조회하고, 목록 조회는 판정할 자원이 아직 존재하지 않음. 분홍 상자만 색이 다른 것은 그 지점이 프레임워크가 아니라 직접 쓴 도메인 코드라는 뜻.

검문소 비유 — 신분증을 확인하고(인증) 출입증 등급을 봄(역할). 그러나 "이 서류가 당신 부서 것인가"는 검문소가 알 수 없고, 서류를 꺼내오는 사무실(저장소)이 확인.

RBAC 3층과 권한 상수

📊 역할 → 권한 상수 → 기능, 그리고 RBAC 밖의 검증
오른쪽 붉은 밴드는 왼쪽 흐름의 연장이 아니라 병렬로 필요한 별개 검사 — 화살표를 잇지 않은 이유가 그것. 밴드 안 각 항목의 아래 줄은 그 검증이 빠졌을 때 성립하는 조회. 아래 세 등급 띠의 색은 위험도이며 같은 자원 안에서 필드별로 갈리는 구분이지 역할 구분이 아님. L3 붉은 띠에 학생 사진이 들어 있는데도 매니저 앱이 받는 근거는 맨 아래 보라 줄.

    // ...
);

@PreAuthorize("hasPermission('BOARDING_WRITE')")   // 역할 문자열을 컨트롤러에 미분산
public BoardingResult record(...) { ... }

권한을 토큰에 싣지 않는 이유 — 토큰에 권한 목록을 실으면 매핑을 고쳐도 기존 토큰이 옛 권한을 그대로 보유하며, refresh 만료까지 최대 며칠. 역할 하나는 계정 상태와 함께 어차피 검증하므로 유도 비용이 부재.

상태 전이 — 무엇이 어디에 있는가

📊 상태 전이도 — 값 · 규칙 · 원자성의 담당 분리와 경합 여부 분기
회색 점선 박스는 검토 후 불채택 표기 — 그림 안의 어느 경로에도 등장하지 않음. 갈림의 판정 기준은 상태의 개수가 아니라 같은 행을 여러 실행이 동시에 노리는가이며, 왼쪽 경로는 사용자 조작 1건이라 읽기→판단→쓰기 사이의 창이 문제가 되지 않음. 오른쪽 초록 상자가 DB 색을 쓰는 것은 원자성 보장의 주체가 애플리케이션이 아니라 DB 라는 뜻이고, 그래도 @Modifying @Query 는 Spring Data JPA 기능이라 JPA 안.
Java · 조건부 UPDATE (JPQL) 
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("""
    update Run r
       set r.status = :confirmed, r.confirmedAt = :now
     where r.id = :runId and r.status = :idle
    """)
int markConfirmed(@Param("runId") Long runId,
                  @Param("idle") RunStatus idle,
                  @Param("confirmed") RunStatus confirmed,
                  @Param("now") Instant now);
// 반환값 1 = 선점 성공, 0 = 다른 실행이 이미 처리 → 건너뜀

애플리케이션 락 · 인메모리 플래그에 의존하지 않는 근거 — 인스턴스를 늘리는 순간 같은 회차가 두 번 확정. DB 가 단일 진입을 보장하면 증설이 조건부 UPDATE 하나로 성립. 낙관적 락(@Version)은 쓰임이 다름 — 조건부 UPDATE 는 "선점 실패 시 건너뜀"이고 @Version 은 "충돌 시 예외 후 재시도"라 노선 배포 버전에 적용.

알림 아웃박스 2단

📊 트랜잭셔널 아웃박스 — 즉시 발송과 워커 회수의 2단 구성
붉은 점선 구간이 AFTER_COMMIT 단독일 때 알림이 사라지는 창 — 이벤트가 메모리에만 있어 "보내야 했다"는 사실 자체가 남지 않고, 그래서 재시도할 대상을 특정할 수 없음. 트랜잭션 안에 notification_log INSERT 를 넣는 이유가 그 사실을 DB 에 먼저 남기는 것. 왼쪽 두 붉은 점선 상자는 흐름이 아니라 이 구조에서 하지 않기로 한 것. 아웃박스 대상은 전부가 아니며, 관제 WebSocket position 처럼 5~10초 뒤 다음 신호가 오는 것은 즉시 발행으로 충분.

인증 · 인가 Spring Security — 역할 · 권한까지만 Security 로 학원 격리 인가와 서비스가 같은 데이터를 두 번 조회. 목록 조회는 판정할 자원이 아직 부재
로그인 방식 아이디 · 비밀번호 form + JWT 2종 (C-01 · C-14) Security 의 formLogin() stateless — 서버 세션 부재. 제품 사양의 "form 로그인"과 이름만 같은 별개 기능
권한 모델 RBAC — 권한 상수 enum + 역할↔권한 매핑(코드) DB 권한 테이블 · Security ACL · 토큰에 권한 적재 역할 6종이 사양 고정값이라 DB 로 빼면 운영에서 권한이 바뀌어 사양 위반이 런타임에 허용. 토큰 적재는 매핑 수정 후에도 기존 토큰이 옛 권한을 보유
민감 데이터 역할별 응답 DTO + 조회 시 마스킹 + L3 감사 로그 엔티티 직렬화 · @JsonIgnore 의존 애너테이션 하나로는 역할별 분기가 불가능하고 내부 호출에는 값이 그대로 적재. 엔티티 직렬화는 필드가 하나 늘 때마다 전 역할에 자동 노출
배치 @Scheduled + ThreadPoolTaskExecutor + ShedLock Spring Batch · Quartz 회차 수십 건 · 건당 독립이라 청크 처리가 대상 밖. JobRepository 메타 테이블 6개가 늘고 회차마다 다른 도래 시각을 Job 파라미터로 표현해야 함. Quartz 는 스케줄러 전체 교체 비용이 이익을 초과
상태 전이 JPA 엔티티 메서드 + 허용 전이 상수 Spring StateMachine 상태 4계열 × 계열당 전이 4~5개 규모. 머신 인스턴스 + persister 로 JPA 와 상태 저장이 이중화
경합 전이 JPA @Modifying 조건부 UPDATE (JPQL) 변경 감지(dirty checking) · 애플리케이션 락 읽기 → 판단 → 쓰기 사이에 두 실행이 같은 행을 확정하는 창이 존재. 인메모리 락은 인스턴스 증설 순간 무효
외부 지도 API Resilience4j — TimeLimiter · CircuitBreaker · Bulkhead 무방비 동기 호출 지도 API 장애가 곧 확정 배치 전체 정지. 매 회차마다 타임아웃 대기가 누적
이벤트 트랜잭셔널 아웃박스 — notification_log 겸용 AFTER_COMMIT 단독 · 트랜잭션 안 발송 커밋과 리스너 사이 크래시는 "보내야 했다"는 사실 자체가 미잔존. 트랜잭션 안 발송은 푸시 실패가 승하차 기록을 롤백
시각 Clock 빈 주입 LocalDateTime.now() 직접 호출 30분 · ±3분 · 3분 규칙이 전부 시각 의존이라 고정 시계 없이는 경계값 테스트가 불가. 나중 전환은 시간 쓰는 곳 전수 수정
데이터 접근 전 구간 JPA — DTO 프로젝션 + fetch join JdbcClient · QueryDSL · MyBatis 같은 테이블을 두 방식으로 다루면 매핑 · 트랜잭션 · 테스트가 두 벌. 관제 조회가 프로젝션으로 감당되지 않는 시점에 그 조회만 분리
테스트 Testcontainers + Awaitility + Clock.fixed H2 멱등이 UNIQUE 위반 예외에 의존 — H2 는 PostgreSQL 방언 · 부분 인덱스 · 제약 위반 예외 코드를 미재현
불채택 결정은 근거를 남기지 않으면 반드시 다시 제안됨 "배치니까 Spring Batch", "상태가 있으니 StateMachine" 은 이름만 보고 내리기 쉬운 판단. 위 표의 왜 안 쓰는가 열이 그 되돌림을 막는 장치이며, 뒤집힐 조건도 함께 고정 — Spring Batch 는 수십만 행을 가공하는 잡이 생길 때, StateMachine 은 서브머신 · 병렬 상태가 필요해질 때, 전 구간 JPA 는 관제 조회가 프로젝션 · fetch join 으로 감당되지 않을 때.
