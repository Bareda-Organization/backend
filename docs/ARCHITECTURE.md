## 1. 전체 구성

### 1.1 런타임 구성 요소

```
┌─ 학부모·학생 앱 (Flutter, 390) ─┐
├─ 매니저 앱 (Flutter, 390 다크) ─┤   HTTPS / WSS
├─ 관계자 웹 (1440) ─────────────┤ ──────────────► nginx ──► Spring Boot API (인스턴스 1)
└─ 메인 관리자 콘솔 (1440) ───────┘                              │
                                                                 ├─► PostgreSQL   영속 · 노선 · 명단 · 이력
                                                                 ├─► Redis        최신 좌표 · 멱등키 · 배치 락
                                                                 ├─► Kafka        도메인 이벤트 · 알림 팬아웃
                                                                 └─► 외부 지도 API  경로·거리·ETA · 지오코딩
```

**백엔드 인스턴스는 1개를 전제.** 근거는 §9.5 — 확정 배치의 단일 실행, 인메모리 WebSocket 세션, 위치 캐시 지역성. 증설 시 필요한 조치를 §9.5 에 명시.

### 1.2 요청이 흐르는 네 갈래

| 갈래 | 경로 | 성격 |
|---|---|---|
| **동기 조회·명령** | 앱·웹 → REST → DB | 명단 · 노선 · 승인 · CRUD |
| **시각 도래 배치** | 스케줄러 → 노선 계산 → 배포 | 출발 30분 전 확정 (§9) |
| **온디맨드 계산** | 관계자 조작 → 노선 계산 → 미리보기·배포 | ②구간 승인 · 경유 지점 지정 (§8.4) |
| **실시간 전달** | 위치·상태 변경 → 이벤트 → WebSocket·푸시 | 관제 · 학부모 화면 (§10) |

**갈래를 넷으로 가른 이유** — 노선 계산이 배치와 사용자 대기 경로 **양쪽에서 호출**되기 때문. 같은 계산 코드를 쓰되 타임아웃·동시성·실패 처리 정책이 서로 달라야 함 (§8.3).

### 1.3 설계 의도

- **시각이 상태를 만든다.** 회차의 `idle → confirmed` 전이는 사용자 조작이 아니라 **출발 30분 전 도달**이 일으킴 (C-04 · RTE-02). 이 시스템에서 가장 많은 결함이 나올 지점이라 §9 에서 따로 다룸.
- **인가는 서버 한 곳.** 화면 숨김은 UX 이고 차단은 서버 책임 (C-01). §5 에서 3층으로 구성.
- **계산과 배포를 분리.** 노선 계산 결과를 곧바로 반영하지 않고 **미리보기 → 관리자 확인 → 배포** 단계를 둠 (A-05 · A-15). 배포된 노선에는 버전을 붙여 기사 단말이 무엇을 보고 있는지 특정 가능.

## 3. 백엔드 모듈 구조

### 3.1 도메인 모듈

기능 도메인 코드(`FEATURE_SPEC §4`)와 1:1 로 맞추지 않는다 — 도메인 코드는 기능 분류이고 모듈은 **함께 바뀌는 것의 묶음**.

| 모듈 | 담는 것 | 관련 기능 |
|---|---|---|
| `academy` | 학원 등록·수정·비활성화, 학원별 설정 | ACAD |
| `account` | 계정 · 가입 요청 · 승인 · 로그인 차단 · 토큰 | AUTH |
| `student` | 학생 CRUD · 요일별 주소 · 특이사항 · 보호자 연결 | STU · P-02 · P-05 |
| `manager` | 운행인력 CRUD · 배치 · 충돌 검증 | MGR |
| `bus` | 차량 · 정원 계산 | BUS |
| `schedule` | 운행 스케줄 · 일일 회차 생성 | SCH |
| `routing` | **노선 계산 파이프라인 · 확정 배치 · 경유 지점** | RTE |
| `request` | 탑승 의사 · 변경 신청 · 승인 처리 | ATT · REQ |
| `run` | 운행 실행 · 도착 처리 · 종료 판정 | RUN |
| `boarding` | 승하차 처리 · 명단 · 오프라인 동기화 | BRD · RST |
| `exception` | 미승차 에스컬레이션 · 예외 보고 · **비상 알림** | EXC |
| `location` | 위치 수신 · 최신 좌표 · 근접 판정 | LOC |
| `notification` | 알림 생성 · 발송 · 수신 확인 · 로그 | NTF |
| `monitoring` | 관계자 대시보드 · 메인 관리자 관제 | MON |

| `global` | 인가 · 예외 · 응답 규약 · 설정 · 관측 | — |

**`request` 를 별도 모듈로 뺀 이유** — 탑승 의사(ATT)와 변경 신청(REQ)은 담는 데이터가 다르지만 **3구간 판정·승인 큐·회차당 1회 한도**라는 규칙을 공유. 두 모듈로 갈라두면 그 규칙이 양쪽에 복제되어 한쪽만 고쳐지는 결함이 발생.

**`routing` 이 가장 무거운 모듈.** 계산 파이프라인 · 배치 · 경유 지점 · 버전 관리를 모두 담으므로 §8 에서 내부 구조를 따로 서술.

### 3.2 계층 규칙

```
controller  →  command / query  →  repository  →  entity
                     │
                     └─►  domain (정책 객체 · 계산)
```

| 계층 | 책임 | 금지 |
|---|---|---|
| `controller` | HTTP 매핑 · 인가 애너테이션 · DTO 변환 | 비즈니스 판단 |
| `command` | 상태 변경 · 트랜잭션 경계 · 이벤트 발행 | 조회 전용 로직 |
| `query` | 조회 · 응답 조립 | 상태 변경 |
| `domain` | 시간 창 판정 · 정원 계산 · 상태 전이 규칙 | 저장소 접근 |
| `repository` | 영속화 | 도메인 판단 |

### 3.2.1 `spec` / `impl` 추상화 — 교체 축을 인터페이스로 고정

**교체 가능성이 있는 것은 예외 없이 인터페이스(`spec`) + 구현체(`impl`) 로 가른다.** 호출자는 `spec` 만 의존하고 `impl` 을 직접 참조하지 않는다.

| 교체 축 | 인터페이스 (`spec`) | 왜 갈라야 하는가 |
|---|---|---|
| **순서 최적화** | `RouteOptimizer` | 알고리즘 기준이 미확정 (PRD §10.1 G). 휴리스틱 → 정교한 해법으로 교체 예정 |
| **동승자 자동 배정** | `EscortAssigner` | 근무 시간·충돌 판정 규칙이 학원마다 달라질 가능성 |
| **도로 경로·거리** | `MapRouteClient` | **네이버 API 확정**(C-18). 폴백(직선거리 근사) 구현체도 같은 인터페이스라 장애 시 교체만으로 동작 |
| **지오코딩** | `GeocodingClient` | **네이버 API 확정**(C-18). 학부모의 일일 승하차지 등록 시점에 호출 (P-06 · STU-05) |
| **푸시 발송** | `PushSender` | FCM · APNs · 알림톡(2~3단계)이 서로 다른 채널 |
| **위치 원천** | `PositionSource` | 실 단말 GPS ↔ 개발용 시뮬레이션 |
| **알림 문구 생성** | `NotificationComposer` | 문구·다국어가 바뀔 축 |

**구현체 선택은 설정 한 곳에서 한다** — `@ConditionalOnProperty` 나 이름 기반 레지스트리로 주입하고, 호출부에 분기를 두지 않는다. 분기를 호출부에 두면 교체가 전수 수정이 된다.

**단순 CRUD 는 분리하지 않는다.** 학생·차량·매니저 저장소처럼 구현이 바뀔 축이 없는 것에 인터페이스를 씌우면 파일만 두 배가 되고 읽는 사람이 실제 코드를 한 번 더 찾아가야 한다.

### 3.2.2 DTO · 공통 응답

**엔티티를 컨트롤러 밖으로 내보내지 않는다.** 요청·응답은 전용 DTO 를 쓴다.

| 규칙 | 근거 |
|---|---|
| **응답 DTO 는 역할별로 가른다** | 같은 명단이라도 매니저 앱에는 보호자 번호를 마스킹하고 L3 필드를 빼야 함 (FEATURE_SPEC §6.3). 엔티티 직렬화는 필드가 하나 늘 때마다 전 역할에 자동 노출 |
| **요청 DTO 에 Bean Validation** | 필수·형식은 `@NotNull`·`@Pattern` 으로. 도메인 규칙(3구간·정원)은 DTO 가 아니라 `domain` 이 판정 |
| **공통 응답 봉투를 전 엔드포인트에 적용** | 성공·실패의 모양이 갈리면 클라이언트가 경로마다 다르게 파싱 |
| **DTO ↔ 엔티티 변환은 한 방향으로** | DTO 가 엔티티를 만들지 않는다. 생성은 `command` 가 도메인 메서드로 |

공통 응답 형식(성공 봉투 · 에러 봉투 · 페이징 봉투)의 정의처는 **[API_SPEC §1.10](./API_SPEC.md)** — 여기서 형식을 다시 적지 않는다.

### 3.2.3 객체 생성 방식

**대상마다 다르게 쓴다.** 한 방식으로 통일하면 어딘가에서 손해가 난다.

| 대상 | 방식 | 금지 |
|---|---|---|
| **엔티티** | **정적 팩토리 메서드 + `private` 생성자** (JPA 용 `protected` 기본 생성자만 별도) | `@Builder` · `@Setter` · public all-args 생성자 |
| **요청 DTO** | `record` + Bean Validation | 가변 클래스 |
| **응답 DTO** | `record` + 정적 팩토리 `from(...)` — **역할별로 별도 타입** | 엔티티 직접 반환 |
| **값 객체** (좌표 · 시간 창 · 정원) | `record` | |
| **테스트 픽스처** | **빌더** — 기본값 + 일부만 덮어쓰기 | 프로덕션 코드에 빌더 노출 |

#### 엔티티에 빌더를 두지 않는 이유

**빌더는 불변식을 우회한다.** 이 시스템의 엔티티는 상태 전이 규칙을 갖는데, 빌더가 있으면 그 규칙을 건너뛴 객체를 아무 데서나 만들 수 있다.

```java
// 빌더가 있으면 이것이 컴파일되고 통과함 — waiting → alighted 는 허용되지 않는 전이인데도
RunRider.builder().status(ALIGHTED).build();
```

정적 팩토리는 **생성 경로를 이름으로 제한**한다. `RunRider.forConfirmedRoute(run, student, stop)` 만 있으면 초기 상태는 언제나 `waiting` 이고, 그 이후는 `changeTo()` 를 통과해야 한다. **"어떻게 만드는가"가 아니라 "언제 생기는가"를 이름이 말한다.**

부수 이점 — 필수값 누락이 **컴파일 단계**에서 걸린다. 빌더는 `build()` 시점에 `null` 로 통과하고 DB 제약 위반으로 런타임에 터진다.

#### 같은 타입 파라미터가 여러 개일 때

`RunRider.forConfirmedRoute(Long runId, Long studentId, Long stopId)` 는 셋 다 `Long` 이라 **순서를 바꿔도 컴파일된다.** 대응은 둘.

1. **엔티티 참조를 받는다** — `forConfirmedRoute(Run run, Student student, Stop stop)`. 타입이 갈리므로 순서 실수가 컴파일 오류
2. 식별자만 받아야 하면 **팩토리 파라미터 순서를 전 엔티티에서 통일**하고(부모 → 자식 → 부속) 테스트로 고정

식별자마다 값 객체(`RunId` · `StudentId`)를 씌우는 방식은 **채택하지 않는다** — 타입 안전은 올라가나 JPA 매핑에 컨버터가 붙고 파일 수가 테이블 수만큼 늘어난다. 이 규모에서는 1번으로 충분하다.

#### 응답 DTO 를 `record` 로 두는 이유

Java 25 의 `record` 는 불변이고 `equals`·`hashCode`·`toString` 이 자동이라 응답 조립에 맞는다. **필드가 10개를 넘으면 빌더를 고려하기 전에 "이 응답이 너무 많은 것을 담고 있지 않은가"를 먼저 본다** — 대개 화면 하나가 두 가지 일을 하고 있다는 신호다.

---

**3구간 판정은 `domain` 의 정책 객체 하나에 모은다.** `controller` 나 각 `command` 에 흩어지면 같은 요청이 호출 경로에 따라 다른 구간으로 판정됨.

### 3.3 모듈 간 의존 방향

```
notification · audit · monitoring   ← (구독) ← 전 모듈이 발행하는 도메인 이벤트
routing → student · bus · schedule · request   (읽기)
run · boarding → routing (확정 노선 조회) · notification (이벤트 발행)
account → academy
```

- **역방향 참조를 금지.** `student` 가 `routing` 을 알면 주소 수정 트랜잭션 안에 외부 지도 API 호출이 포함됨. 주소 변경은 **이벤트만 발행**하고 재계산 여부는 `routing` 이 판단.
- **비상 알림의 소유는 `exception` 모듈** — 발신은 매니저 앱(기사·동승자 **둘 다**), 수신은 관계자·메인 관리자. 승하차와 달리 역할을 제한하지 않는 유일한 쓰기 경로 (EXC-04).
- **`run` 테이블은 세 모듈이 쓴다** — `schedule` 이 생성(SCH-02), `routing` 이 확정 전이(§9.3), `run` 이 시작·종료. 소유는 `run` 모듈이고 나머지 둘은 **상태 전이 메서드를 통해서만** 접근. 다른 모듈이 컬럼을 직접 갱신하면 §9.3 의 조건부 UPDATE 규칙이 우회됨.
- **승하차지 마스터(`stop`)의 소유는 `student` 모듈** — 생성 계기가 주소 검증(STU-05)이기 때문. `routing`·`boarding` 은 읽기만.
- `notification` 은 **누구도 직접 호출하지 않는다** — 이벤트 구독으로만 동작. 승하차 처리 트랜잭션이 푸시 발송 실패로 롤백되는 상황을 막기 위함 (BRD-04).

## 4. 프론트엔드 구조

### 4.1 제품 4종의 코드 공유 범위

| 제품 | 배포 단위 | 공유 |
|---|---|---|
| 학부모·학생 앱 | 앱 1개 — 역할로 화면 분기 | 학생은 조회 전용(S-01~04). 예외는 부모 연결 인증 코드 생성(S-05)뿐이고, 학부모 전용 기능은 비노출 |
| 매니저 앱 | 앱 1개 — 역할로 화면 분기 | 기사 = 운행모드 중심, 동승자 = 명단 중심. **공통은 회차·명단 조회** |
| 관계자 웹 | 웹 | — |
| 메인 관리자 콘솔 | 웹 | 관계자 웹과 화면이 다름 — 전 학원 관제가 핵심 |

**학부모/학생, 기사/동승자를 각각 한 앱에 합친 이유** — 두 역할이 같은 데이터(회차 · 명단 · 노선)를 보고 조작 권한만 다름. 앱을 가르면 API 클라이언트·모델·실시간 구독이 통째로 복제됨. 분기는 `go_router` 의 `redirect` 한 곳.

### 4.2 레이어

```
presentation (화면 · 위젯)
    ↓
application (상태 · 유스케이스)
    ↓
data (repository → dto → api client)
```

- **포트/어댑터는 교체 가능성이 있는 것만** — 지도(`MapSurface`), 실시간 게이트웨이(STOMP), 보안 저장소.
- **오프라인 큐는 `data` 층에 둔다** (BRD-06). 승하차 처리를 로컬 큐에 적재하고 복구 시 `client_key` 로 재전송 — 서버가 멱등 처리 (API_SPEC §1.7).

### 4.3 운행모드의 특수 규칙

- 테마와 무관하게 **항상 다크** (제품 정책).
- 상태는 색 + 라벨 병기 (C-09 색 규칙).
- **낙관적 UI 금지** (C-10) — 서버 2xx 확인 뒤에만 성공 표시. `dio` interceptor 가 아니라 **각 화면의 상태 기계**에서 강제.

## 5. 인증 · 인가

### 5.1 3층 구성

```
① 계정 상태 게이트   PENDING·REJECTED·BLOCKED 차단          (C-01 · API §1.4)
② 역할 권한          역할 6종 × 기능                        (FEATURE_SPEC §6)
③ 자원 소속 검증     학원 격리 · 보호자↔자녀 · 매니저↔회차   (§6)
```

**세 층을 모두 통과해야 접근이 성립.** 한 층만 두면 아래 구멍이 생김 — 역할만 검사하면 **다른 학원의 관계자**가 남의 학원 명단을 조회하고, 학원 격리만 검사하면 **승인 대기 계정**이 같은 학원 명단을 조회.

### 5.2 계정 상태 게이트

상태 4종과 상태별 허용 API 목록의 정본은 **[API_SPEC §1.4](./API_SPEC.md)** — 이 문서는 중복 기재하지 않음.

**`PENDING` 에도 토큰을 발급하는 이유** — 대기 화면이 서버 조회를 필요로 함(학원명 · 신청 일시 · 상태). 토큰을 안 주면 그 화면을 비인증 API 로 열어야 하고, 그러면 신청 정보가 인증 없이 노출.

구현 지점은 **필터 또는 인터셉터 한 곳**. 각 컨트롤러에 흩어 놓으면 새 엔드포인트를 추가할 때마다 누락 가능성이 생김 — 허용 목록(allowlist) 방식으로 두고 **기본 차단**.

### 5.3 역할 6종

`parent` · `student` · `driver` · `escort`(동승자) · `staff`(학원 관계자) · `system_admin`. 값의 정본은 [API_SPEC §9.1](./API_SPEC.md).

- **한 계정은 한 학원에 속한다.** 역할과 소속을 `account.role` · `account.academy_id` 두 컬럼으로 표현하고 별도 연결 테이블을 두지 않음 (ERD §3.1). 근거는 가입 시 학원을 하나만 고르고(C-01), 로그인 응답의 `academy` 가 배열이 아닌 단일 객체이며(API_SPEC §2.5), 학원은 요청 파라미터가 아니라 **토큰에서 서버가 결정**하기 때문 (API_SPEC §1.5). 다중 소속이 필요해지면 그때 연결 테이블로 전환 — 지금 넣으면 격리 판정이 "어느 학원 자격으로 온 요청인가"를 매번 되물어야 해 §5.1 ③층이 복잡해짐.
- **역할 문자열을 컨트롤러에 흩지 않는다.** 권한 판정은 **권한 상수**(`BOARDING_WRITE` · `EMERGENCY_RAISE` 등 [FEATURE_SPEC §6.2](./FEATURE_SPEC.md) 카탈로그)를 거치고, 역할↔권한 매핑을 한 파일에 모음. 승하차가 동승자 전용(C-06)이라는 규칙이 코드 여러 곳에 역할 문자열로 박히면 역할이 하나 늘 때 전수 수정이 필요.
- **매핑은 코드 상수** — DB 테이블이 아니다. 역할 6종이 사양 고정값이고 관계자 권한 등급은 스코프 제외라, DB 로 빼면 운영에서 권한이 조용히 바뀌어 사양 위반이 런타임에 허용됨.
- **응답 조립에서 필드 등급을 강제한다** (FEATURE_SPEC §6.3). 같은 명단 API 라도 매니저 앱에는 보호자 번호를 마스킹해 내보내고, L3 필드(주소 원문·좌표·특이사항)는 권한 보유자에게만 포함. **엔티티를 그대로 직렬화하지 않고 역할별 응답 DTO 로 가른다** — 엔티티 직렬화는 필드가 하나 늘 때마다 전 역할에 자동 노출되는 구조라 개인정보 사고의 상수 원인.
- **L3 필드 조회는 감사 로그에 남긴다** (SYS-01). 누가·언제·어느 학생의 어떤 등급을 봤는지.

### 5.4 토큰

access(단기) + refresh(장기). 실행·새로고침 시 refresh 로 자동 재발급 (C-14). refresh 만료·로그아웃·차단 시 무효화.

**refresh 보관 위치가 클라이언트별로 갈린다** — 앱은 기기 보안 저장소, 웹(관계자 웹 · 메인 관리자 콘솔)은 서버가 내리는 HttpOnly 쿠키. access 는 양쪽 모두 `Authorization` 헤더이며 웹은 메모리에만 보관한다. 계약은 `API_SPEC §1.2.1`, 근거는 `TECH_DECISIONS §2.4`.

이 갈림은 **서버에서 컨트롤러 한 층에만 나타난다** — 토큰 발급·적재·무효화 규칙은 전송 수단과 무관하므로 서비스·저장소 계층은 클라이언트 종류를 모른다.

**로그인 실패 5회 누적 시 계정 단위 차단** (C-11). 실패 카운터는 계정 레코드에 두고, 성공 시 초기화. IP 단위 차단은 하지 않음 — 근거는 PRD §6.4.

## 6. 멀티테넌시 — 학원 격리

### 6.1 격리 강제 지점

**DB 레벨(RLS)이 아니라 애플리케이션 코드에서 강제.** 판정은 §5.1 의 ③층 한 곳.

| 대상 | 검증 |
|---|---|
| 조회 | 요청자의 소속 학원과 자원의 `academy_id` 대조 |
| 목록 | 쿼리에 `academy_id` 조건을 **저장소 계층에서 강제** — 서비스가 빠뜨려도 새지 않도록. 단 `academy_id` 를 직접 보유한 테이블에만 성립하고 나머지는 **부모까지 조인해 확인** — 보유 여부의 정의처는 ERD §6.1 |
| 학부모 | 추가로 `GuardianStudent` 연결 확인 — 같은 학원의 남의 자녀 차단 |
| 매니저 | 추가로 `Assignment` 확인 — 배치되지 않은 회차 차단 |
| 메인 관리자 | **격리 예외** — 전 학원 범위 (O-05·06). 경로에 학원 ID 를 명시해 의도를 드러냄 |

⚠ **가장 흔한 사고 지점** — 목록 조회에서 `academy_id` 조건을 빠뜨리는 것. 단건 조회는 대조가 눈에 보이지만 목록은 조건 하나가 빠져도 동작해서 테스트를 통과. **저장소 계층에 강제**하고 회귀 테스트로 고정.

### 6.2 메인 관리자의 예외 범위

메인 관리자는 전 학원 관제를 위해 위치·노선·명단 조회 권한을 보유 (FEATURE_SPEC §6). **다만 운영 데이터를 바꾸는 권한은 부재** — 학원 등록·관계자 승인·차단 해제만 수행. 조회와 변경의 범위가 다르다는 점을 인가 매핑에 명시.

## 8. 노선 계산 파이프라인

### 8.1 입력

**노선 산출의 입력은 그날의 일일 승하차지** (C-16). 요일별 주소(P-05)를 기본값으로 하고 그날의 일일 변경(P-06)이 있으면 그것이 우선. 여기에 금일 탑승 의사(ATT-01)를 반영해 대상 명단을 확정.

```
요일별 주소 ──┐
일일 변경   ──┼─► 그날의 승하차지 ──┐
              │                      ├─► 대상 명단 ──► 계산
탑승 의사   ──┘                      │
강제 추가 · 수동 조정 · 경유 지점 ───┘
```

### 8.2 계산 단계

**학생↔버스 대응은 계산이 아니라 편성이 결정.** 고정 노선(RTE-01 · A-08)이 버스별 요일·방향 묶음을 이미 갖고 있고 회차가 그 버스를 물려받음(`run.bus_id` ← `schedule.bus_id`). 확정 배치는 **회차 1건 = 버스 1대**를 입력으로 받으므로 파이프라인에 "학생을 버스에 배정하는 단계"가 부재.

```
회차 1건 (버스 1대 · 방향 1개)
  ① 좌표 해석         그날 승하차지 → 좌표. 좌표 미확보 학생 분리
  ② 순서 최적화       ← 전략 포트. 경유 지점은 위치 고정
  ③ 도로 경로         ← 외부 지도 API. 경유지 상한 초과 시 구간 분할
  ④ ETA 산출          누적 시간 계산 · 결과 조립
  ⑤ 동승자 자동 배정  ← 최적화 결과를 입력으로. 근무 시간·중복 배치 충돌 검증 (MGR-05·06)
```

**⑤ 가 계산 뒤에 오는 이유** — 동승자 배정은 소요 시간이 확정된 뒤라야 근무 시간 충돌을 판정 가능 (PRD §5.1 2단계). 기사 배치는 그 전에 관계자가 수동으로 끝냄.

**승하차지 근접 병합은 이 파이프라인에 부재** — 학생 등록·주소 수정 시점에 "주소 검증 → 승하차지 매칭·생성"으로 이미 끝남 (STU-05 · ERD §3.3). 계산 시점에 다시 묶으면 승하차지 생성 주체가 두 곳이 되어 명단·미경유 판정의 단위가 갈림.

- **② 가 전략 포트인 이유** — 최적화 알고리즘 기준(거리·시간·정원 가중치)이 미확정(PRD §10.1 G). 알고리즘을 바꿔도 나머지 단계가 영향받지 않아야 함.
- **경유 지점(RTE-10)은 ②에서 위치를 고정**하고 나머지 승하차지만 재배열. 관리자가 지정한 순번을 최적화가 뒤집으면 지정의 의미가 소멸.
- **③ 은 외부 호출이라 실패·지연이 상수.** 타임아웃과 폴백(직선거리 근사)을 두고, 폴백으로 계산된 결과는 그 사실을 표시.

### 8.3 계산의 두 소비자

| 소비자 | 호출 시점 | 정책 |
|---|---|---|
| **확정 배치** | 출발 30분 전 도래 | 백그라운드. 긴 타임아웃 허용, 실패는 재시도 |
| **온디맨드** | ②구간 승인 미리보기·확정, 경유 지점 지정 | **사용자 대기 중.** 짧은 타임아웃, 실패 시 즉시 오류 반환 |

**같은 계산 코드, 다른 실행 정책.** 파이프라인은 하나로 두고 타임아웃·재시도·동시성 제한을 **호출자가 주입**. 배치용 정책을 온디맨드에 그대로 쓰면 관리자가 승인 화면에서 수십 초를 대기.

### 8.4 온디맨드 계산의 응답 시간 예산

⚠ **승인 대기 목록에서 항목마다 재최적화를 돌리면 N배 계산이 발생.** 목록 조회는 요약만 반환하고 **전/후 대조는 상세 조회에서 1건만 계산**하는 구조로 둘 것 — 목록에 N건이 쌓인 시각이 곧 응답 지연.

계산 결과는 **요청 단위로 캐시**하고 입력(명단 · 승하차지 · 경유 지점)이 바뀌면 무효화. 관리자가 미리보기를 보고 승인을 누르는 사이 다시 계산하면 화면에서 본 것과 배포되는 것이 달라짐.

### 8.5 배포와 버전

```
확정 배치      계산 → 즉시 배포(버전 1) → 기사·동승자 푸시 → 확인 응답(RUN-07)
관리자 조작    계산 → 미리보기(확정 노선 불변) → 관리자 확인 → 배포(버전 +1) → 푸시 → 확인 응답
```

**관리자 확인 단계는 ②구간 승인(A-05)·경유 지점 지정(A-15)에만 존재.** 확정 배치는 비교 대상이 될 기존 노선이 아직 부재하므로 곧바로 배포.

- **배포 전까지 확정 노선은 불변.** 경유 지점 지정 API 의 `apply` 플래그가 이 경계 (API_SPEC §5.15).
- 배포마다 버전을 올리고 기사 단말이 보고 있는 버전을 기록 — **어느 판을 보고 운행 중인지** 관계자 화면에서 확인 가능 (MON-05).
- **운행 시작과 동시에 노선 잠금** (C-04 ③). 이후 배포 경로는 부재하고, 미등원 요청은 미경유 표시로만 반영 (C-05).

## 9. 시간 기반 배치 — 이 시스템의 중심축

회차마다 출발 시각이 다르므로 **"출발 30분 전"은 회차별로 서로 다른 시각**. 고정 시각 cron 으로는 표현 불가.

### 9.1 실행 방식 — 도래분 폴링

```
30초마다:
  SELECT * FROM run
   WHERE status = 'idle' AND confirm_at <= now()
   ORDER BY confirm_at
   LIMIT N
  → 회차마다 확정 처리
```

**세 가지 대안 중 폴링을 택한 근거는 사양 자체에 있음.** `C-04` 가 "배치 지연 시 **실행 시점 최신값**을 읽되 판정은 항상 **출발−30분 시계**, 스냅샷 부재"라고 규정 — 이는 폴링 지연을 흡수하라는 지시이며, 정시 실행을 전제했다면 나올 수 없는 문구.

| 대안 | 미채택 이유 |
|---|---|
| 회차별 동적 등록 (`TaskScheduler.schedule`) | 등록이 메모리에만 존재해 재시작 시 소실. 회차 시각 변경 시 재등록 누락 위험 |
| 외부 스케줄러 (Quartz JDBC · 지연 메시지) | 인프라가 늘어남. 인스턴스 1대 전제인 현 단계에 비용이 이익을 초과 |

폴링의 부수 이익 — **장애·재시작으로 놓친 회차가 다음 틱에 자동 회수**. 별도 복구 절차가 불필요.

### 9.2 두 시계를 분리

| 시계 | 용도 |
|---|---|
| **실행 시각** (`now()`) | 어떤 값을 읽을지 — 배치가 25분 전에 돌아도 그 시점 최신값 |
| **판정 시각** (출발 − 30분) | 무엇을 허용할지 — 추가·삭제의 구간 판정은 언제나 이 시계 |

**분리하지 않으면 배치 지연이 마감을 옮김.** 배치가 25분 전에 돌았다고 해서 27분 전 요청을 ①구간으로 처리하면, 학부모마다 마감이 달라져 "왜 저 집은 됐는데 우리는 안 되냐"가 발생.

### 9.3 멱등성 — 중복 확정 차단

**`Run.status` 전이를 조건부 UPDATE 로 잡는다.**

조건 검사와 갱신을 **한 문장**에 담고 **갱신 행 수가 1인지**로 선점 여부를 판정 — 0이면 다른 실행이 이미 처리한 것이라 건너뜀. 구현 형태(JPQL `@Modifying`)는 [TECH_DECISIONS §5](./TECH_DECISIONS.md), **네이티브 쿼리가 아니다**.

애플리케이션 락이나 인메모리 플래그에 의존하지 않는 이유 — **인스턴스를 늘리는 순간 같은 회차가 두 번 확정**. DB 가 단일 진입을 보장하면 §9.5 의 증설이 조건부 UPDATE 하나로 성립.

### 9.4 동시 도래 폭주

⚠ **가장 현실적인 장애 시나리오.** 학원 N곳 × 호차 M대가 같은 출발 시각(08:00)을 쓰면 07:30 한 틱에 수십 건이 동시 도래. 회차당 계산은 외부 지도 API 호출을 포함해 수백ms~수초.

| 대응 | 내용 |
|---|---|
| 배치 크기 제한 | 한 틱에 처리할 회차 수 상한(`LIMIT N`). 남은 건은 다음 틱 |
| 동시 실행 제한 | 계산 워커 풀 크기를 외부 지도 API 레이트리밋에 맞춤 |
| 회차 단위 격리 | 한 회차의 실패가 나머지를 막지 않도록 `try/catch` 로 감쌈 |
| 실패 재시도 | 상태를 `idle` 로 되돌려 다음 틱에 재시도. 연속 실패 횟수를 기록해 관계자에 경보 |
| 관측 | 도래 후 확정까지의 지연을 지표로 노출 — 이 값이 늘면 증설 신호 |

**처리 시간이 폴링 주기를 넘기면 밀림이 누적.** 지연 지표가 임계를 넘으면 배치 크기가 아니라 **워커 수나 인스턴스**를 늘려야 함.

### 9.5 인스턴스 증설 시 필요한 것

현재 1대 전제. 증설하면 아래가 동시에 필요.

| 항목 | 조치 |
|---|---|
| 확정 배치 | §9.3 조건부 UPDATE 로 이미 안전. 추가 조치 부재 |
| 다른 스케줄러 | 미승차 판정 · 근접 알림 등은 **분산 락** 필요 — 없으면 알림이 인스턴스 수만큼 중복 |
| WebSocket 세션 | 인메모리 보관이라 인스턴스 간 미공유 — 외부 브로커(Redis Pub/Sub · Kafka)로 팬아웃 |
| 최신 좌표 | Redis 에 두면 이미 공유됨 |

### 9.6 다른 주기 작업

| 작업 | 주기 | 하는 일 |
|---|---|---|
| 일일 회차 생성 | 하루 1회 | 스케줄 기준으로 그날의 `Run` 생성 (SCH-02) |
| 확정 배치 | **30초 폴링** | 출발 30분 전 도래분 확정 (RTE-02) |
| ②구간 자동 거절 | **동기 + 30초 폴링** | 운행 시작은 `POST /runs/{runId}/start` **트랜잭션 안에서 동기 종결** — 폴링만 두면 시작 직후 최대 30초 동안 승인이 통과. 출발 시각 도달분만 폴링이 담당 (C-04) |
| 미승차 에스컬레이션 | 30초 폴링 | 3분 경과 무응답 건을 관계자에 보고 (EXC-01) |
| 위치 유실 판정 | 10초 폴링 | 좌표가 끊긴 회차를 "마지막 확인 위치"로 전환 (P-07) |
| **알림 아웃박스 워커** | 30초 폴링 | `push_state='pending'` 회수 후 재발송. 즉시 발송이 실패했거나 앱 크래시로 누락된 건이 대상 (§11) |
| 보존 정리 | 하루 1회 | 알림 14일 초과분 · 위치 이력 정리 (§13) |

**임계값을 코드 상수로 두지 않는다.** 미승차 대기 3분은 **학원별 설정**(EXC-01)이므로 학원 설정 테이블에서 읽음. 주기(얼마나 자주 검사)와 임계값(언제 발동)을 가르고, 임계값 중 학원별로 다른 것은 반드시 데이터로 둘 것.

## 10. 실시간

### 10.1 위치 파이프라인

```
매니저 앱 (5~10초 주기, moving 상태에서만)
   → POST /runs/{runId}/position
   → Redis 최신 좌표 갱신 + 이력 적재
   → 근접 판정 (서버가 위치 기반으로 "곧 도착" 발송, NTF-04)
   → WebSocket 팬아웃 (학부모·학생·관계자·메인 관리자)
```

- **"곧 도착합니다" 알림의 트리거는 서버의 위치 판정.** 기사의 도착 처리가 아님 (NTF-04). 기사 조작은 기록·포인터 전진 전용 (M-11).
- 근접 판정은 **실제 좌표 기반**. 계획 ETA 근사로 판정하면 지연 운행에서 어긋남.
- 신호 유실 시 "마지막 확인 위치 · N분 전"으로 전환 (P-07) — 위치가 없는 것과 오래된 것을 화면에서 구분.

### 10.2 WebSocket 채널

채널 4개와 채널별 방송 이벤트의 정본은 **[API_SPEC §7](./API_SPEC.md)** — 이 문서는 중복 기재하지 않음.

**채널을 역할별로 가른 이유** — 이벤트마다 수신자를 정하는 대신 채널을 나누면 **구독 권한 검증 한 번으로 노출 범위가 결정**됨. 특히 학부모·학생 채널에는 `rider_changed` 를 싣지 않는다 — 그 payload 에 타 학생 이름과 탑승 인원이 들어 있어 C-08(탑승 인원 미표시) · API_SPEC §1.12 에 어긋남. 학부모 화면의 본인 자녀 상태는 REST 조회로 충당.

**구독 시점에 인가를 검증.** 연결만 인증하고 구독 경로를 검사하지 않으면 토큰 보유자가 남의 채널을 구독. §5.1 의 3층을 구독 핸들러에서도 통과시킬 것.

### 10.3 관제는 폴링이 아니라 WebSocket

이전 판은 3초 REST 폴링이었으나 **WebSocket 으로 전환**. 관제 화면이 전 학원 버스를 동시에 보므로 폴링은 학원 수에 비례해 부하가 증가하고, 승하차 상태 반영 5초 이내(NFR-02)를 3초 폴링으로 맞추면 대부분의 요청이 변화 없는 응답.

## 11. 알림 파이프라인

2단 구조(트랜잭션 내 적재 → 커밋 후 즉시 발송 → 워커 재시도)의 정의처는 **[TECH_DECISIONS §7](./TECH_DECISIONS.md)**.

**레코드 생성과 푸시 발송을 가른다** (C-09 · NTF-07). 사용자가 끄는 것은 **단말 푸시**일 뿐 통지 자체가 아니며, 레코드는 항상 남아 앱 목록·관계자 로그에서 조회 가능. 미수신 주장이 나와도 발송 사실을 확인 가능해 책임 소재가 소멸하지 않음.

**레코드를 상태 변경과 같은 트랜잭션에 넣는 이유** — 커밋 직후 앱이 죽어도 "보내야 했다"는 사실이 DB 에 남음. 이벤트를 메모리에만 두면 그 창에서 알림이 영구 유실되고 재시도할 대상조차 특정 불가 (TECH_DECISIONS §7).

- **발송은 트랜잭션 밖.** 승하차 처리가 푸시 실패로 롤백되면 안 됨 (§3.3).
- **중복은 DB 가 차단** — `notification_log.dedup_key` UNIQUE. 즉시 발송과 워커가 같은 건을 동시에 집어도 한쪽만 성공.
- **알림 문구에 자녀 이름 필수** (P-02) — 다자녀 가정에서 어느 아이 얘기인지 화면 상태와 무관하게 식별 가능해야 함.
- `absent` 학생은 도착·지연 알림 대상 밖 (C-02).
- **비상 알림(EXC-04)도 아웃박스에 적재하되 워커를 기다리지 않고 커밋 직후 즉시 발송** + 팝업 — 관계자·메인 관리자 동시 수신이고 설정 항목이 부재(C-17). 재시도 간격은 다른 알림보다 짧음. 분류 근거는 TECH_DECISIONS §7.3. 학부모·학생은 수신 대상 밖 — 안내 시점·문구는 사실을 파악한 관계자가 판단.
- **관제 WebSocket `position` 은 아웃박스 대상 밖** — 5~10초 뒤 다음 좌표가 오므로 유실을 복구할 필요가 부재.

## 12. 스키마 관리

Flyway 가 스키마를 관리하고 Hibernate 는 `ddl-auto: validate` 로 검증만.

- **개발 단계에서는 기존 마이그레이션 파일을 직접 고치고 로컬 DB 를 재구성**하는 편을 우선. 로컬은 영속 볼륨이 없어 잃을 데이터가 부재.
- **영속 환경(demo · prod)에 한 번이라도 적용된 뒤에는 원칙이 뒤집힘** — 기존 파일 수정 금지, 새 버전 추가만 허용. 체크섬 불일치는 곧 기동 불가.
- 시드는 별도 위치에 두고 `local` · `demo` 프로파일에서만 로드. 비밀번호 해시는 placeholder 주입.

방향 전환으로 스키마가 대폭 바뀌므로 **첫 배포 전까지는 마이그레이션을 통합·재작성**하고, 첫 배포 시점에 이 항목을 갱신할 것.

## 13. 인프라 · 배포

### 13.1 구성

EC2 1대 + Docker Compose. nginx 가 TLS 종단과 리버스 프록시를 담당하고 `/ws` 경로에 WebSocket 업그레이드를 허용.

| 서비스 | 역할 |
|---|---|
| `api` | Spring Boot — **인스턴스 1개** (§9.5) |
| `postgres` | 영속 |
| `redis` | 최신 좌표 · 멱등키 · 캐시 |
| `kafka` | 도메인 이벤트 |
| `nginx` | TLS · 프록시 · 정적 웹 |

### 13.2 보존 · 정리

데이터별 보존 기간과 삭제 방식의 정본은 **[ERD §7](./ERD.md)**.

⚠ **정리 배치가 없으면 위치·알림 테이블이 무한 증가.** 위치는 회차당 수백 행이 쌓이므로 파티셔닝 또는 주기적 정리가 필수.

### 13.3 관측

지표 목록·알럿 등급의 정의처는 **[TECH_DECISIONS §13](./TECH_DECISIONS.md)** — 이 문서는 중복 기재하지 않음.

**구조 관점의 요지 하나** — 대표 지표는 **확정 배치 도래→완료 지연**. §9.4 의 처리 밀림 누적을 감지하는 유일한 신호이고, 임계를 넘으면 배치 크기가 아니라 **워커 수나 인스턴스**를 늘려야 함 (§9.5).
