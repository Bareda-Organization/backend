### 1.1 앱 하나가 여러 역할을 담음 — 역할 분기 규칙 (2026-09-10 사용자 확정)

**앱을 역할마다 만들지 않고, 앱 하나가 로그인 결과의 역할로 갈라짐.**

| 앱 | 담는 역할 | 갈리는 지점 | 공유하는 것 |
|---|---|---|---|
| `parent-app` | 학부모 · **학생** | 로그인 후 진입 라우트 · 탭바 구성 · 쓰기 권한 | 화면·위젯 대부분 |
| `manager-app` | 버스기사 · **동승자** | 회차 화면의 조작 권한 · 탭바 구성 | 화면·위젯 대부분 |

**갈리는 것은 화면이 아니라 권한과 진입점.** 같은 화면을 두 벌 만들지 않음.

- **학생은 조회 전용** (`UF-S-01`) — 학부모 화면을 그대로 쓰되 등원 여부 변경 · 탑승 위치 변경
  진입점을 감춤. 학생 전용은 부모 연결 코드 생성(`S-05` · `§3.3`) 하나
- **기사와 동승자는 조작 권한이 갈림** (`UF-D-*` ↔ `UF-E-*`) — 기사는 도착·지연 알림 전송,
  동승자는 개인별 승하차 상태 결정. 같은 `StopRoster` 화면에서 **버튼 노출이 갈림**
- 분기는 화면 안 `if` 가 아니라 **`core/auth` 의 역할 정책 한 곳**에서 판정하고 화면은 그 결과만 받음
  — 화면마다 조건문을 흩으면 권한 규칙이 어디 있는지 알 수 없게 됨

⚠ **두 앱을 하나로 더 합치지 않음 — 2026-09-10 사용자 확정.** 매니저 앱은 운행 내내
**위치 권한(백그라운드)과 오프라인 큐**가 필요함(`M-06` · `§4.12`). 학부모 앱에 합치면
학부모 단말에도 그 권한을 요구하게 되고, 스토어 심사와 사용자 신뢰 양쪽에서 값을 치름.
대상 사용자도 고객(학부모·학생)과 운영 인력(기사·동승자)으로 갈림.

**따라서 Flutter 앱은 2개이고, 각 앱 안에서 역할 2종으로 갈라짐.** 위 표가 그 전부.

## 2. 디렉터리 구조

```
frontend/
├── CONVENTIONS_REACT.md              React/TypeScript 컨벤션
├── CONVENTIONS_FLUTTER.md      Flutter/Dart 컨벤션
├── IMPLEMENTATION_PLAN.md      이 문서
├── design-system/              claude.ai 디자인 시스템 사본 (읽기 전용)
├── packages/
│   └── baraeda_ui/             Flutter 공용 위젯 패키지 — 두 앱이 의존
└── apps/
    ├── academy-web/            Next.js (관계자 + 메인 관리자)
    ├── parent-app/             Flutter
    └── manager-app/            Flutter
```

각 앱 내부 구조는 컨벤션 문서가 정본 —
웹은 `CONVENTIONS_REACT.md` "디렉터리" 절, Flutter 는 `CONVENTIONS_FLUTTER.md` §2·§3.
둘 다 **기능(도메인) 하나 = 폴더 하나**이고 **기능끼리 서로 import 하지 않는 것**이 확장의 근거.

`design-system/` 은 **읽기 전용 사본**. 고칠 일이 생기면 원격 프로젝트를 고치고 다시 내려받음
— 로컬에서 직접 고치면 다음 동기화에 덮임.

### 2.1 ⚠ `design-system/ui_kits/` 를 앱에서 import 하지 않음

킷의 `*Screens.jsx` · `kit.jsx` 는 **브라우저로 생김새를 보는 클릭 스루 시안**이고 앱 코드가 아님.
`김하준` · `3-2호차` · `대치사거리` 같은 값이 파일 안에 박혀 있는 것은 그 용도 때문.

| 무엇 | 어디 | 데이터 출처 |
|---|---|---|
| 시안 | `design-system/ui_kits/` | 값이 박혀 있음. **읽기 전용 참조** |
| 실제 화면 | `apps/*/features/` | **API 응답** — `API_SPEC` 계약 |
| 시험 데이터 | 각 앱 테스트 디렉터리 | 테스트 안에서만. 화면 코드에 섞지 않음 |

- 시안의 값을 앱 코드로 옮겨 붙이지 않음. **보는 것은 배치·간격·문면이고 데이터가 아님**
- 화면은 로딩·성공·실패 세 갈래를 전부 그림. 시안에는 성공 갈래만 있음
- `window.DesignSystem_9e66e1` · `window.MapSurface` 같은 전역 참조는 **시안 실행 방식**이며
  앱에서는 쓰지 않음

⚠⚠ **위 3건은 "구현 완료" 로 적혀 있었으나 앱 어디에서도 그 화면으로 이동하지 않았다**(2026-09-21 실측).
정본이 이미 같은 형태를 판정해 뒀다 — *"도달 못 하는 화면은 없는 것과 같다"*(이 문서 `§2.11` 단말 등록 건).
**화면을 만든 것과 갈 수 있는 것은 별개이고, 완료 판정은 뒤쪽이다.**

⚠⚠ **매니저 앱도 같았다 — `delay`·`routeMap`·`offlineQueue` 3개**(2026-09-21 같은 검사로 확인).
그중 **오프라인 큐는 단순한 죽은 화면이 아니었다** — `OfflineQueueScreen` 자바독이
*"자동 폴링·재전송은 두지 않는다. 재전송은 이 화면의 버튼을 눌렀을 때만"* 이라고 적는다.
**도달 불가면 통신 두절로 쌓인 승하차 처리가 영영 안 나간다.** 명단 화면에서 열었다.
✅ **이월 해소 (2026-09-21, `afa51409`)** — `M-06` 의 "복구 시 **자동** 동기화" 를 구현했다.
재생을 부르는 곳이 셋이 됐다 — ①큐 화면의 수동 버튼 ②쓰기 한 건이 나가기 직전(`sendOrQueue`)
③`OfflineQueueAutoSync` 의 30초 타이머(앱 트리 최상단). **WS 없이 닫았다** — 폴링은 큐가
비어 있지 않을 때만 네트워크를 건드린다.

- **순서가 이 구현의 핵심이다** — 새 요청을 큐보다 먼저 보내면 오프라인에서 쌓인 옛 처리가
  복구 후의 새 처리를 **덮어쓴다**(오프라인 '탑승' → 복구 후 '되돌리기' → 재생이 다시 '탑승')
- **두절이 이어지면 재생은 첫 실패에서 멈춘다** — 남은 행마다 타임아웃을 되풀이할 이유가 없고,
  중간 건만 성공하면 큐 안의 순서가 뒤집힌다
- **로그인 전에는 자동 재생하지 않는다** — 토큰이 없어 401 이 오고, 재생 규칙상 4xx 는 큐에서
  **영구 제거**라 쌓아 둔 승하차 처리가 통째로 사라진다
- 검사 3건 신설(순서 · 두절 지속 · 주기 재생) + 스모크 시험에 **앱 트리 마운트 단언**.
  코드를 일부러 망가뜨려 5종 전부 검출 확인
⇒ `parent-app/test/app/reachable_routes_test.dart` 가 라우터 등록분과 실제 이동을 대조한다 —
   등록만 하고 아무도 안 가는 화면이 생기면 실패한다.

## 5.17 `R46-WEB` 목표 표 — 관계자 웹 바로 고칠 것 · 승인 놓침 방지 · 폴링 (2026-10-01 계획 · 기준 HEAD `ea37ba6c` `mskim98/r46-web` · 판정 `Ruling 420~426`)

### 5.17.1 판정

- **`Ruling 420` — 승인 대기는 기존 목록 API 의 `pending_count` 로 센다(서버 변경 없음).** 가입 승인 `GET /staff/signup-requests?status=pending&size=1` · 구간 변경 `GET /staff/approvals?status=pending&size=20`(가장 이른 `deadline_at` 을 고르려 한 쪽을 받음). 관계자 레이아웃의 `ApprovalPendingProvider` 가 한 곳에서 세고 사이드바 배지 · 운행 관리 `처리 대기 · 기한 임박` 띠 · 탭 제목이 같은 값을 본다. `approval_requested` 통지는 운행 관리 화면이 아니라 레이아웃 전역에서 받아 즉시 다시 센다(폴링 30초는 통지를 놓친 경우와 가입 신청 — 통지 없음 — 을 받친다). 대기 목록에 `자동 거절까지` 열. 버린 안 — 새 집계 엔드포인트(백엔드 창과 동시 작업이라 충돌 위험 · 기존 API 로 충분)
  - 탭 제목 `(N) 비상 발생 · 바래다 관계자 웹`, **소리·브라우저 알림은 머리줄 `[알림음]` 을 사용자가 켠 경우에만**(기본 꺼짐 · 권한 요청은 켜는 조작 안에서만 · 저장은 `localStorage`)
  - 메인 관리자는 채널에 승인 통지가 없어 가입 승인 대기·차단 계정 수를 30초 폴링(`AdminPendingProvider`)
- **`Ruling 421` — 비상 알림은 화면 위에 띄우지 않고 머리줄 아래 흐름 속 띠로 둔다.** `position: fixed`(top 72 · right 24)가 등록·배치 변경 버튼을 덮었다(조사 B1 #1). 제공자는 상태만, `EmergencyAlertStrip` 이 그린다. **메인 관리자 레이아웃에도 같은 제공자**를 쓰되 출처(관리자 조회·관리자 채널)를 넘기고 **확인 버튼은 없다**(확인 주체는 관계자). 사양 문장 갱신 — `USER_FLOWS` 비상 알림 수신 절(R32-W5 보완 줄) · 같은 절에 메인 관리자·탭 제목·알림음 보완 줄 추가
- **`Ruling 422` — 폴링 규약(`usePolling`).** ①응답을 받은 뒤 다음 요청을 예약(`setInterval` 금지) ②탭이 숨으면 멈추고 돌아오면 즉시 1회 ③실패하면 간격 ×2 씩(상한 ×8), 성공하면 원래 간격. 대시보드·금일 운행·전체 관제·비상 알림 4곳 적용. **명단 폴링 7초 간격 자체는 그대로**(서버 감사 기록과 얽힘 — 조사 D #3 은 사용자 판정 대기)
- **`Ruling 423` — 대시보드 `매니저 미배치` 는 "오늘 배치 없는 매니저 N명" 으로 표기한다.** 서버 정의가 재직 매니저 **사람 수**(`API_SPEC §5.3`)라 라벨·단위(건)가 틀렸던 것. 조사가 제안한 "기사·동승 미배치 **회차** N건" 으로 바꾸는 안은 **사양(사람 수)과 어긋나 기각** — 회차 기준 강조가 필요하면 별도 지표로 추가할 일. `API_SPEC §5.3` 에 사람 수임을 명시
- **`Ruling 424` — 시각 표기.** 운행 출발·도착은 **시:분:초 유지**(`R21-B` 사용자 지시 "출발·도착시간 몇시, 몇분, 초" — 조사 B1 #23 의 `HH:mm` 통일 제안은 이 지시와 충돌해 **그 부분 기각**), 그 밖 예정 시각은 `HH:mm`. 머리줄 날짜는 브라우저 시계가 아니라 **서울 기준**(`formatHeaderDate`). 같은 이름 회차 구분을 위해 회차 목록·리포트 회차 선택 앞에 **출발 시각**을 붙인다(`08:00 1호차 · 등원`)
- **`Ruling 425` — 금일 운행 상세는 명단 표를 전체 폭으로 쓴다.** 현재 위치 · 승하차지 카드는 표 위 가로 배치, 1100px 이하에서는 오른쪽 버스 목록이 지도 아래로 내려온다. 표는 칸이 글자 단위로 꺾이지 않고(`nowrap`) 폭이 모자라면 상자 안에서 가로 스크롤. `R21-B` 의 행마다 출발·도착 열은 사용자 지시라 **유지**(조사의 중복 열 제거 제안 기각)
- **`Ruling 426` — 학원 등록 주소는 선택 입력 그대로(`API_SPEC §6.2`), 비우면 경고를 보인다.** ⚠ **`Ruling 450`(2026-10-01)이 뒤집었다 — 주소는 필수이고 화면은 경고 대신 저장을 막는다.** "주소를 비워 두면 이 학원의 회차 확정이 시작되지 않습니다" — 서버 검증·필수화는 사양이 정한 대로 두고 화면은 원인을 드러낸다(조사 A #10 의 화면 쪽)

### 5.20.1 판정

- **`Ruling 470` — 지도에 내 승하차지 핀(B2 #10).** 좌표는 이미 있는 `GET /students/{id}/route`(§3.10)의 `my_stop_id` 항목 `lat`·`lng` 을 그대로 쓴다(`routeDetailProvider` 를 `core/routes` 로 올려 지도·노선 화면이 공유). 핀 라벨 `내 승하차지` + 지도 아래 한 줄 `내 승하차지 · 이름` + `[내 승하차지로]`. 노선을 못 받았거나 좌표가 `null` 이면 핀만 빠지고 오류 띠는 더하지 않는다(핀은 부가 정보). **C-08 — ETA·"몇 곳 전"·탑승 인원은 붙이지 않는다.** 조사가 "N곳 전" 은 시간이 아니라 허용 여지가 있다고 했으나 서버가 그 값을 주지 않고, 클라이언트가 노선 순서와 마지막 도착 승하차지로 계산해 채우면 "서버가 안 주는 값을 클라이언트가 만들어 규칙을 우회" 하는 형태라 **기각**. 지도·홈 렌더된 글자 전체에 `도착 예정|ETA|예상|곳 전|정거장 전|분 후|탑승 인원|N명` 이 0건임을 시험이 검사(서버가 `eta`·인원을 실어도).
- **`Ruling 471` — 지도 카메라는 버스를 따라간다(B2 #12).** 기본 켬. SDK 의 카메라 변경 이유가 `gesture`·`control`(사용자) 일 때만 따라가기를 끄고, `[버스 위치로]` 가 다시 켠다. 코드가 옮긴 카메라(`developer`)는 끄지 않는다. 이동은 1.8초 선형 애니메이션 — 마커가 새 좌표까지 약 2초에 걸쳐 미끄러지는 것과 맞춰, 카메라가 즉시 옮겨 가 마커가 중앙에서 튕기는 것을 피한다. 이전 판정 `F05-09`("카메라 고정, `[버스 위치로]` 로만 이동")를 뒤집지만 그 이유(2초마다 사용자가 옮긴 지도가 되돌아감)는 제스처 감지로 그대로 막는다. `forceGesture: true`(R41-CHK) 유지 — 기존 구조 시험이 계속 지킨다.
- **`Ruling 472` — 다자녀(B2 #13).** ①고른 자녀는 기기 보안 저장소(`flutter_secure_storage`, 새 의존성 없음)에 식별자 하나만 기억하고 앱을 다시 켜면 이어서 보여준다 — 이번 실행의 선택 → 기억한 선택 → 첫 자녀 순이며, 목록에 없는 식별자(연결 해제·다른 계정)는 버린다 ②전환 UI 는 홈·지도·일정·노선 네 화면이 `StudentSwitcher` 하나를 공유한다: **2~3명은 이름 칩(분할 버튼) 한 번 누름, 4명 이상은 드롭다운** — 드롭다운은 열고 고르는 두 번 누름이 아침마다 쌓이고, 이름 칩은 4명 이상에서 좁아진다 ③**두 자녀 상태를 한 화면에 나란히 두지 않는다** — 회차 카드가 자녀당 2개(등원·하원)에 스위치·배지·확정 안내까지 길어 한 화면에 둘을 담으면 스크롤이 길어지고, 알림은 선택과 무관하게 전 자녀가 와 급한 신호는 놓치지 않는다. 필요가 확인되면(자녀 3명 이상 · 사용자 요구) 그때 다시.
- **`Ruling 473` — 가입 → 승인 대기(B2 #20).** 서버는 가입 응답(§2.2)에 토큰을 주지 않지만 `pending` 계정도 로그인은 성공(§2.5)하므로, 가입이 접수되면 **방금 입력한 아이디·비밀번호로 바로 로그인**해 라우터가 대기 화면으로 보내게 한다(`USER_FLOWS UF-X-01` 이 이미 "→ 승인 대기 화면" 이라 적은 것을 코드가 따라간 것). 자동 로그인이 실패하면 예전처럼 로그인 화면으로(가입 실패로 보이지 않게 접수 안내 유지). 대기 화면은 **30초마다·앱 복귀 즉시** 화면 변경 없이 다시 조회하고(`pendingStatusPollInterval` 상수, `VisiblePoller` 재사용) 연결 실패는 오류 화면 대신 다음 간격으로 넘긴다. `[가입 신청하기]` 가 꺼진 이유는 버튼 아래 `아직 채우지 않은 항목 · …` 로 알린다(길이 오류는 입력칸 옆 기존 표시).
- **`Ruling 474` — 연결 코드(B2 #21).** `[코드 복사]`(6자리) · `[안내 문구 복사]`(입력 위치 + 만료 시각) · 만료 시각 아래 `남은 시간 N분`(1분 갱신) · 만료되면 문구와 함께 복사 버튼 비활성. **공유 시트는 도입하지 않았다** — `share_plus` 는 네이티브 의존성을 늘리고(iOS pod · Android 설정), 복사한 문장을 메신저에 붙이는 것으로 같은 목적에 닿는다. 필요하면 사용자 결정 후 추가. **"학생 계정이 없는 어린 자녀는 연결이 막힌다" 는 사양 판단(`Ruling 324`)이라 바꾸지 않았다**(보고서 2항에 의견).
- **`Ruling 475` — 네트워크 끊김(B2 #22).** `connectivity_plus` 를 **쓰지 않고** 요청 결과로 판정한다: 앱의 Dio 에 `NetworkStatusInterceptor` 를 붙여 연결 실패·시간 초과는 끊김, 서버가 4xx·5xx 로 답한 것은 닿은 것으로 본다. 기기가 와이파이에 붙어 있어도 서버에 못 닿는 경우(음영 구간·서버 중단)를 기기 연결 상태는 알려 주지 못하고 의존성도 늘지 않는다. 끊기면 앱 어느 화면이든 **맨 위 한 줄** `네트워크 연결이 끊겼습니다 · 마지막 갱신 H:mm` 이 붙고 다음 성공 응답에 사라진다. 홈 회차 카드 위 `이전 정보입니다` 띠는 끊긴 동안 만들지 않는다(처음부터 데이터가 없는 곳의 오류·재시도 띠는 그대로). 위치 WebSocket 끊김 띠(`연결 끊김`)는 지도 화면 안의 별개 상태라 그대로 둔다.

### 5.21.1 판정

- **`Ruling 490` — 요일 다중 등록은 서버 일괄 API 없이 웹이 요일마다 기존 `POST` 를 차례로 부른다.** 노선(`POST /staff/routes`)·스케줄(`POST /staff/schedules`) 등록 폼은 요일 체크박스 7개(`WeekdayPicker`)이고 고른 요일마다 1건씩 만든다. 한 요일이 실패해도 멈추지 않고(`runPerWeekday`) 결과를 요일별로 돌려받아 **"4개 요일은 저장됐고 1개 요일은 저장하지 못했습니다 — 목요일 — 같은 차량·요일·방향의 편성이 이미 있습니다"** 처럼 실패한 요일과 사유만 보이고, 실패한 요일만 선택된 채 남아 다시 저장하면 그 요일만 다시 시도한다. 일괄 API 를 두지 않은 이유 — 서버가 "전부 성공 또는 전부 취소" 를 고르면 한 요일의 중복 때문에 나머지 4건까지 막히고, 요일은 최대 7건이라 왕복 비용이 작다. **복사**(`RouteCopyDialog` · `ScheduleCopyDialog`)는 같은 호출을 원본 값으로 한다. 노선 복사는 원본의 정차 순서(`stop_ids`)를 그대로 잇는다 — 정차지는 요일 사이에 공유되는 승하차지 기록이라 새로 만들지 않는다. 수정 폼은 요일 하나 그대로.
- **`Ruling 491` — 본인 비밀번호 변경은 헤더 버튼 + 대화상자, 강제 변경 표식은 만들지 않는다. → 강제 변경은 `Ruling 540`·`544` 로 해소(2026-10-01 R46-FUFEAT — 서버 표식 + 웹·앱 강제 이동). 헤더 버튼·대화상자는 그대로 남아 강제 화면이 같은 대화상자를 쓴다.** 관계자·메인 관리자 두 레이아웃 머리줄에 `[비밀번호 변경]`(`POST /auth/password`, `changePassword`). 새 비밀번호 한글 24자(72바이트)·확인 입력 일치를 서버 호출 전에 검사하고, 현재 비밀번호가 틀리면(`401 INVALID_CREDENTIALS`) 그 사유만 보이고 로그아웃하지 않는다. 성공하면 서버가 refresh 토큰을 전부 무효화하므로 **"다시 로그인" 안내 → 로그아웃**. 임시 비밀번호 강제 변경 표식(`must_change_password` 류)은 서버에 없다(`grep -rIli 'mustChange\|must_change\|password_change_required' backend/src/main docs/API_SPEC.md` 0건) — 로그인 직후 변경 화면으로 보내는 흐름은 **만들지 않았다**. 만들려면 계정 컬럼 · 초기화 때 켜기 · 변경 때 끄기 · 로그인·`/me` 응답 필드가 필요한 보안 기능이라 사용자 확인 뒤 별도 갈래로 둔다(후속 후보).
- **`Ruling 492` — 노선 변경 확인 표시는 확정·운행 중 회차의 배치된 사람에게만 그린다.** 서버 `ack_driver`·`ack_escort` 는 "현재 확정 노선 버전을 확인했는가" 이고 노선이 없는 대기(idle) 회차는 늘 거짓이라 의미가 없으며, 끝난 회차는 확인을 재촉할 이유가 없다. 대시보드 표(기사·동승 매니저 칸)와 금일 운행 상세 현재 위치 카드에 `확인`(초록) · `미확인`(빨강) 뱃지(`RouteAckMark`).
- **`Ruling 493` — 첫날 체크리스트는 새 `onboarding` 기능이 다섯 목록을 직접 읽는다.** 기능끼리 import 하지 않는 규칙 때문에 차량·매니저·학생(`size=1`, `total_count`)·노선·스케줄(`size=100`) 다섯 목록 엔드포인트를 이 기능의 `api` 가 직접 부른다. 순서 **차량 → 매니저 → 학생 → 노선 → 스케줄**, 각 단계 완료 시 `완료(N)`, 다섯 단계를 다 끝내면 사라진다. **노선 없는 스케줄 경고**는 단계를 다 끝낸 뒤에도 남는다 — 차량·요일·방향이 같은 **활성 노선이 없는 활성 스케줄** 수(앞 100건 기준). 조회가 실패하면 대시보드를 막지 않고 그리지 않는다(보조 안내). 실서버에서 DB 직접 집계와 일치 확인(2건).
- **`Ruling 494` — 비상 대응 조치 메모는 이번에 만들지 않는다. → `Ruling 541`·`545` 로 해소(2026-10-01 R46-FUFEAT — 컬럼 1 + 확인 요청 선택 본문 + 상세 표시).** `emergency_alert` 에 조치 내용을 담을 컬럼이 없고(`acked_by`·`acked_at` 뿐) 자유 문장은 개인정보 검토가 필요한 새 입력이다. 대신 **연락처 `tel:` 링크 + 복사 버튼**(`PhoneContact`)과 **배너 문구**("[확인]은 알림을 봤다는 표시이지 조치를 마쳤다는 뜻이 아닙니다. 누르면 이 띠가 사라지고 다른 관계자 화면에서도 확인됨으로 바뀝니다")만 반영. 조치 메모는 후속 후보(컬럼 1개 + 확인 요청 본문 선택 필드 + 상세 표시).
- **`Ruling 495` — 가입 승인 후보에 신청자 이름으로 미리 검색 · 동명이인 구분 · 이미 가입한 학생 비활성.** 검색칸을 신청자 이름으로 채워 처음 조회하고(못 찾으면 비우고 전체 후보로 복귀), 학생 후보는 `반 · 보호자 연락처`(목록 응답이 이미 주는 값, 보호자 미연결이면 "보호자 미연결")로 같은 이름을 가른다. **이미 다른 계정에 연결된 학생은 고를 수 없게**(`이미 가입한 학생`) — 학생 목록 응답에 `account_linked`(boolean, 식별자 아님)를 더했다(`API_SPEC §5.11`, 서버 1필드). 매니저 후보는 서버가 `linked=false` 로 이미 연결된 사람을 빼고 있어(`Ruling 391`) 조사 주장("연결된 사람이 표시되지 않는다")은 매니저에 한해 해소돼 있었다.
- **`Ruling 496` — 주소 없는 옛 학원은 상태 변경 때 주소 없이 저장한다**(조율자 결정 02:10). 원래 주소가 비어 있고 **상태가 바뀐** 수정만 `address` 키를 보내지 않는다(서버는 키 없음 = 유지, `API_SPEC §6.3`). 상태를 안 바꾼 수정은 주소 필수 유지(`Ruling 450`). 상태 변경과 함께 이름 등을 고쳐도 허용된다(서버가 허용하고 구분 비용이 큼).
- **`Ruling 497` — 전체 관제 요약은 기존 `GET /admin/emergencies?status=open` 한 번으로 학원별 미확인 비상을 센다. → 지연·확정 실패 집계는 `Ruling 543`·`547` 로 해소(2026-10-01 R46-FUFEAT — `GET /admin/runs/attention`).** 학원 선택 위에 "미확인 비상이 있는 학원" 띠(학원 버튼을 누르면 그 학원으로 전환) + 선택 목록에 `· 비상 N건`. 30초 폴링. **지연·확정 실패의 학원별 집계는 만들지 않았다** — 학원마다 `GET /admin/academies/{id}/runs/live` 를 부르면 학원 수에 비례해 요청이 늘어, 서버 집계 API 가 맞다(후속 후보, 새 엔드포인트 4곳 등재 필요).

### 5.22.1 판정

- **`Ruling 510` — 푸시 토큰은 공급자 포트 `PushTokenSource` 가 준다.** 기본 `PlaceholderPushTokenSource` 는 기기별 자리표시 토큰을 주고(서버가 FCM 거부를 받아 해지 — `Ruling 331`), Firebase SDK 는 이번에 넣지 않는다(설정 파일 없이 검증 불가). `AuthApi.login` 이 로그인 직후 `POST /me/devices` 를 부르고(실패해도 로그인은 성공 · 다음 `/me` 가 재시도), `AuthApi.logout` 이 `device_id` 를 실어 서버가 그 기기 토큰을 해지한다. 학부모·학생 앱 설정 스위치는 공급자 토큰을 쓰고, 끄면 그 사실을 저장해 다음 로그인·앱 실행이 다시 켜지 않는다(공급자가 토큰을 못 주면 안내만). `DeviceRegistrationStorage` 는 두 앱이 함께 쓰게 돼 `baraeda_core` 로 올렸다(저장 키 그대로)
- **`Ruling 511` — 관계자 웹 브라우저 푸시는 사양에 없어 만들지 않는다.** 웹 `registerDevice` · `unregisterDevice`(`features/auth/api/devices.ts`)는 호출처 0 그대로 둔다 — 비상 알림 수신은 열린 화면의 실시간 수신 + 탭 제목 + 알림음(`R46-WEB`)이 이미 맡는다

## 5.24 `R46-FUFEAT` 목표 표 — 임시 비밀번호 강제 변경 · 비상 조치 메모 · 알림 눌러 이동 · 관제 지연·확정 실패 집계 (2026-10-01 · 기준 HEAD `a2b29078` `mskim98/r46-fufeat` · 판정 `Ruling 540~547`)

`R46-WEBF` 가 보류한 3건(강제 변경 표식 · 조치 메모 · 지연·확정 실패 집계)과 `R46-MGR` 이 남긴 알림 이동을 한 갈래로 묶었다. 사용자 자리 비움 중이라 조율자가 "만든다" 로 정했고(`DECISIONS` 10:40) 세부 선택은 작업 창이 `Ruling` 으로 기록했다. 서버 변경은 `docs/IMPLEMENTATION_PLAN.md §8.82` 에 있다(`Ruling 540~543`).

### 5.24.1 판정 (클라이언트 몫)

- **`Ruling 544` — 강제 변경 화면은 웹 = 가드가 본문 대신 취소 없는 대화상자 · 앱 = 라우터가 변경 화면에 고정.** 웹: `AuthGateGuard` 가 `session.mustChangePassword` 를 보고 본문 대신 `PasswordChangeDialog forced`(R46-WEBF 헤더 버튼과 **같은 대화상자** — `[취소]` 없음 · Esc 무시 · 안내 한 줄)만 그린다. 별도 라우트를 만들지 않은 이유는 `(staff)`·`(admin)` 두 레이아웃이 같은 가드를 부르므로 판정이 한 곳이고, 라우트로 만들면 사용자가 주소를 바꿔 우회하는 길을 막는 코드가 따로 필요해서다. 서버도 막으므로(`§1.4`) 이 화면은 막힌 호출이 쏟아지지 않게 하는 쪽이다. 변경에 성공하면 서버가 refresh 토큰을 전부 끊으므로 기존 "다시 로그인" 흐름 그대로 로그아웃한다. 로그인·`/me` 가 표식을 세션에 옮기고, 어떤 API 가 `403 PASSWORD_CHANGE_REQUIRED` 를 받으면 http 계층이 `AUTH_PENDING` 과 같은 길(`auth-pending` 통지)로 세션을 다시 확인해 `/me` 의 표식으로 화면을 바꾼다. 앱(매니저): `mustChangePasswordProvider` 가 로그인·`/me` 응답으로 켜지고, 라우터 `redirect` 가 켜진 동안 비밀번호 변경 화면 밖으로 가지 못하게 한다. 그 화면은 뒤로 가기를 없애고 `[로그아웃]` 만 연다. 역할이 비는 모든 경로(로그아웃·세션 만료·변경 뒤 로그아웃)에서 `RouterRefreshNotifier` 가 표식도 함께 끈다. 공용 `baraeda_core` 의 `LoginResponse`·`MeResponse` 는 `mustChangePassword`(기본 `false`)만 더했다 — 학부모 앱은 코드 변경 없이 `analyze` 0. **학부모·학생 앱은 같은 표식을 받는데 이 갈래 시점에는 이동 처리가 없었다 → `R46-LAST` `Ruling 581` 이 매니저 앱과 같은 방식으로 더함(§5.27).** 그 전에는 표식이 켜진 학부모 계정이 서버가 막은 `403 PASSWORD_CHANGE_REQUIRED` 오류 화면을 봄.
- **`Ruling 545` — 조치 메모 입력은 비상 상세 대화상자에서만, 행의 [확인] 은 메모 없이 그대로.** 비상은 빨리 눌러야 하는 화면이라 행 버튼·팝업의 `[확인]` 은 지금처럼 한 번에 확인한다(메모 선택). 사후 조치를 적고 싶을 때만 행을 열어 상세 대화상자의 `조치 메모(선택)` 칸(최대 200자 · 글자 수 표시)에 적고 `[확인]` 한다. 확인된 건의 상세는 `확인자`·`조치 메모` 두 줄을 보인다. 메인 관리자 상세(`EmergencyDetailDialog`)는 `조치 메모` 줄을 더했다. **기존 결함 1건도 함께 고쳤다** — 메인 관리자 웹이 `acked_by` 를 문자열로 읽었는데 서버는 `{name}`(§5.16 · §6.11) 객체라 `확인됨 ([object Object])` 로 보였을 형태. 타입을 `{name, memo}` 로 정정. 발신자(매니저 앱 §4.15) 응답에는 메모를 싣지 않았다 — 요청 범위 밖이고 현장 메모가 발신자 화면에 어떻게 보일지는 별도 판단(보고 2항).
- **`Ruling 546` — 알림 눌러 이동은 `run_id` 가 있는 노선·배치 변경 알림만.** `route_changed` → 노선 화면(`/route-map`) · `assignment_changed` → 기사는 운전 화면(`/drive-mode`) · 동승자는 명단 화면(`/roster`)(홈에서 회차 카드를 누를 때 `canOperateRun` 으로 가르는 것과 같은 판정). 이동 전 `selectedRunIdProvider` 에 그 회차를 넣는다(화면들이 이 값을 읽는다). 이미 읽은 알림도 이동하고, `run_id` 가 없는 옛 알림·그 밖의 종류는 읽음 처리만 한다. 가리키는 회차가 오늘 것이 아니면 도착 화면이 조회 오류를 보인다(14일 보관 — 별도 처리를 만들지 않았다).
- **`Ruling 547` — 전체 관제 요약 띠 하나를 더한다.** 기존 "미확인 비상이 있는 학원" 띠 아래에 `지연·확정 실패가 있는 학원` 띠(호박색) — 학원 버튼 `송파학원 지연 1건 · 확정 실패 2건`(0 인 쪽은 적지 않음)을 누르면 그 학원으로 전환하고 학원 선택 목록에도 같은 표시를 붙인다. `GET /admin/runs/attention` 을 비상 요약과 같은 30초 주기로 읽고, 실패해도 관제 화면을 막지 않는다(요약이 비어 보일 뿐).

`Ruling 548`·`549` 는 쓰지 않았다.

### 5.27.1 판정

- **`Ruling 580` — 비밀번호 초기화 감사 행에도 접속 IP.** `AuditLog.forAccountPasswordReset` 에 `String ip` 인자를 더하고 호출부(`AccountPasswordResetCommandService.reset`)가 `ClientIp.ofCurrentRequest()` 를 넘김. `Ruling 550` 이 같은 파일의 인접 줄 충돌을 피하려 남긴 마지막 1곳(수정·삭제 행 4곳 중 3곳은 `Ruling 550`). 엔티티가 요청 컨텍스트를 모르게 인자로 받는 방식도 그대로. `ERD §3.4` 의 "비밀번호 초기화 행은 아직 비어 있음" 구절 삭제
  - 범위 밖 발견 — `AccountUnblockCommandService`(`forAccountUnblock`, `category=login` 의 `unblock`)의 감사 행은 IP 가 비어 있음. `ERD §3.4` 는 `category=login` 행에 IP 를 채운다고 적었으므로 같은 종류의 누락 가능성. 이 갈래에서 고치지 않고 보고서에 기록
- **`Ruling 581` — 학부모·학생 앱도 임시 비밀번호 강제 변경 화면에 고정(매니저 앱과 같은 갈래).** 학부모·학생 계정의 초기화 경로는 **실재**함 — 관계자 웹 학생 수정 화면의 `AccountPasswordResetDialog`(`StudentForm.tsx`) → `POST /staff/accounts/{accountId}/password-reset`(`§5.22`), 서버 대상 역할 `PARENT`·`STUDENT`·`DRIVER`·`ESCORT`(`AccountPasswordResetCommandService.RESETTABLE_ROLES`)
  - `mustChangePasswordProvider`(`core/auth/account_session.dart`)가 로그인·`/me`(자동 로그인) 응답의 `mustChangePassword` 로 켜지고, 라우터 `redirect` 가 켜진 동안 `/password-change` 밖으로 못 가게 함. 계정 상태 게이트(`pending`·`rejected` → 대기 화면) 다음 순서
  - **표식은 역할을 반영하기 전에 켬.** 역할이 서는 순간 라우터가 판정하므로 그 시점에 표식이 있어야 함. 매니저 앱은 역할 → 표식 순서인데 `go_router` 가 판정을 비동기로 미뤄 문제가 없었을 뿐이고, 학부모 앱은 순서 의존을 없애는 쪽을 택함
  - 변경 화면(`password_change_screen.dart`)은 표식이 켜진 동안 **뒤로 가기 없음**(`AppHeader.onBack` 을 비우면 뒤에 화면이 없어 버튼이 안 그려짐) · 안내 배너 · `[로그아웃]`. 로그아웃은 이 앱 다른 곳과 같은 `confirmLogout`(확인 대화 1회) — 매니저 앱은 대화 없이 즉시이나 학부모 앱은 이미 `settings`·`pending_approval` 이 확인 대화를 쓰므로 맞춤
  - 표식을 끄는 곳은 역할이 비는 모든 경로(로그아웃·세션 만료·변경 성공 뒤 로그아웃) — `RouterRefreshNotifier` 의 역할 구독이 `이전 역할 있음 → 없음` 전이에서 함께 끔. 로그인 화면의 "이 앱이 지원하지 않는 역할" 갈래도 표식을 되돌림
  - 서버가 마지막 방어선이므로(`Ruling 540`) 이 이동 처리는 막힌 호출이 오류 화면으로 쏟아지지 않게 하는 쪽
- **`Ruling 582` — 공용 `RunSummaryCard` 의 큰 글자 가로 넘침은 알약 + `호차 · 등원` 줄을 전체 너비 `Wrap` 으로.** 실측(`R46-FUMGR` 매니저 운행 화면 시험의 허용 예외를 걷은 채 실행) — **글자 2.0배에서만** 360×640 에서 57px · 375×750 에서 42px 가로 넘침, 1.0·1.3배는 넘침 없음(`Ruling 573` 이 적은 "1.3~2.0배" 는 실측과 어긋남). 원인은 `Row[알약, Spacer, 호차·등원]` 의 두 자식이 한 줄에 못 들어가도 줄을 바꿀 수 없는 구조
  - `SizedBox(width: infinity)` 안의 `Wrap(alignment: spaceBetween)` — 한 줄에 들어가면 예전과 같이 알약 왼쪽 · 호차 오른쪽 끝, 2.0배에서는 `호차 · 등원` 이 둘째 줄 왼쪽으로 내려감. **`Wrap` 만으로는 내용 너비로 줄어들어 오른쪽 끝 정렬이 사라져**(1.0배에서 라벨 위치 229px, 기대 320px — 시험으로 확인) 전체 너비를 줌

  - **적용 6칸** — 매니저 앱: 비상 신고 상황 메모(`emergency_alert.memo`) · 현장 보고 상황 메모(`exception_report.memo`) · 지연 안내 문구(탑승 학생 전원의 보호자에게 나가므로 다른 학생 정보가 새는 쪽 위험이 큼) / 관계자 웹: 비상 조치 메모(`emergency_alert.ack_memo`) · 임시 추가 메모(`run_forced_addition.note`) · 이동 대기 비고. 안내는 칸의 `hint`(칸 아래 보조 문구)에 붙임. 문구 상수는 앱 `limited_text_controller.dart` 의 `freeTextPrivacyNotice`(이미 자유 입력 메모 도우미가 있는 파일) · 웹 `shared/lib/freeTextNotice.ts`

- **`Ruling 650` — 매니저 앱 오프라인 큐: 서버 5xx 도 큐에 쌓고, 5xx 를 되풀이하는 행은 영구 실패로 재생에서 빼 뒤를 막지 않게 한다(S-9).**
  - **쌓는 규칙** — `NetworkFailure` 에 더해 서버가 응답한 **5xx 전부**(`status >= 500`)를 큐 대상으로. JSON 본문이면 `ApiFailure`, nginx HTML 이면 `UnknownFailure` 로 오는데 후자는 상태 코드가 값으로 없어 `Failure.unknown` 에 `int? statusCode` 를 더했다(`baraeda_core` — 선택 필드라 기존 호출 영향 없음). 승하차 PATCH · **비상 발신 POST** 둘 다 `client_key` 멱등이라 서버 중복 안전. 4xx 는 쌓지 않고 그대로 던짐. 지시의 열거(500·502·503·504)를 5xx 전부로 넓힌 이유 — 스테이징 Cloudflare Tunnel 이 origin 이 죽으면 520~530 으로 답함(쌓는 쪽과 재생의 시도 횟수 쪽이 한 판정 함수를 씀)
  - **영구 실패** — 행별 `attempts`(drift `schemaVersion 3→4`, `ALTER ... ADD COLUMN` · 기존 행 0). 상한 **10회 또는 쌓인 지 30분**에 닿으면 영구 실패(`attempts = 10` 표식 하나로 읽음). 영구 실패 행은 **지우지 않는다** — 재생에서 빠지고(같은 재생에서 뒤 행이 이어서 나감) 큐 화면에 `전송 실패 · 서버가 계속 받지 못했습니다` + `[삭제]`, 명단 위에 `서버가 계속 받지 못해 보내지 못한 처리 N건 · 대기열에서 확인하세요`. 학생 행은 `전송 대기` 표시 대상이 아니고 중복 판정에서도 빠져 다시 눌러 새로 보낼 수 있음
  - **무엇을 세는가** — ①서버가 5xx 로 응답한 **머리 행**만(두절은 행이 아니라 망의 문제라 세지 않음 — 터널·음영이 길어도 쌓아 둔 승하차를 버리지 않음. 나이 상한도 5xx 를 받은 행에만 적용) ②**주기 재생(30초)·수동 재시도만**(새 요청 앞의 재생은 세지 않음 — 서버가 죽은 동안 정류장에서 학생을 연달아 누르면 머리 행이 누른 횟수만큼 곧바로 영구 실패가 됨) → 상한 10회 ≈ 5분
  - **버린 길** ① 검토안(`droppedPermanently` 로 세고 삭제) — 자동 재생(`OfflineQueueAutoSync`)이 반환값을 버려 사용자가 영영 못 봄 ② 횟수만/나이만 단독 — 횟수만이면 연타에, 나이만이면 독성 행이 30분 막음 ③ `mapDioExceptionToFailure` 가 비-JSON 5xx 를 `ApiFailure` 로 바꾸기 — 학부모 앱 포함 모든 소비처의 오류 문구 분기가 바뀜
  - **재생 순서** — 재생·대기 목록 `orderBy(id)` 명시. SQLite 일반 `SELECT` 가 이미 rowid 순이라 RED 불가 — 계약 고정용 시험
- **`Ruling 651` — 실시간 연결은 포기하지 않고 30초 상한으로 계속 다시 붙는다 · 앱 복귀·온라인 복귀 때 바로 다시 붙는다(S-5).**
  - Flutter 공용 `WsBackoffPolicy.maxAttempts` 를 `int?` 로(기본 `null` = 무제한) · 웹 `WsBackoffPolicy` 도 같음 + **웹에 지터 추가**(`jitteredDelayFor` · 최대 −30% · 난수 주입 가능). 6회(약 1분) 뒤 포기하던 옛 기본값은 터널·음영 1분 초과·백엔드 재기동 90초(`start_period`)에서 연결을 끊긴 채 방치(매니저 앱은 다른 직원의 변경을, 학부모 지도는 갱신을 못 받음). 비용은 망이 죽은 동안 30초마다 소켓 시도 1회
  - ⚠ **무제한이 되면서 드러난 결함** — `delayFor` 가 정수 `pow(2, attempt-1)` 로 계산해 **64회째부터 넘쳐 0 이 됨**(대기 0ms 재연결 폭주 — 30초 간격이면 약 30분 뒤). 실수 계산으로 고침(RED: 1000회째 대기가 0)
  - `BaraedaWebSocketClient.reconnectNow()` 신설 — `reconnecting`·`gaveUp` 일 때만 즉시 `connect()`(횟수 0 으로). `disconnected`(연결한 적 없음·일부러 끊음·세션 만료)·`connecting`·`connected` 는 건드리지 않음. 호출 — 매니저 앱 홈 복귀 훅이 신호(`appResumedProvider`)를 올리면 운행 화면의 연결 컨트롤러가 호출 · 학부모 앱 `AppShell` 이 복귀 때 공용 클라이언트에 호출 · 웹은 기존 `online`·`visibilitychange` 핸들러가 `gaveUp` 에 더해 `reconnecting` 도 다시 붙임
  - 화면 — `WsConnectionState.gaveUp` 와 그 화면 처리(매니저 앱 `gaveUp` 배너 · 학부모 지도 `연결 끊김` · 웹 `다시 연결` 버튼)는 상한을 준 정책에서만 쓰이는 길로 남김(운영에서는 도달하지 않음 — 제거는 범위·위험이 커 보고). 재연결 중 문구 조정 — 매니저 앱 `연결이 돌아올 때까지 자동으로 계속 다시 붙습니다 …` · 웹 `연결될 때까지 자동으로 계속 시도합니다. 그동안 목록은 7초마다 새로 받습니다.`
- **`Ruling 652` — 전체 관제(`MonitoringPage`) 회차 목록 폴링은 실시간 연결이 `connected` 면 30초 · 아니면 7초(L3).** 가장 무거운 GET(`GET /admin/academies/{id}/runs/live` — 취소 아닌 회차 전부 + 정차 목록) 이 방송과 중복이라 안전망으로만 느리게. 재연결 중·권한 거부·연결 전에는 7초 유지. **재연결 직후 한 번 바로 받음**(끊긴 사이 놓친 방송은 되찾을 길이 없는데 안전망이 30초로 늦춰지기 전에 메움 — 지시에는 없던 보강). 관계자 대시보드(`DashboardPage`)의 7초 폴링은 그대로(`staff_live` 는 가벼움 — 지시 범위 밖)
- **`Ruling 653` — 이벤트 뒤 재조회 묶기(L4).** ① 웹 `DashboardPage` — `MonitoringPage` 와 같은 300ms 묶음(창을 밀지 않음 — 첫 이벤트가 타이머를 걸고 그 안의 이벤트는 같은 묶음). `stop_arrived` 는 위치만, `rider_changed`·`run_started`·`run_ended` 가 하나라도 있으면 지표·회차 표도. 화면을 떠나면 예약 취소 ② 매니저 앱 연결 컨트롤러 — 이벤트 뒤 명단(`rosterProvider`·`driveModeRosterProvider`)·노선 재조회를 **첫 이벤트 뒤 1초 창 안 한 번**으로(지시는 "1초 디바운스" — 창을 미는 후행 디바운스는 이벤트가 쉬지 않고 이어지면 갱신이 영영 안 나가 **밀지 않는 창**으로 함. 회차 목록(`todayRunsProvider`)은 즉시 그대로)
- **`Ruling 654` — 오프라인 대기열 카드 폭(화면 확인에서 발견).** 큐 목록 `Column` 이 가운데 정렬이라 문구가 짧은 카드(`대기 중`)만 내용 폭(284pt)으로 줄어 가운데에 뜨고, 문구가 긴 `전송 실패` 카드(629pt)와 폭이 제각각이었음(이번 `전송 실패` 문구가 길어 차이가 드러남 — 원래 있던 결함). `Ruling 592` 와 같은 처리로 `crossAxisAlignment: stretch`. 위젯 시험 1건 RED(`{628.75, 284.25}`) → GREEN · `stretch` 를 지운 변형이 그 시험에만 걸림

## 5.31 `R46-FIXCONN` — 실시간 연결 감시 · 재연결 정리 (2026-10-01 · 기준 HEAD `be9d8cde` `mskim98/r46-fixconn` · 판정 `Ruling 616·617` + `660~668`)

검토(`review-conn` C-1~C-14 · `review-transport` K-1~K-8)가 짚은 실시간 연결의 수명·감시·보충·표시를 지금 구조(STOMP over WebSocket) 안에서 정리하는 창. 사용자 자리 비움 중이라 세부 선택은 창이 `Ruling` 으로 기록. 백엔드는 건드리지 않음(클라이언트 전용). C-14(토큰 15분 재접속)·K-4·K-5·K-7·K-8 은 서버 범위·권고라 하지 않음. 연결 값 전체는 `docs/API_SPEC.md §7.2` 표.

### 5.31.1 판정

- **`Ruling 616` — 비상 신고는 오프라인 큐의 영구 실패 상한(5xx 10회·30분)에서 뺀다. 성공하거나 사용자가 큐 화면에서 지울 때까지 계속 재시도한다.** 5분 넘는 서버 장애에 비상 신고가 재생에서 조용히 빠지면 아무에게도 안 간 신고가 사라진 것과 같다(`client_key` 멱등이라 늦게 도착해도 서버 중복 접수 없음). 승하차 상한은 그대로. 구현 — 비상 판별은 기존 `PendingRequestSummary` 가 쓰던 `endpoint` 규칙을 정적 함수(`isEmergencyEndpoint`)로 올려 저장소·화면이 한 기준을 씀(스키마 변경 없음) · 비상 5xx 는 시도·나이를 세지 않고 남기되 **뒤 행은 이어 보냄**(`continue` — `break` 로 두면 서버가 그 본문만 계속 거절할 때 승하차가 영구히 막힘) · 비상 화면은 큐에 비상 행이 남아 있는 동안 *"전송 실패 — 계속 다시 보내는 중 · 급하면 학원에 전화"* + [학원에 전화] 를 표시(화면을 나갔다 다시 열어도 큐 기준으로 표시 · 영구 실패로 굳은 옛 행은 해당 없음). ⚠ **서버 접수 화면은 앱이 누른 시각을 보이지 않는다** — `raised_at` 은 서버 접수 시각(`received_at`)이고 단말 시각(`occurred_at`)은 조작 가능이라 응답에 일부러 싣지 않음(`API_SPEC §5.16`). 늦게 도착한 비상은 도착 시각만 보임 → 서버 몫으로 보고
- **`Ruling 617` — 실시간 전송은 STOMP over WebSocket 을 유지하고, 인스턴스 증설 결정 때 SSE 를 재평가한다**(조율자 결정 · 근거 `review-transport`). conn 지적 14건 중 SSE 로 사라지는 것은 1건(+단순화 3건)이고 그것도 설정 몇 줄로 지금 닫힘 · 바꾸는 비용(서버 33·웹 24·Flutter 27·k6 6 파일 + 부하 재측정) · 브라우저 `EventSource` 는 `Authorization` 헤더 불가. 재평가 조건 — 인스턴스 2대 필요 · 동시 연결 약 5,000 · 웹이 쿠키 세션으로 전환 · FCM 도입 · `stomp_dart_client` 유지보수 중단. 사용자가 뒤집을 수 있음
- **`Ruling 660` — 웹 숨은 탭에서도 비상 경로가 끊기지 않는다(C-1).** ①stompjs `heartbeatStrategy: Worker` ②`usePolling(task, interval, enabled, hiddenIntervalMs?)` 4번째 인자 — 비상 제공자만 숨은 탭에서 **30초** 간격으로 계속 폴링(다른 폴링은 숨은 탭에서 멈춤 그대로) ③재연결 직후 보충을 `useRealtimeChannel(destination, onEnvelope, onReconnected?)` 공용 콜백으로 올려 비상·승인·관제가 REST 1회를 부름. ⚠ FIXRT 가 관제에 넣은 "직전 렌더 상태가 `reconnecting` → 지금 `connected`" 검출은 실제 클라이언트가 재연결 대기 뒤 `connecting` 을 거치는 순서에서는 거짓이 될 수 있어(기존 시험의 가짜 훅은 건너뜀) "끊김(`reconnecting`·`gaveUp`)을 겪었는가" 플래그로 바꿈
- **`Ruling 661` — 학부모 앱 실시간 연결은 지도 화면이 열려 있는 동안만 산다 · 로그아웃·세션 만료 때 닫는다(C-2·K-3).** 전역 연결이 로그아웃 뒤에도 옛 계정 토큰으로 살아 있어 같은 단말에서 계정을 바꿔 지도를 열면 옛 권한으로 구독해 *조회 권한 없음* 이 뜨던 것(서버는 연결 시점의 인증 주체로 판정). `webSocketHoldProvider`(autoDispose)를 지도가 `ref.listen` 으로 붙잡고 마지막 지도가 닫히면 `disconnect()` · `signOut`·`endSessionAsExpired` 도 닫음. 자녀 전환의 겹침(새 지도가 옛 지도보다 먼저 생김)에서는 끊기지 않음. 버린 길 — `webSocketClientProvider` 를 autoDispose 로(`RouterRefreshNotifier` 가 시작 때 만료 신호를 구독해 곧바로 소멸)
- **`Ruling 662` — 시간 제한 값(C-3·C-4·C-7·C-8·K-1·K-2).** 웹 `discardWebsocketOnCommFailure: true` · `connectionTimeout 10초` · GET `15초`(`AbortController` — 쓰기는 끊지 않음) / Flutter `connectTimeout 10초`(소켓 열기 + `CONNECTED` 감시 워치독) · WebSocket `pingInterval 10초` / 매니저 앱 위치 POST 송신 `4초`·응답 `5초`(요청별 옵션). 전부 `API_SPEC §7.2`
- **`Ruling 663` — 학부모 지도 스피너는 첫 진입의 첫 연결 시도에만(C-5) · 재연결 스냅샷이 더 새로우면 WS 좌표를 교체(C-9).** 재연결 시도마다 `connecting` 이 와서 지도와 전체 스피너가 번갈아 보이던 것 — 한 번이라도 연결·끊김을 겪은 뒤의 `connecting` 은 `reconnecting`(지도 + 안내 배너)로 표시. 스냅샷은 `receivedAt` 이 WS 좌표보다 새로울 때만 교체(더 오래됐으면 그대로)
- **`Ruling 664` — `gaveUp` 상태·화면 처리는 지우지 않고 남긴다.** 기본 재연결 정책이 포기하지 않아 운영에서는 도달하지 않지만, ①`WsBackoffPolicy.maxAttempts` 를 주면 쓰이는 정식 경로이고 ②지우려면 3개 앱·공용 패키지 11개 파일과 시험이 걸리며 ③남는 비용은 죽은 분기뿐이다. 웹은 연결 안내를 `RealtimeConnectionStrip` 하나로 모아 `gaveUp` 의 [다시 연결] 도 거기 한 곳에만 둠(Ruling 666). `MonitoringPage` 주석 *"하트비트(10초)가 감지"* 는 실제 20~30초라 정정(C-3)
- **`Ruling 665` — 망 복귀·복귀 직후 죽은 연결(C-10·C-11).** 학부모 앱 — `AppShell` 이 오프라인→서버 도달 전이를 듣고 `reconnectNow()` · 매니저 앱 — 위치 전송 성공이 `serverReachedProvider` 를 올리고 연결 컨트롤러가 `reconnectNow()`(이미 연결·연결 중이면 클라이언트가 건드리지 않아 2초마다 올라도 무해). `BaraedaWebSocketClient.reconnectNow()` 는 `connected` 에서도 **마지막 서버 프레임(하트비트 포함)이 20초를 넘었으면** 소켓을 닫고 새로 연다(`stomp_dart_client` 가 받은 모든 데이터를 디버그 메시지 `<<<` 로 알리는 것을 이용해 시각 기록 · 시계 주입). 옛 소켓의 늦은 닫힘 신호가 새 시도를 끊김으로 오인하지 않게 **연결 시도 번호표**(`_attemptSeq`)를 도입
- **`Ruling 666` — 연결 끊김 문구는 한 벌, 웹은 레이아웃 연결 띠(C-12).** 제목 `재연결 시도 중입니다` · `실시간 연결 끊김` · `실시간 조회 권한 없음`(웹 `getWsConnectionNotice` · Flutter 두 앱 동일). 웹은 `(staff)`·`(admin)` 레이아웃 머리줄 아래에 `RealtimeConnectionStrip` 을 한 번만 두어 비상·승인 등 연결 상태를 안 읽던 화면에서도 끊김이 보이고, 대시보드·관제의 개별 배너는 제거(중복 표시 방지). 정상·연결 시도 중·직접 끊음에는 그리지 않음(처음 열 때 깜빡임 방지). 위치 전송 칩 6초/30초·학부모 유실 2분은 의도된 계단이라 그대로
- **`Ruling 667` — 웹 감사·접속 이력은 시작일을 비우면 "최근 30일" 임을 안내한다(`Ruling 632` 후속).** 서버가 `from` 이 없으면 `to`(없으면 지금)로부터 30일만 돌려주므로 시작일 칸에 힌트를 붙이고 버튼을 `전체 기간 보기` → `최근 30일 보기` 로 바꿈(거짓 문구 제거). 더 오랜 이력은 시작일을 직접 고른다
- **`Ruling 668` — `API_SPEC §7.2` 연결 감시·재연결 규약 표를 신설한다(C-13·K-6).** 하트비트 10초 · 무송신 20초 끊김 판정 · 백오프 1→30초 · 지터 30% · 연결 한도 10초 · 복귀·망 복귀 · REST 시간 제한 · 숨은 탭 폴링. 웹·Flutter 상수가 이 표를 인용하고, 웹 `stompClient.ts` 주석의 *"API_SPEC §7 이 못박는다"*(§7 에 하트비트 서술이 없던 거짓 인용)를 정정. 서버의 무송신 클라이언트 정리 시간은 이 저장소에서 미실측이라 사양 값으로 약속하지 않음

##### ✅ 1. 인증 — 키 이름과 실패 처리를 확정했다

| | iOS | Android |
|---|---|---|
| 선언 방식 | `info.plist` 키 **`NMFNcpKeyId`** | manifest `<meta-data>` **`com.naver.maps.map.NCP_KEY_ID`** |
| 코드 방식 | `NMFAuthManager.shared().client = NMFNcpKeyClient(...)` | `NaverMapSdk.getInstance(ctx).client = NaverMapSdk.NcpKeyClient("...")` |
| 폐기된 것 | **`NMFAuthManager.ncpKeyId` 는 deprecated** — `client` 방식을 쓴다 | 문서에 옛 방식 서술 부재 |
| 최소 OS | iOS **9** | **API 21**(5.0) |

**인증 실패 처리** — Android 는 `NaverMapSdk.onAuthFailedListener` 를 등록하면 기본 토스트 대신
`onAuthFailed(exception)` 이 온다. 등록하지 않으면 **토스트가 뜬다**(사용자에게 보인다).

| errorCode | 예외 | 원인 |
|:-:|---|---|
| 401 | `UnauthorizedClientException` | 클라이언트 ID·유형 오류, **콘솔의 앱 패키지명 등록 오류** |

| 800 | `ClientUnspecifiedException` | 클라이언트 ID 미지정 |

##### ✅ 2. 마커 위치 보간 — **API 가 없다. 직접 보간한다**

`NMFMarker` 의 속성은 `position`·`anchor`·`angle`·`alpha`·`zIndex`·캡션 계열뿐이고,
**이동 지속 시간·이징·보간 방식을 받는 속성이나 메서드가 부재**하다. `position` 에 대입하면 그 좌표로
바로 옮겨 간다. 문서에서 애니메이션이 붙는 대상은 **카메라**(`3-2.html`)이지 마커가 아니다.

⇒ 디자인 시스템의 *"버스 마커는 깜빡이지 않고 **위치만 600ms 로 보간**"* 은 **우리가 구현한다.**
프레임 타이머(iOS `CADisplayLink` 계열)로 시작·목표 좌표를 매 프레임 계산해 `position` 에 반복 대입한다.

- **위치 전송 주기가 5~10초**(`API_SPEC §4.12`)인데 보간은 600ms 다 — **보간이 끝난 뒤 다음 좌표까지
  멈춰 있는 시간이 대부분**이다. 이 멈춤이 어색하면 보간 시간을 늘리는 것이 아니라
  **다음 좌표 도착 시각까지 균등하게 펴는 방식**을 검토한다(F4 에서 실측)
- **프레임 끊김을 F4 에서 눈으로 확인한다** — 마커가 여럿일 때가 기준이다

##### ⬜ 3. `flutter_naver_map` 이 신규 키를 지원하는가 — **아직 미확인**

위 두 가지는 **네이티브 SDK 문서**의 사실이고, 우리가 앱에서 쓰는 것은 래퍼 `flutter_naver_map` 1.4.4 다.

- 네이티브 Android 최신은 **3.24.0** · minSdk **21** 인데 래퍼는 **Android 23 / iOS 12** 를 요구한다(더 엄격)
- **래퍼가 무는 네이티브 버전과, 그것이 `NCP_KEY_ID` 신규 키 이름을 받는지는 패키지에서 직접 확인해야 한다.**
  래퍼 최종 게시가 8개월 전이라 **옛 키 이름을 쓰고 있을 가능성이 있다**
- 확인 방법 — 패키지 소스의 manifest·초기화 코드에서 키 이름 문자열을 찾고, **실제 빌드로 인증까지 성공시킨다.**
  문서만 보고 "지원한다" 로 넘기지 마라
- Flutter 3.44.8 호환도 같은 빌드에서 함께 확인한다

  (iOS 번들 식별자에 밑줄을 못 쓴다). **양쪽을 있는 그대로** 등록한다
- ⚠ **`...RunnerTests` 로 끝나는 식별자는 등록하지 않는다** — 테스트 타깃이라 지도를 쓰지 않는다
- **애플리케이션은 하나로 만든다.** 콘솔의 Application 하나가 세 항목을 각각 여러 개 받으므로
  키·사용량이 한 곳에 모인다(공급자를 하나로 고정한 것과 같은 이유)
- ⚠ **등록 시 `Dynamic Map` 체크 필수** — 빠뜨리면 키가 맞아도 **429**. 패키지명 오등록은 **401**

#### 8.3.1 요금 때문에 공급자를 바꿀 수 있다 — 그래서 지도를 포트 뒤에 둔다

사용자 지시(2026-09-10): *"무료 이용이 안 된다면 티맵으로 변경하는 것도 고려"*.

**요금은 확인하지 못했다** — 조율자가 네이버 클라우드 플랫폼 요금 페이지를 열었으나 본문을 받지 못했다.
**F4 착수 전에 요금 페이지에서 월 무료 제공량과 초과 단가를 직접 확인하고 판정한다.**

⚠ **앞서 인용한 "2025-07-01 무료 이용량 제공 중단"은 옛 인증 방식에 대한 것**이고
네이버 지도 전체가 유료로 바뀐다는 뜻이 아니다. 신규 인증 API 로 옮기는 것이 전제.

**티맵으로 바꿀 때의 실제 비용 (실측 2026-09-10)** — pub.dev 검색 결과 **티맵 지도를 렌더링하는
Flutter 패키지가 부재**하다(경로탐색 REST 래퍼조차 없음). 즉 티맵을 쓰면 앱 2개에서
**네이티브 SDK 를 platform channel 로 직접 감싸거나 WebView 로 띄워야** 하고,
후자는 `§8.3` 2번의 마커 보간 요구를 더 어렵게 만든다. 웹은 티맵 JS SDK 가 있어 부담이 덜하다.

**그래서 구현 규칙 하나를 고정한다 — 지도를 포트 뒤에 둔다.**

| 스택 | 자리 | 화면이 아는 것 |
|---|---|---|
| 웹 | `features/map/` 의 인터페이스 1개 | 좌표·정류장·버스 위치. **SDK 이름을 모른다** |
| Flutter | `packages/baraeda_ui` 가 아니라 각 앱 `core/map/` 의 추상 위젯 | 같음 |

- **화면 코드가 `NaverMap` · `NMarker` 같은 SDK 타입을 직접 쓰지 않는다.** 어댑터 안에서만 쓴다
- 디자인 시스템의 `MapSurface` 가 이미 이 모양이다 — *"실제 SDK 타일이 들어갈 자리"*
- 이렇게 두면 공급자 교체가 **어댑터 1개 교체**로 끝나고, 화면 20여 개를 건드리지 않는다
- 교체 가능성이 실재하므로 이것은 과설계가 아니다

### 8.1 디자인이 부재한 화면을 만들 때 지킬 것

킷에 없는 화면(관계자 웹 7종 · 메인 관리자 8종 · 매니저 앱 2종)은 새로 설계하되,
**임의로 만들지 않고 디자인 시스템의 규칙을 근거로 유도함.**

| 근거 | 위치 |
|---|---|
| 색 · 상태 색 매핑 · 화이트 셸 규칙 | `design-system/readme.md` VISUAL FOUNDATIONS · `tokens/semantic.css` |
| 타입 · 여백 · 모서리 · 그림자 · 모션 | 같은 문서 · `tokens/*.css` |
| 카피 문면 (어미 · 시각 표기 · 버튼 라벨) | 같은 문서 CONTENT FUNDAMENTALS |
| 화면 골격 (헤더 56 · 사이드바 248 · 본문 최대 1160) | 같은 문서 여백·레이아웃 |
| 비슷한 화면의 구성 | 기존 킷 7화면 (`WebScreens.jsx`) |

**하지 않을 것** — 배경 이미지·그라디언트·블러 · 이모지 · 왼쪽 컬러 보더 카드 ·
바운스 애니메이션 · 파란 하이라이트. 전부 디자인 시스템이 명시적으로 금지한 것.

### 8.2 ✅ 남은 미결정 — **전부 닫힘** (2026-09-12 사용자 확정, Ruling 270)

| # | 항목 | 확정 | 파급 |
|:-:|---|---|---|
| 1 | **Flutter web 사용 여부** | **안 씀** | 앱 2개는 **스토어 배포만**. `§7` 의 "Flutter web 빌드를 쓸 경우 nginx 정적 서빙" 갈래는 **폐기** |
| 2 | **지도 SDK 공급자** | **네이버로 확정 — 티맵 대안 검토 종료** | `§8.3.1` 의 *"무료 이용이 안 되면 티맵 고려"* 지시는 이 확정으로 닫힌다 |

#### 1번(Flutter web 안 씀)이 바꾸는 것

- **Docker 배포 대상은 관계자 웹(Next.js) 하나뿐이다.** `§7` 표의 두 번째 행은 이제 조건 없이 "컨테이너 부재"
- ⚠ **F5 의 매니저 앱 실기기 왕복이 더 중요해진다** — web 빌드를 안 쓰므로 **시뮬레이터 외에 확인할 수단이
  실기기뿐**이다. R1 에서 "시뮬레이터로는 결론이 안 바뀐다" 며 F5 로 미룬 항목이 여기로 모인다
- 검사 방식은 그대로다(`flutter test` 는 화면 없이 돈다)

#### 2번(네이버 확정)이 바꾸는 것과 **바꾸지 않는 것**

- **바꾸는 것** — `§8.3.1` 의 티맵 전환 검토는 종료. pub.dev 에 티맵 Flutter 패키지가 부재해
  앱 2개에서 네이티브를 직접 감싸야 했던 부담이 사라진다
- ⚠ **바꾸지 않는 것 — 지도를 포트 뒤에 두는 규칙(`§8.3.1`)은 유지한다.** 공급자가 고정됐어도
  **요금은 여전히 미확인**이고(아래), 어댑터 1개짜리 비용이라 유지 편이 싸다.
  화면 코드가 `NaverMap`·`NMarker` 를 직접 쓰지 않는다는 규칙은 그대로다
- ⚠ **`§8.3` 의 F4 착수 전 확인 3가지는 그대로 남는다** — ①신규 인증 API 의 키 발급 절차·파라미터
  ②버스 마커 위치 보간(600ms) API 의 실재 ③`flutter_naver_map` 1.4.4 와 Flutter 3.44.8 호환.
  **공급자 확정은 이 셋을 대신하지 않는다**
- **요금 확인은 F4 착수 전 과제로 남는다.** 사용자가 공급자를 확정했다는 것이 요금을 확인했다는 뜻은
  아니다 — 무료 제공량과 초과 단가는 여전히 조회되지 않았고, 그 값은 **쓸지 말지가 아니라
  사용량 설계(폴링 주기·타일 캐시)** 에 필요하다
