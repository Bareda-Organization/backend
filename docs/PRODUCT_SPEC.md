## 1. 서비스 개요 & 목적

학원 통학버스 운영에서 전화·수기로 흩어져 있던 정보를 하나의 데이터 흐름으로 연결해 **안전성 + 운영 효율**을 올린다.

- **6대 서비스:** ① 노선표·배차 ② 학생 승하차 ③ 학원·기사·학부모 커뮤니케이션 ④ 차량·운행인력 관리 ⑤ 운행 모니터링·사고 대응 ⑥ 통계·법정 운행기록
- **핵심 가치:** 지도에 버스를 표시하는 것이 아니라, **승하차 기록 · 명단 · 배차 · 예외 대응 · 법정 기록이 끊기지 않고 연결되는 것**. 실시간 위치는 그 위에 얹히는 한 조각이다.
- **해결하는 문제:** 학부모가 자녀 탑승 여부를 알려고 전화한다 / 기사가 종이 명단으로 승하차를 확인한다 / 결석·시간변경이 구두로 전달돼 명단에 반영되지 않는다 / 사고·미승차 시 누가 언제 무엇을 했는지 기록이 남지 않는다.

## 2. 사용자 계층 & 권한

하나의 승하차 기록(`RideEvent`)을 여러 계층이 **각자 권한 범위 안에서만** 조회한다 — "계층별 조회 권한 분리"가 설계의 핵심이다.

기획 원본(docx)은 운영 4역할(학원관리자·기사·동승보호자·학부모)을 정의하지만, 코드의 `Role` enum은 여기에 **학생·플랫폼 관리자**를 더한 **5계층**이다. 동승보호자는 MVP에서 별도 역할로 분리하지 않고 **기사 앱의 승하차 확인 흐름에 흡수**했다(추후 역할 승격 가능).

| 계층(`Role`) | 조회 범위 | MVP 화면 | 백엔드 API |
|---|---|---|---|
| `STUDENT` 학생 | 본인 기록 + 본인 위치 + SOS | ⬜ **0개** | ✅ 구현(`/me` 계열) |
| `PARENT` 학부모 | 자녀(형제자매 포함) 기록·위치·알림함·결석신고·시간변경 | ⬜ **0개** | ✅ 구현(`/children` 계열) |
| `DRIVER` 기사 | 담당 버스 명단·노선·운행 세션 | ✅ 2화면 | ✅ 구현 |
| `ACADEMY_ADMIN` 학원관리자 | **소속 학원(tenant)** 전체 이력·관제·배차 | ✅ 4화면 | ✅ 구현 |
| `PLATFORM_ADMIN` 플랫폼관리자 | **전 학원** 운영(학원 등록·크로스 테넌트 조회) | ✅ 4화면(학원관리자와 동일) | ✅ 구현 |

- 학원관리자 ≠ 플랫폼관리자. 권한 범위가 완전히 별개다.
- 두 관리자 역할은 **화면이 완전히 동일**하고, 차이는 tenant 결정 방식뿐이다 — 학원관리자는 JWT의 소속 학원 고정, 플랫폼관리자는 `GET /api/tenants` 목록에서 드롭다운 선택.
- **멀티테넌시는 N:M.** `User`에 `tenant_id`를 직접 박지 않고 **`UserTenantRole(user_id, tenant_id, role)` 연결 테이블**로 표현한다. 학부모 1명이 서로 다른 학원에 자녀를 둘 수 있고, 기사가 복수 학원에 소속될 수 있기 때문이다. 플랫폼관리자는 `tenant_id`가 `NULL`인 전역 역할로 저장된다.
- 학생(`Student`)은 단일 학원 종속이다(`student.tenant_id` NOT NULL).

⚠ **흔한 오해:** "학생·학부모 API가 없다"가 아니다. 백엔드에는 학생·학부모 전용 엔드포인트가 **이미 다 구현돼 있고**, 그것을 호출하는 **프론트 화면이 없을 뿐이다**. 두 역할은 로그인은 성공하지만 "준비 중" 배너만 본다(→ 12장 O1).

## 3. 도메인 데이터 모델

기획 항목을 실제 엔티티에 매핑한 결과다. `@Entity` **16개** + 공통 상위 `@MappedSuperclass` `BaseTimeEntity` 1개(= 클래스 17개), DB 테이블 16개.

| 기획서(docx 3장) | 핵심 항목 | 실제 엔티티 | 구현 상태 |
|---|---|---|---|
| 학생정보 | 이름, 담당 버스, 승차 정류장, 하차 좌표, 보호자 연결 | `Student` + `StudentGuardian` | 🟡 사진·정규 등하원 요일·혼자 귀가 여부 **필드 없음** |
| 정류소정보 | 이름, 순서(seq), 좌표 | `Stop` | 🟡 상세 위치·사진·**지오펜스 반경·허용 승하차 시간 필드 없음** |
| 차량정보 | 이름, 차량번호, 좌석 정원, 담당 기사, 보험 만료일 | `Bus` | 🟡 어린이통학버스 신고 정보 **필드 없음** |
| 운행인력정보 | 계정·소속 학원·역할 | `User` + `UserTenantRole` | 🟡 자격·안전교육 이수·유효기간 **필드 없음** |

### 3.1 엔티티 전체 (16개)

**마스터 데이터** — `Tenant`(학원, depot 좌표 보유) · `User`(`app_user` 테이블, `user`가 예약어라 개명) · `UserTenantRole` · `Student` · `StudentGuardian` · `Bus` · `Route` · `Stop`

**운영 데이터** — `RideEvent`(승하차 허브) · `DriveSession`(운행 세션) · `RoutePlan` + `RoutePlanStop`(당일 노선 계획) · `AttendanceException`(결석·휴원) · `ScheduleChangeRequest`(시간 변경) · `SosEvent` · `NotificationLog`

⚠ **기존 문서 오류 정정 2건**
1. `PROJECT_MASTER_PLAN.md` §3의 엔티티 목록에 있는 **`AuditLog`는 실제로 존재하지 않는다.** 감사 로그 테이블·엔티티가 없으므로 "민감 조작 이력"은 현재 남지 않는다.
2. 같은 목록에 `DriveSession` · `RoutePlan` · `RoutePlanStop` **3개가 빠져 있다.** 이 셋은 실제 구현·사용 중인 핵심 엔티티다.

### 3.2 설계 결정

- **`RideEvent`가 허브다.** Student·Bus·Stop·Route와 연결되고, 4계층이 각자 범위로 조회한다.
- **정정은 덮어쓰기가 아니라 append-only.** 원본을 남기고 `source=CORRECTION` · `corrected_by` · `corrected_at` · `original_ref`를 채운 **새 행**을 만든다.
- **대용량·이벤트성 테이블은 JPA 연관 대신 평문 `Long` 참조**를 쓴다(`RideEvent` · `DriveSession` · `RoutePlan` · `SosEvent` · `NotificationLog` · `AttendanceException` · `ScheduleChangeRequest`). 그래서 DB FK 제약은 13개뿐이고 나머지 참조 무결성은 애플리케이션이 책임진다.
- **`tenant_id` 보유 엔티티 11개 / 16개.** `Stop`은 `Route` 경유, `StudentGuardian`은 `Student` 경유, `RoutePlanStop`은 `RoutePlan` 경유로 간접 격리한다.
- **정원 개념이 두 갈래다.** `Bus.seatCapacity`(물리 좌석 수)와 `Route.assignCapacity`(노선 배정 정원)는 **별개 값이고 서로 동기화되지 않는다.** 자동 배차의 실제 판단은 `seatCapacity`만 쓰고, `assignCapacity`는 화면의 "정원 초과" 경고 표시에만 쓰인다.
- 스키마는 **Flyway**가 관리한다(`ddl-auto: validate`). 마이그레이션 5개(V1 베이스라인 + V3~V5는 CHECK 제약 확장, V2는 로컬 전용 데모 시드).

⚠ **흔한 오해:** "정류소 = 주소"가 아니다. 주소와 별개로 **실제 승하차 지점**(동 앞·출입구, 진행 방향, 유턴 여부, 대기 안전장소, 지오펜스)을 따로 관리해야 한다. 현재 `Stop`은 이름·순서·좌표만 갖고 있어 이 요구사항을 아직 만족하지 못한다.

## 4. 노선 · 배차 관리

노선은 최단거리가 아니라 **정원·안전·시간 제약을 만족하는 "운행 가능한" 경로**다. 변경은 덮어쓰지 않고 **버전 관리**한다.

### 4.1 요구사항

- **관리 단위:** 요일별 / 등원·하원 / 수업시간별 / 차량별 / 학기·방학별 + 적용 시작·종료일
- **최적화 제약(기획 목표):** 차량 정원, 학생별 승하차 가능 시간, 학원 도착 마감, 교통량, 정차 소요시간, 아파트 진입·회차, 일방통행·유턴·높이 제한, 어린 학생 최대 도보거리, 학생별 최대 탑승시간, 형제자매 동일 차량, 진행방향 반대편 하차 방지, 위험 횡단 방지
- **임시 변동 절차:** ① 학부모 신청 → ② 시스템이 정원·노선 영향 자동확인 → ③ 관리자 승인/거절 → ④ 기사·동승보호자 전달·확인 → ⑤ 학부모 최종 안내
- **정책:** 기사·학부모가 직접 합의한 변경도 **학원 승인을 거쳐야 효력**이 생긴다. 정규 노선은 관리자 최종 승인 후에만 적용된다.

### 4.2 계획 생명주기 (구현됨)

```
DRAFT / RECOMMENDED  --approve-->  APPROVED  --publish-->  PUBLISHED
```

- `PUBLISHED`가 되어야 기사 앱 조회 API에 노출된다.
- **재계산은 기존 행 수정이 아니라 `version + 1`인 새 행 생성**이다. 이력이 보존되고, 기사 앱은 같은 버스·방향에서 최신 version을 골라 쓴다.
- 배포 후 취소·철회 전이는 **존재하지 않는다.**
- 결석 승인·시간변경 처리·학생 배정 변경·하차지 변경 4가지 이벤트가 발생하면, 해당 버스의 **당일 계획만** 국소 재계산(replan)된다. 실패하면 기존 계획을 그대로 두고 경고 로그만 남긴다.

### 4.3 자동 배차 알고리즘 (실측)

2단계다. ① 학생을 버스에 나눠 담고 → ② 버스별 정차 순서를 최적화한다.

1. **버스 배정 — sweep 방식**: 학원(depot) 기준으로 학생 좌표를 **방위각 순으로 정렬**한 뒤, 버스를 id 오름차순으로 순회하며 `seatCapacity`만큼 순차로 잘라 담는다.
2. **정차 순서 — 휴리스틱 3단계**: sweep 정렬(결정적 초기 순서) → nearest-neighbor(그리디) → 2-opt(구간 반전 개선, 최대 1000 pass). 거리 함수는 **Haversine 직선거리**라 이 단계에서 외부 API 호출이 없다.
3. **실제 도로거리·ETA**: 순서가 확정된 뒤 외부 경로 API를 1회 호출해 얻는다. 기본 제공자는 Naver Directions(키 필요), 미설정 시 OSRM 공개 데모 서버로 폴백한다.
4. **방향 처리**: DROPOFF는 `[depot, …]`, PICKUP은 최적 순서를 뒤집어 `[…역순, depot]`. "대칭거리에서는 depot 고정 최적경로를 뒤집어도 총거리가 같다"는 성질에 기대 최적화를 1회만 수행한다.

**⬜ 반영되지 않은 제약** — 4.1의 최적화 제약 중 실제로 반영되는 것은 **좌석 정원 하나뿐**이다. 시간창(등원 도착 마감·하원 출발 시각), 버스 간 부하 분산, 정차 소요시간, 형제자매 동일 차량, 도로 통행제한, 기사 배정 여부·보험 만료 필터는 전부 미반영이다. 구조적으로 **앞 버스부터 정원까지 꽉 채우므로 마지막 버스가 비는 편향**이 생긴다.

⚠ **흔한 오해:** "노선이 하나"가 아니다. 시스템에는 **고정 노선(`Route` + `Stop`)**과 **당일 계획(`RoutePlan` + `RoutePlanStop`)**이 별개로 존재하고, 자동 배차는 고정 노선의 정류장 순서(`Stop.seq`)를 **전혀 보지 않고** 매번 새로 계산한다. 한 버스가 서로 다른 두 순서를 동시에 가질 수 있으며, 둘의 정합성을 맞추는 코드는 없다. `Route`/`Stop`은 사실상 "정류장 마스터 데이터 + 정원 경고 표시" 용도로만 남아 있다.

## 5. 승하차 관리 & 학생 상태머신

승차·하차를 **하나로 묶지 않고 각각** 기록한다.

### 5.1 학생 운행 상태 전이 (기획 목표)

```
탑승예정 → 정류소 대기 → 승차완료 → 운행중 → 하차예정 → 하차완료 → 보호자 인계완료 → 운행완료
                 └─(미승차/예외 분기 → 6장)
```

현재 코드가 실제로 기록하는 것은 이 중 **BOARD(승차완료) · ALIGHT(하차완료) · HANDOVER(보호자 인계완료) 3개 지점**이다. "정류소 대기", "하차예정" 같은 중간 상태는 저장되지 않는다.

### 5.2 확인 방식

기획상 초기에는 **명단 + 사진 육안 + NFC/RFID + QR + 실패 시 수동 + 탑승 인원·좌석 자동 대조**를 병행하기로 했다.

- 실제 구현된 경로는 **기사 수동 기록 하나뿐**이다. `RideSource` enum에 QR·NFC가 정의돼 있으나 이를 생성하는 코드 경로가 없어 기록의 `source`는 항상 `MANUAL`로 고정된다.
- 기록 시각(`occurredAt`)도 서버의 `now()`로 고정된다 — 과거 시각으로 남기려면 정정 API를 써야 한다.
- 사진 육안 확인은 `Student`에 사진 필드가 없어 불가능하다.

### 5.3 운행 세션과 차내 잔류 방지

승하차 기록은 **운행 세션(`DriveSession`)** 안에서 이뤄진다. 기사가 방향(등원/하원)을 골라 시작하고, 명단을 처리한 뒤 종료한다.

- 같은 (버스, 방향, 운행일)에 진행 중 세션이 이미 있으면 시작이 거부된다.
- 명단은 **당일 승인된 결석자를 자동으로 제외**한 실제 명단이다.
- **차내 잔류 방지: 구현됨.** 종료 시 세션 구간의 승하차 기록을 학생별로 훑어 **마지막 기록이 BOARD인 학생이 하나라도 남아 있으면 종료를 차단**한다.
- 세션 구간 판별에 `drive_session_id` 컬럼이 아니라 **busId + 시간창**을 쓴다 — "버스당 진행 중 세션은 1개"라는 전제에 의존한다.

⚠ **흔한 오해 2건**
1. **태그(QR/NFC)만으로 확정하면 오확정 위험이 있다.** 명단·실제 학생을 함께 확인하는 이중 구조가 원래 요구사항이며, 현재는 기사 수동 확인이 그 역할을 대신하고 있다.
2. **하차완료 ≠ 보호자 인계완료.** 저학년은 단순 하차 버튼만으로 운행을 끝내면 안 된다. 그래서 `HANDOVER` 타입을 별도로 두었다.

## 6. 예외상황 · 에스컬레이션

각 예외를 **대기 → 연락 → 관리자 보고 → 후속조치**의 정해진 순서·임계시간으로 처리한다.

| 예외 | 흐름(타임라인) | 구현 상태 |
|---|---|---|
| 미승차 | 정류소 도착 → **+10분 미확인** → NO_SHOW 판정 → 학부모+관리자 알림 | ✅ 스케줄러 구현(15초 주기 재평가) |
| SOS | 발신 → 즉시 학부모+관리자 → **+3분 미확인** → 플랫폼관리자 에스컬레이션 | ✅ 백엔드 구현(30초 주기 재평가) / ⬜ 발신·확인 화면 없음 |
| 근접 알림 | 도착 예상 **5분 전** → 학생+학부모 | ✅ 스케줄러 구현 |
| 연결 끊김 | 학생 위치 heartbeat 끊김 → **+30초** → CONNECTION_LOST | ✅ 구현 |
| 보호자 부재 | 하차위치 도착 → 대기·연락 → 연락 실패 → 관리자 보고 → 재탑승·복귀 | ⬜ **미구현** (해당 이벤트·상태·알림 타입 없음) |
| 태그/단말기 오류 | 수동·오프라인 처리, 통신 복구 후 자동 동기화 | ⬜ **미구현** (오프라인 큐 없음) |
| 차량 고장/사고 | 긴급신고 · 명단 자동전달 · 대체차량 | ⬜ **미구현** |
| 차내 잔류 방지 | 운행 종료 전 미하차 학생 확인, 남아 있으면 종료 차단 | ✅ 구현 |

- **미승차 판정의 ETA 근거:** `세션 시작 시각 + 해당 정차의 etaSeconds` 근사값을 정류소 도착 시각으로 본다. 계획(`routePlanId`)이 없는 수동 운행 세션은 판정 대상에서 제외된다.
- **에스컬레이션에는 API가 없다.** 스케줄러만이 트리거이며 수동 실행 엔드포인트는 존재하지 않는다.

⚠ **법적 근거:** 도로교통법상 어린이 **하차확인장치** 작동, 좌석안전띠·보호자 동승, **안전운행기록 작성·보관·분기 제출**이 의무다. 즉 위 확인·기록은 편의 기능이 아니라 **법정 요건**이다. 현재 운행 기록은 DB에 남지만 **법정 서식 출력·제출 기능은 없다.**

## 7. 실시간 위치 · 알림 정책

학부모에게 전체 노선이 아니라 **자녀 관련 제한 위치만** 제공한다. 알림은 "이벤트 1건 = 발송 1건"이 되도록 **멱등(중복 억제)** 처리한다.

### 7.1 위치 데이터 경로 (실측)

| 구간 | 방식 | 상태 |
|---|---|---|
| 기사 앱 → 서버 (버스 위치) | 5초 주기 `POST /api/locations/bus` | ✅ 단, **기본 좌표원이 Mock** |
| 서버 → 관리자 (관제) | Kafka → STOMP `/topic/tenant/{id}/bus-locations` | ✅ 백엔드만 — **프론트는 아직 3초 REST 폴링** |
| 학생 앱 → 서버 (학생 위치) | REST 또는 STOMP `/app/location` | ✅ 백엔드만 (학생 앱 없음) |
| 서버 → 학생·학부모·기사 (학생 위치 push) | Kafka → STOMP `/user/queue/location` | ✅ 백엔드만 (구독 화면 없음) |
| 서버 → 관리자 (알림 push) | STOMP `/topic/tenant/{tenantId}/notifications` | ✅ 구현·사용 중 |

- **버스 위치도 이벤트를 발행해 실시간 push 로 이어진다**(`BusLocationUpdatedEvent` → Kafka → `BusLocationPushConsumer`). 관제 화면이 폴링을 쓰는 것은 **프론트 미전환** 때문이지 서버에 경로가 없어서가 아니다.
- 위치는 Redis에 **최신 1건만** 보관한다 — 학생 TTL 약 9초(`tick-ms`×3), 버스 TTL **15초**(`app.location.bus-ttl-seconds`). **위치 이력 조회 API는 존재하지 않는다.**
- 버스 좌표는 TTL 만료 시 관제 조회에서 제외된다 — 보고를 멈춘 버스가 마지막 위치에 계속 표시되지 않는다(2026-08-21~).

### 7.2 알림 파이프라인

```
이벤트 감지 → dedup_key 계산 → 이미 발송됐나? → YES 무시 / NO 저장 + 발송
dedup_key = (유형 + 학생 + 대상일자 + 정류장/단계)
```

멱등은 **2단 방어**로 구현돼 있다 — ① 애플리케이션의 `existsByDedupKey` 선(先) 체크, ② `notification_log.dedup_key` **UNIQUE 제약**이 동시 틱 경쟁을 최종 차단(위반 예외는 삼키고 무시).

### 7.3 임계값 (문서·코드 공통 상수)

아래 값은 코드의 `NotificationThresholds` 상수로 **실제 존재하며 스케줄러가 참조한다.**

| 알림 | 임계 | 대상 | `NotificationType` | 구현 |
|---|---|---|---|---|
| 미승차 판정 | 정류소 도착 +**10분** | 학부모+관리자 | `NO_SHOW` | ✅ |
| 근접 알림 | 도착 예상 **5분 전** | 학생+학부모 | `APPROACH` | ✅ |
| SOS 에스컬레이션 | 관리자 미확인 **3분** | 플랫폼관리자 | `SOS` | ✅ |
| 위치 연결 끊김 | heartbeat 끊김 +**30초** | 관리자 | `CONNECTION_LOST` | ✅ |
| 승차/하차/인계 완료 | 즉시 | 학부모 | `BOARD_DONE`/`ALIGHT_DONE`/`HANDOVER_DONE` | ✅ |
| 시간변경 결과 | 처리 시 | 학부모 | `SCHEDULE_RESULT` | ✅ |
| 노선 추천·배포 | 처리 시 | 기사 | `ROUTE_RECOMMENDED`/`ROUTE_PUBLISHED` | ✅ |

**⬜ 정책상 목표값이나 미구현:** "GPS 단발 이상치 오탐을 막기 위해 위치 기반 판정은 **연속 N회(예: 3회) 관측**이 모두 조건을 만족할 때만 발송한다"는 규칙은 **코드에 없다.** 현재는 dedup_key 멱등만으로 중복을 막고 있어, 단발 이상치가 곧바로 판정으로 이어질 수 있다. 마찬가지로 **푸시 실패 시 지수 백오프 재시도**도 미구현이다(발송 실패 결과가 `NotificationLog`에 기록되지 않는다).

⚠ **흔한 오해:** 미승차를 매 틱 알리면 알림 폭탄이 된다. 같은 `dedup_key`가 재감지돼도 **1회만** 발송하는 것이 핵심이다. 스케줄러 주기(15초·30초)는 "얼마나 자주 다시 훑느냐"일 뿐 **임계값이 아니다** — 임계값은 10분·5분·3분이다.

## 8. 개인정보 · 위치정보 · 법

학생 사진·주소·연락처·위치는 민감 개인정보다. 수집목적·보유기간·접근권한을 설계 단계에서 확정해야 한다.

- **동의:** 학부모 수집·이용 동의 + 만 14세 미만 **법정대리인 동의** + 사진 별도 안내
- **보호:** 암호화, 계층별 접근권한, 조회·수정 이력, 캡처·다운로드 제한, 퇴사·노선변경 시 권한 즉시 회수
- **위치정보:** 차량 위치가 학생·기사와 연결되면 개인위치정보에 해당할 수 있어 위치정보사업 신고 여부에 대한 법률 검토가 필요하다. 보유기간 최대 1년.

**현재 구현 상태: 위 항목 전부 ⬜ 미구현.** 동의 UI·동의 저장 스키마·보유기간 정책·접근 이력(`AuditLog`)이 모두 없다.

⚠ **실서비스 전환 선행조건:** MVP(Mock)는 실 위치를 수집하지 않아 유예 가능하지만, **동의 UI와 저장 스키마는 실 GPS 전환 전에 반드시 구현해야 한다.** 미루면 Mock→실 GPS 전환이 법적으로 막힌다.

⚠ **흔한 오해 3건**
1. **"백엔드가 덜 됐다"가 아니다.** SOS·결석·일정변경·버스/학생/회원/학원 관리·승하차 정정은 **백엔드가 다 구현돼 있고 프론트 화면만 없다.** 남은 일의 성격은 "API 구현"이 아니라 "화면 구현"이다.
2. **관제는 실시간 push가 아니다.** STOMP 연결은 있지만 **알림 전용**이고, 버스 위치는 3초 REST 폴링이다.
3. **기사 앱이 보내는 좌표는 기본값이 가짜다.** 스위치를 켜면 노선 polyline을 따라 왕복하는 Mock 좌표(≈43km/h)가 서버로 전송된다. 다만 **출처 표기는 2026-08-21부터 정직하다** — 앱이 `origin` 을 실어 보내고 서버가 그대로 기록해, 관제 화면이 "단말/시뮬레이터"를 구분해 보여준다.

## 12. 미구현 · 갭 목록

11장의 매트릭스를 **"무엇이 안 되는가 / 사용자에게 어떤 결과인가 / 어디를 고쳐야 하는가"** 관점으로 재정리했다. 총 **28건** — 운영불가 5 · 기능누락 15 · 사소 8.

**2026-08-23 코드 실측 갱신.** 해소된 항목도 지우지 않고 `✅ 해소` 표기와 근거(파일:줄)를 남긴다 — 무엇이 왜 없어졌는지 추적하기 위함이다. 현재 상태는 **완전 해소 4건**(F8 · M2 · M3 · M7) · **부분 해소 5건**(O4 백엔드분 · F4 · F5 · F9 · F12) · 나머지 19건 미해소다. 12.4 의 백엔드 리스크는 7항목 중 3항목 완전 해소 · 3항목 부분 해소.

심각도 정의:
- **운영불가** — 이 상태로 서비스를 열면 해당 기능이 성립하지 않는다
- **기능누락** — 화면은 동작하나 기능·정확성에 구멍이 있다
- **사소** — 죽은 코드·하드코딩 등 품질 항목

### 12.1 운영불가 (5건)

**O1. 학생·학부모가 쓸 화면이 하나도 없다**
5계층 중 2계층이 로그인 직후 "준비 중" 배너에서 멈춘다. 자녀 위치·승하차 기록·알림함·결석 신고·시간 변경·SOS를 **앱에서 할 수 없다.** 서비스의 핵심 사용자가 서비스를 못 쓰는 상태다.
→ 고칠 곳: **프론트엔드 전용.** 백엔드 엔드포인트(`/me`·`/children` 계열)는 이미 다 구현돼 있다.

**O2. SOS 기능이 화면에 전혀 없다**
학생이 긴급 상황을 알릴 수단이 없고, 관리자가 확인·종료할 화면도 없다. 백엔드 6개 엔드포인트와 3분 에스컬레이션 스케줄러가 **아무도 호출하지 않는 상태로 돌고 있다.** 안전이 제품 가치의 중심인데 그 기능이 도달 불가하다.
→ 고칠 곳: 프론트 SOS 발신 화면(학생) + 관제 화면의 SOS 확인·종료 UI.

**O3. 결석 신고·시간 변경을 넣을 화면이 없다**
기사 명단 화면은 "결석 신고된 학생은 자동으로 빠진다"고 안내하지만, **신고를 넣는 화면도 승인하는 화면도 없다.** 결과적으로 명단 자동 제외 기능이 동작할 조건 자체가 만들어지지 않는다.
→ 고칠 곳: 프론트 학부모 신고 화면 + 관리자 승인·반려 화면.

**O4. 버스·학생·회원·학원을 등록할 화면이 없다**
관제 화면의 빈 상태 문구가 "버스 관리에서 버스를 먼저 등록하면…"이라고 안내하지만 **그 화면이 존재하지 않는다.** 프론트의 HTTP 클라이언트에는 `put`·`delete` 메서드조차 없고 쓰기 호출은 7종(로그인·재발급·위치보고·승하차·운행 시작/종료·배차)뿐이다. 데이터는 오직 **DB 시드나 Swagger로만** 들어간다.
→ 고칠 곳: 프론트 관리자 CRUD 화면 + HTTP 클라이언트에 쓰기 메서드 보강. **백엔드 수정·삭제 API 는 2026-08-23 실측 기준 대부분 해소**(→ F12) — 남은 것은 프론트뿐이다.

**O5. 기사 앱의 위치 출처 기본값이 Mock이다**
기사가 전송 스위치를 켜면 기본으로 **가상 좌표**가 서버에 저장되고, 관리자는 그것을 실제 위치로 본다. 실 GPS를 쓰려면 매번 수동 전환해야 한다. 또한 Mock 소스는 노선이 없으면 예외를 던져 **전송이 통째로 멈춘다.**
→ 고칠 곳: 기본값을 실 GPS로 바꾸고 Mock은 개발 빌드 플래그 뒤로. 노선 부재 시 폴백 경로 필요.

### 12.2 기능누락 (15건)

**F1. 기사에게 알림 화면이 없다** — 개인 큐(`/user/queue/notifications`) 구독 코드는 준비돼 있으나 이를 쓰는 화면이 없어 **도달 불가능한 코드**다. 노선 배포·미승차 알림이 기사에게 닿지 않는다. → 기사 셸에 알림 탭 추가.

**F2. 플랫폼관리자의 관제 화면이 다른 화면과 다른 학원을 본다** — 지도·목록은 **항상 1번 학원 고정**인데, 같은 화면의 상세 패널·노선 조회는 드롭다운 선택값을 따른다. 배차·노선 화면에서 다른 학원을 골라도 **관제 지도만 계속 1번 학원을 보여준다.** → 관제 화면도 공통 tenant 선택 상태를 쓰도록 통일.

**F3. "학원 1번" 폴백이 3곳에 중복 하드코딩** — 관제·공통 tenant·알림 세 군데에 같은 상수가 흩어져 있어 알림 화면도 플랫폼관리자면 무조건 1번 학원으로 고정된다. → 단일 출처로 합치기(F2와 같은 뿌리).

**F4. "현재 진행 중인 운행" 전용 API가 없다** — 🟡 **부분 해소**(2026-08-23, BG-7). 백엔드는 `status` 쿼리 파라미터를 받는다 — `GET /api/drive-sessions/bus/{busId}?status=IN_PROGRESS` 와 `GET /api/drive-sessions?status=IN_PROGRESS` 둘 다 서버가 걸러 준다(`DriveSessionController.java:104·118`, 생략 시 전체 이력을 주는 하위 호환 유지). **프론트는 아직 미전환** — 전체 이력을 받아 앱에서 고르는 코드가 그대로다(`frontend/lib/features/drivesession/data/drive_session_repository.dart:32` 주석이 "전용 엔드포인트가 없어서"라고 적힌 채 남아 있다). → 프론트 호출에 `status=IN_PROGRESS` 를 실어 보내는 것만 남음.

**F5. 승하차 기록 조회가 날짜 단위라 세션 구간을 클라이언트가 자른다** — 🟡 **부분 해소**(2026-08-23 실측으로 서술 정정). 버스별 조회와 기간 필터는 **이미 있다** — 전용 엔드포인트 `GET /api/ride-events/bus/{busId}?date=` 와 학원 목록의 `studentId`·`from`·`to` 파라미터(`RideEventController.java:106·121~131`)를 프론트가 실제로 쓴다(`frontend/lib/features/rideevent/data/ride_event_repository.dart:61~63`). "학원 전체를 받아 앱에서 버스별로 거른다"는 옛 서술은 현재 코드와 다르다. **남은 문제 2가지**: ① 조회 단위가 하루라 등원·하원이 한 응답에 섞여 오고 운행 세션 구간 분리가 클라이언트 몫이다(`frontend/lib/features/location/application/bus_operation_status.dart:137` 주석이 이 사정을 적어 둔다) ② 목록 조회 전반에 **페이지네이션이 없다**(백엔드 전체에 `Pageable` 사용처 0건). → 세션 범위 파라미터 추가 + 페이지네이션 도입.

**F6. 기사 노선 조회의 정렬을 서버가 보장하지 않는다** — 재배차로 version이 올라간 새 계획이 생겨도 서버는 방향으로만 정렬해 주므로 **앱이 직접 최신 version을 골라낸다.** 다른 클라이언트가 붙으면 옛 노선을 볼 수 있다. → 서버가 버스·방향별 최신 version만 반환하도록 수정.

**F7. 기록 시각에 타임존이 없어 절대 시각을 표시할 수 없다** — 서버가 `LocalDateTime`을 그대로 내려보내 9시간 어긋난다. 관제 화면은 "몇 초 전 갱신"을 **클라이언트 수신 시각으로 대체 계산**하고 있고, 서버가 실제로 기록한 시각은 화면에 쓸 수 없다. → API 응답을 타임존 포함 형식으로 전환.

**F8. 위치 출처(`origin`)가 실제와 다르다** — ✅ **해소**(2026-08-21, MON-2). 예정대로 보고 요청에 출처를 실어 보내고 서버가 그대로 저장한다. 기사 앱은 `LocationSourceKind` 토글값을 보내고, 생략한 요청은 `GPS` 로 간주해 구버전 클라이언트가 깨지지 않는다. ⚠ 단말 자기신고라 서버는 검증하지 않는다.

**F9. 버스 위치에 실시간 push가 없다** — 🟡 **부분 해소**(2026-08-23). 백엔드 push 경로는 완성됐다 — `BusLocationCommandService` 가 저장 후 `BusLocationUpdatedEvent` 를 발행하고(`BusLocationCommandService.java:57`), `BusLocationPushConsumer` 가 `/topic/tenant/{id}/bus-locations` 와 보호자 개인 큐 `/queue/bus-location` 으로 내보낸다(`BusLocationPushConsumer.java:41·43`). **프론트만 미전환** — 관제 화면은 여전히 3초 폴링이고(`frontend/lib/features/location/application/bus_monitor_controller.dart:93·164`), Flutter 코드 전체에 `bus-location` 구독이 0건이다. → 관제 화면을 STOMP 구독으로 교체.

**F10. 노선 계획 응답에 정류장 이름과 학원 좌표가 없다** — 화면이 **polyline의 첫 점을 학원으로 간주**하고, 운행 시작 전에는 정류장을 "N번 정차"로만 표시한다. 기사가 어디에 서는지 이름으로 알 수 없다. → 계획 응답에 정류장명·depot 좌표 포함.

**F11. 승하차 순서를 서버가 검증하지 않는다** — 승차 기록 없이 하차를 보내도 서버가 200을 준다. 앱이 버튼을 하나만 노출해 막고 있을 뿐이라 **다른 클라이언트나 직접 호출은 막히지 않는다.** → 서버에 순서·중복 검증 추가.

**F12. 마스터 데이터의 수정·삭제 API가 없다** — 🟡 **부분 해소**(2026-08-23, BE-13·BE-14). 구성원 수정·비밀번호 재설정·삭제(`MemberController.java:100·116·135`), 학생 수정·퇴원·재배정·하차지 변경(`StudentController.java:95·111·122·135`), 보호자 연결 해제(`StudentController.java:162`), 버스 담당자 재배정(`BusController.java:116`)이 모두 생겼다. **남은 것 2가지**: ① 배정 해제 표현은 여전히 부재 — `UpdateStudentAssignmentRequest` 의 `assignedBusId`·`boardingStopId` 를 null 로 보내면 "변경 없음"으로 해석된다(`StudentCommandService.java:104·108` 이 `!= null` 일 때만 갱신) ② 버스 자체의 삭제 엔드포인트 부재. → 명시적 해제 표현(예: 별도 해제 엔드포인트)과 버스 삭제 추가.

**F13. 승하차 기록 정정을 앱에서 할 수 없다** — 백엔드 정정 API는 있으나 프론트가 호출하지 않아, 기사가 잘못 기록하면 **되돌릴 방법이 전혀 없다**("되돌릴 수 없다"고 안내만 한다). → 명단 화면에 정정 UI 추가.

**F14. 노선 계획의 개별 승인·배포·수동 생성 UI가 없다** — 프론트는 자동배차 제안 + 확정 경로만 쓴다. 확정 한 번에 승인·배포가 함께 일어나므로 **"승인은 하되 배포는 나중에" 같은 운영 판단을 할 수 없다.** → 노선 상세 화면에 승인·배포 액션 추가.

**F15. 계정을 만들 경로가 앱 안에 전혀 없다** — 회원가입 화면을 두지 않은 것은 "계정은 관리자가 생성한다"는 의도적 결정인데, **그 관리자용 생성 화면도 없다.** 결과적으로 어느 쪽으로도 계정을 만들 수 없다. → O4와 함께 해결.

### 12.4 백엔드 측 리스크 (프론트 갭과 별개)

화면 유무와 무관하게 **API 자체에 남아 있는 문제**다. 학생·학부모 앱을 붙이기 전에 처리해야 한다.
**아래는 2026-08-23 코드 실측 갱신본이다** — 7항목 중 3항목 완전 해소 · 3항목 부분 해소 · 1항목 재분류.

- **권한 상승 가능:** ✅ **해소**(BE-11, 커밋 `2a60a18`). `AuthCommandService` 가 `ATTENDANT`·`ACADEMY_ADMIN`·`PLATFORM_ADMIN` 을 `ADMIN_GRANTED_ROLES` 로 묶어 self-signup 요청이면 403 으로 거부한다(`AuthCommandService.java:44~52`). ⚠ **남은 것**: 회원가입 자체는 여전히 인증 없이 열려 있고(`SecurityConfig.java:68` 의 `/api/auth/**` permitAll), 요청 body 의 `tenantId` 를 승인 절차 없이 그대로 쓴다 → **아무나 임의의 학원에 `STUDENT`·`PARENT`·`DRIVER` 로 가입할 수 있다.** 권한 상승은 막혔지만 무단 소속은 남았다.
- **테넌트 격리 누락 1건:** ✅ **해소**(2026-08-23). `RouteQueryService.getStops(AuthUser, Long)` 가 노선 소유 학원과 요청자를 대조해 다른 학원이면 403 을 던진다(`RouteQueryService.java:48~57`). 재발 방지는 `ControllerAuthorizationConventionTest` 의 등록제 예외 목록 — 인가 애너테이션 없는 매핑은 `METHOD_LEVEL_EXEMPT` 에 근거와 함께 적어야 통과한다.
- **WebSocket 역할 검사 누락:** 🟡 **재분류**(2026-08-23). 역할 애너테이션이 없는 것은 그대로다 — `@MessageMapping` 은 `@Can*` 인가 체계가 닿지 않는 통로이고, 인가는 CONNECT 시 1회 인증된 `Principal` 로 이루어진다. 다만 서비스 계층이 스코프를 자기 자신으로 고정한다 — `LocationCommandService.reportSelf` 가 `principal.userId()` 로만 자기 `Student` 레코드를 조회해(`LocationCommandService.java:53~58`) 남의 데이터에 닿을 경로가 없다. 이 예외는 근거와 함께 `METHOD_LEVEL_EXEMPT` 에 등록돼 있다.
- **정정 권한이 넓다:** ✅ **해소**(2026-08-23). `requireCorrectionPermission` 이 플랫폼관리자 · 해당 학원 관리자 · **그 기록이 난 버스의 담당 선탑자 본인** 세 경우만 통과시킨다(`RideEventCommandService.java:117~128`). "같은 학원이면 담당 아닌 버스도 정정" 경로는 사라졌다.
- **참조 무결성 미검증:** 🟡 **부분 해소**(BE-7). 버스 담당자 지정은 `loadUserWithRole(userId, tenantId, Role.DRIVER)` 로 **역할·소속을 둘 다** 검사하고(`BusCommandService.java:138~149`), 보호자 연결도 같은 방식이다(`StudentCommandService.java:222~231`). ⚠ **남은 것**: 학생 등록의 연결 계정은 여전히 **존재 확인이 없다** — `req.userId()` 를 그대로 엔티티에 넣는다(`StudentCommandService.java:82`).
- **입력 검증 느슨:** 🟡 **부분 해소**(2026-08-23). 비밀번호는 가입·구성원 생성·재설정 3경로 모두 `@Size(min = 8)` 이 붙었다(`SignupRequest.java:17` · `CreateMemberRequest.java:18` · `ResetPasswordRequest.java:14`). ⚠ **남은 것**: 좌표 위경도 범위 검증 부재 — `LocationReportRequest` 의 `lat`·`lng` 에 `@NotNull` 뿐이고 백엔드 전체에 `@DecimalMin`·`@DecimalMax` 사용처가 0건이다.
- **성능:** 🟡 **부분 해소**(2026-08-23). N+1 은 두 목록 모두 제거됐다 — 노선은 count 쿼리 한 번(`RouteQueryService.assignedCount` → `countByAssignedBus_Route_IdAndActiveTrue`), 버스는 배정 학생을 `IN` 조회 한 번으로 읽어 버스별로 접는다(`BusQueryService.java:52~54`). 조회 인덱스도 `V6__add_lookup_indexes.sql` 로 14종 추가(`tenant_id` 복합·FK 컬럼). ⚠ **남은 것**: 페이지네이션 부재 — 백엔드 전체에 `Pageable` 사용처가 0건이다.
