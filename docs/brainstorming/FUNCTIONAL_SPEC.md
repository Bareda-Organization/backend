## 1. 서비스 개요

### 1.1 목적

학원 통학버스의 **노선 편성 → 학생 승하차 → 학부모 안내 → 차량 및 운행인력 관리**를 하나의 시스템으로 통합하여 운영의 안전성과 효율성을 높인다.

### 1.2 제품 구성

| # | 제품 | 플랫폼 | 유저 타입 | 기본 테마 | 뷰포트 |
|---|---|---|---|---|---|
| 1 | 학부모·학생 앱 | 모바일 | 학부모, 학생 | Light | 390 × 844 |
| 2 | 매니저 앱 | 모바일 | 버스기사, 버스 인솔자 | Dark | 390 × 844 |
| 3 | 관계자 웹 | 웹 | 학원 관계자 | Light | 1440 / 1120 |
| 4 | **메인 관리자 콘솔** | 웹 | **운영사 관리자** | Light | 1440 |

메인 관리자 콘솔은 학원 자체를 등록·관리하고 학원 관계자 계정을 발급하는 **내부 도구**다. 관계자 웹과 접근 경로를 분리한다.

**운행모드만 예외** — 테마 설정과 무관하게 **항상 어둡게** 표시한다.

### 1.3 유저 타입

| 유저 | 소속 제품 | 핵심 목적 |
|---|---|---|
| 학부모 | 학부모·학생 앱 | 자녀 승하차 확인, 탑승 위치·여부 관리 |
| 학생 | 학부모·학생 앱 | 버스 위치·도착 확인 |
| 버스기사 | 매니저 앱 | 당일 노선·명단 확인, 운행모드 |
| 버스 인솔자 | 매니저 앱 | 개인별 승하차 관리 |
| 학원 관계자 | 관계자 웹 | 명단·노선·인력 관리 (데이터 원본) |
| **메인 관리자** | 메인 관리자 콘솔 | 학원 등록·관리, 학원 관계자 계정 발급 |

## 2. 도메인 모델

### 2.1 노선 개념 정의 ★

두 개념은 명확히 다르다. 구현 시 **다른 테이블**로 봐야 한다.

| 개념 | 정의 | 갱신 주기 |
|---|---|---|
| **노선** (`Route`) | 변경 사항이 반영되지 않은 **기본 노선** | 학기/연초 단위, 관리자 수동 |
| **확정 노선** (`ConfirmedRoute`) | **전날 등원을 표시한 학생들의 주소 + 승차 위치 변경 학생**을 기점으로 산출한 노선 | 매 회차, 출발 **1시간 전** |

> 비유하자면 `Route`는 시간표이고 `ConfirmedRoute`는 오늘 실제로 도는 코스다. 시간표는 학기 내내 그대로지만, 오늘 누가 안 오는지에 따라 코스는 매일 달라진다.

### 2.2 엔티티

| 엔티티 | 설명 |
| --- | --- |
| `Academy` | 학원. **학원 코드 + 학원명** 보유. **메인 관리자가 사전 등록** |
| `AcademyAdmin` | 학원 관계자 계정. **메인 관리자가 생성** |
| `SystemAdmin` | **메인 관리자(운영사)** 계정 |
| `Student` | 학생 |
| `Guardian` | 보호자 계정. **한 계정에 자녀 N명을 연결**한다 (C-27) |
| `GuardianStudent` | **보호자 ↔ 학생 연결 테이블** (신규). `Guardian` 에 `student_id` 를 직접 박지 않는다 |
| `Manager` | 운행인력. 역할 = 버스기사 / 인솔자 |
| `Bus` | 호차 |

### 2.3 탑승 상태 (`RunRider.status`)

| 코드 | 라벨 | 색 토큰 | 변경 주체 | 의미 |
|---|---|---|---|---|
| `waiting` | 대기 | `--status-idle` | (초기값) | 명단에 있으나 아직 처리 전 |
| `boarded` | 탑승 완료 | `--status-boarded` | 인솔자 / 자동(하원) | 버스에 탑승함 |
| `alighted` | 하차 완료 | `--status-boarded` | 인솔자 / 자동(등원) | 목적지에서 내림 |
| `absent` | **미등원** | `--status-idle` | 시스템 (학부모 설정 결과) | 학부모가 **사전에** 탑승을 끔 |
| `no_show` | **미승차** | `--status-missed` | 인솔자 | 예정된 학생이 정류장에 **나오지 않음** |

```
waiting ──► boarded ──► alighted
   └─────► no_show (종결, 미승차 알림 발송)

absent  ── 확정 노선 산출 시점에 부여. 기사·인솔자 명단에서 제외 (회색 표시 아님)
```

**`absent` 학생은 기사·인솔자 명단에서 제외한다 (확정).** 회색 표시로 남겨두지 않는다.
운행 중인 기사에게 "오늘 안 타는 아이"를 계속 보여주면 정류장별 탑승 인원 수를 눈으로 세는 순간 실제 인원과 어긋나고,
`absent`와 `no_show`가 시각적으로 비슷하게 보여 **미승차를 못 알아채는 위험**이 생긴다.
단 **명단 집계(RST-04)에는 `미등원 N명`으로 숫자만 남긴다** — 명단에서 빠지는 것은 개인 행(row)이지 집계가 아니다.
관계자 웹의 호차별 일일 명단(RST-03)에서는 🔴 빨강으로 계속 보인다 — 관리자는 "누가 왜 빠졌는지"를 봐야 하기 때문이다.

**`absent`와 `no_show`는 반드시 구분한다.** 전자는 학부모가 미리 알린 정상 상황이라 학부모 알림을 보내지 않고 관계자에게만 통지한다. 후자는 예정된 아이가 나오지 않은 이상 상황이라 학부모에게 즉시 알리고 대기·에스컬레이션 절차가 시작된다. 하나의 상태로 묶으면 정상 결석에도 경보가 울린다.

### 2.4 운행 상태 (`Run.status`)

| 코드 | 라벨 | 전이 조건 |
|---|---|---|
| `idle` | 운행 전 | 초기 |
| `confirmed` | 노선 확정 | 출발 1시간 전 배치 |
| `moving` | 운행 중 | 기사가 운행모드 시작 |
| `finished` | 운행 종료 | 기사가 **운행 종료하기** 클릭 |

### 2.5 변경 구분 (`RunRider.change` / `Stop.change`)

| 코드 | 표기 | 의미 | 적용 대상 |
|---|---|---|---|
| `added` | 🟢 초록 하이라이트 | 당일 추가된 탑승자/정류장 | 탑승자, 정류장 |
| `removed` | 🔴 빨강 하이라이트 | 당일 삭제된 탑승자 | 탑승자 |
| `skipped` | 🔴 빨강 + 취소선 | **미경유 정류장** — 잔여 탑승자 0명이 되어 들르지 않음 | 정류장 |

`skipped` 정류장은 목록에서 **제거하지 않고 취소선으로 남긴다.** 기사가 "여기는 원래 들렀는데 오늘은 안 든다"를 인지해야 하기 때문이다. 순서 번호도 재부여하지 않는다.

## 3. 인증 · 계정 (전면 개정) ★

### 3.1 개정 배경

디자인에는 6자리 `CodeInput` 로그인이 구현돼 있으나, **form 회원가입/로그인으로 확정**됐다. 학원 코드는 로그인 수단이 아니라 **소속 학원을 특정하는 식별자**로 역할이 바뀐다.

**학원 코드는 학원이 배포하지 않는다.** 메인 관리자가 학원을 사전 등록해 두고, 사용자는 회원가입 과정에서 **등록된 학원 목록에서 검색·선택**한다. 코드를 종이로 나눠주고 사용자가 옮겨 적는 단계가 사라진다.

### 3.2 회원가입 플로우

| 단계 | 행위자 | 내용 |
|---|---|---|
| 1 | 사용자 | 회원가입 폼 입력 (아이디/비밀번호 등) |
| 2 | 사용자 | **소속 학원 선택** — 학원 코드 또는 학원명으로 검색 후 목록에서 선택 |
| 3 | 시스템 | 선택된 `Academy`에 `SignupRequest` 생성 → 해당 학원 관계자에게 전달 |
| 4 | 관계자 | 관계자 웹에서 **수락 / 거절** |
| 5 | 시스템 | 수락 시 계정 활성화, 학생·학부모 레코드와 연결 |
| 6 | 사용자 | 로그인 가능 |

**학원 선택 UI 요건**

| 항목 | 내용 |
|---|---|
| 검색 대상 | 메인 관리자가 등록한 `Academy` 목록 — **학원 코드 + 학원명** 양쪽으로 검색 |
| **결과 표기** | **`{학원명} · {지역} · {학원 코드}`** — 세 값을 모두 노출 |
| 입력 방식 | 자유 입력이 아니라 **검색 → 선택**. 오탈자로 인한 미매칭을 원천 차단 |
| 선택 확인 | 선택 후 확정 전에 **학원명 + 지역 + 학원 코드**를 다시 보여주고 확인받는다 |
| 미등록 학원 | "학원을 찾을 수 없습니다 — 학원에 문의해 주세요" 안내. 사용자가 학원을 만들 수 없음 |
| 비활성 학원 | 검색 결과에서 제외 |

**표기 예시**

```
┌──────────────────────────────────────────┐
│ 한빛학원                                  │
│ 서울 강남구 · HB-1024                     │
├──────────────────────────────────────────┤
│ 한빛학원                                  │
│ 경기 성남시 분당구 · HB-2087              │
└──────────────────────────────────────────┘
```

학원명이 같아도 **지역과 코드로 구분**된다. 학원이 학부모에게 "우리 코드는 HB-1024예요"라고 안내하면 그 값이 화면에 그대로 보이므로 확인이 즉시 된다.

### 3.2.1 승인 대기 상태 — 접근 범위 (C-28 확정)

가입은 끝났지만 관계자가 아직 수락하지 않은 상태다. **이 계정이 볼 수 있는 것은 대기 안내 화면 하나뿐이다.**

| 구분 | 허용 |
|---|---|
| 로그인 | **성공한다** — 인증은 통과한다 |
| 볼 수 있는 화면 | **승인 대기 안내 화면 (`CM-S04`) 하나** |
| 그 화면에 있는 것 | 신청한 **학원명·지역·학원 코드**, 신청 일시, 현재 상태, **학원 문의처**, `로그아웃` |
| 볼 수 없는 것 | 홈·명단·노선·실시간 위치·알림 목록·설정 — **전부** |
| 수신하는 알림 | **승인 / 거절 결과 알림만.** 운행 관련 알림은 대상이 아니다 |

**서버 측 강제 (화면 숨김만으로는 부족하다)**

| 항목 | 규칙 |
|---|---|
| 계정 상태 | `PENDING` / `ACTIVE` / `REJECTED` / `BLOCKED` |
| 토큰 | `PENDING` 상태에도 **토큰은 발급한다** (대기 화면 조회에 필요) |
| API 접근 | 대기 화면 조회·로그아웃을 **제외한 모든 API가 403** |
| 판정 위치 | 화면 라우팅이 아니라 **서버 인가 계층**에서 막는다 |

> **⚠ 여기가 가장 흔한 보안 사고 지점**: 프론트에서 라우팅만 막고 API를 열어두면,
> **토큰만 들고 명단 API를 직접 호출하는 것으로 남의 학원 학생 명단이 통째로 빠져나간다.**
> 화면을 감추는 것은 UX이고, 막는 것은 서버의 일이다. 이 둘을 같은 것으로 취급하면 안 된다.

**거절된 경우**

| 항목 | 처리 |
|---|---|
| 화면 | 같은 자리에 **거절 사유**를 표시한다 |
| 재신청 | 대기 화면에서 **재신청 진입점**을 제공한다 — **학원을 다시 고를 수 있어야 한다** |
| 이유 | 학원을 잘못 선택한 경우가 거절 사유의 상당수인데, 재신청 경로가 없으면 계정을 버리고 새로 가입하는 수밖에 없다 |

---

### 3.3 로그인 보안 요건

| ID | 요건 |
| --- | --- |
| AUTH-01 | 로그인 시도 횟수 제한 — **약 5회** |
| AUTH-02 | 제한 초과 시 **해당 계정을 차단**한다. IP 단위 차단은 하지 않는다 — 학원 와이파이나 한 가정의 공용 회선에서 무고한 사용자까지 잠기기 때문이다 |
| AUTH-03 | 차단 해제는 **메인 관리자**가 수행 |
| AUTH-04 | 학원 코드는 **메인 관리자가 사전 등록**하며, 사용자는 목록에서 선택만 한다 |

### 3.4 역할별 가입 경로

| 역할 | 가입 경로 | 승인·생성 주체 |
|---|---|---|
| 학부모 | form 가입 + 학원 선택 | 학원 관계자 승인 |
| 학생 | form 가입 + 학원 선택 | 학원 관계자 승인 |
| 버스기사 | form 가입 + 학원 선택 | 학원 관계자 승인 |
| 인솔자 | form 가입 + 학원 선택 | 학원 관계자 승인 |
| **학원 관계자** | **가입 불가 — 메인 관리자가 계정을 생성해 전달** | **메인 관리자** |
| **메인 관리자** | 내부 발급 | 운영사 |

> **초보자가 놓치기 쉬운 지점**: 여기서 **인증(Authentication)과 인가(Authorization)가 분리**된다. 학원 선택은 "이 사람이 우리 학원 소속이라고 주장한다"까지만 처리하고, 실제 신원 확인은 관계자 승인 단계가 담당한다. 회원가입이 끝나도 승인 전까지는 아무 데이터에도 접근할 수 없어야 한다 — 가입 완료와 이용 가능을 같은 것으로 구현하면 미승인 계정이 명단을 조회하는 사고가 난다. **접근 범위의 구체적 규칙은 §3.2.1에 있다.**

### 3.5 계정 생성 책임 체계

```
메인 관리자 (운영사)
   ├─► 학원(Academy) 등록  ──────► 학원 코드·학원명 생성
   └─► 학원 관계자 계정 생성 ──────► 학원에 계정 정보 전달
                                        │
                                        ▼
                              학원 관계자 (관계자 웹)
                                        │
                                        └─► 학부모·학생·기사·인솔자 가입 요청 승인
```

3단계 위임 구조다. 메인 관리자는 학원까지만 만들고, 그 안의 사용자는 학원 관계자가 관리한다.

## 4. 시간 정책 ★

이 서비스에서 가장 많은 버그가 나올 영역이다. 표로 못 박는다.

### 4.1 노선 확정

| 항목 | 정책 | 비고 |
|---|---|---|
| 확정 기준 시점 | **노선 출발 1시간 전** | 기존 "밤 12시 기준" / "30분 전" 모두 폐기 |
| 확정 대상 | 전날 등원 표시 학생 주소 + 승차 위치 변경 반영 | `ConfirmedRoute` 생성 |
| **배치 지연 시 기준값** | **실행 시점의 최신 탑승 의사를 읽는다** (확정) | 60분 전 스냅샷을 쓰지 않는다 |
| 확정 후 표시 | 추가·변경 노선은 하이라이트 | 🟢 추가 / 🔴 삭제 |

**배치가 늦게 돌면 무엇을 읽는가 — "실행 시점 최신값" (확정)**

배치 잡은 출발 60분 전에 도는 것이 원칙이지만, 큐 적체·재시작 등으로 55분 전에 실행될 수 있다.
이때 **60분 전 상태를 복원해 쓰지 않고, 배치가 실제로 도는 그 순간의 최신 탑승 의사를 읽는다.**

| 항목 | 처리 |
|---|---|
| 읽는 값 | **배치 실행 시각 기준 최신 `BoardingIntent` + 승인된 위치 변경** |
| 60분 전 스냅샷 | **만들지 않는다** |
| 구간 판정 기준 | 여전히 **출발 시각 - 60분**이라는 시계 기준이다 (배치 실행 시각이 아니다) |
| 지연 실행 로그 | 실행 지연 시간을 기록해 관계자가 원인을 추적할 수 있게 한다 |

> **왜 스냅샷을 쓰지 않는가** — 스냅샷을 쓰면 "60분 전 ~ 배치 실행 시각" 사이에 승인된 삭제가 확정 노선에
> 반영되지 않아, **안 타는 아이를 태우러 가는 경로**가 그대로 배포된다. 최신값을 읽으면 그 구간의 변경이
> 자연히 흡수된다.
>
> **⚠ 초보자가 놓치기 쉬운 지점**: "최신값을 읽는다"와 "구간 판정 기준"은 별개다.
> 배치가 55분 전에 돌았다고 해서 **추가 마감이 55분 전으로 밀리지 않는다.** 추가·삭제 가능 여부는
> 언제나 `출발 시각 - 60분`이라는 **시계**로 판정하고, 배치는 그 판정 결과를 읽어 노선을 만들 뿐이다.
> 이 둘을 한 값으로 합치면 배치가 늦은 날에만 추가가 되는 비결정적 동작이 나온다.

### 4.2 노선 변경 기준 ★★ (확정)

**세 구간으로 나뉜다. 구간마다 "무엇이 가능한지"가 다르다.**

| 구간 | 시점 | **추가** | **삭제** | 노선 최적화 |
|---|---|:-:|:-:|---|
| ① | 출발 **60분 이전** | ● 가능 | ● 가능 | 변경분 반영해 재최적화 |
| ② | 출발 **59분 59초 ~ 운행모드 시작 전** | **✕ 불가** | **● 가능** | **재최적화 없음** |
| ③ | **운행모드 시작 이후** (운행 중) | ✕ 불가 | ✕ 불가 | — |

**핵심 규칙 3줄**

1. **추가는 60분 전까지만.** 60분을 넘기면 어떤 경로로도 탑승자를 넣을 수 없다.
2. **삭제는 운행 시작 전까지 언제나 가능하다.** 60분 이내여도 막지 않는다.
3. **운행모드를 누르는 순간 전부 잠긴다.**

> 왜 삭제만 열어두는가 — 추가는 노선을 늘리므로 다른 학생의 도착 시각에 영향을 준다. 반면 삭제는 노선을 줄이기만 하므로 다른 학생이 손해 볼 일이 없다. **비대칭 정책은 의도된 것**이다.

### 4.3 "삭제"의 의미 — 인원 삭제 vs 정류장 삭제 ★

삭제 요청이 들어왔을 때 무엇이 지워지는지는 **그 정류장에 남는 인원 수**로 결정된다.

| 조건 | 결과 | 노선 영향 |
|---|---|---|
| 해당 정류장에 **다른 탑승자가 남아 있음** | **해당 인원만 명단에서 삭제** | 없음 — 정류장은 그대로 경유 |
| 해당 정류장에 **그 학생 혼자** | **정류장 자체 삭제** → **미경유** | 해당 정류장 스킵 |

**판정 시점**: 삭제 처리 시마다 해당 정류장의 잔여 탑승자 수를 재계산한다. 즉 3명 중 3명이 순차로 빠지면 마지막 삭제 시점에 정류장이 미경유로 전환된다.

### 4.4 미경유 정류장 처리 ★ (확정)

| 항목 | 정책 |
|---|---|
| **노선 재최적화** | **진행하지 않는다** |
| **주행 경로** | **기사가 판단하여 최단거리로 패스** |
| 시스템 역할 | 미경유 정류장을 화면에 🔴 표시하고, 다음 경유 정류장을 안내하는 것까지 |
| 마지막 정류장인 경우 | 동일 — 패스 |

이 정책의 배경은 명확하다. 출발 60분 이내에 노선을 다시 계산해 기사 단말에 재배포하면, 기사가 이미 머릿속에 넣은 경로와 달라져 오히려 위험하다. **"이 정류장은 안 들러도 된다"만 알려주고 실제 주행 판단은 기사에게 맡기는 것**이 안전하다.

**구현 시 주의**: 미경유가 발생해도 `ConfirmedRoute`의 정류장 순서·ETA는 **재계산하지 않는다.** 미경유 정류장에 `skipped` 플래그만 세운다. 뒤 정류장 도착 시각이 실제로는 앞당겨지겠지만, 시스템은 그걸 예측해 알리지 않는다.

### 4.5 관리자 개입 범위

| 구간 | 관리자 확인 | 처리 |
|---|---|---|
| ① 60분 이전 | **불필요** | 추가·삭제 모두 검증 통과 시 즉시 반영 |
| ② 60분 이내 삭제 | **필수** | 관계자 승인 후 반영 (AW-15) |
| ② 60분 이내 추가 | — | 경로 자체가 없음 (불가) |
| ③ 운행 중 | — | 변경 불가 |

**60분 이내 삭제에 승인을 요구하는 이유** — 출발이 임박한 시점의 삭제는 정류장 미경유로 이어져 기사의 주행 경로를 바꾼다. 이미 확정 노선이 배포된 뒤라 관리자가 영향을 확인하고 판단해야 한다.

**승인 화면 요건**: 출발까지 남은 시간이 짧으므로 관계자가 늦게 확인하면 승인 자체가 무의미해진다. 목록 배지가 아니라 **푸시로 즉시 통지**하고, 승인 화면에 **남은 시간을 카운트다운으로 노출**한다.

### 4.6 책임 소재

> 1시간 이내 변경 건은 **학원 관리자가 직접 확인**하여 기존 노선 대비 변경되는 **시각과 거리**를 보고 판단한다. **책임 소재는 관리자에게 있다.**

따라서 관리자 승인 화면에는 반드시 다음이 표시돼야 한다.

| 표시 항목 | 이유 |
|---|---|
| 변경 전/후 예상 도착 시각 | 다른 학생 지연 영향 판단 |
| 변경 전/후 총 운행 거리 | 물리적 실현 가능성 판단 |
| 영향받는 학생 수 | 파급 범위 판단 |
| 정원 초과 여부 | 승인 차단 조건 |

**삭제 항목 상세**

|---|---|

| 실시간 운행정보 상세 내역 | 홈 카드 하단부 |

> 학부모에게 다른 학생의 탑승 인원을 보여주지 않는 것은 개인정보 관점에서도 맞다. "학부모에게는 전체 노선이나 다른 학생의 위치정보를 제공하지 않는다"는 원칙과 같은 방향이다.

**다자녀 처리 — 한 계정에 자녀 N명 (C-27 확정)**

자녀마다 계정을 만들어 묶는 방식은 쓰지 않는다. 학부모는 **계정 하나로 로그인**하고, 그 계정에 자녀가 N명 연결된다.

| 항목 | 규칙 |
|---|---|
| 데이터 구조 | `Guardian` 1 : N `Student` — **`GuardianStudent` 연결 테이블**로 표현 |
| 자녀 선택 UI | 자녀가 **2명 이상일 때만** 홈 상단에 노출. 1명이면 숨긴다 |
| 화면 전환 범위 | 선택된 자녀 기준으로 **실시간 운행 정보 · 상세 노선 · 지도 · 탑승 토글 · 위치 변경**이 모두 전환된다 |
| 자녀별 독립성 | 자녀마다 **호차·노선·정류장·탑승 여부가 각각 다르다.** 형제라도 같은 버스라는 보장이 없다 |
| 자녀 추가 | 동생이 새로 등록되면 관계자가 **기존 계정에 연결만 추가**한다. 학부모가 다시 가입할 필요 없음 (AUTH-11) |
| 연결 해제 | 퇴원 시 연결을 끊되 과거 이력은 보존한다 |

> **⚠ 가장 흔한 구현 실수 — 알림을 자녀 선택에 종속시키는 것.**
> 화면은 선택된 자녀 기준으로 바뀌지만, **알림은 선택과 무관하게 연결된 모든 자녀의 것을 전부 받아야 한다.**
> 첫째 화면을 보고 있는데 둘째의 미승차 알림이 안 오면 그게 바로 이 서비스가 막으려던 사고다.
> 그래서 **모든 알림 문구에는 자녀 이름이 반드시 들어가야 한다** — "OO가 승차했습니다"이지 "승차했습니다"가 아니다.

### PA-04. 등하원별 버스 탑승 여부 ★ 신규

**요구 배경**: 학부모가 "등원은 버스를 타지만 하원은 안 탄다"를 표시할 수 있어야 한다.

**설계 결정**

| 질문 | 결정 |
|---|---|
| 등하원을 별도로 관리하는가? | **아니다.** 등하원이 아니라 **버스 탑승 여부**로 결정한다 |
| 구현 방식 | 예정된 노선 중 **빠른 노선(등원) off / 늦은 노선(하원) on** |
| 버스로 등하원하지 않는 케이스도 관리하는가? | **관리하지 않는다** |

**화면 명세**

| 항목 | 내용 |
|---|---|
| 위치 | 홈 — **기존 미등원 드롭다운 자리에서 위치 변경** |
| 컨트롤 | 회차별 `Switch` 2개 |
| 라벨 | `등원 (8:30 출발)` / `하원 (20:00 출발)` |
| 기본값 | 둘 다 ON |
| 저장 | 즉시 저장 + 토스트 피드백 |
| 변경 마감 | §4.2 3단계 규칙 적용 |

**연동 효과**

| 토글 | 결과 |
|---|---|
| 등원 OFF | 해당 회차 `RunRider` 제외 → 확정 노선에서 해당 정류장 승차 인원 감소 |
| 정류장 승차 인원 0명 | **해당 정류장 패스** (운행 중 변경 시에도 적용) |
| 관계자 | 등원 여부 알림 수신 |

**다자녀 처리**: 계정에 연결된 자녀별로 토글이 독립 존재한다. 자녀 선택 → 회차 토글 구조.

### PA-05. 탑승 위치 변경 신청

**입력 폼** (디자인 구현 유지)

| 필드 | 컴포넌트 | 필수 |
|---|---|:-:|
| 변경할 요일 | `Select` | ● |
| 탑승 정류장 | `Select` | ● |
| 변경 위치 상세 주소 | `Input` | ● |
| 변경 사유 | `Input` | ○ |

**처리 정책 — §4.2 구간 규칙 적용**

| 신청 시점 | 위치 변경(=삭제+추가) | 탑승 취소(=삭제만) | 화면 안내 |
|---|:-:|:-:|---|
| 출발 **60분 이전** | ● 가능 | ● 가능 | "변경 사항이 반영됩니다" |
| **60분 이내 ~ 운행 시작 전** | **✕ 불가** | **● 가능** | "지금은 탑승 취소만 가능합니다. 위치 변경은 학원으로 연락해 주세요." |
| **운행 시작 이후** | ✕ 불가 | ✕ 불가 | 버튼 비활성 + "운행이 시작되어 변경할 수 없습니다" |

> **위치 변경은 내부적으로 삭제 + 추가다.** 추가가 막히는 60분 이내 구간에서는 위치 변경 자체가 불가능해진다. 화면에서 "탑승 취소"와 "위치 변경"을 별개 버튼으로 분리해야 이 차이가 사용자에게 전달된다.

**신청 상태 표시** (신규 필요)

| 상태 | 학부모 화면 표기 |
|---|---|
| `pending` | 신청 완료 · 학원 확인 중 |
| `approved` | 반영 완료 |
| `rejected` | 거절 — 사유 표시 |

> v0.1의 최우선 이슈였던 "승인 플로우 부재"가 해소됐다. 관리자 승인 화면(AW-15)과 학부모 상태 표시가 함께 구현돼야 한다.

| 되돌리기 | 오조작 취소 기능 필요 + 취소·수정 이력 보존 |

**연쇄 효과**

| 상태 변경 | 학부모 앱 | 관계자 웹 | 알림 로그 |
|---|---|---|---|
| → `boarded` | 승차 알림 푸시 | 실시간 현황 갱신 | 승차 |
| → `alighted` | 하차 알림 푸시 | 실시간 현황 갱신 | 하차 |
| → `no_show` (미승차) | **미승차 알림 즉시 푸시** | 미승차 카운트 +1 + **에스컬레이션 시작** | 미승차 |
| → `absent` (미등원) | **푸시 없음** — 학부모가 스스로 설정한 값이다 | 미등원 카운트 +1 | 미등원 |

> `absent`에 학부모 알림을 보내면 **자기가 끈 것을 자기가 다시 통보받는다.** 관계자에게만 통지한다.

**미승차 대기 · 에스컬레이션 (EXC-01) — 기본 대기 3분 (확정)**

| 시점 | 처리 |
|---|---|
| T+0 | 인솔자가 `미승차` 선택 → **학부모에게 즉시 알림** + 관계자 동시 통지 → **대기 타이머 시작** |
| T+0 ~ 3분 | 대기. 학부모 응답(전화·앱)이 오면 타이머 중단하고 현장 판단으로 처리 |
| 대기 중 | 무응답이면 **보호자에게 전화 시도**, 시도 기록 저장 |
| **T+3분** | 무응답 확정 → **관계자에게 에스컬레이션 보고** → 관계자 판단에 따라 출발 |

| 항목 | 값 |
|---|---|
| **기본 대기 시간** | **3분** |
| 설정 단위 | **학원별 설정값** — 3분은 기본치이며 학원이 조정할 수 있다 |
| 무응답 판정 | **대기 시간과 동일한 창을 쓴다.** 3분 안에 응답이 없으면 무응답 |
| 타이머 표시 | 인솔자 화면에 **남은 시간 카운트다운** 노출 |
| 기록 | 대기 시작·종료 시각, 연락 시도 이력, 최종 판단(출발/재시도)을 저장 |

> **왜 3분인가** — 정류장당 3분이 넘어가면 뒤 정류장 도착 시각이 눈에 띄게 밀리고, 그 지연이 나머지 전 구간에 누적된다.
> 반대로 1분은 아이가 엘리베이터에서 내려오는 시간도 안 된다. **한 아이를 기다리는 시간과 나머지 전원의 지연을 맞바꾸는 값**이라
> 현장에서 가장 민감하며, 그래서 학원별로 조정 가능하게 둔다.

**오프라인 큐잉 (필수)**: 통신 두절 시에도 승하차 처리가 가능해야 하며, 단말기에 임시 저장 후 복구 시 자동 동기화한다. 서버는 멱등 처리한다.

### MA-05. 운행모드 (재설계) ★

**디자인 수정 지시**

| # | 지시 | 상세 |
|---|---|---|
| 1 | **카드 컴포넌트 삭제** | `RunSummaryCard` 제거 |

| 4 | 벤치마킹 | **카카오택시 콜 받는 UI** |

**재설계 방향**

| 영역 | 구성 |
|---|---|
| ① 현재 이동 중인 정류장 | **대형 텍스트** — 정류장명 + 주소. 클릭 → 탑승자 명단 |
| ② 다음 정류장 | 중형 텍스트 — 정류장명 + 주소. 클릭 → 탑승자 명단 |
| ③ 도착 알림 전송 | 대형 버튼 (기사) |
| ④ 도착 지연 알림 전송 | 대형 버튼 |
| ⑤ **운행 종료하기** | 최종 학원 도착 후 활성화 |

**미경유 정류장의 운행모드 표기** [확정]

| 상황 | 표기 |
|---|---|
| 다음 정류장이 `skipped` | ②에 **다음 경유 정류장**을 표시하고, 그 위에 "○○ 정류장은 오늘 미경유" 라인 추가 |
| 경로 안내 | **제공하지 않음.** 재최적화 없이 기사가 최단거리로 판단 |
| ETA | **갱신하지 않음** — 미경유로 앞당겨지는 시간을 시스템이 예측하지 않음 |

운행모드가 보여줘야 하는 것은 "다음에 실제로 들를 곳이 어디인가" 하나다. 어떻게 갈지는 기사 판단에 맡긴다.

카카오택시 콜 UI의 요체는 **정보 밀도를 극단적으로 낮추고 액션 타깃을 화면 절반 크기로 키우는 것**이다. 카드로 감싸지 말고 배경 위에 직접 얹는 편이 그 방향에 맞다.

**추가 요건**: 현재 이동 중인 정류장 주소에서 **타 내비게이션 앱으로 이동하는 버튼** 제공.

### MA-06. 정류장 도착 처리 (= 도착 알림 발송)

| 항목 | 내용 |
|---|---|
| 트리거 | 운행모드의 **`정류장 도착` 버튼** (기사) |
| **누르는 시점** | **도착 직전 (확정)** — 해당 정류장에 진입하기 직전, 대략 **1~2분 전** |
| 효과 | ① 해당 정류장 탑승자 보호자·학생에게 **도착 예고 알림 발송** ② 운행모드의 현재/다음 정류장 포인터 전진 |
| 알림 문구 | **"{호차}가 {정류장}에 곧 도착합니다"** — 예고형. "도착했습니다"가 아니다 |
| 중복 방지 | 동일 정류장 재처리 차단 |
| 제외 대상 | `absent`·`no_show` 학생, 알림 off 사용자(푸시만 제외) |

**자동 트리거는 사용하지 않는다.** "정류장 n개 전 자동 발송"과 수동 버튼이 병존하면 중복 발송과 시점 불일치가 생긴다. 기사의 도착 처리 하나로 단일화한다.

**왜 "도착 직전"인가 (확정)**

도착 **후**에 누르면 학부모가 알림을 받았을 때 버스가 이미 서 있다. 그때부터 아이가 나오면 버스는 그만큼 정차해야 하고,
그 지연이 뒤 정류장 전체로 밀린다. **알림의 가치는 "예고"에 있지 "기록"에 있지 않다.**
도착 직전에 누르면 학부모가 나오는 시간과 버스가 오는 시간이 겹쳐 정차 시간이 줄어든다.

| 항목 | 규칙 |
|---|---|
| 권장 시점 | 해당 정류장 **진입 직전** (신호 대기·직전 골목 등) |
| 버튼 라벨 | `정류장 도착` — 예고 성격이 드러나도록 화면 안내 문구에 "곧 도착 알림이 발송됩니다" 병기 |
| 너무 이르게 누른 경우 | 시스템이 막지 않는다. **운영 규칙으로 관리**하고, 실제 도착까지 걸린 시간을 로그로 남겨 관계자가 확인한다 |

> **⚠ 구현 시 반드시 갈라야 하는 두 가지**: 기사의 **정류장 포인터**가 넘어가는 것과, 인솔자의 **승하차 처리 대상 명단**이 넘어가는 것은 **별개**다.
> 도착 직전에 눌러 포인터가 전진해도, 해당 정류장의 승하차 처리 명단은 **인솔자가 처리를 마칠 때까지 계속 열려 있어야 한다.**
> 이 둘을 한 값으로 묶으면 기사가 버튼을 누르는 순간 인솔자 화면에서 아직 태우지도 않은 아이들의 명단이 사라진다.

### AW-15. 노선 변경 승인 ★ 신규

**대상**: **출발 60분 이내**에 접수된 탑승 취소·삭제 요청.

| 요청 유형 | 승인 필요 | 비고 |
|---|:-:|---|
| 위치 변경 (60분 이전) | ✕ | 검증 통과 시 즉시 반영 |
| 탑승 취소 (60분 이전) | ✕ | 즉시 반영 |
| **탑승 취소 (60분 이내)** | **●** | 승인 후 반영. 미경유 전환 여부를 함께 표시 |
| 위치 변경 (60분 이내) | — | 신청 자체가 불가 |
| 강제 추가 (AW-03) | ● | 관리자가 직접 수행 |

**승인 화면 필수 요소**

| 항목 | 이유 |
|---|---|
| 출발까지 **남은 시간 카운트다운** | 판단 시간이 촘촘함 |
| 요청 학생 · 정류장 | 대상 확인 |
| 해당 정류장 **잔여 인원** | 미경유 전환 여부 판단 |
| 삭제 시 정류장 미경유 여부 | 기사 주행 경로 변경 예고 |

| 표시 항목 | 목적 |
|---|---|
| 변경 전/후 예상 도착 **시각** | 지연 영향 판단 |
| 변경 전/후 총 운행 **거리** | 실현 가능성 판단 |
| 영향받는 학생 목록 | 파급 범위 |
| 정원 초과 여부 | 승인 차단 |

| 액션 | 결과 |
|---|---|
| `승인` | 명단에서 제외 → (잔여 0명이면) **정류장 미경유 전환** → 기사·인솔자 앱에 변경 배포 → 학부모 통보 |
| `거절` | 사유와 함께 학부모에게 통보 |

> ⚠ **승인해도 노선을 재최적화하지 않는다.** §4.4에서 확정한 대로 미경유 정류장은 `skipped` 플래그만
> 세우고 정류장 순서·ETA는 그대로 둔다. 관리자가 확인하는 "변경 전/후 시각·거리"는 **재최적화 결과가 아니라
> 미경유로 인해 예상되는 영향치**다. 재최적화가 일어나는 경로는 **60분 이전 변경(§4.2 구간 ①)** 과
> **수동 학생 조정(AW-16)** 둘뿐이다.

**책임 소재는 승인한 관리자에게 있다.** 승인 이력(누가·언제·무엇을)을 반드시 저장한다.

### AW-16. 수동 학생 조정 · 버스 간 이동 ★ 신규

**결정**: 노선 최적화 시 **수동 조정을 허용한다 (yes)** — 강제 방문지 추가 방식.

**버스 간 이동 처리 절차**

| 단계 | 처리 |
|---|---|
| 1 | 기존 버스 노선의 정류장 탑승 명단에서 해당 학생 **제외** |
| 2-A | 신규 버스 노선에 **강제 방문지 추가**, 또는 |
| 2-B | 근처 정류장이 있으면 **그 정류장 명단에 추가** |
| 3 | **두 버스 노선 모두 재최적화** |
| 4 | 양쪽 기사·인솔자에게 변경 배포 |

**주의**: 학생 한 명을 옮기면 **출발 버스와 도착 버스의 노선이 둘 다 바뀐다.** 관리자에게 양쪽 영향을 함께 보여줘야 한다.

### SA-04. 학원 비활성화 / 삭제 (Delete)

| 항목 | 정책 |
|---|---|
| 기본 동작 | **비활성화 (soft delete)** — 물리 삭제하지 않는다 |
| 비활성화 효과 | ① 회원가입 학원 검색 결과에서 제외 ② 신규 가입 요청 차단 |
