## 1. 문서 개요

### 1.1 서비스 목적

학원 통학버스의 **노선 편성 → 학생 승하차 → 학부모 안내 → 차량·운행인력 관리** 를 하나의 시스템으로 통합하여, 통학버스 운영의 **안전성**과 **효율성**을 높인다.

기존에는 이 네 가지가 전화·카톡·엑셀로 흩어져 있어서, "우리 애 탔나요?" 라는 질문 하나에 학원 → 기사 → 학부모로 이어지는 3단계 연락이 필요했다. 이 시스템은 그 연락 사슬을 **앱 안의 상태값 하나**로 대체하는 것이 핵심이다.

### 1.2 문서 범위

| 포함 | 제외 |
|---|---|
| **회원가입 · 학원 선택 · 승인 대기**를 포함한 모든 화면 전환 | 결제·정산 |
| 각 단계의 분기 조건 / 예외 케이스 | 관리자 통계·리포트 |
| 화면 인벤토리, 상태 정의, 알림 매트릭스 | 기사·인솔자의 **일괄 승하차** (스코프 제외) |
| 역할 간 데이터 연결 지점 | 메인 관리자 콘솔 상세 (→ `FUNCTIONAL_SPEC.md` §7) |

### 1.3 확정된 전제

1. **승하차 체크는 수동이다.** 비콘·NFC·QR 없이 앱에서 직접 탑승자 상태를 누른다. 단 **누를 수 있는 사람은 인솔자뿐**이며, 기사는 조회만 한다.
2. **로그인은 form 회원가입/로그인이다.** 6자리 코드 로그인은 폐기됐다. 가입 시 **소속 학원을 학원 코드 또는 학원명으로 검색해 선택**하고, **학원 관계자가 승인해야** 계정이 활성화된다.
3. **당일 노선은 회차 출발 60분 전에 확정된다.** 기존의 "밤 12시 기준"·"30분 전"은 **모두 폐기**다. 확정 이후 기사·인솔자가 보는 노선이 "확정 노선"이다.
4. **노선 변경은 3구간 규칙을 따른다.** 출발 60분 이전은 추가·삭제 모두 가능, 59분 59초부터 운행모드 시작 전까지는 **삭제만** 가능, 운행모드 시작 이후는 **전면 불가**다. (→ §3.5)
5. **등하원을 별도로 관리하지 않는다.** 학부모는 **회차별 버스 탑승 여부**만 켜고 끈다. 버스를 아예 이용하지 않는 등하원은 **관리 대상이 아니다**.
6. **미경유가 생겨도 노선을 재최적화하지 않는다.** 시스템은 "이 정류장은 안 들러도 된다"까지만 알리고, 실제 주행 경로는 **기사가 최단거리로 판단**한다.
7. **일괄 승하차 기능은 이번 스코프에서 제외한다.** (FigJam 인솔자 보드에 있는 `일괄 하차` / `일괄 탑승` 노드는 반영하지 않음)

### 1.4 용어 정의

| 용어 | 정의 |
|---|---|
| **노선** (`Route`) · **고정 노선** | **변경 사항이 반영되지 않은 기본 노선.** 한 대의 버스가 한 회차에 도는 정류장의 순서 있는 목록이며 학기 단위로 고정된다. 학원 관계자가 관리하며, 관계자 웹의 UI 라벨은 `고정 노선`이다 |
| **확정 노선** (`ConfirmedRoute`) | **전날 등원을 표시한 학생들의 주소 + 승차 위치 변경 학생**을 기점으로 산출한 당일 노선. **회차 출발 60분 전**에 확정된다 |
| **운행모드 시작** | 기사가 `운행모드 시작` 버튼을 누른 시점. **이후 노선은 일절 변경 불가**이며, 모든 잠금 규칙의 기준선이다 |
| **회차** (`Run`) | 하루 중 한 번의 운행 단위. **빠른 회차 = 등원 / 늦은 회차 = 하원**으로 구분된다 |
| **호차** | 버스 식별 단위 (1호차, 2호차 …) |
| **매니저** | 버스에 배치되는 운행인력 총칭 = **버스기사 + 인솔자**. 관계자 웹의 "매니저 관리"가 이에 해당 |
| **인솔자** | 버스에 동승해 학생 승하차를 관리하는 인력. **승하차 상태 변경은 인솔자만 수행한다** (구 명칭: 인솔자) |
| **탑승자** | 특정 회차 노선에 배정된 학생 |
| **자녀 선택** | 학부모 계정에 연결된 자녀 중 지금 보고 있는 대상. **한 계정에 자녀 N명**이 연결된다 (자녀별 계정을 묶지 않음) |
| **탑승 여부** | 학생이 **오늘 그 회차의 버스를 타는지** 여부. 학부모가 회차별로 on/off 한다 |
| **미경유** | 잔여 탑승자가 0명이 되어 들르지 않기로 한 정류장. **재최적화 없이** 기사가 패스한다 |

## 3. 전 제품 공통 규칙

### 3.1 회원가입 · 로그인 (모든 역할 공통) ★ v0.2 전면 개정

**코드 로그인은 폐기됐다.** 학원 코드는 로그인 수단이 아니라 **소속 학원을 특정하는 식별자**로 역할이 바뀐다.

```
[로그인 화면]
   ├─ 신규 사용자 → [회원가입 폼] → [소속 학원 검색·선택] → 가입 요청 생성
   │                                        │
   │                                        ▼
   │                              [승인 대기 화면]  ← 이 상태에서는 어떤 데이터도 못 봄
   │                                        │
   │                          관계자 수락 ──┴── 관계자 거절 → 사유 통지
   │                                │
   │                                ▼
   │                          계정 활성화 → [홈]
   └─ 기존 사용자 → 아이디/비밀번호 인증 → [홈]
```

**회원가입 단계**

| # | 행위자 | 내용 |
|---|---|---|
| 1 | 사용자 | 회원가입 폼 입력 (아이디 / 비밀번호 / 이름 / 연락처) |
| 2 | 사용자 | **소속 학원 선택** — 학원 코드 **또는** 학원명으로 검색 후 목록에서 선택 |
| 3 | 시스템 | 선택된 학원에 `SignupRequest` 생성 → 해당 학원 관계자에게 전달 |
| 4 | 관계자 | 관계자 웹에서 **수락 / 거절** + 계정 ↔ 학생·매니저 레코드 연결 |
| 5 | 사용자 | 로그인 가능 |

**학원 선택 UI 요건**

| 항목 | 내용 |
|---|---|
| 검색 대상 | 메인 관리자가 사전 등록한 학원 목록 — **학원 코드 + 학원명 양쪽**으로 검색 |
| 결과 표기 | `{학원명} · {지역} · {학원 코드}` — 동명 학원 구분을 위해 세 값 모두 노출 |
| 입력 방식 | 자유 입력이 아니라 **검색 → 선택**. 오탈자 미매칭을 원천 차단 |
| 미등록 학원 | "학원을 찾을 수 없습니다 — 학원에 문의해 주세요". 사용자가 학원을 만들 수 없음 |
| 비활성 학원 | 검색 결과에서 제외 |

**역할별 가입 경로**

| 역할 | 가입 경로 | 승인·생성 주체 |
|---|---|---|
| 학부모 · 학생 · 버스기사 · 인솔자 | form 가입 + 학원 선택 | **학원 관계자 승인** |
| 학원 관계자 | **가입 불가** — 계정을 발급받아 사용 | **메인 관리자** |
| 메인 관리자 | 내부 발급 | 운영사 |

**예외 처리 (공통)**

| 상황 | 처리 |
|---|---|
| 아이디 중복 | 인라인 유효성 에러, 서버 호출 1회 (중복 확인) |
| 학원 미선택 | 다음 단계 버튼 비활성화 |
| **로그인 5회 실패** | **해당 계정 차단.** IP 차단은 하지 않는다 — 학원 와이파이·가정 공용 회선에서 무고한 사용자까지 잠기기 때문 |
| 차단 해제 | **메인 관리자만** 가능. 사용자 스스로 못 푼다 |
| 승인 대기 중 접근 | **승인 대기 안내 화면 하나만.** 홈·명단·노선·위치·알림 목록·설정 전부 차단 (아래 상세) |
| 세션 만료 | 로그인 화면으로 이동 |

**승인 대기 상태의 접근 범위 (v0.2 확정)**

| 구분 | 허용 |
|---|---|
| 로그인 | **성공한다** — 인증은 통과한다 |
| 볼 수 있는 화면 | **승인 대기 안내 화면 하나** |
| 그 화면의 구성 | 신청한 **학원명 · 지역 · 학원 코드**, 신청 일시, 현재 상태, **학원 문의처**, `로그아웃` |
| 볼 수 없는 것 | 홈 · 명단 · 노선 · 실시간 위치 · 알림 목록 · 설정 — **전부** |
| 수신 알림 | **승인 / 거절 결과만.** 운행 관련 알림은 대상이 아니다 |
| 서버 처리 | 계정 상태 `PENDING`. 토큰은 발급하되 **대기 화면 조회·로그아웃 외 모든 API가 403** |
| 거절된 경우 | 같은 화면에 **사유 표시** + **재신청 진입점**(학원 재선택 가능) |

> **⚠ 화면을 감추는 것과 막는 것은 다르다.** 프론트에서 라우팅만 막고 API를 열어두면
> **토큰만 들고 명단 API를 직접 호출해 남의 학원 학생 명단을 통째로 가져갈 수 있다.**
> 차단은 반드시 **서버 인가 계층**에서 한다.

> **초보자가 흔히 놓치는 부분**: 여기서 **인증(Authentication)과 인가(Authorization)가 분리**된다.
> 학원 선택은 "이 사람이 우리 학원 소속이라고 **주장**한다"까지만 처리하고, 실제 신원 확인은 **관계자 승인**이 담당한다.
> `가입 완료 = 이용 가능`으로 구현하면 **미승인 계정이 남의 학원 명단을 조회하는 사고**가 난다.
> 로그인 성공과 데이터 접근 권한은 반드시 별개의 검사로 둔다.

### 3.2 색상 규칙 (전 제품 공통)

| 색상 | 의미 | 사용처 |
|---|---|---|
| 🟢 초록 | 당일 **신규 추가**된 노선/탑승자 | 기사 노선 지도, 관계자 금일 운행 페이지 |
| 🔴 빨강 | 당일 **삭제**된 노선/탑승자 | 기사 노선 지도, 관계자 금일 운행 페이지 |

기사가 운행 직전에 "어제와 뭐가 다른지"만 3초 안에 파악하게 하려는 장치다. 실무에서 사고는 대부분 "오늘 추가된 애를 못 태웠다"에서 나온다.

### 3.3 탑승자 상태 정의

| 상태 | 의미 | 변경 주체 | 다음 상태 |
|---|---|---|---|
| `대기` | 명단에 있으나 아직 정류장 도달 전 | (초기값) | 탑승 완료 / 미등원 |
| `탑승 완료` | 버스에 탑승함 | **인솔자** | 하차 완료 |
| `미등원` | 정류장에 나오지 않음 | **인솔자** | (종결) |
| `하차 완료` | 목적지에서 내림 | **인솔자** | (종결) |

**상태 전이도**

```
                ┌──── 탑승 완료 ────► 하차 완료
   대기 ────────┤
                └──── 미등원 (종결)
```

**예외**

- `미등원` 확정 시 → 학부모에게 **미탑승 알림** 자동 발송 (on/off 불가)
- `탑승` → `미승차` 되돌리기 허용 여부 **미정 → §10.2-D**
- 학부모가 회차 탑승 여부를 OFF 하면 확정 노선 산출 시점에 `미등원`이 부여되고, **기사·인솔자 명단에서 제외된다** (회색 표시로 남기지 않음 — v0.2 확정)
- 기사에게도 상태는 보이되 **변경 버튼은 인솔자에게만** 노출된다 (v0.2 확정)

### 3.4 알림 매트릭스

| 알림 | 수신자 | 발생 트리거 | on/off |
|---|---|---|---|
| 버스 도착 알림 | 학부모, 학생 | 기사가 `도착 알림 전송` 버튼 클릭 | **가능** |
| 도착 지연 알림 | 학부모, 학생 | 기사 또는 인솔자가 지연 시간 선택 후 전송 | **불가** |
| 승차 알림 | 학부모 | 상태가 `탑승 완료`로 변경 | **가능** |
| 하차 알림 | 학부모 | 상태가 `하차 완료`로 변경 | **가능** |
| 미탑승 알림 | 학부모 | 상태가 `미등원`으로 변경 | **불가** |
| **탑승 여부 알림** | 관계자 | 학부모가 회차 탑승 여부 변경 | — |
| **60분 이내 삭제 요청** | 관계자 | 출발 60분 이내 탑승 취소 접수 | **불가** (푸시 즉시 통지) |
| **확정 노선 변경 알림** | 기사, 인솔자 | 확정 후 강제 추가·미경유 발생 | **불가** |

> 안전 관련 알림(지연·미탑승)은 끌 수 없게 만드는 것이 원칙이다. "알림이 너무 많아서 껐는데 하필 그날 애가 안 탔다"가 이 서비스에서 가장 치명적인 실패 시나리오다.

### 3.5 노선 변경 시간 규칙 ★★ (전 제품 공통 · v0.2 확정)

**모든 변경 관련 플로우(UF-P-03 · UF-P-04 · UF-M-05)가 이 표 하나를 참조한다.**
기준은 밤 12시가 아니라 **해당 회차의 출발 시각**이다.

| 구간 | 시점 | **추가** | **삭제** | 최적화 | 관리자 확인 |
|---|---|:-:|:-:|---|---|
| ① | 출발 **60분 이전** | ● 가능 | ● 가능 | 변경분 반영해 **재최적화 후 배포** | 불필요 |
| ② | 출발 **59분 59초 ~ 운행모드 시작 전** | **✕ 불가** | **● 가능** | **재최적화 없음** | **필수** |
| ③ | **운행모드 시작 이후** | ✕ 불가 | ✕ 불가 | — | — |

**핵심 3줄**

1. **추가는 60분 전까지만.** 넘기면 어떤 경로로도 탑승자를 넣을 수 없다.
2. **삭제는 운행 시작 전까지 언제나 가능하다.** 60분 이내여도 막지 않고, 관리자 승인을 거칠 뿐이다.
3. **운행모드를 누르는 순간 전부 잠긴다.**

> 왜 삭제만 열어두는가 — 추가는 노선을 **늘리므로** 다른 학생의 도착 시각에 영향을 준다.
> 반면 삭제는 노선을 **줄이기만** 하므로 다른 학생이 손해 볼 일이 없다. **비대칭은 의도된 것**이다.

**"삭제"의 단위 — 그 정류장에 남는 인원 수로 결정된다**

| 조건 | 결과 | 노선 영향 |
|---|---|---|
| 해당 정류장에 **다른 탑승자가 남아 있음** | **그 인원만 명단에서 제외** | 없음 — 정류장은 그대로 경유 |
| 해당 정류장에 **그 학생 혼자** | **정류장 자체 삭제 → 미경유** | 해당 정류장 스킵 |

판정은 **삭제 처리 시마다 잔여 인원을 재계산**한다. 3명 중 3명이 순차로 빠지면 마지막 삭제 시점에 미경유로 전환된다.

**미경유 정류장 처리**

| 항목 | 정책 |
|---|---|
| 노선 재최적화 | **하지 않는다** |
| 주행 경로 | **기사가 판단해 최단거리로 패스** |
| 시스템 역할 | 미경유 정류장 🔴 표시 + 다음 경유 정류장 안내까지만 |
| **마지막 정류장인 경우** | **동일 — 패스** |
| 뒤 정류장 ETA | **재계산하지 않는다** (`skipped` 플래그만 세움) |

> 출발 60분 이내에 노선을 다시 계산해 기사 단말에 재배포하면, 기사가 이미 머릿속에 넣은 경로와 달라져 **오히려 위험하다.**
> "이 정류장은 안 들러도 된다"만 알려주고 주행 판단은 기사에게 맡기는 것이 안전하다.

**확정 배치가 지연 실행되면 — "실행 시점 최신값" (v0.2 확정)**

| 항목 | 처리 |
|---|---|
| 읽는 값 | **배치가 실제로 도는 그 순간의 최신 탑승 의사 + 승인된 위치 변경** |
| 60분 전 스냅샷 | **만들지 않는다** |
| 구간 ①②③ 판정 기준 | 여전히 **`출발 시각 - 60분`이라는 시계** — 배치 실행 시각이 아니다 |

> 스냅샷을 쓰면 "60분 전 ~ 배치 실행" 사이에 승인된 삭제가 누락돼 **안 타는 아이를 태우러 가는 경로**가 배포된다.
>
> **⚠ 흔한 오해**: 배치가 55분 전에 돌았다고 해서 **추가 마감이 55분 전으로 밀리지 않는다.**
> 가능 여부는 시계로 판정하고, 배치는 그 결과를 읽어 노선을 만들 뿐이다. 두 값을 합치면 **배치가 늦은 날에만 추가가 되는** 비결정적 동작이 나온다.

**책임 소재**

> 60분 이내 변경 건은 **학원 관리자가 직접 확인**해 기존 노선 대비 **시각과 거리** 변화를 보고 판단한다.
> **책임 소재는 승인한 관리자에게 있으므로** 누가·언제·무엇을 승인했는지 이력을 저장한다.

승인 화면에는 다음이 반드시 보여야 한다 — 변경 전/후 **예상 도착 시각**, 변경 전/후 **총 운행 거리**,
**영향받는 학생 수**, **정원 초과 여부**, 그리고 **출발까지 남은 시간 카운트다운**.

### 3.6 다자녀 처리 (전 제품 공통 · v0.2 확정)

**한 계정에 자녀 N명을 연결한다.** 자녀마다 계정을 만들어 묶는 방식은 쓰지 않는다.

| 항목 | 규칙 |
|---|---|
| 구조 | `Guardian` 1 : N `Student` — **`GuardianStudent` 연결 테이블** |
| 자녀 선택 UI | 자녀가 **2명 이상일 때만** 홈 상단에 노출. 1명이면 숨긴다 |
| 전환 범위 | 선택된 자녀 기준으로 **실시간 위치 · 상세 노선 · 탑승 토글 · 위치 변경**이 모두 바뀐다 |
| 자녀별 독립성 | 자녀마다 **호차·노선·정류장·탑승 여부가 각각 다르다.** 형제라도 같은 버스라는 보장이 없다 |
| 자녀 추가 | 동생이 등록되면 관계자가 **기존 계정에 연결만 추가**한다. 재가입 불필요 |
| 연결 해제 | 퇴원 시 연결을 끊되 과거 이력은 보존 |

> **⚠ 가장 흔한 구현 실수 — 알림을 자녀 선택에 종속시키는 것.**
> 화면은 선택된 자녀 기준으로 바뀌지만, **알림은 선택과 무관하게 연결된 모든 자녀의 것을 전부 받아야 한다.**
> 첫째 화면을 보고 있는데 둘째의 미승차 알림이 안 오면, 그게 바로 이 서비스가 막으려던 사고다.
> 그래서 **모든 알림 문구에 자녀 이름이 들어가야 한다** — "OO가 승차했습니다"이지 "승차했습니다"가 아니다.

### UF-P-04. 회차별 버스 탑승 여부 변경 ★ v0.2 전면 개정

**목적**: 오늘 자녀가 **그 회차의 버스를 타는지**를 미리 알린다.
**진입점**: 홈 > 회차별 탑승 토글 (구 "등원 상태 드롭다운" 자리)

**결정 사항**

| 질문 | 결정 |
|---|---|
| 등하원을 별도로 관리하는가? | **아니다.** 등하원이 아니라 **버스 탑승 여부**로 결정한다 |
| 구현 방식 | 예정된 노선 중 **빠른 회차(등원) off / 늦은 회차(하원) on** 을 각각 토글 |
| 버스로 등하원하지 않는 케이스도 관리하는가? | **관리하지 않는다** |

| # | 단계 | 화면 |
|---|---|---|
| 1 | 로그인 | 로그인 |
| 2 | 홈 진입 | 홈 |
| 3 | (다자녀) 자녀 선택 | 홈 |
| 4 | `등원 (8:30 출발)` / `하원 (20:00 출발)` 스위치 on/off | 홈 |
| 5 | 즉시 저장 + 토스트 피드백 | 홈 |

**화면 명세**

| 항목 | 내용 |
|---|---|
| 컨트롤 | 회차별 `Switch` 2개 (드롭다운 아님) |
| 라벨 | `등원 (출발시각)` / `하원 (출발시각)` — 회차를 시각으로 식별시킨다 |
| 기본값 | **둘 다 ON** |
| 다자녀 | 자녀별로 토글이 독립 존재. 자녀 선택 → 회차 토글 구조. 자녀가 **2명 이상일 때만** 선택 UI 노출 |

**분기 / 예외 — §3.5 구간 규칙 적용**

| 조건 | 처리 |
|---|---|
| **구간 ① (출발 60분 이전) OFF** | 즉시 반영 → 확정 노선 산출에 반영 |
| **구간 ② (60분 이내) OFF** | **삭제이므로 가능하나 관계자 승인 필요.** 승인 화면에 카운트다운 노출 |
| **구간 ② (60분 이내) ON 으로 되돌리기** | **불가** — 되돌리기는 "추가"에 해당한다 |
| **구간 ③ (운행모드 시작 후)** | **변경 불가.** 토글 비활성화 + 사유 안내 |
| OFF 결과 | 해당 회차 명단에서 제외 → 상태 `미등원` 기록 → 관계자 알림 |
| 정류장 잔여 인원 0명 | **해당 정류장 미경유** (재최적화 없음 — §3.5) |
| 학생 계정으로 로그인한 경우 | 이 기능 **비노출** (학부모 전용) |

> **흔한 오해**: "등원 OFF = 오늘 학원에 안 간다"가 아니다. **"오늘 등원 버스를 안 탄다"**일 뿐이다.
> 학부모가 직접 데려다주고 하원만 버스를 태우는 케이스가 흔하기 때문에, 이 서비스는 **출결이 아니라 탑승만** 관리한다.

### UF-D-05. 도착 알림 전송 ★ v0.2 개정

**누르는 시점**: **도착 직전 (확정)** — 해당 정류장 진입 **1~2분 전**

| # | 단계 |
|---|---|
| 1 | 정류장 진입 직전, 운행모드 화면에서 `정류장 도착` 버튼 클릭 |
| 2 | 해당 정류장 탑승 예정 학부모·학생에게 **"곧 도착합니다"** 예고 알림 발송 |
| 3 | 전송 완료 피드백 (버튼 상태 변경 / 배너) |
| 4 | 현재/다음 정류장 포인터 전진 |

**분기 / 예외**

| 조건 | 처리 |
|---|---|
| 중복 클릭 | 동일 정류장 재전송 방지 (쿨다운 또는 1회 제한) |
| 알림 off 설정한 사용자 | 발송 대상에서 제외 |
| 대상 학생이 `미등원`·`미승차` | 발송 대상에서 제외 |
| 너무 이르게 누름 | 시스템이 막지 않는다. **운영 규칙으로 관리**하고 실제 도착까지 걸린 시간을 로그로 남긴다 |

> **왜 도착 후가 아니라 직전인가** — 도착 후에 누르면 학부모가 알림을 받았을 때 버스가 이미 서 있다.
> 그때부터 아이가 나오면 그만큼 정차하게 되고 지연이 뒤 정류장 전체로 밀린다.
> **알림의 가치는 "예고"에 있지 "기록"에 있지 않다.**

> **⚠ 구현 시 갈라야 할 두 가지**: 기사의 **정류장 포인터**와 인솔자의 **승하차 처리 대상 명단**은 별개다.
> 도착 직전에 눌러 포인터가 전진해도 그 정류장의 명단은 인솔자가 처리를 마칠 때까지 열려 있어야 한다.
> 묶어버리면 기사가 버튼을 누르는 순간 **아직 태우지도 않은 아이들의 명단이 인솔자 화면에서 사라진다.**

> **자동 트리거는 쓰지 않는다 (확정).** MVP 정의서의 "n번째 정류장 전 자동 발송"은 폐기됐다.
> 자동과 수동이 병존하면 중복 발송과 시점 불일치가 생기므로 **기사의 도착 처리 하나로 단일화**한다.

### UF-A-02. 탑승자 개인별 상태 변경 ★핵심

**목적**: 정류장마다 학생 한 명 한 명의 탑승·미승차·하차를 기록한다.

> **`미등원`과 `미승차`는 다른 버튼이다.** `미등원(absent)`은 학부모가 **사전에** 끈 것이라 명단에 아예 없고,
> 인솔자가 현장에서 누르는 것은 **`미승차(no_show)`** — 나올 예정이던 아이가 안 나온 이상 상황이다.

| # | 단계 | 화면 |
|---|---|---|
| 1 | 로그인 | 로그인 |
| 2 | 담당 운행 노선 | 담당 운행 노선 |
| 3 | 노선 클릭 | — |
| 4 | 정류장 리스트 | 정류장 리스트 |
| 5 | 정류장 클릭 | — |
| 6 | 정류장별 탑승자 명단 | 정류장별 탑승자 명단 |
| 7 | 탑승자 개인 선택 → 상태 지정 | 탑승자별 상태 |
| 8 | `탑승` / `미승차` / `하차` 중 선택 | — |
| 9 | 상태 반영 → 학부모 알림 자동 발송 | 정류장별 탑승자 명단 |

**상태 변경이 만드는 연쇄 반응** — 이 서비스의 심장부다.

```
인솔자가 [탑승 완료] 터치
        │
        ├─► 학부모 앱: 승차 알림 푸시
        ├─► 관계자 웹: 실시간 탑승 현황 갱신
        └─► DB: 해당 회차 탑승 이력 기록

인솔자가 [미승차] 터치
        │
        ├─► 학부모 앱: 미승차 알림 푸시 (끌 수 없음)
        ├─► 관계자 웹: 미승차 인원 목록에 추가
        └─► 대기 타이머 시작 (기본 3분)
```

**미승차 대기 · 에스컬레이션 — 기본 대기 3분 (v0.2 확정)**

| 시점 | 처리 |
|---|---|
| T+0 | `미승차` 선택 → **학부모 즉시 알림** + 관계자 동시 통지 → **3분 타이머 시작** |
| T+0 ~ 3분 | 대기. 학부모 응답(전화·앱)이 오면 타이머 중단하고 현장 판단으로 처리 |
| 대기 중 | 무응답이면 **보호자에게 전화 시도**, 시도 이력 저장 |
| **T+3분** | 무응답 확정 → **관계자에게 에스컬레이션 보고** → 관계자 판단에 따라 출발 |

| 항목 | 값 |
|---|---|
| **기본 대기 시간** | **3분** — 학원별 설정으로 조정 가능한 기본치 |
| 무응답 판정 | **대기 시간과 같은 창.** 3분 안에 응답 없으면 무응답 |
| 화면 표시 | 인솔자 화면에 **남은 시간 카운트다운** |
| 기록 | 대기 시작·종료 시각, 연락 시도 이력, 최종 판단(출발/재시도) |

> **왜 3분인가** — 정류장당 3분을 넘기면 뒤 정류장 도착 시각이 눈에 띄게 밀리고 그 지연이 전 구간에 누적된다.
> 반대로 1분은 아이가 엘리베이터에서 내려오는 시간도 안 된다.
> **한 아이를 기다리는 시간과 나머지 전원의 지연을 맞바꾸는 값**이라 학원별로 조정 가능하게 둔다.

**분기 / 예외**

| 조건 | 처리 |
|---|---|
| 잘못 누른 경우 되돌리기 | 허용 여부 **§10.2-D**. 최소한 "취소" 유예 시간(예: 10초) 권장 |
| 네트워크 끊김 (지하차도 등) | **오프라인 큐잉 필수** → 복구 시 자동 동기화 |
| 정류장 전체 처리 | 일괄 처리 **금번 스코프 제외** — 개인별로만 처리 |

> **오프라인 처리는 선택이 아니라 필수다.** 통학버스 노선에는 터널·지하주차장이 반드시 끼어 있고, 그 순간 상태 변경이 유실되면 학부모에게 알림이 안 간다. 로컬에 먼저 쓰고 서버에 재전송하는 구조로 설계해야 한다.

## 8. 관계자 웹 — 학원 관계자 플로우

관계자 웹은 **모든 데이터의 원본(Source of Truth)** 이다. 앱 3개가 보는 명단·노선·인력은 전부 여기서 만들어진다.

### 8.1 정보 구조 (홈 하위)

```
홈
 ├─ 운행 관리
 │   ├─ 고정 노선 (버스별 / 노선별 정류장 리스트)
 │   ├─ 금일 운행 현황 → 호차별 탑승자 명단
 │   ├─ 노선 강제 추가 (이머전시)
 │   └─ 매니저 배치
 ├─ 학생 정보 관리
 │   ├─ 학생 목록 / 검색
 │   ├─ 학생 추가
 │   ├─ 학생 정보 수정
 │   └─ 학생 삭제 (퇴원)
 └─ 매니저 관리
     ├─ 매니저 목록 / 검색
     ├─ 매니저 추가
     ├─ 매니저 정보 수정
     └─ 매니저 삭제
```

### UF-M-05. 버스 노선에 학생 강제 추가 · 수동 조정 (이머전시) ★ v0.2 개정

**목적**: 앱에서 처리하지 못한 변경(전화 요청, 노선 범위 밖 주소)을 관계자가 직접 반영한다.
**사전조건**: 해당 회차가 **출발 60분 이전**일 것 — **추가는 60분을 넘기면 관계자도 할 수 없다** (§3.5)

|---|---|---|

| 4 | `고정 노선` 또는 `이머전시` 선택 → 클릭 | — |
| 5 | 노선 강제 추가 페이지 | 노선 강제 추가 페이지 |
| 6 | 정보 입력 (아래 표) | 노선 강제 추가 페이지 |
| 7 | `노선 추가하기` 버튼 클릭 | — |
| 8 | 추가 완료 → 운행관리 페이지 복귀 | 운행관리 페이지 |

**입력 항목**

| 항목 | 필수 |
|---|:-:|
| 학생 이름 | ● |
| 학생 주소 | ● |
| 학부모 이름 | ● |
| 학부모 전화번호 | ● (필수) |
| 학생 전화번호 | ○ (선택) |

**분기 / 예외**

- 추가된 탑승자는 기사·인솔자 화면과 관계자 금일 운행 페이지에 🟢 초록으로 표시
- **확정(출발 60분 전) 이후 변경이 생기면 기사에게 푸시를 보낸다 (확정)** — 화면만 초록으로 바뀌면 기사가 다시 볼 이유가 없다
- **출발 60분 이내에는 추가 자체가 차단**된다. 버튼 비활성화 + 사유 안내
- 기존 등록 학생인지, 완전 신규인지 구분 필요 → 현재 폼은 이름을 직접 입력받으므로 **중복 생성 위험** **→ §10-Q**

**수동 학생 조정 · 버스 간 이동 (v0.2 신규 확정)**

노선 최적화 결과를 관계자가 수동으로 조정하는 것을 **허용한다** — **강제 방문지 추가** 방식이다.

| 단계 | 처리 |
|---|---|
| 1 | 기존 버스 노선의 정류장 탑승 명단에서 해당 학생 **제외** |
| 2-A | 신규 버스 노선에 **강제 방문지 추가**, 또는 |
| 2-B | 근처에 정류장이 있으면 **그 정류장 명단에 추가** |
| 3 | **두 버스 노선을 모두 재최적화** |
| 4 | 양쪽 기사·인솔자에게 변경 배포 |

> **주의**: 학생 한 명을 옮기면 **출발 버스와 도착 버스의 노선이 둘 다 바뀐다.**
> 이미 최적화된 노선과 인원 배정이 조정될 수 있다는 것을 전제로 하며, 관리자 화면에 **양쪽 영향을 함께** 보여줘야 한다.
> 정원 초과 시에는 저장을 차단하고 현재 인원과 정원을 함께 표시한다.

## 11. 개선 제안 (스코프 외, 참고용)

- 인솔자 지연 사유를 **프리셋 버튼(정체/사고/기상/차량/기타) + 선택적 메모**로 구성하면 운행 중 입력 부담이 크게 준다.
- 매니저 앱 상태 변경에 **오프라인 큐잉**을 넣어야 터널·지하 구간에서 데이터가 유실되지 않는다. (§7 참조 — 이건 제안이 아니라 필수에 가깝다)
- 관계자 웹 **금일 운행 페이지에 실시간 탑승 현황을 통합**하면 §10-R이 자연스럽게 해소된다.
- 학부모 앱 홈에 **"오늘 우리 아이 상태" 단일 카드**(대기/탑승/하차)를 두면 알림을 놓쳐도 앱만 열면 확인된다.
