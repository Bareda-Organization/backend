## 3. ⚠ 이 Phase 에서 가장 의심스러운 지점

### 3.1 🔴 발송 경로가 **설정을 참조하지 않는다** — 목표 8 의 본체

조율자 실측 — **`NotificationSetting` 을 읽는 프로덕션 코드가 `RunStartedNotificationListener` 단 하나뿐이다.**

```bash
grep -rln 'NotificationSetting' backend/src/main/java   # 기대 2개(엔티티 + 리스너 1개)
```

즉 **문구 조립기 16개 중 15개 경로가 설정을 무시하고 푸시까지 보낸다.** 목표 8 은 이것을 닫는 항목이다.

- ⚠ **차단 지점을 리스너마다 흩지 마라** — 16곳에 같은 판정을 복사하면 다음 알림 종류가 추가될 때 또 빠진다. **`NotificationDispatcher`·`PushSender` 경계 한 곳**에서 판정하는 쪽을 먼저 검토하고, 다르게 정하면 근거를 보고하라
- 🔴 **`off` 는 푸시만 막고 `notification_log` 행은 항상 생성한다**(`ARCHITECTURE §11`). **레코드까지 막으면 미수신 주장이 나왔을 때 발송 사실을 확인할 수단이 사라진다**
- ⚠ **설정 대상은 3종뿐이다**(`arrive`·`boarding`·`no_show`). **`delay`·`emergency`·`emergency_canceled` 는 설정 항목 자체가 부재**해 항상 발송된다(`C-17`·`NTF-07`). **나머지 13종은 어느 쪽인가를 정본에서 판정하라** — `§3.14` 는 3종만 적고 나머지를 말하지 않는다. **추측해서 코드에 박지 말고 판정 근거를 보고하라**
- **"운행 시작" 은 `boarding` 토글에 귀속된다** — `§3.14` 가 `boarding` 을 *"등하원(승차·하차·**운행 시작**) 알림"* 으로 명시한다(오픈 이슈 N 이 이렇게 닫혔다)

### 3.2 목표 8·9 는 **"무엇이 일어나지 않는다" 형태**다 — 짝을 같은 시험에 두어라

*"`off` 면 푸시 미발송"* 은 **푸시가 통째로 죽어 있어도 통과**한다.

**두 갈래를 각각 심어라.**

| 심는 것 | 실패해야 하는 것 |
|---|---|
| 설정 판정을 없앤다(항상 발송) | **`off` 에서 푸시 미발송** 단언 |
| 푸시 발송 호출을 조용히 **no-op** 으로 | **`on` 에서 푸시 발송** 단언 |
| 설정 판정이 **레코드 생성까지** 막게 한다 | **`off` 에서도 `notification_log` 행이 생긴다** 단언 |

**세 번째가 목표 8 의 핵심이다** — 첫 둘만 검사하면 "레코드는 항상 생성" 이 무검증으로 남는다.

### 3.3 목표 4(14일 보관)는 **오늘 날짜에 기대면 하루 뒤 썩는다**

⚠ **시드의 "오늘" 행은 DB 를 만든 날에 굳는다**(`PROJECT_NOTES` 의 알려진 함정). 14일 경계를 검사하려면 **`Clock` 을 고정하거나 `sent_at` 을 직접 지정**하라. `Clock.fixed` 로 얼리면 다른 신선도 검사가 무너질 수 있으니 **`Clock.offset` 을 먼저 검토**하라(Phase 10 에서 실제로 그렇게 갈랐다).
- **경계 양쪽을 검사하라** — 13일 전은 보이고 15일 전은 안 보인다. **정확히 14일** 시점의 방향은 정본에 문면이 없으니 **판정하고 근거를 적어라**

### 3.4 목표 6(자녀 이름 포함)은 **조립기 16개가 이미 만든 문구**에 걸린다

`title`·`body` 에 자녀 이름이 필수(`ATT-03`·`P-02`)인데 **조립기는 Phase 2~11 산출물**이다. 이 Phase 는 **목록 응답이 그 값을 그대로 싣는지**를 검사하는 자리다.
- ⚠ **조립기 문구를 이 Phase 에서 고치지 마라** — 어긋나면 **보고하고 멈춘다.** 16개를 손대면 앞선 Phase 의 시험이 무너진다
- **`student_id`·`student_name` 이 선택 필드**라 `null` 인 종류가 있다. 어떤 종류가 그런지 판정하고 시험에 반영하라

### 3.5 좌석 경계 — `acked` 를 **쓰는 곳과 읽는 곳이 갈린다**

`§3.13` 이 *"중요 통지는 이 처리가 수신 확인(NTF-10)의 근거"* 라고 적는다. 즉 **읽음 처리(T2)가 `acked` 를 쓰고 관계자 로그(T3)가 읽는다.**

🔴 **Phase 10 의 Critical 이 정확히 이 형태였다** — 세 좌석이 각자 손으로 만든 데이터를 심어 **자기 쪽만** 검사했고, 실제 쓰기 → 실제 읽기를 잇는 시험이 하나도 없어 **전 시험이 초록인데 운영이 파손**됐다.

⇒ **T2 가 실제로 읽음 처리를 태운 뒤 T3 의 조회에서 `acked`·`unacked_count` 가 바뀌는 것을 확인하는 시험이 최소 1건 있어야 한다.** 손으로 `UPDATE` 한 행으로 대체하지 마라.
- **어느 종류가 "중요 통지" 인가를 정본에서 판정하라** — `NTF-10` 이 그 말을 쓰는데 목록이 없다. 판정 근거를 보고하고, 근거가 없으면 **그렇게 보고하라**

⚠ **남은 좌석 간 결합 2건을 발주문에 명시한다.**

|---|---|

## 5. 좌석 공통 규칙 — 8항

1. 착수 전 `git log --oneline -1` 이 **기대 분기점**인지 확인. 다르면 즉시 `BLOCKED` 보고
2. **`git add` 는 파일 경로로.** `-A` · `.` 금지. 오류를 `2>/dev/null` 로 가리지 마라. 커밋 후 `git show --stat` 의 `insertions` 가 0 이 아닌지 확인
3. **서브에이전트를 띄우지 마라**
4. **결함 심기는 커밋 후에.** 변형 1회 = 원복 1회 = `git status --porcelain` 확인 1회를 묶어 돈다. `git checkout -- <경로>` 금지 — **심은 줄만 손으로** 되돌린다. 삭제 대신 **주석 처리**
5. 보고서는 **4항만** — ①판단 근거(고른 길과 **버린 길**) ②우려·확신 없는 지점 ③실측 3줄(커밋 해시 · **실패 클래스 이름** · 테스트 수) ④심은 변형 목록. 경로는 **메인 저장소의 `report-p12-t<N>.md`**(워크트리가 아니다)
6. **파일 쓰기가 도구에서 거부되면 전문을 메시지로 보내라.** 조율자가 저장한다 — **Phase 11 에서 6회 연속 거부됐다**
7. **컴파일되는 지점마다 중간 커밋.** 이 프로젝트는 세션 한도로 끊긴 전례가 반복됐고 Phase 11 에서 좌석 3개가 그렇게 정지했다
8. 인프라 부재로 인한 실패는 **환경 문제로 분류**해 코드 결함과 구분해 적어라

⚠ **"시험이 없다" 를 영문 `grep` 으로 판정하지 마라** — 이 저장소는 **시험 메서드·헬퍼 이름을 한글로 쓴다**(`알림_행수(...)` 류). 조율자가 실제로 있는 시험을 없다고 판정해 발주한 전례가 있다. **검사 대상 테이블·컬럼 문자열로 훑고 파일을 열어 확인하라.**


- ⚠ **포트 15432**(redis 16379 · kafka 29092). `application.yml:25` 기본값은 **`5432`** 이고 이 머신의 5432 는 **다른 프로젝트 postgres** 라 붙으면 `password authentication failed` 가 **전 클래스에서** 난다. 착수 시 `docker port school-bus-postgres-1` 로 **다시 실측**하라

- ⚠ **판정 근거는 콘솔이 아니라 `build/test-results/test/TEST-*.xml` 의 `tests=`·`failures=`·`errors=`.** `:test` 줄의 `UP-TO-DATE`·`FROM-CACHE` 는 통과가 아니라 **미실행**이다
- ⚠ **파이프·배경 실행의 종료 코드를 믿지 마라** — 조율자가 실제로 배경 알림의 `exit code 0` 을 읽었는데 gradle 은 `EXIT=1`·`BUILD FAILED` 였다(복합 명령의 마지막 원소 코드)
- **금지** — 인자 없는 `./gradlew test` · `clean` · `docker compose down` · `-v` · `DROP DATABASE`
- ⚠ **Redis 를 쓰면 `testsupport/redis/RedisTestContainerBase`(클래스 전용 컨테이너)를 상속**하라
- ⚠ **`SNAKE_CASE` 는 요청 역직렬화에도 걸린다** — 시험 요청 본문은 **정본의 snake_case 키**를 쓴다. 카멜케이스를 쓰면 값이 바인딩되지 않고 **`422`** 로 나타나 원인을 검증 쪽에서 찾게 된다(Phase 11 에서 10개 중 9개가 그렇게 실패했다)
- 참고 — `*ConcurrencyTest` 는 전체 실행에서 `TimeoutException` 이 나고 **단독 재실행에서 통과**한다(부하 의존, Phase 8 부터 이월. 코드 결함 아님)

## 8. 🔴 T4 전용 — 되돌리기 정정 알림 (목표 13·14, Ruling 219)

### 지금 코드가 사실과 다른 알림을 보낸다 — 조율자 실측

```java
// BoardingCommandService:181 — 되돌리기도 같은 이벤트를 쓴다. status 는 "되돌아간" 상태다
eventPublisher.publishEvent(new RiderStatusChangedEvent(..., statusName(targetStatus), now));

// RiderStatusChangedComposer:24 — else 가 하차로 떨어진다
String body = "boarded".equals(subject.status()) ? BODY_BOARDED : BODY_ALIGHTED;
```

| 상황 | 지금 학부모가 받는 문구 | 옳은 것 |
|---|---|---|
| 승차를 취소 | 🔴 **"자녀가 버스에서 하차했습니다."** (사실과 다름) | **"승차 취소"** 뜻의 새 알림 |
| 하차를 취소 | 🔴 **"자녀가 버스에서 하차했습니다."** (같은 문구 재발송) | **"하차 취소"** 뜻의 새 알림 |

⚠ **`else` 를 하차로 떨어뜨리는 형태 자체가 결함이다** — 상태가 늘어날 때마다 조용히 오답이 된다. **분기를 열거값으로 완전 분해**하고, 알 수 없는 값은 **떨어뜨리지 말고 드러나게** 하라.

### 확정된 정책 (Ruling 219 · 사용자 판정)

> **이미 나간 알림은 정정하지 않는다. 새 알림을 발행한다.**
> 승차 알림이 나간 뒤 승차를 취소하면 **승차 알림 행은 그대로 두고** "승차 취소" 알림을 **새로** 보낸다.

- 🔴 **원본 알림 행을 지우거나 고치지 마라.** 목표 13 이 그것을 검사한다
- **되돌리기를 구별할 정보가 이벤트에 부재하다** — 현재 이벤트는 **되돌아간 상태만** 실어 "무엇이 취소됐는지" 를 알 수 없다. **발행 지점에는 `fromStatus` 가 이미 있다**(`BoardingCommandService:168`). 이벤트에 정보를 더할지 **별도 이벤트를 둘지는 네가 판정**하고 근거를 보고하라
  - ⚠ **기존 이벤트를 고치면 그 이벤트를 쓰는 다른 구독자가 함께 영향받는다** — `rider_changed` WebSocket 방송이 같은 이벤트를 쓴다(`BoardingCommandService:180` 주석). **구독자를 먼저 세라**
- **알림 종류를 신설하고 `notification_log.type` CHECK 를 `V6` 로 넓힌다** — `V1`·`V3`·`V4`·`V5` 가 이미 있어 **다음 번호는 `V6`** 이고 **번호가 겹치면 `local` 프로파일에서 Flyway 가 기동을 거부한다**
  - ⚠ **`V5` 가 이미 같은 CHECK 를 `DROP` 후 재정의했다**(19종). `V6` 은 **`V5` 의 19종 전부 + 신설분**을 다시 적어야 한다 — `V1` 을 베끼면 `exception_reported` 가 사라진다
  - ⚠ **`EnumCheckConstraintParityTest` 가 마이그레이션 전체를 버전 오름차순으로 읽어 같은 제약 이름은 나중 파일로 덮어쓴다.** 열거값과 CHECK 가 어긋나면 그 시험이 잡는다 — **자바독의 "19종" 수치도 함께 고쳐라**(직접 세서)
- **몇 종류를 만들지도 판정 대상이다** — 승차 취소·하차 취소를 **2종으로 가를지 1종으로 묶고 문구로 가를지.** 목표 14 가 요구하는 것은 **문구가 구별되는 것**이다
- **설정 축 귀속을 판정하라** — `§3.14` 의 `boarding`(등하원) 토글에 귀속되는가. 정정 알림도 등하원 축으로 보는 것이 자연스러우나 **정본에 문면이 부재**하니 판정 근거를 보고하라. ⚠ **T1 이 푸시 차단을 배선하므로 이 판정이 T1 과 맞닿는다** — 조율자에게 보고하면 전파한다
