# 부하 한계 측정 계획 — 목표 규모 "학원 10개 × 버스 10대 × 학생 20명"

작성 2026-09-09. 사용자 확정 목표 규모: **학원 10 · 버스 100 · 학생 2,000**.
분기점 `main` = `3c7e19e`. 이 파일 하나만 읽으면 착수할 수 있게 적는다.

## 0. 왜 하는가 — 기존 측정과의 차이

2026-09-05 부하 라운드(F3 L · F5 S2, 원장 `docs/IMPLEMENTATION_PLAN.md §5.6`)는 **"정해진 부하에서 약속을 지키는가"** 만 봤고 **포화 지점을 관측하지 않았다.** 이번은 반대다 — **깨질 때까지 올려 한계와 병목을 찾는다.**

## 1. 목표 규모 → 필요한 부하 (환산 근거 포함)

| 부하원 | 환산 | 목표 | 기존 측정 | 배율 |
|---|---|---|---|:-:|
| 실시간 세션(학부모·학생) | 100대 × 20명 | **2,000 세션** | 200 | **10배** ⚠ |
| 위치 수신(기사) | 100대 ÷ 5초(사양 하한) | **20 req/s** | 20VU×7초 = 2.9 req/s | **7배** ⚠ |
| 확정 배치 | 등원 피크 동시 도래 | 100 회차 | 200 통과 | 여유 ✅ |
| 온디맨드 승인(②) | 회차당 1회 한도 | 수 건~수십 | 20 통과 | 여유 ✅ |
| 관제(관계자) | 학원 10 × 1~2 | 10~20 세션 | 200 통과 | 여유 ✅ |

⇒ **미지의 영역은 실시간 세션과 위치 수신 둘뿐이다.** 나머지는 이미 목표를 넘겨 측정했다.

## 2. 판정 기준(SLO) — 사양에서 가져온다. 숫자를 지어내지 않는다

| 대상 | 기준 | 근거 |
|---|---|---|
| 위치 송신 · 방송 지연 | p95 **5초** 이내 | `FEATURE_SPEC §2.1` 승하차 상태 반영 5초 |
| 확정 배치 | 미확정 **0** · 완료가 출발 **30분 전** 창 안 | `C-03` · `RTE-02` |
| 실패율 | > 1% 면 포화로 판정 | 관례(사양에 수치 부재 — 판정에 쓰되 사양값이 아님을 명시) |
| 승인 응답 | **임계 부여하지 않음**(측정만) | `§5.3` — 사양에 수치 부재 |

## 3. 라운드

| # | 대상 | 올리는 방식 | 멈추는 지점 |
|:-:|---|---|---|
| **R0** | 시드 확장 | 학원 10 · 버스 100 · 학생 2,000 · 회차 200(등원·하원) 생성 SQL | 데이터 적재 확인 |
| **R2** | 위치 수신 | `SCENARIO2_INTERVAL_SEC=5`, 회차(VU) 20→50→100→200 | p95 > 5s 또는 실패율 > 1% |
| **R1** | 실시간 세션 | `SCENARIO3_TARGET_VUS` 500→1000→2000→3000 | 연결 실패 또는 방송 p95 > 5s |
| **R3** | **혼합(등원 피크)** | 위치 20 req/s + 세션 2,000 + 배치 100 동시 도래 + 관제 20 | 위 전부 |
| **R4** | 여유 확인(선택) | R3 통과 시 1.5배·2배 | 위 전부 |

**순서는 R0 → R2 → R1 → R3.** R2 를 먼저 하는 이유는 거기서 드러나는 커넥션 풀 설정이 R3 의 조건을 바꾸기 때문이다.

## 4. 포화 순간에 함께 기록할 것 — 없으면 "증설로 풀리는가" 에 답할 수 없다

| 지표 | 출처 | 병목이면 뜻하는 것 |
|---|---|---|
| HikariCP 활성·대기 | Grafana / actuator | 풀·쿼리 문제 → 튜닝으로 풀림 |
| CPU · **메모리** | node-exporter | 기계 문제 → 증설. ⚠ 메모리는 t3.medium(4GB) 환산에 필수 |
| 톰캣 스레드 · 열린 소켓 | actuator | WS 세션 상한 → **팬아웃 구조 전환**이 필요(증설로 안 풀림) |
| `throttled_total{caller}` | actuator | 지도 API 대역 → 증설로 안 풀림 |
| 배치 도래→완료 지연 | 앱 지표 | 워커 수 조정 대상 |
| `pg_stat_activity` | psql | 락 대기·커넥션 총량 |

## 5. 실행 환경 — 사용자 확정 "노트북 먼저(A)"

- 포트 **18080**(Swagger 용 8080 과 분리) · DB **`schoolbus_load`** · Redis 16379 · postgres 15432
- 지도 API 는 스텁(300~1200ms · `max_concurrent` 4, 출처 `backend/load/README.md §5`) — 키 미보유
- ⚠ **노트북 숫자는 절대값이 아니다.** 운영은 t3.medium 한 대에 앱·DB·Redis·nginx 가 함께 올라간다(메모리 4GB). 그래서 R1·R2 에서 **메모리 사용량을 반드시 함께 기록**해 환산 가능하게 한다

## 7. 알아 둘 제약

- 백엔드는 **1대만** 띄울 수 있다(시각 촉발 배치 중복 · WS 세션이 인스턴스에 묶임). 이번 답은 "단일 인스턴스로 어디까지".
- 증설 선결 3가지 — 분산 락(준비됨) · **WS 팬아웃 외부 브로커 전환(미준비)** · 위치 캐시 Redis 공유(성립).
- ⚠ **이 작업은 병렬 좌석에 맞지 않는다** — 앱 인스턴스·포트·DB 가 하나뿐이라 좌석 둘이 동시에 측정하면 서로의 부하가 섞인다. **한 좌석이 순차로** 돌리거나 조율자가 직접 한다.
