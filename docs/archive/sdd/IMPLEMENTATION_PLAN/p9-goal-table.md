## 착수 전 판정 — Ruling 201~205

### Ruling 201 — 내비 공급자는 **요청이 고르지 않는다.** 서버 설정이 정하고 응답이 알린다

`API_SPEC §4.16` 원안은 `?provider=tmap|kakao` 를 **필수 요청 파라미터**로 뒀다. MVP 가 카카오 단독으로 확정된 상태에서 이 구조는 두 가지가 어긋난다.

| | 요청 파라미터 | 서버 설정 |
|---|---|---|
| 값의 종류 | `kakao` 하나 — 매번 같은 값을 보내는 파라미터 | 앱이 아무것도 안 보냄 |
| 티맵 전환 시 | **앱 재배포** — 앱이 보내는 값을 바꿔야 함 | **설정 한 줄** |
| 고를 근거 | 앱은 상한(4)을 모른다 | 서버가 상한을 안다 |

⇒ **요청에서 `provider` 를 제거**하고 `app.navigation.provider` 가 활성 공급자를 정한다. **응답의 `provider` 필드는 남긴다** — 앱이 어느 내비를 띄울지 알아야 하는 값이다.

⚠ **자르기 판단을 앱에 넘기지 않는 이유가 그대로 여기에도 적용된다** — 앱이 고르면 기기마다 다른 공급자·다른 상한이 되어 **같은 회차가 폰마다 다른 경로로 안내**된다.

### Ruling 202 — 운행 시작 창 **±3분 → ±10분** (X-01 해소)

2026-08-31 사용자 확정. 대안 두 개(지연 사유 입력 후 시작 허용 · 관계자 원격 해제)를 **모두 폐기**한다 — 전자는 기사 단독 우회가 가능해 창의 의미가 없어지고, 후자는 관계자 미접속이면 운행 자체가 막힌다. **어느 쪽도 새 실패 지점을 만든다.**

**함께 확정된 것** — 출발 **30분 전 `confirmed` 시점부터 기사가 노선을 볼 수 있어야** 하며, 그 수단은 **별도 화면이 아니라 RUN-08 외부 내비 전달**이다. `API_SPEC §4.16` 은 `idle` 만 막으므로 **계약은 이미 맞고 빠진 것은 검사 조건**이다 ⇒ 목표 20 으로 등재.

⚠ **`±10분` 은 코드 상수다**(`§7` 규칙 10 — 전역 정책 상수는 `application.yml` 이 아니라 코드). 학원별 설정 대상이 아니다.

### Ruling 203 — 동승자가 없는 회차는 없다고 가정한다 (X-03 해소)

기사에게 승하차 기록 권한을 임시로 주는 안을 폐기한다. 채택했으면 `C-06`(승하차는 동승자 전용)이 **회차마다 갈리는 조건부 규칙**이 되어 인가 판정이 데이터에 의존한다 — `ARCHITECTURE §5` 3층 구조에서 가장 비싼 형태의 예외다. 결근은 운영에서 대체 동승자 배치로 흡수한다.

⇒ **Phase 9 권한 모델은 불변.** 승하차 = 동승자 전용, 도착 처리·운행 시작 = 기사 전용.

### Ruling 204 — 내비 상한은 **카카오 4곳**, 티맵은 미구현 (V 해소)

| 공급자 | 승하차지 | 근거 | MVP |
|---|:-:|---|:-:|
| `kakao` | **4** = 경유지 3 + 목적지 1 | SDK 레퍼런스 `navigateIntent(destination, option, viaList)` 의 `viaList` 가 **"경유지 목록(최대: 3개)"** 로 명시 | ● 단독 |
| `tmap` | — | 앱 실행 스킴의 경유지 파라미터에 **공식 근거 부재**(SK 가 규격 미공개). 상한 1 이면 `remaining` 이 `next` 와 같아져 기능이 성립하지 않음 | ➖ 미구현 |

⚠ **앱에서 사용자가 손으로 넣는 경유지 수(카카오 5)와 다른 앱이 넘겨 주는 수(3)는 별개 값이다.** 손 입력 수를 상한으로 잡으면 실제보다 넓게 잡아 **조용히 잘린다** — 이 항목의 유일한 사고 형태다.

⇒ 상한은 **`KakaoNavProvider` 한 곳에만** 둔다(목표 22). 조립·자르기 코드에 숫자가 흩어지면 공급자를 바꿀 때 한 곳이 남는다.

### Ruling 205 — `§4.3 GET /runs/{runId}/route` 는 **Phase 9 소유**

Phase 9 절 본문이 이 엔드포인트를 "`LOC-03`, Phase 10" 으로 적었다. **응답 필드를 직접 세면 다르다.**

`stops[]` · `current_stop` · `next_stop` · `skipped_notice` — **버스 위치 필드가 0개**다. 전부 확정 노선(Phase 7) + 미승차 반영(`C-05`)이라 **Phase 9 산출물만으로 구성된다.** `LOC-03` 태그는 이 데이터를 쓰는 **화면(M-09)** 귀속이지 데이터 출처가 아니다.

**반대로 이것이 없으면 `RUN-03`(운행모드, Phase 9 범위)에 노선 조회 수단이 부재**해진다 — 범위에 든 기능 ID 를 만들 재료가 사라진다.

⇒ `§4.3` 은 이 Phase 가 만든다. `next_stop.lat`·`lng`(외부 내비 콜백용)도 함께.

### 좌석 간 의존 — 2건뿐이고 둘 다 계약으로 끊는다

1. **T2 ↔ T3 — 하원 자동 종료.** "마지막 탑승자가 `alighted` 되는 순간 `finished`"(목표 10)는 T3 이 상태를 바꾸고 T2 의 전이 규칙이 판정한다. ⇒ **T2 가 `RunCompletionService` 를 먼저 만들고 T3 이 호출**한다. T3 은 이 서비스를 가짜 객체로 두고 진행하되 **호출했는지를 검사**한다.
2. **T4 ← T1 — `skipped` 판정.** 목표 18 의 "미경유 제외" 는 T1 의 `run_stop.status` 판정에 기댄다. ⇒ **저장 컬럼 값으로만 계약**하고(T4 는 `status='skipped'` 행을 시험 데이터로 직접 넣는다) 서로의 코드를 부르지 않는다.

⚠ **T2 와 T3 은 둘 다 `run_rider` 를 쓴다.** 파일은 안 겹치지만 **같은 테이블**이라 시험 데이터가 섞이면 판정이 오염된다 ⇒ **좌석마다 전용 테스트 DB**(`-PtestDbUrl=...`)를 준다.

### 병합 후 필수 절차 — Phase 8 에서 결함 9건이 여기서만 드러났다

1. **전 좌석 병합 후 단독 전체 실행** — 개별 브랜치는 전부 통과했는데 병합 후 9건이 나왔다. **이것이 유일한 탐지 수단이었다**
2. **충돌 해소 병합 직후 `./gradlew compileJava compileTestJava`** — Phase 8 에서 조율자가 컴파일 불가 트리를 병합했다
3. **이벤트 생성자 인자 순서와 리스너 중복 구독을 따로 본다** — 둘 다 `Long` 이면 순서가 뒤바뀌어도 컴파일된다. 같은 이벤트를 두 좌석이 각자 구독하면 알림이 2건 나간다

### 게이트 리뷰 발주문에 반드시 실을 것

> 이 워크트리는 너에게 배정된 일회용 사본이다. **여기서는 프로덕션에 결함을 심고 되돌리는 것이 필수**이며 정의의 읽기 전용 조항은 메인 저장소에만 적용된다. 변형마다 원복 후 `git status --porcelain` 이 빈 결과인지 확인하라. **판정문에 "내가 직접 심었는가" 를 명시하라.**

## 착수 후 정정 2건 (2026-08-31, T4 실측으로 드러남)

### 정정 1 — 목표 21 에서 `403` 이 누락돼 있었다 (조율자 오기)

원장 `docs/IMPLEMENTATION_PLAN.md` Phase 9 완료 조건은 **"확정 전 `idle` 회차 요청은 `409 RUN_NOT_CONFIRMED`, 배치되지 않은 회차는 `403`"** 인데, 이 표로 옮기면서 **뒤쪽 `403` 이 사라졌다.** 목표 18~22 어디에도 `403` 이 없었다(직접 계수 확인).

T4 가 "`FORBIDDEN` 경로가 시험에 없는데 목표 표에 명시가 없어 범위 밖으로 판단했다" 고 신고해 드러났다. **범위 밖이 아니라 표가 빠뜨린 것**이다.

⚠ **이것이 `phase-goal-loop §6` 이 말하는 그 사고다** — 파생본(목표 표)이 정본(원장 완료 조건)에서 항목 하나를 잃었고, 그 표가 판정 기준이라 **검사되지 않은 채 통과할 뻔했다.** 인가가 빠지면 배치되지 않은 사람에게 **남의 회차 좌표가 나간다.**

**교훈 — 목표 표를 만든 뒤 원장 완료 조건과 항목 수를 대조하라.** 이번엔 21항 → 표 23행으로 늘어난 것만 확인하고 **어느 항목이 어느 행으로 갔는지는 대조하지 않았다.**

### 정정 2 — 목표 22 의 검사 명령이 결함 없이도 항상 실패한다

원안 `grep -rn '\b4\b' run/navigation/` 은 **조율자 재현 결과 19건이 걸리고 전부 자바독의 `API_SPEC §4.16` 인용**이다. 즉 이 명령은 상한 리터럴의 산개 여부를 재지 못한다.

**검사 대상은 그대로 두고 오탐 원인만 뺀다** — `/* */` · `//` 주석을 제거한 뒤 코드 본문에서만 독립 리터럴 `4` 를 찾는다. T4 가 `NavigationCapConventionTest` 로 이미 그렇게 구현했고 그 방향이 옳다.

⚠ **문서 인용 문자열이 코드 검사에 섞이는 것은 이 저장소에서 반복될 형태다** — 자바독에 사양 절 번호를 적는 관례가 있어, 숫자·경로 문자열을 세는 검사는 **주석 제거를 기본으로** 둔다.
