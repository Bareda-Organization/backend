## 1. 배경과 문제

### 1.1 현재 운영의 문제

학원 통학버스 운영은 전화·카카오톡·엑셀 세 갈래로 분산. "우리 애 탔나요?" 질문 하나에 **학부모 → 학원 → 기사 → 학원 → 학부모** 왕복 연락이 필요.

| 문제 | 현재 상태 | 결과 |
|---|---|---|
| 승하차 사실의 소재 | 기사·동승자의 기억과 종이 명단 | 확인에 사람 개입 필수, 시간차 발생 |
| 당일 변경 접수 | 전화·카톡으로 학원에 개별 접수 | 접수 누락, 반영 시점 불명, 책임 소재 부재 |
| 노선 편성 | 엑셀 수기 편성 | 변경 반영이 사람 손 경유, 기사 배포본과 원본이 불일치 |
| 미승차 대응 | 현장 판단 | 이력 부재, 대응 시각 미기록 |
| 학원 간 데이터 | 학원별 독립 | 운영사 관점의 관제 부재 |

### 1.2 해결 방식

연락 사슬을 **앱 안의 상태값 하나**로 대체. 노선 편성 → 학생 승하차 → 학부모 안내 → 차량·운행인력 관리를 하나의 데이터 흐름으로 연결.

핵심 축은 **탑승 상태 5종**(`waiting` · `boarded` · `alighted` · `absent` · `no_show`, C-02). 이 값 하나가 학부모 푸시 · 관계자 현황 · 알림 로그 세 곳에 동시 반영되어 전화 확인을 대체.

### 2.2 사용자 6종

학부모 · 학생 · 버스기사 · 동승자 · 학원 관계자(학원당 1명) · 메인 관리자. **역할별 가입 경로·승인 주체 표는 [FEATURE_SPEC §1.2](./FEATURE_SPEC.md) 가 정의처** — 이 문서는 중복 기재하지 않음.

### 2.3 승인 주체가 두 갈래인 이유

관계자만 메인 관리자 승인 대상. 관계자는 학원 전체 데이터의 원본을 쥐는 **유일 계정**이며, 관계자 승인을 관계자 자신이 하면 최초 1명을 만들 주체가 부재. 학원당 1명 정원(C-01 · O-02)도 운영사 쪽에서만 강제 가능.

## 3. 목표 · 비목표

### 3.1 목표 (MVP)

| 목표 | 달성 판정 |
|---|---|
| 승하차 사실을 즉시 학부모에게 전달 | 상태 변경 → 푸시·현황·로그 3곳 동시 반영, **5초 이내** |
| 당일 변경이 규칙 안에서 종료 | 3구간 규칙으로 추가·삭제 마감 고정, 30분 이내 변경은 관리자 승인 + 이력으로 책임 소재 기록 |

## 5. 배차 · 노선 최적화 파이프라인

### 5.1 5단계

| 단계 | 정의 · 규칙 | 근거 기능 |
|---|---|---|
| 1. 회차 생성 | 등록된 요일·시간별 스케줄로 매일 그날의 `Run` 자동 생성 (호차 · 구분 · 출발 시각). 휴원·특강은 회차 임시 추가·취소로 처리하고 정규 스케줄은 불변 | SCH-01 · SCH-02 · SCH-03 |
| 2. 인력 배차 | 회차별 기사 배치 + 동승자는 노선 최적화 후 배차 시 자동 배정(수동 변경 가능). 근무 시간 불일치·동일 매니저 시간 겹침은 검출·경고. 당일 배치 변경은 매니저 앱에 즉시 반영 + 푸시 | MGR-05 · MGR-06 |
| 3. 입력 수집 | 확정 전까지 **그날의 일일 승하차지**(요일별 주소 + 일일 변경분)와 **금일 탑승 의사**(탑승 함/안 함)가 누적. 여기에 강제 추가·수동 조정·경유 지점 지정이 더해짐 | C-16 · ATT-01·02 · REQ-01~04 · RTE-06 · RTE-07 · RTE-10 |
| 4. 확정 · 최적화 | 출발 **30분 전** 배치가 최신 입력을 읽어 확정 노선 산출·재최적화 — 산출 기준은 **그 시점의 일일 승하차지 + 탑승 의사**. 탑승 정원 · 정차 시간 · 도착 마감 · 도로 제약 고려(가중치 기준은 보류, §10.1 G) | C-16 · RTE-02 · RTE-09 |
| 5. 배포 · 재최적화 · 잠금 | 확정 노선을 기사·동승자 앱에 배포. **②구간(30분 안쪽~출발 전) 승인분은 재최적화 후 재배포** — 관리자가 전/후 대조를 보고 선택. 관리자의 경유 지점 지정도 같은 경로. **운행 시작과 동시에 노선 잠금** — 이후 미등원 요청은 최적화 없이 미경유(`skipped`) 표시만 | RUN-07 · RTE-05 · RTE-10 · RUN-02 |

### 5.2 확정 배치의 두 시계 — 분리가 필요한 이유

배치 잡은 출발 30분 전 실행이 원칙이나 큐 적체·재시작으로 25분 전에 실행될 가능성이 존재. 이때 읽는 값과 판정 기준을 분리.

| 항목 | 처리 | 이유 |
|---|---|---|
| 읽는 값 | **배치 실행 시각 기준 최신** 탑승 의사 + 승인된 위치 변경 | 30분 전 스냅샷을 쓰면 "30분 전 ~ 실행 시각" 사이에 승인된 삭제가 확정 노선에 미반영 → 미탑승 학생을 태우러 가는 경로가 그대로 배포 |
| 30분 전 스냅샷 | **미생성** | 위와 동일 |
| 구간 판정 기준 | 항상 **출발 시각 − 30분** 시계 | 배치가 25분 전에 돌았다고 추가 마감이 25분 전으로 이동하면, 배치가 늦은 날에만 추가가 되는 비결정 동작이 발생 |
| 지연 실행 로그 | 실행 지연 시간을 기록 | 관계자가 원인 추적 |

> **흔한 오해** — "최신값을 읽는다"와 "구간 판정 기준"을 한 값으로 합치는 것. 두 값은 별개이며, 배치는 판정 결과를 읽어 노선을 만들 뿐 마감을 이동시키지 않음.

## 6. 확정 정책과 채택 이유

규칙 전문은 FEATURE_SPEC §2 (C-01~C-17). 이 절은 각 정책의 **채택 근거**만 기술.

### 6.1 시간 정책

| 정책 | 한 줄 | 채택 이유 | 규칙 |
|---|---|---|---|
| 노선 3종 분리 | 고정 노선 / 확정 노선 / 실시간 노선 | 학기 단위 편성(고정)과 그날 실제로 도는 코스(확정)를 한 레코드로 두면 당일 변경이 원본을 오염. 운행 중 반영분(실시간)까지 분리해야 기사 단말과 관계자 화면의 기준이 일치 | C-03 |
| 확정 시점 = 출발 **30분 전** | 매일 회차 출발 30분 전에 확정 노선 산출·배포 | 기사가 배포본을 확인하고 이동을 시작하기까지 필요한 최소 여유. 구 기획의 60분은 학부모의 당일 변경 접수 창을 과도하게 좁혀 전화 접수로 회귀 | C-03 · C-04 |
| 3구간 규칙 | ① 30분 전까지 승인 없이 즉시 반영 + 재최적화 / ② 30분 안쪽~출발 전은 관리자 승인 경유, **승인 시 재최적화·재배포** / ③ 운행 시작 후는 노선 변경 부재, 미등원 요청만 미정차로 반영 | 추가는 노선을 늘려 다른 학생의 도착 시각에 영향. 삭제는 노선을 줄이기만 하므로 타 학생 손해가 부재 — **비대칭은 의도된 설계** | C-04 |
| ②구간 승인의 효과 = **재최적화·재배포** | 승인 화면에 기존 노선과 재최적화 결과를 나란히 제시하고 관리자가 선택. 거절 시 기존 경로 유지 | 30분 안쪽이어도 버스는 아직 출발 전이라 기사가 주행 중이 아니고, 배포본은 다시 확인 응답을 받는다(RUN-07). 재최적화를 포기하면 빠진 학생의 승하차지를 그대로 도는 낭비가 남음. 자동 반영이 아니라 **관리자가 전/후 차이를 보고 선택**하게 해 무단 변경을 막음 | C-04 · A-05 · REQ-04 |
| ③구간은 **미등원 요청만** 수용 | 출발 후 접수분은 노선을 바꾸지 않고 해당 승하차지를 통과·미정차 처리. 추가·위치 변경은 불가 | 주행 중 경로 재계산·재배포는 기사가 이미 인지한 경로와 어긋나 주행 위험이 증가. 반면 "여기는 안 섭니다" 한 줄은 경로를 건드리지 않아 안전하게 전달 가능 | C-04 · C-05 |
| ②구간 **회차당 1회** | 한도 단위는 회차(`Run`) — 등원 회차와 하원 회차가 각각 1회씩. 소진 후 "금일은 변경할 수 없습니다" | 한도 부재 시 출발 직전 반복 요청이 관계자 승인 큐를 점유하고, 승인 화면의 카운트다운이 매번 초기화되어 판단 시간이 소멸. 서버 처리 실패는 횟수 미소진 — 사용자 귀책이 아닌 실패로 권리를 잃지 않도록 | C-04 · C-10 |
| ②구간 미응답 = **자동 거절 · 기존 노선 유지** | **출발 시각 도달 또는 운행 시작 중 먼저 오는 시점**에 서버가 자동 거절 + 학부모 통지, 횟수 미소진 | 자동 승인은 관계자 미확인 상태에서 노선이 바뀌어 책임 소재가 소멸. 기존 노선 유지는 이미 배포된 확정 노선과 일치해 기사 단말 재배포가 불필요. **운행 시작을 함께 마감 기준으로 둔 이유** — 운행 시작 버튼이 출발 시각 **±10분**이라 버스가 출발 시각보다 먼저 떠날 수 있고, 그 뒤에 승인이 들어오면 주행 중 재배포가 발생 (재검토 대상 — §10.2 X-02) |
| 운행 시작 **±10분** | 기사 운행 시작 버튼은 출발 시각 전후 10분 이내에만 활성 | 회차를 잘못 골라 시작하면 노선이 잠기고 위치 송신이 선택하지 않은 다른 회차에 붙음. 시간 창으로 오조작 자체를 차단. **±3분 에서 넓힌 이유** — 차량·교통 지연이 3분을 넘기면 시작 수단이 사라져 운행 자체가 막혔다. 예외 절차를 만드는 대신 창을 넓혀 흡수 (2026-08-31 확정, X-01 해소) |
| 미경유 = 표시만 | 잔여 0명 승하차지는 `skipped` 표시(취소선·순번 유지), 재최적화·ETA 재계산·경로 안내 부재. 발생 경로는 **③구간 미등원**과 **운행 중 미승차** 둘 | **주행 중**에 노선을 다시 계산해 기사 단말에 재배포하면 기사가 이미 인지한 경로와 어긋나 주행 위험이 증가. "이 승하차지는 미정차"만 전달하고 주행 판단은 기사에게 위임. 출발 전인 ②구간은 이 위험이 부재하므로 재최적화를 허용 | C-05 · C-04 |
| 관리자 경유 지점 지정 | 출발 전 확정 노선에 특정 지점을 강제 경유지로 추가 → 재최적화 → 전/후 대조 확인 후 배포 | 학원 사정·도로 통제·임시 집결지처럼 학생 주소로 표현되지 않는 경유 요구가 존재. 강제 추가(RTE-06)는 학생 단위라 이 경우를 담지 못함 | A-15 · RTE-10 |

### 6.2 역할 분리

| 정책 | 한 줄 | 채택 이유 | 규칙 |
|---|---|---|---|
| 승하차는 **동승자만** | 기사는 조회 전용, 상태 변경 API 도 403 | 운전 중 단말 조작을 원천 차단. 화면에서만 숨기면 기사 토큰으로 API 직접 호출이 가능하므로 서버에서 차단 | C-06 |
| 도착 처리는 **기사만** | 기사 포인터와 동승자 처리 명단은 별개로 동작 | 기사는 위치·주행 사실을 아는 유일 주체. 두 흐름을 한 포인터로 묶으면 동승자 처리 지연이 기사 진행을 차단 | RUN-04 |
| **최종 도착 처리 = 운행 종료** | 별도 종료 버튼 부재. 등원은 학원 도착 처리 즉시 종료 + 전원 자동 하차, 하원은 잔류 0명이 되는 시점에 서버가 자동 종료 | 운전 중 조작 수를 줄이는 것이 우선. 기사가 도착 처리와 종료를 따로 누르면 종료 누락으로 회차가 `moving` 에 남아 위치 송신과 관제 표시가 계속됨. 종료를 서버 판정으로 옮기면 미하차 상태에서 종료되는 경로 자체가 소멸 | C-15 · RUN-05 · RUN-06 |
| 등하원 비대칭 | 등원 = 승차 처리 + 종료 시 전원 자동 하차 / 하원 = 시작 시 전원 자동 승차 + 하차 처리 | 등원의 하차는 전원이 같은 지점(학원)에서 동시 발생, 하원의 승차도 동일. 개인별 처리를 요구하면 의미 없는 반복 조작만 증가 | C-07 |
| 승하차지 기반 노선 | 공용 정류장 개념 부재 — 학생 요일별 주소 좌표가 노선·명단·미경유 판정의 단위 | 학원 통학버스는 학생 집 앞 정차가 기본이며, 공용 정류장을 두면 요일별 주소 변경을 정류장 재매핑으로 흡수해야 해 원본이 이중화 | C-12 |
| 승하차 확인 = **사진 + 명단 육안** | 태그(NFC/QR) 미사용 | 태그는 단말·카드 배포와 분실 대응 비용이 발생하고, 카드 대여로 확인 자체가 무효화. 사진 육안 확인은 추가 하드웨어가 불필요 | M-12 |
| 일괄 승하차 부재 | 개인별 처리로만 운영 | 일괄 버튼은 실제 확인 없이 전원 처리하는 조작을 유발 — 승하차 기록의 신뢰도가 소멸 | FEATURE_SPEC §7 |

### 6.3 알림 · 통지

| 정책 | 한 줄 | 채택 이유 | 규칙 |
|---|---|---|---|
| "곧 도착" 알림은 **서버 자동 발송** | 기사 조작이 아니라 서버가 실시간 위치 기반 이벤트로 발송 | 기사 조작을 트리거로 두면 조작 누락·지연이 그대로 알림 누락. 기사 도착 처리는 기록·포인터 전진 용도로 분리 | NTF-04 · M-11 |
| `absent` ≠ `no_show` | 사전 OFF 는 학부모 알림 부재 + 관계자 통지 · 명단 제외 / 현장 미승차는 즉시 알림 + 에스컬레이션 | 두 상태를 합치면 학부모가 스스로 끈 결과에도 경보가 발송되어 알림 신뢰도가 하락하고, 진짜 미승차가 그 안에 묻혀 관측 불가 | C-02 |
| `absent` 학생은 매니저 앱 명단에서 행 제외 | 집계에는 "미등원 N명" 유지, 관계자 웹에서는 빨강으로 계속 표시 | 명단에 남기면 동승자가 승하차지별 인원을 육안으로 셀 때 실제 인원과 불일치. 관계자는 누가 왜 빠졌는지 확인이 필요하므로 웹에서는 존치 | RST-02 · RST-03 · RST-04 |
| **비상 알림은 끌 수 없다** | 매니저 앱의 비상 발신(EXC-04)은 학원 관계자·메인 관리자에게 항상 발송 + 팝업. **학부모·학생은 수신 대상 밖** | 사고 현장에서 조작 수를 최소화해야 하므로 수신 설정을 묻지 않음. 학부모를 뺀 이유는 **상황이 확인되지 않은 시점의 통지가 혼란을 키우기 때문** — 안내 시점·문구는 사실을 파악한 관계자가 정함. 관계자와 운영사에 **동시** 발송하는 이유는 관계자 1명 체제라 그가 응답하지 못하는 상황이 곧 공백이기 때문 | C-17 · EXC-04 · A-16 · O-07 |
| 안전 알림은 레코드가 항상 존치 | **지연** 알림은 설정 항목 자체가 미제공(항상 발송). **미승차는 설정 대상이나 off 가 차단하는 것은 단말 푸시뿐** — 알림 레코드는 항상 생성되어 앱 알림 목록·관계자 로그에 존치 | 학부모가 끄는 대상은 통지 자체가 아니라 **단말 푸시**. 레코드가 남으므로 미수신 주장이 나와도 발송 사실 확인이 가능해 책임 소재가 소멸하지 않음 | C-09 · NTF-03 · NTF-07 |
| 알림 문구에 자녀 이름 필수 | 알림은 자녀 선택과 무관하게 전 자녀 수신 | 다자녀 가정에서 자녀 선택 UI 의 현재 값에 알림을 종속시키면 선택하지 않은 자녀의 미승차 알림이 미수신 | P-02 · ATT-03 |
| 서버 처리 결과 통지 · 낙관적 UI 금지 | 서버 2xx 확인 후에만 "처리되었습니다" 표시, 실패는 명시 | 탑승 여부·위치 변경은 실패가 조용히 넘어가면 학부모는 반영된 줄 알고 아이는 버스를 미탑승 | C-10 |
| ETA 비노출 | 학부모·학생 앱에서 도착 예정 시각·탑승 인원 미표시 | 교통 상황에 따라 재계산될 때마다 값이 바뀌는 ETA 를 노출하면 그 시각이 약속으로 인식되어 항의·대기 유발. 메인 관리자 콘솔의 관제 ETA(O-05)는 내부 판단용이라 별개 | C-08 |
| 지연 알림은 **동승자 전용** | 사유 프리셋 + 메시지 수정 + 미리보기 + **5분 단위** 시간. 수신자는 **관계자 + 아직 탑승하지 않은 학생·학부모** | 기사는 운전 중이라 문구를 고르고 다듬는 조작 자체가 위험 — 승하차를 동승자에게 맡긴 것(C-06)과 같은 근거. 관계자를 수신자에 넣는 이유는 학부모 문의가 학원으로 먼저 오기 때문 | M-05 · NTF-06 |

### 6.4 인가 · 보안

| 정책 | 한 줄 | 채택 이유 | 규칙 |
|---|---|---|---|
| 인가는 서버 계층 | `pending` 차단 · 학원 격리 · 역할 권한 모두 서버에서 강제 | 프론트에서 라우팅만 막고 API 를 열어두면 토큰만으로 명단 API 를 직접 호출해 학원 학생 명단이 유출. 화면 숨김은 UX 이고 차단은 서버 책임 — 상호 대체 불가 | C-01 · FEATURE_SPEC §3.6 |
| 전원 form 가입 + 승인 | 코드 로그인·발급 계정 부재. 관계자도 form 가입 후 메인 관리자 승인 | 발급 계정 방식은 초기 비밀번호 전달 경로(문자·구두)가 그대로 유출 경로. 승인제는 계정 생성 책임을 사용자에게, 활성화 책임을 승인자에게 분리 | C-01 |
| 로그인 차단은 **계정 단위** | 실패 5회 누적 시 계정 차단, IP 차단 부재. 해제는 메인 관리자만 | IP 차단은 학원 와이파이·가정 공용 회선을 공유하는 무관한 사용자까지 잠금. 해제 권한을 메인 관리자로 올린 이유는 관계자 본인 계정이 차단됐을 때 해제 주체가 소멸하는 상황을 방지 | C-11 |
| 학원 비활성화해도 기존 로그인 유지 | 신규 가입만 차단, 검색 목록에서 제외 | 운행 중 계약 종료 처리가 들어오면 기사·동승자가 즉시 로그아웃되어 승하차 기록이 중단 | O-01 |
| 서비스 대상 = 학생 계정 보유자 | 휴대전화 보유 학생만 대상 | 자녀 연결 인증 코드와 학생 앱 알림이 모두 학생 계정을 전제 — 계정 없는 학생은 연결 수단이 부재 | C-13 |
| 자동 로그인 기본 | access(단기) + refresh(장기) | 기사·동승자가 출발 직전 로그인 절차를 거치면 ±10분 시작 창을 소모. 차단·로그아웃 시 refresh 무효화로 권한 회수 | C-14 |
| refresh 보관을 클라이언트별로 가름 | 앱은 기기 보안 저장소, 웹은 HttpOnly 쿠키 | 두 환경의 위협이 다름 — 앱에는 페이지 스크립트가 존재하지 않아 HttpOnly 로 막을 대상이 부재하고, 실제 위협은 기기 탈취라 OS 키체인이 대응 수단. 반대로 관계자 웹·메인 관리자 콘솔은 XSS 한 건으로 학생 명단·보호자 연락처·전 노선 관제 권한이 통째로 이전되므로 스크립트가 읽을 수 없는 보관처가 필요. **양쪽에 같은 방식을 강제하면 한쪽은 반드시 방어가 비어 있음** | C-14 |
| access 는 쿠키로 옮기지 않음 | access 는 양쪽 모두 `Authorization` 헤더 유지 | access 까지 쿠키로 바꾸면 전 엔드포인트가 CSRF 방어 대상이 되고 STOMP 구독 인가 경로까지 재설계 대상. refresh 하나만 쿠키로 내리면 탈취 시 노출분이 수명 짧은 access 로 한정되면서 변경 범위는 `/auth` 3개 엔드포인트에 국한 | C-14 |

### 6.5 정책 상수

**정의처는 [FEATURE_SPEC §2.1](./FEATURE_SPEC.md)** — 10개 항목(확정 30분 전 · ②구간 회차당 1회 · 운행 시작 ±10분 · 미승차 대기 3분 · 위치 송신 5~10초 · 승하차 반영 5초 · 알림 보관 14일 · 로그인 차단 5회 · 관계자 1명 · 지연 5분 단위). 값을 이 문서에 중복 기재하지 않음 — 두 곳에 두면 한쪽만 갱신되어 어긋남.
