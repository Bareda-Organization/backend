## 1. 서비스 정의

전화·카카오톡·엑셀로 흩어진 통학버스 운영을 하나의 상태값으로 통합. 노선 편성 → 학생 승하차 → 학부모 안내 → 차량·운행인력 관리를 한 데이터 흐름으로 연결.

### 1.1 제품 4종

학부모·학생 앱(390) · 매니저 앱(390, 운행모드 항상 다크) · 관계자 웹(1440) · 메인 관리자 콘솔(1440). **제품별 사용자·핵심 과업 표는 [PRD §2.1](./PRD.md) 이 정의처** — 이 문서는 중복 기재하지 않음.

### 1.2 사용자 6종

| 역할 | 소속 | 가입 경로 | 승인 주체 |
|---|---|---|---|
| 학부모 | 학원 | form 가입 + 학원 선택 | 학원 관계자 |
| 학생 | 학원 | form 가입 + 학원 선택 | 학원 관계자 |
| 버스기사 | 학원 | form 가입 + 역할·학원 선택 | 학원 관계자 |
| 동승자 | 학원 | form 가입 + 역할·학원 선택 | 학원 관계자 |
| 학원 관계자 | 학원 (1명) | form 가입 + 학원 선택 | **메인 관리자** |
| 메인 관리자 | 운영사 | 내부 발급 — 가입 경로 부재 | — |

**용어**

| 용어 | 정의 |
|---|---|
| **동승자** | 버스에 함께 타 학생 승하차를 관리하는 인력. **승하차 상태 변경의 유일한 주체** |
| **버스기사** | 운전과 승하차지 도착 처리 담당. 승하차 상태는 조회만 |
| **매니저** | 버스기사 + 동승자의 총칭. 매니저 앱의 사용자 |
| **승하차지** | 학생의 요일별 등하원 주소 좌표. 공용 정류장 개념 부재 (C-12) |
| **회차 (Run)** | 하루의 개별 운행 단위. 호차 × 등원/하원 × 출발 시각 |

## 2. 공통 규칙 (확정 정책)

| ID | 규칙 | 정의 |
|---|---|---|
| C-01 | form 회원가입 · 승인 | 전 인원(학부모·학생·버스기사·동승자·학원 관계자)이 form 회원가입·로그인 사용 — 코드 로그인·발급 계정 부재. 아이디·비밀번호 form 가입 → 등록된 학원 목록에서 검색·선택(`{학원명} · {지역} · {학원 코드}` 표기) → 승인으로 계정 활성화. 승인 전(`pending`)에는 승인 대기 화면 하나만 접근 가능하며 서버 인가 계층에서 그 외 모든 API 가 403 |
| C-02 | 탑승 상태 5종 | `waiting`(대기) · `boarded`(탑승 완료) · `alighted`(하차 완료) · `absent`(미등원 — 학부모 사전 OFF, 학부모 알림 부재) · `no_show`(미승차 — 현장에서 동승자가 처리, 즉시 알림 + 3분 에스컬레이션). **`absent` 와 `no_show` 는 반드시 구분** |
| C-03 | 노선 3종 | 고정 노선 = 학생 요일별 주소 기반의 상시 노선(최적화 가능). **확정 노선 = 그날의 일일 승하차지와 금일 탑승 의사를 입력으로 출발 30분 전에 산출하는 일일 노선.** 실시간 노선 = 운행 중 버스 기준, 확정 노선에 미승차·③구간 미등원까지 반영한 노선 |
| C-16 | 노선 산출의 입력 = 일일 승하차지 | 노선은 **학부모가 기입한 그날의 승하차지**를 기준으로 산출한다. 값은 요일별 주소(P-05)를 기본으로 하되 그날의 일일 변경(P-06)이 있으면 그것이 우선. 여기에 **금일 등하원 탑승 의사**(ATT-01 — 탑승 함/안 함)를 함께 반영해 대상 명단을 확정한 뒤 최적화 (RTE-02·09) |
| C-04 | 노선 변경 3구간 | 기준은 회차 출발 시각. **①** 출발 30분 전까지: 승인 없이 즉시 반영 — 일일 승하차지·탑승 의사 기준 추가·삭제 + 노선 재최적화. **②** 30분 안쪽~출발 전: 관리자 승인을 통해서만 반영 — **승인 시 노선 재최적화 후 재배포**. 승인 화면은 기존 노선과 변경 노선을 **나란히 제시해 관리자가 차이를 확인하고 선택**(A-05). 거절 시 **기존 경로 유지**. **회차당 1회만** — 한도의 단위는 회차(`Run`)이며 등원·하원이 각각 1회씩 보유. 소진 후 "금일은 변경할 수 없습니다" 안내. 서버 처리 실패 시 기존 상태 복구·횟수 미소진(C-10). **출발 시각 도달 또는 운행 시작(`moving` 전이) 중 먼저 오는 시점**에 미처리 요청은 **자동 거절** — 재최적화 없이 **기존 노선을 그대로 유지**하고 학부모 통지, 횟수 미소진. **③** 운행 시작 후: **노선 변경 부재.** 미등원(탑승 취소) 요청은 **승인 없이 즉시 수용**되며 해당 승하차지는 **경로상 경유하되 정차하지 않음**(`skipped`) — 추가·위치 변경·되돌리기는 불가 (C-05). ⚠ **① 의 "재최적화" 는 호출이 아니라 결과다** (2026-08-30, Ruling 198) — ①구간 동안 회차는 `idle` 이라 재최적화할 확정 노선이 부재하고, 반영은 뒤이은 확정 배치(RTE-02)가 탑승 의사를 읽어 산출하는 것으로 이뤄진다. 근거와 예외(임시 추가 회차)는 `API_SPEC §3.6` ① 각주 |
| C-05 | 미경유 승하차지 | 잔여 탑승자 0명이 된 승하차지는 `skipped` 처리(빨강 취소선, 순번 유지) — 미정차일 뿐 경로는 불변. 재최적화·ETA 재계산·경로 안내 부재. 발생 경로는 **③구간 미등원 요청**과 **운행 중 미승차(`no_show`)** 둘 — ②구간 승인분은 재최적화로 노선에서 제거되므로 여기 해당하지 않음 (C-04) |
| C-06 | 승하차 처리 주체 | 승하차 상태 변경은 **동승자만**. 기사는 조회만(운전 중 조작 방지). 일괄 처리 부재 |
| C-07 | 등하원 비대칭 | 등원 = 승하차지별 승차 처리 + **종료 시 전원 자동 하차 + 하차 알림 발송**. 하원 = 운행 시작 시 전원 자동 승차 + 승하차지별 하차 처리. **자동 처리분도 알림 대상** — 학부모가 "학원에 도착했다"를 알아야 하므로 발송 여부를 묻지 않음 (2026-08-24 확정) |
| C-15 | 최종 도착 처리 = 운행 종료 | **별도 운행 종료 버튼 부재.** 기사의 최종 지점 도착 처리가 운행 종료를 겸함. 등원은 학원(도착지) 도착 처리 즉시 `finished` + 전원 자동 `alighted`. 하원은 마지막 승하차지 도착 처리 시 도착만 기록되고 **종료는 보류**되며, 마지막 탑승자가 `alighted` 되는 순간 서버가 자동으로 `finished` 전이 — 미하차 학생이 남아 있는 동안 종료가 성립하지 않음 (RUN-04·05·06) |
| C-08 | 시간 정보 비노출 | 학부모·학생 앱에서 도착 예정 시각(ETA)·탑승 인원 미표시 — 노선에서 위치만. 메인 관리자 콘솔의 관제 ETA 는 별개(O-05) |
| C-09 | 변경분 색 규칙 | 당일 추가 = 초록, 삭제 = 빨강, 미경유 = 빨강 취소선. 상태 색은 그린(완료) / 앰버(이동·지연) / 레드(미승차·긴급) / 스톤(대기·종료), 3개 제품 공통 |
| C-18 | 외부 지도·지오코딩 = **네이버 API** | 경로·거리·ETA 산출과 주소 → 좌표 변환에 **네이버 API 를 사용**한다 (2026-08-24 확정). 클라이언트 지도 SDK 도 동일 공급자를 우선 검토 — 서버 계산 경로와 화면 표시가 어긋나지 않게 하기 위함 |
| C-17 | 비상 알림은 끌 수 없다 | 매니저 앱이 발신하는 비상 알림(EXC-04)은 **수신 설정 항목 자체가 부재** — 학원 관계자·메인 관리자에게 항상 발송되고 팝업을 병행. 지연 알림(NTF-07)과 같은 원칙이며 대상만 다름. 학부모·학생은 **수신 대상 밖** — 상황이 확인되지 않은 시점의 통지가 혼란을 유발하고, 안내 시점·문구는 관계자가 판단 |
| C-10 | 서버 처리 결과 통지 | 서버에 요청하는 모든 동작은 서버의 정상 처리 확인 뒤에만 "처리되었습니다" 표시. 타임아웃·서버 오류는 "처리되지 않았습니다" 명시. **낙관적 UI 금지** |
| C-11 | 로그인 보안 | 실패 5회 누적 시 **계정 단위** 차단(IP 차단 부재 — 근거는 PRD §6.4). 해제는 메인 관리자만. 아이디·비밀번호 복구는 전화번호 인증 또는 관리자 경유 (AUTH-08) |
| C-12 | 승하차지 기반 노선 | 공용 정류장 개념 부재 — 노선은 각 학생의 승하차지(요일별 주소 좌표) 기반으로 산출·정렬하고, 명단·승하차 처리·미경유 판정의 단위도 승하차지 |
| C-13 | 서비스 대상 | 휴대전화(학생 계정) 보유 학생만 대상 — 자녀 연결 인증 코드·학생 앱 알림이 모두 학생 계정 전제 |
| C-14 | 자동 로그인 · 토큰 | access 토큰(단기) + refresh 토큰(장기). **refresh 보관 위치는 클라이언트 종류로 가름** — 앱(매니저·학부모·학생)은 기기 보안 저장소, 웹(관계자 웹·메인 관리자 콘솔)은 서버가 내리는 **HttpOnly 쿠키**(브라우저가 보관하고 페이지 스크립트는 접근 불가). access 토큰은 양쪽 모두 `Authorization` 헤더로 전송하며 웹은 메모리에만 보관. 실행·새로고침 시 refresh 로 access 자동 재발급 — 자동 로그인 기본. refresh 만료·로그아웃·계정 차단 시 무효화 후 재로그인 요구 |

## 3. 도메인 모델

### 3.1 노선 3종의 관계

```
고정 노선 (Route)              학생 요일별 주소 기반, 상시 유지, 관계자가 편성·최적화
      │
      │  ← 탑승 의사(ATT) · 승인된 변경(REQ) · 강제 추가(RTE-06) · 수동 조정(RTE-07)
      ▼
확정 노선 (ConfirmedRoute)      출발 30분 전 배치가 산출, 일일 단위, 기사·동승자에 배포
      │
      │  ← 미승차(no_show)만 반영
      ▼
실시간 노선                      운행 중 버스 기준, 미경유(skipped) 표시 반영
```

고정 노선은 학기 단위로 유지되는 편성이고, 확정 노선은 그날 실제로 도는 코스. 확정 이후의 삭제는 재최적화 없이 미경유 표시만 (C-05).

### 3.2 엔티티

### 3.3 탑승 상태 (`RunRider.status`)

| 코드 | 라벨 | 색 | 변경 주체 | 의미 |
|---|---|---|---|---|
| `waiting` | 대기 | 스톤 | (초기값) | 명단에 있으나 미처리 |
| `boarded` | 탑승 완료 | 그린 | 동승자 / 자동(하원 시작) | 버스에 탑승 |
| `alighted` | 하차 완료 | 그린 | 동승자 / 자동(등원 종료) | 목적지에서 하차 |
| `absent` | 미등원 | 스톤 | 시스템 (학부모 사전 OFF 결과) | 당일 미탑승 |
| `no_show` | 미승차 | 레드 | 동승자 | 승하차지에 미출현 |

**전이**

```
waiting ──► boarded ──► alighted
   └─────► no_show   (종결 — 즉시 학부모 알림 + 3분 에스컬레이션)

absent  ── 확정 노선 산출 시점 부여. ②구간 승인 시에도 부여.
           기사·동승자 명단에서 행 제외, 집계에는 "미등원 N명" 유지
```

`absent` 학생은 매니저 앱 명단에서 **개인 행만** 제외하고 집계는 유지 (RST-04). 관계자 웹의 호차별 일일 명단(RST-03)에서는 빨강으로 계속 표시. 채택 근거는 PRD §6.3.

되돌리기(BRD-05)는 이력 보존 전제. 기발송 알림은 후속 처리 대상.

### 3.4 운행 상태 (`Run.status`)

| 코드 | 라벨 | 전이 조건 |
|---|---|---|
| `idle` | 운행 전 | 초기 |
| `confirmed` | 노선 확정 | 출발 **30분 전** 배치 실행 |
| `moving` | 운행 중 | 기사가 운행모드 시작 (출발 시각 ±10분에만 가능) |
| `finished` | 운행 종료 | **최종 지점 도착 처리**로 전이 (C-15). 등원은 도착 처리 즉시. 하원은 전원 `alighted` 된 시점에 서버가 자동 전이 — 미하차 잔류 중에는 `moving` 유지 |

`moving` 진입과 동시에 노선 전면 잠금 + 위치 송신 시작.

### 3.5 변경 구분 (`RunRider.change` / `Stop.change`)

| 코드 | 표기 | 의미 | 적용 대상 |
|---|---|---|---|
| `added` | 초록 하이라이트 | 당일 추가된 탑승자·승하차지 | 탑승자 · 승하차지 |
| `removed` | 빨강 하이라이트 | 당일 삭제된 탑승자 | 탑승자 |
| `skipped` | 빨강 + 취소선 | 미경유 승하차지 — 잔여 탑승자 0명 | 승하차지 |

`skipped` 승하차지는 목록에서 제거하지 않고 취소선으로 존치. 순번도 재부여 부재. 채택 근거는 PRD §6.1.

### 3.6 계정 상태 (`Account.status`)

| 코드 | 로그인 | 접근 범위 |
|---|---|---|
| `pending` | 성공 — 토큰 발급 | 승인 대기 화면 조회 · 로그아웃 **2개만**. 그 외 전 API 403 |
| `active` | 성공 | 역할별 권한 범위 |
| `rejected` | 성공 | 대기 화면에 거절 사유 표시 + 학원 재선택 재신청 진입점 |
| `blocked` | 실패 | 없음 — 해제는 메인 관리자 |

**판정 위치는 서버 인가 계층** — 화면 숨김은 UX 이고 차단은 서버의 책임이며 서로 대체 불가. 채택 근거는 PRD §6.4.

`pending` 계정이 수신하는 알림은 승인·거절 결과만. 운행 알림은 대상 밖.

| P-03 | 등하원 변경 (당일 토글) | 당일 등원/하원의 탑승 여부 토글 (ATT-01). ①구간 = 즉시 반영 + 재최적화. ②구간 = 관리자 승인 경유(회차당 1회, 승인 시 **재최적화·재배포**). ③구간 = 반영 불가. 어느 구간이든 서버 반영 여부를 사용자에게 리턴 (C-10). ②구간 요청은 홈·해당 회차에 **승인 대기 표시 + 출발까지 카운트다운**. 미탑승 = `absent` 기록·명단 제외 (ATT-02, C-04) |
| P-04 | 날짜별 등하원 정보 | 학생별(다자녀 포함) × 날짜별 등·하원 스케줄 조회 — 회차 · 탑승 승하차지 · 상태 |
| P-05 | 요일별 등하원 주소 설정 | 요일(월~일) × 등/하원별 승·하차 주소 직접 기입 — **기본 주소 개념 부재**, 노선 산출의 기준 (STU-05·06 연동). 변경이 없으면 매주 같은 요일의 주소가 반복 적용 |
| P-06 | 일일 스케줄 변경 | 특정 날짜 하루만 등하원 위치 변경 (REQ-01). ①구간 = 승인 없이 즉시 반영 + 재최적화. ②구간 = 관리자 승인 경유 (REQ-02). ③구간 = 불가. 신청 상태 `pending` / `approved` / `rejected` 조회 (REQ-03). **홈에 처리 대기 건수 배지**, 신청 목록의 각 행에 상태 뱃지(처리중 · 반영 · 거절) 표시 — 신청이 접수만 되고 결과를 못 보는 상태를 남기지 않음. **우선순위: 일일 변경 > 요일별 주소** — 해당 일만 적용, 이후 요일별 주소로 복귀 |
| P-07 | 실시간 버스 위치 | 선택된 자녀의 버스 위치 + 노선 (LOC-02). ETA·탑승 인원 부재 (C-08). 신호 유실 시 "마지막 확인 위치 · N분 전" |
| P-08 | 노선 자세히 보기 | 지도 + 실시간 위치 + 승하차지 요약 — **승차지 이전 2개 · 승차지 · 하차지만** 표시 (LOC-03). 동승자 연락 버튼 포함. 확정 전에는 고정 노선 + "확정 전" 배지, 변경분은 초록/빨강 |
| P-09 | 알림 목록 · 설정 | 승하차·스케줄 변경 알림 14일 보관, 미읽음 배지 (NTF-08). 설정 on/off 대상 = 도착 · 등하원 · 미승차. **지연 알림은 설정 항목 자체가 부재**(항상 발송) (NTF-07). off 는 푸시만 차단, 목록에는 존치 |

### 5.3 매니저 앱 — 버스기사 · 동승자

기사·동승자 계정을 구분. 기사 = 운행모드(**지도·주행 중심**), 동승자 = 승하차 명단 중심 — **동승자에게 지도 화면 부재**(노선·위치 데이터 조회 권한은 보유 — §6. 전용 지도 페이지가 부재할 뿐). 운행모드는 테마와 무관하게 항상 다크.

#### 공통

| ID | 기능 | 정의 |

| A-05 | 30분 안쪽 변경 승인 | ②구간의 등하원 토글·일일 스케줄 변경 요청(회차당 1회 한정, C-04)을 푸시로 즉시 수신 (REQ-05) → 승인 화면: 남은 시간 카운트다운, 영향 학생, 잔여 인원, 정원, 그리고 **기존 노선 vs 재최적화 결과의 대조** — 순서 변경 · 추가·제외되는 승하차지 · 전/후 예상 소요시간·거리 (REQ-04). 관리자가 그 차이를 보고 **승인 시 재최적화 노선을 배포**, 거절 시 **기존 경로 유지** + 사유 통지. **출발 시각 도달 또는 운행 시작 중 먼저 오는 시점**까지 미응답이면 자동 거절 — 기존 노선 유지 + 학부모 통지 (C-04). 승인 조작이 그 시점을 넘겨 도달하면 반영 부재. 처리 이력(누가·언제·무엇·자동 거절 여부·배포된 노선 버전) 저장 |

| A-07 | 수동 학생 조정 · 버스 간 이동 | 출발 버스 명단 제외 + 도착 버스에 강제 방문지 또는 기존 승하차지 추가 → **양쪽 노선 재최적화·배포**. 양쪽 영향을 함께 표시 (RTE-07) |
| A-08 | 고정 노선 관리 | 학생 요일별 주소 기반 노선 편성·최적화, 배치 매니저 표시 (RTE-01). 당일 확정 노선(30분 전 산출)과 별개 (RTE-02) |
| A-09 | 운행 스케줄 | 요일·시간별 운행 계획 등록 → 일일 회차 자동 생성, 특정일 임시 추가·취소 (SCH-01~03). 휴원·특강은 회차 임시 조정으로 처리하고 **정규 스케줄은 불변** |
| A-10 | 학생 관리 | 목록·검색·등록·수정·퇴원(soft delete, 오늘 명단은 유지) (STU-01~04). **관계자가 입력하는 것** — 이름 · **사진**(서버 저장, 매니저 앱 육안 확인 + 관계자 웹 열람, 얼굴인식 부재) · 성별 · 나이(학년) · 반 · **특이사항**(STU-07) · 혼자 귀가 가능 여부 (STU-08). **관계자가 입력하지 않는 것 둘** — ① **보호자 연락처는 연결된 보호자 계정에서 가져옴**(중복 입력 부재, 보호자가 번호를 바꾸면 자동 반영) ② **승하차 주소는 학부모가 요일별·일일로 등록**(P-05 · P-06) — 관계자는 조회만. **보호자 인계 정책 부재** — `alighted` 가 최종 상태 |
| A-11 | 차량 관리 | **관계자가 등록하는 것** — 호차명 · 차량번호 · 정원. **학생 탑승 가능 인원은 배차 시 자동 계산**(= 정원 − 기사 − 동승자) — 관계자가 직접 입력하지 않음. 계산값 초과 배정은 차단 (BUS-01~04) |
| A-12 | 매니저 관리 · 배치 | 기사/동승자 CRUD — 역할이 앱 권한을 결정 (MGR-02·03). **동승자는 노선 최적화 후 배차 시 자동 배정** — 근무 시간·중복 배치 충돌 검증 (MGR-05·06). 배치 중 삭제 차단 (MGR-04) |
| A-13 | 알림 로그 · 수신 확인 | 전송 알림 전수 조회(시각 · 호차 · 대상 · 종류 · 확인 여부) (NTF-11). 중요 통지는 수신 확인까지 추적, 미확인 배지 (NTF-10) |
| A-14 | 전체 차량 위치 | 운행 중 전 차량 위치·진행·지연을 지도에서 모니터링 (MON-07) |
| A-15 | 경유 지점 지정 | **출발 전, 이미 산출된 확정 노선에 관리자가 특정 지점을 강제 경유지로 지정** (RTE-10). 지점은 주소·지도 선택으로 입력하고 주소 검증을 거침 (STU-05). 지정 즉시 그 지점을 포함해 재최적화 → 기존 노선과의 대조(순서 변경·전/후 소요시간·거리)를 제시하고 관리자가 확인 후 배포. 배포 시 기사·동승자에 푸시 + 변경 확인 응답 대상 (RUN-07). **운행 시작 후에는 지정 불가** (C-04 ③) |
| A-16 | **비상 알림 수신 · 처리** | 매니저 앱의 비상 알림을 즉시 수신 (EXC-04) — 팝업 + 미확인 배지. 화면에 유형 · 발신자 · 호차 · 회차 · **발신 시점 위치** · 기사·동승자 연락처 · 탑승자 수를 함께 표시. `[확인]` 으로 접수 응답하면 발신자 앱에 "학원이 확인했습니다" 표시. 확인·조치 이력(누가·언제·무엇) 저장. 미확인 상태는 메인 관리자 콘솔에도 노출 |
| A-17 | 학원 설정 | 학원별 임계값 조회·수정 — 현재 대상은 **미승차 대기 시간**(기본 3분, EXC-01 · M-13). 정책 상수 중 유일하게 학원별로 갈리는 값이며, 나머지 상수(30분 · ±10분 · 14일 · 5회 등)는 전역이라 **수정 대상 밖** |

### 6.2 권한 카탈로그

**역할 문자열을 코드에 흩지 않고 권한 상수를 거친다.** 위 매트릭스를 그대로 코드에 옮기면 `if (role == DRIVER || role == ESCORT)` 같은 판정이 호출 지점마다 복제되어, 역할이 하나 늘 때 전수 수정이 필요해진다. 권한을 한 겹 두면 **역할↔권한 매핑 한 파일만** 고치면 된다.

| 권한 | 뜻 | 보유 역할 |
|---|---|---|
| `STUDENT_READ_BASIC` | 학생 이름 · 반 · 탑승 상태 | 관계자 · 기사 · 동승자 · 메인관리자 · 학부모(자녀) · 학생(본인) |
| `STUDENT_READ_SENSITIVE` | 사진 · 주소 원문·좌표 · 특이사항 · 연락처 원본 | 관계자 · 메인관리자 |

| `ROSTER_READ` | 회차 명단 조회 | 관계자 · 기사 · 동승자 · 메인관리자 |

### 6.3 민감 데이터 등급

학생 개인정보를 다루므로 **같은 자원 안에서도 필드별로 접근이 갈린다.** 역할이 자원에 닿는다고 전 필드를 주지 않는다.

| 등급 | 필드 | 취급 |
|---|---|---|
| **L1 기본** | 이름 · 반 · 탑승 상태 · 승하차지 표시명 | 역할 범위 안에서 그대로 노출 |
| **L2 마스킹** | 보호자 전화번호 · 학생 전화번호 | 매니저 앱은 **마스킹**(`010-2XXX-8814`, NFR-06). 원본은 `STUDENT_READ_SENSITIVE` 보유자만 |
| **L3 제한** | 학생 사진 · 주소 원문·좌표 · 특이사항 · 보호자 연락처 원본 | 권한 보유자만. **조회 시 감사 로그 기록** (SYS-01) |

- **학생 사진은 L3 이나 매니저 앱에 예외 허용** — 승하차 확인이 사진 + 명단 육안 대조라 기능 성립에 필수 (C-06 · M-03). 대신 `STUDENT_READ_PHOTO` 로 권한을 갈라 **다른 L3 필드는 주지 않는다.**
- **메인 관리자의 L3 접근은 관제 목적으로 한정** — O-06 이 승하차지별 학생 리스트에 사진·연락처를 요구. 운영 데이터 변경 권한은 부재 (§6.1).
- 학부모는 **본인 자녀에 한해** L1~L3, 학생은 **본인에 한해** L1.

### 6.4 RBAC 만으로 막지 못하는 것

**역할 권한은 "무엇을 할 수 있는가"만 답한다.** "어느 자원에 대해"는 별도 검증이 필요하다 — 이것이 `ARCHITECTURE §5.1` 의 ③층이다.

| 검증 | 없으면 생기는 일 |
|---|---|
| 학원 격리 | 다른 학원 관계자가 `ROSTER_READ` 로 남의 학원 명단 조회 |
| 보호자↔자녀 | 학부모가 같은 학원 남의 아이 정보 조회 |
| 매니저↔회차 | 배치되지 않은 회차의 명단·위치 조회 |
| 학생 본인 | 학생이 다른 학생의 노선 조회 |

**권한 검사를 통과했다고 접근이 성립하지 않는다.** 두 검사는 순차이며 둘 다 필요하다.
