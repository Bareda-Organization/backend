School-Bus 코드 컨벤션

이 문서는 백엔드(Spring Boot 4 · Java 25)와 프론트(Next.js App Router)가 실제로 따르고 있는 규칙을 명문화한 것입니다. 새 코드는 이 컨벤션을 준수합니다.

0. 핵심 원칙 한 줄 요약

"기능 단위로 패키지를 나누고, 각 계층은 인터페이스(계약)에만 의존하며, 갈아끼울 지점은 포트/어댑터로 뽑는다."

  • 패키지 = 기능(도메인) 단위: src.backend.<domain>.{controller,service,repository,entity,dto}
  • 계층 흐름 단방향: Controller → Service → Repository (역방향 의존 금지)
  • Service 는 인터페이스 + 구현체로 분리(확장·교체 대비)
  • 생성자 주입 + final 필드만 사용(필드 @Autowired 금지)
  • Javadoc 은 "무엇"이 아니라 "왜"를 한국어로 설명

1. 백엔드 계층 구조와 데이터 흐름

한 요청은 아래 순서로 흐릅니다. 각 계층의 책임을 섞지 않는 것이 규칙입니다.

  1. Controller: HTTP 매핑 + 입력 검증(@Valid) + 역할 인가(@PreAuthorize). 비즈니스 로직 없음
  2. Service(interface): 계약. Service(Impl): 트랜잭션 경계(@Transactional) + 업무 규칙 + 테넌트 격리 검사
  3. Repository: 저장/조회만. Spring Data 인터페이스
  4. 응답: 항상 ApiResponse<T> 로 감싸 반환
📊 요청 → 처리 → 응답 계층 흐름
Java · LocationController 
@RestController
@RequestMapping("/api/locations")
public class LocationController {

    private final LocationService locationService; // 인터페이스에만 의존

    public LocationController(LocationService locationService) { // 생성자 주입
        this.locationService = locationService;
    }

    @GetMapping("/children")
    @PreAuthorize("hasRole('PARENT')")             // 역할 인가는 Controller
    public ApiResponse<List<LocationView>> children(@AuthenticationPrincipal AuthUser parent) {
        return ApiResponse.ok(locationService.getChildrenLocations(parent)); // 응답 래핑
    }
}

2. 서비스 = 인터페이스 + 구현체 (MUST)

모든 서비스는 계약(interface)과 구현(*Impl)을 나눕니다. 컨트롤러·테스트는 인터페이스에만 의존하고, Spring 이 런타임에 구현체 빈을 주입합니다. 로직을 확장하거나 구현을 통째로 교체해도(예: 인증을 OAuth 로) 호출부는 그대로입니다.

📊 인터페이스 의존 + 구현체 주입(교체 가능)
Java · RideEventService (계약) 
public interface RideEventService {
    RideEventResponse record(AuthUser driver, RecordRideRequest req);
    RideEventResponse correct(AuthUser actor, Long eventId, CorrectionRequest req);
    List<RideEventResponse> getMyRecords(AuthUser student, LocalDate date);
}

@Service
public class RideEventServiceImpl implements RideEventService {
    // 생성자 주입 · @Override · @Transactional 로 구현
    @Override
    @Transactional
    public RideEventResponse record(AuthUser driver, RecordRideRequest req) { ... }
}
흔한 오해: "Spring Data Repository 도 *Impl 을 직접 만들어야 인터페이스 패턴이다"라고 오해하기 쉽습니다. Repository 는 이미 인터페이스이고 구현체를 Spring 이 프록시로 자동 생성하므로 그 자체가 인터페이스+구현체입니다. 손으로 Impl 을 얹는 것은 오히려 안티패턴입니다.

3. 갈아끼울 지점은 포트/어댑터 (교체지점)

"미래에 데이터 소스가 바뀔 것"이 확실한 지점만 별도 포트(인터페이스)로 뽑고, 상황별 어댑터(구현체)를 둡니다. 위치추적이 대표 예입니다 — MVP 는 Mock 좌표, 실서비스는 학생폰 GPS.

📊 LocationSource 포트 + 어댑터 교체 (설정 플래그로 전환)
실측 확인: 관리자 관제 조회 시 Mock 좌표가 origin=MOCK 으로, 학생이 POST /api/locations 로 직접 보고하면 origin=GPS 로 같은 저장소에 합류함을 end-to-end 로 검증했습니다.

4. 공통 응답·예외 처리

성공·실패 모두 ApiResponse<T> 한 형태로 내려 프론트가 한 가지로 파싱합니다. 예외는 컨트롤러에 흩뿌리지 않고 GlobalExceptionHandler 한 곳에서 BusinessException/ErrorCode 기준으로 상태코드+메시지를 매핑합니다.

Java · 응답 규칙 
// 성공
return ApiResponse.ok(data);            // { success:true, data, message:null }
// 업무 예외 (Service 에서 던짐)
throw new BusinessException(ErrorCode.FORBIDDEN, "담당 기사만 처리할 수 있습니다");
// → GlobalExceptionHandler 가 403 + { success:false, data:null, message } 로 변환

5. 보안 · 멀티테넌시 (권한 이원화)

권한을 두 축으로 나눕니다. 섞으면 "역할은 맞지만 남의 학원 데이터를 보는" 구멍이 생깁니다.

축무엇어디서
역할(Role)STUDENT/PARENT/DRIVER/ACADEMY_ADMIN/PLATFORM_ADMIN 인가Controller @PreAuthorize("hasRole(...)")
학원(Tenant) 격리"어느 학원 데이터를 볼 수 있나"Service 에서 TenantGuard.resolveTenantId(...)
  • 인증은 Spring Security + JWT. 필터가 토큰의 memberships("tenantId:ROLE") 로 principal 을 복원 → DB 조회 없이 인가
  • 세션 없음(STATELESS), 미인증 401 · 권한부족 403

6. 프론트 역할 기반 라우팅

"가상 주소" 하드코딩 대신 Next.js 실제 라우트 + 로그인 게이트 + 역할 가드를 씁니다. 새로고침·뒤로가기·북마크가 살고, 라우트별 레이아웃(폰 셸 vs 웹 셸)이 자연스럽습니다.

  1. 로그인 → 백엔드 /api/auth/login(프록시 경유) → JWT 저장
  2. 토큰의 role 로 roleHome(role) 계산 → 모바일이면 /app/[role], 웹이면 /console/[role]
  3. RoleShell 가드: 세션 없으면 /login, URL 역할 ≠ 세션 역할이면 자기 홈으로 리다이렉트
📊 로그인 후 역할 라우팅 결정
JavaScript · lib/roles.js 
export function roleHome(role) {
  const cfg = ROLE_CONFIG[role];
  if (!cfg) return '/login';
  return cfg.medium === 'mobile' ? `/app/${cfg.key}` : `/console/${cfg.key}`;
}

8. 검증(Two-Pass)

문서·코드 변경 후 아래를 확인합니다.

  • Pass 1(정확성): 본문 규칙이 실제 코드와 일치 · 다이어그램 박스/화살표가 본문 단계와 1:1
  • Pass 2(구조): <svg> 짝 일치 · marker id 중복 0 · viz-frame 내 <pre> 0 · code-card 수 = language-* 수 · Prism 3종 로드
주의: 이 문서의 규칙은 "지금 코드가 실제로 그렇게 되어 있음"을 전제로 합니다. 코드와 문서가 어긋나면 코드의 실제 동작을 사실로 보고 문서(또는 코드)를 맞춥니다.
