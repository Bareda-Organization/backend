이 문서는 백엔드(Spring Boot 4 · Java 25)와 프론트(Next.js App Router)가 따르는 규칙을 명문화한 캐논(canon) 문서입니다.

Phase 2 모듈별 재편은 완료됐습니다 — 현재 15개 모듈 전체가 이 문서의 규칙(선별적 spec/impl 분리, 이벤트 기반 통신)을 따릅니다 — 이력·상세는 PROJECT_MASTER_PLAN.md 12장.

0. 핵심 원칙 한 줄 요약

"패키지는 기능 단위로 나누고, 쓰기(Command)와 읽기(Query)를 분리하며, 모듈 간 통신은 이벤트(Kafka)로, 갈아끼울 지점만 포트/어댑터로 뽑는다."

  • 패키지 = 기능(도메인) 단위: src.backend.<domain>.{controller,command,query,entity,event,projection,repository,dto,infrastructure} — 엔티티 패키지는 entity/가 표준(notification·routing 두 모듈만 역사적 이유로 domain/ 사용, 일괄 rename은 범위 밖 확정)
  • 계층 흐름 단방향: Controller → Command/Query → Domain/Repository (역방향 의존 금지)
  • spec/impl 은 "바뀔 가능성이 있는 것"에만: 단순 CRUD 는 concrete 클래스 하나로 충분
  • CQRS: Command(쓰기)와 Query(읽기)를 분리하고, Command 는 Query 를 호출하지 않는다
  • 모듈 간 통신은 이벤트 우선: 직접 호출 체인 대신 과거형 이벤트 발행 → Kafka → 구독
  • 생성자 주입 + final 필드만 사용(필드 @Autowired 금지)
  • 주석은 "무엇"이 아니라 "왜"를 한국어로 설명

1. 백엔드 계층 구조와 데이터 흐름

한 요청은 아래 순서로 흐릅니다. 각 계층의 책임을 섞지 않는 것이 규칙입니다.

  1. Controller: HTTP 매핑 + 입력 검증(@Valid) + 역할 인가(@PreAuthorize). 비즈니스 로직 없음
  2. Command / Query(또는 단순 CRUD 는 concrete Service): 트랜잭션 경계(@Transactional) + 업무 규칙 + 테넌트 격리 검사. Command 는 쓰기 후 이벤트를 발행, Query 는 조회만
  3. Repository: 저장/조회만. Spring Data 인터페이스(JPA) 또는 비-JPA impl(Redis 등)
  4. 응답: 항상 ApiResponse<T> 로 감싸 반환
📊 요청 → 처리 → 응답 계층 흐름
Java · LocationController 
@RestController
@RequestMapping("/api/locations")
public class LocationController {

    private final LocationQueryService queryService; // concrete 에 직접 의존(단일 구현)

    public LocationController(LocationQueryService queryService) { // 생성자 주입
        this.queryService = queryService;
    }

    @GetMapping("/children")
    @PreAuthorize("hasRole('PARENT')")             // 역할 인가는 Controller
    public ApiResponse<List<LocationView>> children(@AuthenticationPrincipal AuthUser parent) {
        return ApiResponse.ok(queryService.getChildrenLocations(parent)); // 응답 래핑
    }
}

2. 패키지 구조 (표준 모듈 레이아웃)

모든 도메인 모듈(location, notification, rideevent 등)은 아래 9개 하위 패키지 중 필요한 것만 둡니다. 모든 모듈이 9개를 다 가져야 하는 건 아닙니다 — CQRS·이벤트가 필요 없는 단순 모듈은 controller/service/repository/entity/dto 만으로도 충분합니다.

📊 도메인 모듈 표준 패키지 레이아웃
주의: 이 9분류는 "CQRS + 이벤트가 필요한 모듈"의 최대 형태입니다. tenant·student 처럼 단순 CRUD 뿐인 모듈까지 command/query/event/projection 을 억지로 만들지 않습니다 — 3장 판단 기준을 먼저 적용하세요.

3. spec/impl 판단 기준 — "바뀔 가능성이 있는가"

모든 클래스에 인터페이스를 만드는 것이 목적이 아닙니다. "구현이 바뀌거나 늘어날 가능성이 있는가?" 이 질문 하나로 spec(interface)+impl 분리 여부를 판단합니다. 전기 콘센트 규격(포트)은 고정해 두고, 실제로 꽂히는 전자기기(어댑터)만 바뀌는 것과 같은 원리입니다 — 콘센트 모양이 자주 바뀌는 게 아니라면 규격화(인터페이스화)할 이유가 없습니다.

📊 spec/impl 분리 판단 트리
Java · 판단 예시 비교 
// YES — 포트: Mock/Phone/Bus/Beacon 등 구현체가 여러 개 존재/예정
public interface LocationSource {
    boolean isActive();
    void tick();
}

// NO — 구현이 하나뿐이고 바뀔 계획이 없음: concrete 로 바로 구현
@Service
public class BusService {
    private final BusRepository busRepository; // 생성자 주입 + final
    // 인터페이스 없이 바로 구현
}
흔한 오해: "Spring Data Repository 도 *Impl 을 직접 만들어야 인터페이스 패턴이다"라고 오해하기 쉽습니다. Repository 는 이미 인터페이스이고 구현체를 Spring 이 프록시로 자동 생성하므로 그 자체가 인터페이스+구현체입니다. 손으로 Impl 을 얹는 것은 오히려 안티패턴입니다.

포트 실사용 예 — LocationSource 교체지점

"미래에 데이터 소스가 바뀔 것"이 확실한 지점을 별도 포트(인터페이스)로 뽑고, 상황별 어댑터(구현체)를 둡니다. 위치추적이 대표 예입니다 — MVP 는 Mock 좌표, 실서비스는 학생폰 GPS.

📊 LocationSource 포트 + 어댑터 교체 (설정 플래그로 전환)
실측 확인: 관리자 관제 조회 시 Mock 좌표가 origin=MOCK 으로, 학생이 POST /api/locations 로 직접 보고하면 origin=GPS 로 같은 저장소에 합류함을 end-to-end 로 검증했습니다.

4. CQRS + 이벤트 기반 통신(Kafka) + Infrastructure 계층

CQRS(Command Query Responsibility Segregation)는 쓰기와 읽기를 서로 다른 클래스로 분리하는 패턴입니다. 은행에 비유하면 입금 창구(Command)는 느리더라도 반드시 정확해야 하고, 잔액조회 ATM(Query)은 정확성보다 빠른 응답이 우선입니다 — 이 둘의 요구사항이 다르므로 아예 다른 클래스로 나눕니다.

  1. Command: 생성·수정·삭제만 담당하는 concrete 서비스. 저장 후 과거형 이벤트를 발행한다
  2. Query: 조회 전용 concrete 서비스. Command 를 호출하지 않는다(단방향)
  3. Event: Command 가 커밋을 마친 뒤(AFTER_COMMIT)에만 Kafka 로 발행 — 우체국 사서함처럼, 보내는 쪽은 넣고 바로 돌아가고 받는 쪽(Consumer)은 각자 편한 시점에 확인한다
  4. Projection: 이벤트를 구독해 조회 전용 읽기모델(Redis)을 갱신한다. 비즈니스 로직은 두지 않는다
  5. Infrastructure: Kafka·Redis·FCM 등 외부 기술은 이 계층에서만 다루고, Command/Query/Domain 은 구현 기술을 모른다(Port 를 통해서만 접근)
📊 CQRS 쓰기/읽기 분리 + Kafka AFTER_COMMIT 흐름 (location 예시)
Java · location (목표 구조 예시, Phase 3 예정) 
// event/ — 과거형 record. Command/Query 를 이름에 쓰지 않는다
public record LocationUpdatedEvent(Long studentId, Double lat, Double lng, Instant occurredAt) {}

// command/ — concrete, 쓰기 전용
@Service
public class LocationCommandService {
    private final LocationRepository locationRepository;      // 저장(port)
    private final ApplicationEventPublisher eventPublisher;    // 인프로세스 발행(Spring 표준)

    @Transactional
    public void ingest(Long studentId, Double lat, Double lng) {
        locationRepository.save(studentId, lat, lng);
        eventPublisher.publishEvent(new LocationUpdatedEvent(studentId, lat, lng, Instant.now()));
    }
}

// query/ — concrete, 읽기 전용. command 를 호출하지 않는다
@Service
public class LocationQueryService {
    private final LocationRepository locationRepository; // 같은 port, 읽기만 사용
    public List<LocationView> getChildrenLocations(AuthUser parent) { ... }
}

// global/event/ — 커밋 후에만 Kafka 로 내보내는 표준 relay
@Component
public class DomainEventRelay {
    private final DomainEventPublisher kafkaPublisher; // port

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void relay(LocationUpdatedEvent event) {
        kafkaPublisher.publish(event); // 롤백되면 이 메서드 자체가 호출되지 않는다
    }
}

Infrastructure 계층 — 외부 기술은 여기에만

Kafka·Redis·FCM·S3 같은 외부 기술은 infrastructure/ 패키지의 어댑터에만 두고, Command/Query/Domain 은 Port(interface)를 통해서만 접근합니다. 위 다이어그램의 노란 상자(Kafka, Projection)가 모두 infrastructure 위치입니다.

Java · global/infrastructure/KafkaEventPublisher 
public interface DomainEventPublisher {           // global/event/ — port
    void publish(DomainEvent event);
}

@Component                                          // global/infrastructure/ — impl
public class KafkaEventPublisher implements DomainEventPublisher {
    private final KafkaTemplate<String, Object> kafkaTemplate;

    @Override
    public void publish(DomainEvent event) {
        // 토픽 = 클래스명에서 Event 접미사 제거 후 케밥 케이스 (RideCompletedEvent → ride-completed)
        // 파티션 키 = tenantId — 같은 학원 이벤트는 같은 파티션에 쌓여 발생 순서 보장
        kafkaTemplate.send(toTopic(event.getClass()), String.valueOf(event.tenantId()), event);
    }
}

모듈 간 직접 호출 대신 이벤트로

서비스 간 직접 호출 체인은 한 모듈의 실패나 지연이 그대로 전파되고, 모듈을 늘릴 때마다 호출부를 계속 고쳐야 합니다. 대신 Command 가 과거형 이벤트를 발행하고, 관심 있는 모듈이 각자 구독합니다.

권장금지
흐름RideEvent → Kafka → NotificationRideService → NotificationService → HistoryService → StatisticsService
결합도발행자는 구독자를 모른다호출자가 모든 피호출자를 알아야 한다
확장새 구독자 추가 = 새 Consumer만 추가새 기능마다 기존 서비스 수정

새 이벤트는 반드시 과거형으로 짓습니다: LocationUpdatedEvent, RideCompletedEvent, StudentBoardedEvent, SosTriggeredEvent. Command/Query 라는 단어는 이벤트 이름에 쓰지 않습니다.

DB↔Kafka 이중쓰기 정합성: 서비스가 DB 저장과 Kafka 발행을 같은 트랜잭션에 두면, 롤백 시 유령 이벤트가 나가거나 커밋 후 브로커가 다운되면 이벤트가 유실됩니다. 표준 패턴은 ApplicationEventPublisher 로 인프로세스 발행 → @TransactionalEventListener(phase = AFTER_COMMIT) 가 KafkaEventPublisher.publish() 호출 — 커밋 후에만 Kafka 로 나갑니다. 더 강한 보장(브로커 다운까지 방어)은 outbox 패턴이며, MVP 는 AFTER_COMMIT 까지만 하고 하드닝 과제로 남깁니다.

흔한 오해: "Query 가 Command 를 절대 호출하지 않는다 = 항상 오래된 데이터만 보인다"고 오해하기 쉽습니다. 실제로는 Kafka consumer 가 커밋 직후 곧바로 Projection 을 갱신하므로 아주 짧은 지연만 있는 결과적 일관성(eventual consistency)입니다. 또한 Kafka 는 최소 한 번(at-least-once) 전달이라 같은 이벤트가 중복 소비될 수 있는데, NotificationService.notify 의 dedupKey unique 제약이 이미 이 중복을 막는 방어막 역할을 합니다 — Kafka 전환으로 이 설계가 오히려 더 중요해집니다.

5. 공통 응답·예외 처리

성공·실패 모두 ApiResponse<T> 한 형태로 내려 프론트가 한 가지로 파싱합니다. 예외는 컨트롤러에 흩뿌리지 않고 GlobalExceptionHandler 한 곳에서 BusinessException/ErrorCode 기준으로 상태코드+메시지를 매핑합니다.

Java · 응답 규칙 
// 성공
return ApiResponse.ok(data);            // { success:true, data, message:null }
// 업무 예외 (Command/Query 에서 던짐)
throw new BusinessException(ErrorCode.FORBIDDEN, "담당 기사만 처리할 수 있습니다");
// → GlobalExceptionHandler 가 403 + { success:false, data:null, message } 로 변환

6. 보안 · 멀티테넌시 (권한 이원화)

권한을 두 축으로 나눕니다. 섞으면 "역할은 맞지만 남의 학원 데이터를 보는" 구멍이 생깁니다.

축무엇어디서
역할(Role)STUDENT/PARENT/DRIVER/ACADEMY_ADMIN/PLATFORM_ADMIN 인가Controller @PreAuthorize("hasRole(...)")
학원(Tenant) 격리"어느 학원 데이터를 볼 수 있나"Command/Query 에서 TenantGuard.resolveTenantId(...)
  • 인증은 Spring Security + JWT. 필터가 토큰의 memberships("tenantId:ROLE") 로 principal 을 복원 → DB 조회 없이 인가
  • 세션 없음(STATELESS), 미인증 401 · 권한부족 403

7. 프론트 역할 기반 라우팅

"가상 주소" 하드코딩 대신 Next.js 실제 라우트 + 로그인 게이트 + 역할 가드를 씁니다. 새로고침·뒤로가기·북마크가 살고, 라우트별 레이아웃(폰 셸 vs 웹 셸)이 자연스럽습니다.

  1. 로그인 → 백엔드 /api/auth/login(프록시 경유) → JWT 저장
  2. 토큰의 role 로 roleHome(role) 계산 → 모바일이면 /app/[role], 웹이면 /console/[role]
  3. RoleShell 가드: 세션 없으면 /login, URL 역할 ≠ 세션 역할이면 자기 홈으로 리다이렉트
📊 로그인 후 역할 라우팅 결정
JavaScript · lib/roles.js 
export function roleHome(role) {
  const cfg = ROLE_CONFIG[role];
  if (!cfg) return '/login';
  return cfg.medium === 'mobile' ? `/app/${cfg.key}` : `/console/${cfg.key}`;
}
