School-Bus API 엔드포인트 가이드 (Swagger 기준)

67개 REST 엔드포인트 전체를 컨트롤러(기능)별로 묶어 설명합니다(2026-07-22 기준, 컨트롤러 코드 전수 대조). Swagger UI(/swagger-ui/index.html)에는 같은 API가 한글 번호 태그(01. 인증(Auth) ~ 14. 알림(Notification))로 표시되며, MVP 화면이 실제 호출하는 17개는 00. MVP 사용 API 태그에도 중복 노출됩니다(그쪽 상세 명세는 MVP_API_SPEC.md).

0. 이 문서를 읽는 법

한 줄 요약: 그룹(컨트롤러)마다 표 하나로 "어떤 요청을 누가 보낼 수 있는가"를 정리합니다 — 이 문서의 섹션 순서는 컨트롤러 이름 알파벳순이고, Swagger UI는 한글 번호 태그(00~14) 순서라 정렬만 다르고 내용은 같습니다.

각 그룹은 실제 컨트롤러 클래스 하나에 대응합니다. 모든 컨트롤러에 @Tag(name = "01. 인증(Auth)") ~ @Tag(name = "14. 알림(Notification)") 형태의 한글 번호 태그가 직접 붙어 있고, springdoc.swagger-ui.tags-sorter: alpha 설정으로 숫자 접두사 순서대로 정렬됩니다. 여기에 더해 MVP 화면이 실제 호출하는 17개 API는 각 핸들러의 @Operation(tags = {"00. MVP 사용 API", ...}) 선언으로 최상단 00. MVP 사용 API 태그에 한 번 더 나타납니다 — "프론트 작업이면 이 그룹만 먼저 보라"는 안내이며, 원래 카테고리 태그에도 그대로 남아 있습니다.

Swagger UI 사용법: ① POST /api/auth/login을 실행해 accessToken을 받는다 → ② 우측 상단 Authorize 버튼에 Bearer <accessToken> 없이 토큰 값만 입력(스킴이 이미 bearer로 고정) → ③ 이후 모든 "Try it out" 요청에 Authorization 헤더가 자동으로 붙는다. 역할별 계정은 로컬 시드(db/migration-local/V2__seed_data.sql, 비밀번호 전부 password) 참조.
표기 규칙: 권한 칸의 배지는 @PreAuthorize를 그대로 옮긴 것입니다 — ACADEMY_ADMINPLATFORM_ADMIN 두 배지가 같이 있으면 hasAnyRole(...)(둘 중 하나), 하나만 있으면 hasRole(...)(그 역할만)입니다. 공개는 permitAll, 인증 필요는 로그인만 하면 역할 무관(세부 범위는 서비스 계층에서 추가 검사)을 뜻합니다.

1. 전체 개요 — 14개 그룹 · 67개 엔드포인트

한 줄 요약: 인증(Auth)을 시작점으로 attendance→...→tenant까지 14개 그룹 67개 엔드포인트, HTTP 메서드는 GET/POST/PATCH만 존재(DELETE 없음).
📊 그룹별 엔드포인트 수 (이 문서의 섹션 순서)

HTTP 메서드 분포: GET 33개(조회) · POST 21개(생성/트리거) · PATCH 13개(부분 갱신·상태 전이) — DELETE는 하나도 없습니다. 이 도메인의 리소스(학생·버스·기록 등)는 삭제보다 "상태 전이"(승인/반려, 확인/종료 등)로 다루는 게 안전하기 때문입니다.

2. 반복되는 패턴 — 역할별 스코프 조회

한 줄 요약: 같은 데이터를 역할마다 다른 하위 경로(/me, /children, /bus/{busId}, 관리자용 목록)로 노출해, 학생/학부모/기사/관리자가 "자기 몫만" 보게 합니다.

ride-event·location·sos·notification·schedule·attendance 6개 그룹이 정도의 차이는 있지만 모두 이 패턴을 씁니다 — 하나의 QueryService가 호출하는 메서드만 다르고, 실제 필터링(본인 여부·자녀 여부·담당 버스 여부·소속 학원 여부)은 그 안에서 이뤄집니다.

📊 승하차 기록(ride_event) 하나를 4계층이 각자 다르게 조회 (가장 완전한 예시)
그룹본인(STUDENT)자녀(PARENT)담당버스(DRIVER)학원(관리자)
ride-event✅ /me✅ /children✅ /bus/{busId}✅ 목록(tenantId 등)
location✅ /me✅ /children✅ /bus/{busId}✅ 목록(tenantId)
sos✅ /me✅ /children— (기사 조회 없음)✅ 목록(tenantId)
notification— (학생 알림함 없음)✅ /children— ✅ 목록(tenantId)
schedule / attendance— (신청 대상일 뿐)✅ /children(신청도 이 역할)—✅ 목록(tenantId)
흔한 오해: "역할이 다르면 컨트롤러(또는 API)도 따로 만들어야 한다"고 생각하기 쉽지만, 이 프로젝트는 같은 리소스·같은 QueryService 안에서 메서드만 나눕니다(getMyRecords/getChildrenRecords/getRosterRecords/getTenantRecords). 컨트롤러가 여러 개로 쪼개지는 게 아니라, 같은 컨트롤러 안에 역할별 엔드포인트가 나란히 있고 각각 다른 @PreAuthorize가 붙습니다.

17. 부록 — WebSocket(STOMP) 채널 (Swagger에 안 보이는 이유)

한 줄 요약: OpenAPI(Swagger)는 HTTP REST 계약만 문서화하므로, STOMP 메시지 매핑(@MessageMapping)이나 서버→클라이언트 push 채널은 Swagger UI에 나타나지 않습니다.

LocationSocketController는 @RestController가 아니라 @Controller + @MessageMapping이라 REST 엔드포인트로 취급되지 않아 67개 집계에 포함되지 않습니다. 실제 실시간 채널은 다음과 같습니다.

방향목적지설명
연결/ws/location (STOMP endpoint)CONNECT 프레임의 Authorization: Bearer <access>를 StompAuthChannelInterceptor가 1회 검증
클라이언트→서버/app/locationLocationSocketController.report — REST의 POST /api/locations와 동일한 LocationReportRequest 계약 재사용
서버→클라이언트(개인)/user/queue/location, /user/queue/notifications본인·학부모·담당기사에게 위치·알림 개인 push(Spring user-destination 라우팅이 본인 세션에만 배달 보장)
서버→클라이언트(학원)/topic/tenant/{id}/location, /topic/tenant/{id}/notifications관리자 관제용 브로드캐스트 — SUBSCRIBE 시 소속 학원 여부를 인터셉터가 검사
더 자세한 흐름은: BACKEND_ARCHITECTURE.html §6(실시간 위치 파이프라인)에 Kafka→Redis→STOMP push 전체 다이어그램이 있습니다. 이 문서는 "무엇을 호출할 수 있는가"에 집중하고, "왜 이렇게 설계했는가"는 그 문서를 참고하세요.
