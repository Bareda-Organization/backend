School-Bus 관제 대시보드 가이드

Grafana 대시보드 4장 43패널을 읽는 법 정리. 기획서·설계서가 아니라 infra/observability/grafana/dashboards/*.json 실물 대조 결과가 근거.

0. 이 문서를 읽는 법

패널 하나하나의 PromQL 나열이 아니라 "무엇을 재는가 · 정상은 어떤 모양인가 · 문제는 어떤 증상인가 · 그때 어디를 보는가" 네 축으로 정리한 참조 문서.

대시보드 4장은 서로 독립된 화면이 아니라 원인 추적 경로 하나로 이어짐. 대시보드 1(API)에서 증상을 발견하면 대시보드 2(서버) → 3(데이터) → 4(파이프라인) 순으로 원인 후보를 좁혀가는 구조. 43패널 전체를 같은 밀도로 설명하지 않고, 대시보드별 표는 패널 묶음으로 압축하되 단독 패널로는 원인을 가릴 수 없는 조합 6개(§7)만 개별 서술 — 이 문서의 값어치가 여기 집중.

주의: 관리형 APM·알람 SaaS 없이 Prometheus + Grafana 자체호스팅으로 구성된 시스템. §9 에 이 구성의 구조적 한계를 별도로 씀.

2. 전체 지도 — 대시보드 4장 43패널

1(API) → 2(서버) → 3(데이터) → 4(파이프라인) 순서가 대체로 원인 추적 순서와 일치. 각 대시보드는 3개 내외 그룹(row)으로 다시 나뉨.

7. 핵심 조합 — 단독 패널로는 원인을 가릴 수 없는 것

이 문서의 값어치는 43패널 나열이 아니라 이 6개 — 전부 2026-08-21 실측(docker compose stop/start redis 등)으로 확인된 사실이지 추측이 아님.

7.1 Redis 지연이 스레드로 나타나고, 지표 엔드포인트까지 응답 불가

spring.data.redis.timeout 미설정 — backend/src/main/java/src/backend/global/config/RedisConfig.java 는 직렬화만 담당, 타임아웃은 어디서도 지정하지 않아 Lettuce 기본값 60초 그대로 적용. Redis 가 느려지면 요청 스레드가 최대 60초까지 점유될 수 있다는 뜻.

실측(2026-08-21, docker compose stop redis → 75초 대기 → start → 50초 대기): Tomcat 스레드가 소진돼 /actuator/prometheus 스크레이프 자체가 타임아웃됨. Prometheus 가 backend 타깃을 down(context deadline exceeded)으로 표시하며 모든 지표가 조회 불가 상태가 됨. 관측이 가장 필요한 순간에 대시보드가 통째로 비는 셈 — 복구 후 약 60초 뒤 자동 회복.
📊 Redis 정지 실험 타임라인 — 세 지표가 동시에 반응(2026-08-21 실측값)

7.2 Redis 축출과 TTL 만료 — 구분 불가

운영(docker-compose.prod.yml:56)은 maxmemory 128mb + allkeys-lru. 메모리가 차면 위치 좌표가 TTL(버스 15초) 만료 전에 축출됨. 관제 지도에서 버스가 사라지는 현상은 같지만 원인이 TTL 이 아니라 메모리 압박인 경우, redis_evicted_keys_total 패널 없이는 두 원인을 못 가림.

로컬 재현 안 됨: 로컬 docker-compose.yml:35-38 의 redis 는 maxmemory 설정이 없는 redis:7 기본 이미지 — 이 조합은 운영 전용 특성. 로컬에서 축출 건수 패널이 계속 0 이어도 정상.

7.4 스케줄러 경과 게이지의 한계 — "돌고는 있다"만 확인 가능

스케줄러 4개(location-simulation·connection-loss·approach-no-show·sos-escalation)는 메서드 내부에서 예외를 이미 잡으므로 실패 카운터가 거의 오르지 않음. §7.1 실험 내내 schoolbus_scheduler_failures_total 이 끝까지 0 — Redis 정지를 드러낸 것은 경과 게이지뿐.

Java · LocationSimulationScheduler.tick() 
@Scheduled(fixedDelayString = "${app.location.tick-ms:3000}")
public void tick() {
    for (LocationSource source : sources) {
        if (!source.isActive()) {
            continue;
        }
        try {
            source.tick();
        } catch (Exception e) {
            // 한 소스의 실패가 다음 틱·다른 소스를 막지 않도록 삼킨다(로그만 남김).
            log.warn("[location] 소스 '{}' 틱 실패: {}", source.label(), e.getMessage());
        }
    }
}

계측 aspect(ScheduledTaskMetricsAspect)는 @Scheduled 메서드 밖으로 던져진 예외만 recordFailure 로 집계. 위 코드처럼 메서드 안에서 catch 로 삼키면 aspect 의 catch 구간에 도달하지 않아 실패로 잡히지 않음 — 내부 판정이 실패해도 메서드는 성공 반환하는 구조. 이 대시보드로는 안 잡힘. 초록불(실패율 0)을 보고 안심할 근거로 삼지 않음.

7.5 버스 위치 origin 태그 — 실단말과 서버 Mock 구분

버스 위치 수신률 패널의 origin 태그가 MOCK 만 증가하면 기사 앱을 아무도 켜지 않은 상태. 데모 환경은 서버 Mock(MockBusLocationSource)이 3초마다 좌표를 자동 생성하므로, GPS 태그가 전혀 없어도 대시보드는 계속 정상으로 보임 — "실단말 연결 여부"는 이 태그로만 구분됨.

7.6 MON-1 이 넓힌 Redis 반경

§7.1 실험에서 location-simulation 스케줄러도 함께 정지 — 버스 좌표를 Redis 로 옮기면서(RedisBusLocationRepository) 이 스케줄러가 Redis 에 의존하게 됨. "Redis 와 무관한 스케줄러"라는 가정은 코드만 봐서는 드러나지 않고, §7.1 과 같은 장애 주입 실험으로만 확인됨.

9. 이 대시보드가 대체하지 않는 것

구조적 한계 — EC2 가 죽으면 대시보드도 함께 정지. 자체호스팅 Prometheus·Grafana 는 관측 대상과 같은 인스턴스에서 동작 — 관측 대상이 사라지면 관측 도구도 함께 사라짐. 그래서 CloudWatch 알람은 이 대시보드로 대체되지 않고 여전히 필요하나, 해당 항목(MON-13)은 현재 착수 전 상태.
