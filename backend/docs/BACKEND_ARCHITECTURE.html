School-Bus 백엔드 아키텍처 & 서버 구성

학원 통원버스 멀티 테넌트 플랫폼을 실제로 운영하기 위한 백엔드 설계 가이드. Spring Boot 입문자를 대상으로, 왜 이렇게 구성하는지까지 설명합니다.

0. 이 문서를 읽는 법

한 줄 요약: 클라이언트 → Nginx → Spring(API) → PostgreSQL/Redis 로 흐르는 표준 3-tier 구조에, 실시간 위치·알림·외부 경로 API를 붙인 형태입니다.

이 문서는 projectInfo.md의 요구사항(5개 역할, 멀티 테넌시 N:M, Mock→실GPS 추상화, 알림 멱등성, 네이버 경로)을 실제 서버 설계로 옮긴 것입니다. 각 장은 ① 한 줄 요약 → ② 그림 → ③ 왜 이렇게 하나 → ④ 코드 예시 → ⑤ 흔한 오해 순으로 구성됩니다.

비유: 백엔드 서버 구성은 "식당 주방"과 같습니다. Nginx는 손님을 받아 자리를 안내하는 홀 매니저, Spring은 주문을 요리로 바꾸는 주방, PostgreSQL은 재료가 보관된 창고, Redis는 자주 쓰는 재료를 손 닿는 곳에 둔 조리대 선반입니다.

1. 전체 아키텍처

한 줄 요약: 모든 외부 요청은 Nginx 한 곳으로 들어와 Spring API로 전달되고, Spring이 DB·캐시·외부 API를 조율해 응답합니다.
📊 전체 요청 흐름 (Request → Processing → Response)

처리 흐름 (번호 순):

  1. 모바일 앱/관리자 웹이 https://api.도메인/... 로 REST 요청을 보냅니다.
  2. Nginx가 유일한 외부 진입점으로서 TLS(HTTPS)를 종료하고, 경로에 따라 Spring 컨테이너로 프록시합니다.
  3. Spring이 인증(JWT)을 검사하고, Service가 비즈니스 로직을 수행하며 PostgreSQL(영속)·Redis(캐시)·외부 API(네이버 경로)를 조율합니다.
  4. 결과를 JSON으로 반환합니다. 실시간 위치는 별도 WebSocket 채널로 밀어줍니다.
흔한 오해: "프론트(NestJS)와 백엔드(Spring)가 있으니 서버가 둘이면 충분하다"고 생각하기 쉽습니다. 하지만 DB·캐시·리버스 프록시·푸시는 각각 독립 구성요소이며, 특히 외부에 직접 노출되는 건 Nginx 하나뿐이어야 보안·TLS·라우팅을 한 곳에서 통제할 수 있습니다.

2. 서버 구성 — Docker Compose 컨테이너

한 줄 요약: 각 구성요소를 개별 컨테이너로 띄우고 docker-compose 하나로 오케스트레이션합니다.
📊 컨테이너 구성 (docker-compose 서비스 단위)

3. 계층형 구조 — Controller / Service / Repository

한 줄 요약: 요청은 항상 Controller(입구) → Service(두뇌) → Repository(창고) 한 방향으로 흐르고, 반대로 되돌아 응답합니다.
📊 승하차 조회 요청의 계층 이동

왜 나누나? 역할을 분리하면 ① 테스트가 쉬워지고(Service만 단위 테스트) ② 변경 범위가 작아집니다(DB를 PostgreSQL→다른 것으로 바꿔도 Repository만 수정). 통원 서비스처럼 같은 RideEvent를 4개 역할이 다르게 조회하는 요구사항은 "권한별 필터링"을 Service 한 곳에 모아두는 것이 핵심입니다.

Java · RideEventController.java 
@RestController
@RequestMapping("/api/ride-events")
@RequiredArgsConstructor
public class RideEventController {

    private final RideEventService rideEventService;

    // 학부모가 자녀의 승하차 기록을 날짜로 조회
    @GetMapping
    public List<RideEventResponse> list(
            @AuthenticationPrincipal LoginUser user,   // JWT 에서 꺼낸 로그인 사용자
            @RequestParam Long studentId,
            @RequestParam LocalDate date) {
        // 권한 판단은 Controller 가 아니라 Service 로 위임한다
        return rideEventService.findFor(user, studentId, date);
    }
}
Java · RideEventService.java 
@Service
@RequiredArgsConstructor
public class RideEventService {

    private final RideEventRepository rideEventRepository;
    private final AccessPolicy accessPolicy;

    @Transactional(readOnly = true)
    public List<RideEventResponse> findFor(LoginUser user, Long studentId, LocalDate date) {
        // 역할별 조회 권한을 한 곳에서 판단 (학부모=본인 자녀만 / 관리자=소속 학원 전체)
        accessPolicy.assertCanViewStudent(user, studentId);
        return rideEventRepository
                .findByStudentIdAndDate(studentId, date)
                .stream().map(RideEventResponse::from).toList();
    }
}
흔한 오해: 입문자는 Controller 안에서 바로 Repository를 호출하고 권한 검사·비즈니스 로직까지 다 넣곤 합니다. 그러면 같은 로직이 여러 Controller에 복붙되고, 테스트가 HTTP 요청 없이는 불가능해집니다. Controller는 얇게(입출력 변환만), 로직은 Service에가 원칙입니다.

4. 멀티 테넌시 설계 — User↔Tenant는 N:M

한 줄 요약: 학부모 1명이 여러 학원에 자녀를 둘 수 있으므로, tenant_id를 User에 박지 않고 UserTenantRole 연결 테이블로 표현합니다.
📊 잘못된 설계(좌) vs 올바른 N:M 설계(우)
SQL · schema.sql (멀티 테넌시 핵심) 
CREATE TABLE tenant (            -- 학원
    id          BIGSERIAL PRIMARY KEY,
    name        TEXT NOT NULL
);

CREATE TABLE app_user (          -- 사람 (역할은 여기 박지 않음)
    id          BIGSERIAL PRIMARY KEY,
    email       TEXT UNIQUE NOT NULL,
    password    TEXT NOT NULL
);

CREATE TABLE user_tenant_role (  -- N:M 연결 + 역할
    user_id     BIGINT REFERENCES app_user(id),
    tenant_id   BIGINT REFERENCES tenant(id),
    role        TEXT NOT NULL,   -- STUDENT/PARENT/DRIVER/ACADEMY_ADMIN/PLATFORM_ADMIN
    PRIMARY KEY (user_id, tenant_id, role)
);

-- 학생·버스·기록 등 테넌트 종속 데이터는 tenant_id 컬럼으로 격리
CREATE TABLE ride_event (
    id          BIGSERIAL PRIMARY KEY,
    tenant_id   BIGINT NOT NULL REFERENCES tenant(id),
    student_id  BIGINT NOT NULL,
    bus_id      BIGINT NOT NULL,
    type        TEXT NOT NULL,          -- BOARD / ALIGHT
    occurred_at TIMESTAMPTZ NOT NULL,
    lat         DOUBLE PRECISION,
    lng         DOUBLE PRECISION,
    stop_id     BIGINT,
    source      TEXT NOT NULL,          -- qr/nfc/manual/correction
    corrected_by BIGINT, corrected_at TIMESTAMPTZ, original_ref BIGINT
);
CREATE INDEX idx_ride_tenant_student ON ride_event(tenant_id, student_id, occurred_at);
테넌트 격리 실전 팁: 모든 테넌트 종속 쿼리에 tenant_id = ? 조건을 빠뜨리면 다른 학원 데이터가 새어나갑니다. Hibernate @Filter나 Service 상위의 공통 인터셉터로 로그인 사용자의 tenant_id를 자동 주입하면 실수를 구조적으로 막을 수 있습니다.

5. 인증·인가 — 역할 기반 JWT

한 줄 요약: 로그인하면 역할이 담긴 JWT를 발급하고, 이후 요청마다 토큰을 검증해 5개 역할의 접근 범위를 나눕니다.
📊 로그인 → 보호된 API 호출 시퀀스
Java · SecurityConfig.java 
@Configuration
@EnableMethodSecurity   // @PreAuthorize 활성화
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http, JwtFilter jwtFilter) throws Exception {
        http.csrf(csrf -> csrf.disable())            // 토큰 기반이라 CSRF 미사용
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("PLATFORM_ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
Java · 메서드 단위 권한 (역할별 분리) 
// 학원 관리자만, 그리고 자기 학원 데이터만
@PreAuthorize("hasRole('ACADEMY_ADMIN')")
public FleetView getFleet(LoginUser user) {
    return fleetService.findByTenant(user.tenantId());   // tenant_id 자동 격리
}
흔한 오해: "JWT에 역할을 넣었으니 안전하다"—토큰은 서명 검증만 위변조를 막고, 내용은 누구나 디코딩해 볼 수 있습니다. 따라서 민감 정보를 JWT에 넣지 말고, 만료 시간을 짧게(예: 액세스 15분 + 리프레시 토큰) 두어야 합니다.

6. 실시간 위치 파이프라인 — Mock→실GPS 추상화

한 줄 요약: 위치 "소스"를 인터페이스로 추상화해, 지금은 Mock 좌표를 흘려보내고 나중에 실제 폰 GPS로 소스만 교체합니다.
📊 위치 수신 → 저장/브로드캐스트 (소스 교체 가능 구조)
Java · LocationSource 추상화 
// 위치 소스 추상화 — 실 GPS 전환 시 이 인터페이스의 구현만 교체
public interface LocationSource {
    Flux<LocationPing> stream(Long studentId);   // 좌표가 계속 흘러나오는 스트림
}

@Component
@Profile("mock")                                  // MVP: application-mock.yml 로 활성화
public class MockLocationSource implements LocationSource {
    public Flux<LocationPing> stream(Long studentId) {
        // 정해진 경로 위를 1초 간격으로 이동하는 가짜 좌표
        return Flux.interval(Duration.ofSeconds(1))
                   .map(tick -> RouteSimulator.pointAt(studentId, tick));
    }
}

// 추후: @Profile("prod") PhoneGpsSource — 클라이언트가 보낸 실제 좌표를 그대로 흘림
실시간 전송 방식 선택: 위치처럼 서버가 클라이언트로 계속 밀어주는 데이터는 WebSocket(양방향)이나 SSE(서버→클라 단방향)가 적합합니다. 매초 GET으로 폴링하면 요청 수가 폭증하므로, 지도 추적에는 push 방식을 권장합니다.

7. 네이버 경로 프록시 — 비밀키를 서버에 숨기기

한 줄 요약: 네이버 Directions는 비밀키가 필요해 브라우저에서 직접 못 부르므로, Spring이 대신 호출하고 결과만 프론트에 전달합니다.
📊 경로 요청: 프론트 → Spring 프록시 → 네이버
Java · RouteProxyController.java 
@RestController
@RequestMapping("/api/routes")
@RequiredArgsConstructor
public class RouteProxyController {

    private final NaverDirectionsClient naver;   // 비밀키를 아는 유일한 곳

    @GetMapping
    @Cacheable(value = "routes", key = "#from + '_' + #to")   // Redis 캐시로 호출 절약
    public RouteResponse route(@RequestParam String from, @RequestParam String to) {
        // 좌표만 받아 네이버에 위임 → 결과 폴리라인을 프론트가 쓰기 쉽게 변환
        return naver.driving(from, to);
    }
}
운영 근거: 경로는 정류장이 바뀌지 않는 한 결과가 같으므로 Redis에 캐시하면 유료 API 호출 수와 비용을 크게 줄일 수 있습니다. MVP에서는 무료 OSRM으로 이 NaverDirectionsClient 자리만 채워두었다가, 정식 전환 시 구현체를 갈아끼우면 됩니다(6장 추상화와 동일 패턴).

8. 알림 파이프라인 — 멱등성과 오탐 방지

한 줄 요약: 같은 사건이 매 틱 반복 감지돼도 dedup_key로 1번만 발송하고, GPS 오탐은 연속 N회 관측으로 걸러냅니다.
📊 미탑승 알림 판정 (연속 3회 + 멱등키)
Java · NotificationService.java (멱등 발송) 
@Service
@RequiredArgsConstructor
public class NotificationService {

    private final NotificationLogRepository logRepo;
    private final PushSender pushSender;

    @Transactional
    public void notifyNoShow(NoShowEvent e) {
        // dedup_key = 유형+학생+대상일자+정류장 → 동일 사건은 한 행만 존재
        String dedupKey = "NOSHOW_%d_%s_%d".formatted(e.studentId(), e.date(), e.stopId());
        if (logRepo.existsByDedupKey(dedupKey)) return;   // 이미 보냈으면 종료 (멱등)

        logRepo.save(new NotificationLog(dedupKey, e.recipients()));
        pushSender.sendWithBackoff(e.recipients(), e.message());   // 실패 시 지수 백오프
    }
}
흔한 오해: "이벤트가 발생하면 곧바로 알림을 보낸다"고 1:1로 설계하면, 버스가 정류장에 머무는 동안 미승차 조건이 매 틱 참이 되어 학부모에게 알림이 수십 번 갑니다. 이벤트 감지와 발송은 분리하고, 멱등키로 "이미 알린 사건인가"를 반드시 확인해야 합니다.

9. 데이터 모델 → 테이블 개요

한 줄 요약: projectInfo 6장의 엔티티를 PostgreSQL 테이블로 옮기고, 테넌트 종속 테이블에는 tenant_id를 답니다.
테이블핵심 컬럼설계 포인트
tenantid, name, 계약·과금학원 = 테넌트 루트
app_userid, email, password역할·소속을 여기 넣지 않음
user_tenant_roleuser_id, tenant_id, roleN:M 연결 (4장 핵심)
studenttenant_id, bus_id, guardian_ids학생은 단일 학원 종속
busdriver_id, seat_capacity, 보험만료일물리 좌석 수
route / stop정류장 순서, assign_capacity배정 정원 = seat와 별개
ride_eventtype, occurred_at, source, corrected_by, original_ref정정은 덮어쓰지 말고 새 행
audit_logactor, action, before/after민감 조작 감사
sos_eventstatus(open→ack→resolved), acknowledged_by상태 되돌림 불가 · 3분 에스컬레이션
notification_logtype, recipient, dedup_key, 결과멱등·재시도 기록
마이그레이션 도구: 스키마는 손으로 CREATE TABLE 하지 말고 Flyway나 Liquibase로 버전 관리하세요. 팀·배포 환경마다 DB 상태를 동일하게 재현할 수 있어, 운영 서비스에서는 사실상 필수입니다.

10. 서버 스펙 · 배포 권장

한 줄 요약: MVP는 단일 인스턴스 + docker-compose로 시작하고, 트래픽이 늘면 DB 분리·Spring 다중화·로드밸런서로 확장합니다.
단계구성권장 스펙(예)
MVP / 데모단일 VM에 compose 전체 (nginx+spring+nest+pg+redis)2 vCPU / 4GB RAM / 40GB SSD
초기 운영앱 VM + 관리형 PostgreSQL 분리 (백업·장애조치 위임)앱 4 vCPU/8GB, DB 관리형
성장기Nginx/LB 뒤에 Spring 여러 인스턴스, Redis 공용 세션, 관리형 DB read replica수평 확장

배포 관점 체크리스트

  1. 환경 분리: application-mock.yml(로컬) / application-prod.yml(운영). 비밀키·DB 암호는 코드가 아닌 .env·시크릿 매니저로 주입.
  2. TLS: Nginx에서 Let's Encrypt 인증서로 HTTPS 종료.
  3. 헬스체크: Spring Actuator /actuator/health를 compose healthcheck·로드밸런서가 감시.
  4. 로깅·모니터링: 구조화 로그(JSON) + 필요 시 Prometheus/Grafana. SOS·미탑승 같은 안전 이벤트는 별도 알림.
  5. 백업: PostgreSQL 정기 덤프 + 볼륨 스냅샷. 위치·승하차 기록은 법적 보관 요건 확인.
법적 선행조건(projectInfo 4.2): 실제 GPS로 전환하기 전에 위치정보사업 신고, 만 14세 미만 법정대리인 동의 수집 UI·스키마가 준비돼야 합니다. Mock 단계에서는 유예되지만, 동의 데이터 모델은 실 GPS 전환 전에 반드시 구현하세요.

11. 권장 구축 순서

한 줄 요약: 인프라 뼈대 → 인증 → 도메인 → 실시간/알림 → 외부 연동 순으로, 매 단계 배포 가능한 상태를 유지합니다.
  1. 인프라 뼈대: docker-compose로 nginx+spring+postgres+redis를 띄우고 /actuator/health가 200 뜨는지 확인.
  2. 스키마 + 마이그레이션: Flyway로 9장 테이블 생성, 멀티 테넌시(user_tenant_role) 우선.
  3. 인증·인가: 회원가입/로그인, JWT 발급·검증, 5개 역할 @PreAuthorize 골격.
  4. 핵심 도메인: 승하차 기록(RideEvent) CRUD + 역할별 조회 필터 → 기사 체크 → 관리자 조회.
  5. 실시간 위치: LocationSource 추상화 + MockLocationSource + WebSocket 브로드캐스트.
  6. 알림: dedup_key 멱등 발송 + FCM 연동 + 미탑승/근접/SOS 정책 상수화.
  7. 외부 경로: RouteProxyController + OSRM 구현(추후 네이버 교체), Redis 캐시.
  8. 운영 기능: 시간변경 승인, 노선 개편(정원 초과 경고), 통계·감사 로그.
  9. 실 GPS 전환: 법적 요건 충족 후 PhoneGpsSource로 소스 교체.
마무리: 이 아키텍처의 핵심 아이디어는 세 가지입니다 — ① 외부 노출은 Nginx 하나로 좁히고, ② User↔Tenant를 N:M으로 유연하게, ③ 위치·경로·알림 같은 "교체될 수 있는 부분"을 인터페이스로 추상화해 Mock→실서비스 전환 비용을 최소화한다.
