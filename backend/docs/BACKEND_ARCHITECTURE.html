School-Bus 백엔드 아키텍처 & 서버 구성

학원 통원버스 멀티 테넌트 플랫폼의 실제 구현 기준 백엔드 설계 가이드(2026-07-20 갱신, Phase 0~7 완료 기준). Spring Boot 입문자를 대상으로, 왜 이렇게 구성했는지까지 설명합니다.

0. 이 문서를 읽는 법

한 줄 요약: 클라이언트 → Spring Boot API(CQRS) → PostgreSQL/Redis 로 흐르는 요청 흐름에, Kafka 이벤트 버스와 WebSocket(STOMP) 실시간 push를 더한 구조입니다.

이 문서는 projectInfo.md의 요구사항(5개 역할, 멀티 테넌시 N:M, Mock→실GPS 추상화, 알림 멱등성, 외부 경로 API)을 실제 코드 기준으로 정리한 것입니다(단일 소스는 backend/docs/PROJECT_MASTER_PLAN.md·reference.md). 각 장은 ① 한 줄 요약 → ② 그림 → ③ 왜 이렇게 하나 → ④ 코드 예시 → ⑤ 흔한 오해 순으로 구성됩니다.

비유: 백엔드 서버 구성은 "식당 주방"과 같습니다. 지금 MVP 단계에는 손님을 안내하는 홀 매니저(Nginx)가 아직 없어 손님이 주방(Spring)에 직접 주문합니다. PostgreSQL은 재료가 보관된 창고, Redis는 자주 쓰는 재료를 손 닿는 곳에 둔 조리대 선반(위치 좌표 캐시), Kafka는 조리팀↔알림팀이 서로 쪽지를 주고받는 사내 메신저입니다 — 조리팀(rideevent)이 "승차 완료" 쪽지를 메신저에 올리면, 알림팀(notification)이 그걸 보고 학부모에게 알립니다.
실제 구성과 다른 점(중요): 이 프로젝트의 docker-compose.yml에는 Nginx가 없습니다 — backend(:8080)·frontend(:3000)·postgres(:5432)·redis(:6379)·kafka(:29092) 포트가 모두 호스트에 직접 열려 있는 로컬 개발용 구성입니다. Nginx/TLS 종료는 §10에서 "운영 전환 시 할 일"로 남겨둡니다.

1. 전체 아키텍처

한 줄 요약: 클라이언트 요청은 Spring Boot API(Controller→Command/Query)가 바로 받고, DB 커밋 이후에만 Kafka로 이벤트가 나가 Consumer가 알림·실시간 위치 push를 처리합니다.
📊 전체 요청 흐름 (Request → Processing → Response, 15개 모듈 기준)

처리 흐름 (번호 순):

  1. 모바일 앱/관리자 웹이 http://backend:8080/api/... 로 REST 요청을 보냅니다(MVP는 리버스 프록시 없이 백엔드에 직접 접속).
  2. Spring의 JwtAuthenticationFilter가 매 요청 Authorization: Bearer 토큰을 검증하고, Controller가 요청 DTO를 Command Service(쓰기) 또는 Query Service(읽기)로 위임합니다.
  3. 쓰기 요청은 PostgreSQL에 저장 후 ApplicationEventPublisher로 도메인 이벤트를 발행하고, 트랜잭션이 커밋된 뒤에만(@TransactionalEventListener(AFTER_COMMIT)) Kafka로 실제 전송됩니다.
  4. 다른 모듈의 Kafka Consumer(주로 notification·location)가 이벤트를 소비해 알림 로그를 남기고, WebSocket(STOMP)의 개인 큐/학원 토픽으로 실시간 push합니다. 위치는 Redis에 TTL로 캐시됩니다.
흔한 오해: "프론트와 백엔드가 있으니 서버가 둘이면 충분하다"고 생각하기 쉽습니다. 실제로는 DB(PostgreSQL)·캐시(Redis)·이벤트 버스(Kafka)가 각각 독립 컨테이너이며, 지금은 그 앞에 리버스 프록시(Nginx)가 없어 백엔드 포트(8080)가 호스트에 그대로 열려 있는 로컬 개발 구성입니다 — 운영 전환 시 반드시 보강해야 할 지점입니다(§10).

2. 서버 구성 — Docker Compose 컨테이너

한 줄 요약: 실제 docker-compose.yml은 backend·frontend·postgres·redis·kafka 5개 서비스이며, 아직 리버스 프록시 없이 전부 호스트 포트로 직접 열려 있는 로컬 개발 구성입니다.

3. 계층형 구조 — CQRS + 이벤트 기반 모듈 통신

한 줄 요약: 같은 모듈 안에서는 Controller → Command/Query Service(대부분 인터페이스 없는 구현체) → Repository 로 흐르고, 모듈을 넘어가는 통신은 직접 호출 대신 커밋 후 Kafka 이벤트로 분리합니다.

reference.md(Backend Architecture & Development Convention)가 정한 15개 모듈 공통 패키지 레이아웃입니다 — controller / command / query / domain / event / projection / repository(spec·impl) / dto / infrastructure(spec·impl). "바뀔 수 있는 것만" 인터페이스(spec)로 감싸고, 단일 구현 CRUD는 concrete 클래스 하나로 끝냅니다.

📊 같은 모듈 안의 요청 흐름 (승하차 기록 예시)
Java · RideEventController.java (실제 코드) 
@RestController
@RequestMapping("/api/ride-events")
public class RideEventController {

    private final RideEventCommandService rideEventCommandService;
    private final RideEventQueryService rideEventQueryService;

    /** 기사: 승/하차 기록. */
    @PostMapping
    @PreAuthorize("hasRole('DRIVER')")
    public ApiResponse<RideEventResponse> record(@AuthenticationPrincipal AuthUser driver,
                                                 @Valid @RequestBody RecordRideRequest request) {
        return ApiResponse.ok(rideEventCommandService.record(driver, request));
    }

    /** 학생: 본인 하루치 기록. Query 는 Command 를 호출하지 않는다(CQRS). */
    @GetMapping("/me")
    @PreAuthorize("hasRole('STUDENT')")
    public ApiResponse<List<RideEventResponse>> myRecords(
            @AuthenticationPrincipal AuthUser student,
            @RequestParam(required = false) LocalDate date) {
        return ApiResponse.ok(rideEventQueryService.getMyRecords(student, date));
    }
}

모듈을 넘어가는 통신은 이벤트로. 승차 기록이 저장되면 rideevent 모듈은 notification 모듈을 직접 호출하지 않습니다. 대신 StudentBoardedEvent를 발행하고, notification 모듈이 Kafka로 그 이벤트를 소비해 알림을 만듭니다 — 발행 모듈은 "누가 듣는지" 전혀 모릅니다.

📊 모듈 간 이벤트 기반 통신 (승차 완료 → 알림, AFTER_COMMIT 패턴)

왜 이렇게 나누나? ① 같은 모듈 내부는 Command/Query 분리로 "쓰기 로직이 읽기 성능에 영향을 주지 않게" 하고, ② 모듈 간에는 이벤트로 분리해 "알림 로직이 바뀌어도 rideevent 코드를 안 건드리게" 합니다. 이 프로젝트 핵심 요구사항인 "같은 RideEvent를 4개 역할이 다르게 조회"는 RideEventQueryService 안에 getMyRecords/getChildrenRecords/getRosterRecords/getTenantRecords 4개 메서드로 역할별 스코프를 나눠 해결합니다.

흔한 오해: "인터페이스(spec)를 안 만들면 확장성이 없는 나쁜 설계"라고 생각하기 쉽습니다. 이 프로젝트는 반대로 "구현이 바뀔 가능성이 있는 것만" spec/impl로 분리합니다 — LocationSource(Mock↔실GPS), MapRouteClient(OSRM↔네이버), NotificationSender(Log↔WebSocket), DomainEventPublisher(Kafka↔다른 브로커)처럼 실제로 교체될 지점만 포트로 만들고, BusCommandService처럼 구현체가 하나뿐인 CRUD는 인터페이스 없이 클래스 하나로 끝냅니다. 인터페이스를 무조건 만드는 것도, 안 만드는 것도 아니라 "변경 가능성"이 유일한 판단 기준입니다.

4. 멀티 테넌시 설계 — User↔Tenant는 N:M

한 줄 요약: 학부모 1명이 여러 학원에 자녀를 둘 수 있으므로, tenant_id를 User에 박지 않고 UserTenantRole 연결 테이블로 표현합니다.
📊 잘못된 설계(좌) vs 올바른 N:M 설계(우)
SQL · db/migration/V1__init_schema.sql (실제 Flyway 스키마 발췌) 
create table tenant (            -- 학원
    id      bigint generated by default as identity primary key,
    name    varchar(255) not null,
    lat float(53), lng float(53)  -- depot 좌표(routing 계산 기준점)
);

create table app_user (          -- 사람 (역할은 여기 박지 않음)
    id       bigint generated by default as identity primary key,
    email    varchar(255) not null unique,
    password varchar(255) not null,
    name     varchar(255) not null
);

create table user_tenant_role (  -- N:M 연결 + 역할
    id        bigint generated by default as identity primary key,
    user_id   bigint not null references app_user,
    tenant_id bigint references tenant,   -- PLATFORM_ADMIN 은 null(전역 역할)
    role      varchar(255) not null
        check (role in ('STUDENT','PARENT','DRIVER','ACADEMY_ADMIN','PLATFORM_ADMIN')),
    unique (user_id, tenant_id, role)
);

-- 학생·버스·기록 등 테넌트 종속 데이터는 tenant_id 컬럼으로 격리
create table ride_event (
    id          bigint generated by default as identity primary key,
    tenant_id   bigint not null,
    student_id  bigint not null,
    bus_id      bigint not null,
    type        varchar(255) not null check (type in ('BOARD','ALIGHT')),
    occurred_at timestamp(6) not null,
    lat float(53), lng float(53),
    stop_id     bigint,
    source      varchar(255) not null check (source in ('QR','NFC','MANUAL','CORRECTION')),
    corrected_by bigint, corrected_at timestamp(6), original_ref bigint
);
create index idx_ride_tenant_student on ride_event (tenant_id, student_id, occurred_at);
테넌트 격리 실전 팁(실제 구현): 이 프로젝트는 Hibernate @Filter 대신 global.tenant.TenantGuard 헬퍼를 Service 계층에서 명시적으로 호출합니다 — TenantGuard.resolveTenantId(admin, requestedTenantId)가 "플랫폼 관리자는 tenantId 필수 지정, 학원 관리자는 미지정 시 본인 소속·지정 시 소속 검증"을 한 곳에서 강제합니다. AuthUser는 JWT의 memberships 클레임("tenantId:ROLE" 문자열 목록)을 그대로 들고 있어, 매 요청마다 DB 재조회 없이 belongsToTenant(tenantId)로 즉시 검증할 수 있습니다.

5. 인증·인가 — 역할 기반 JWT

한 줄 요약: 로그인하면 소속·역할(memberships)이 담긴 access/refresh 토큰을 발급하고, 이후 REST 요청은 매번·WebSocket은 연결 시 1번 토큰을 검증합니다.
📊 로그인 → 보호된 API 호출 시퀀스
Java · SecurityConfig.java (실제 코드) 
@Configuration
@EnableWebSecurity
@EnableMethodSecurity   // 컨트롤러의 @PreAuthorize 활성화
public class SecurityConfig {

    private final JwtAuthenticationFilter jwtAuthenticationFilter;

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.csrf(csrf -> csrf.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/actuator/health").permitAll()
                .requestMatchers("/ws/**").permitAll()              // STOMP CONNECT 에서 별도 인증
                .requestMatchers("/swagger-ui/**", "/v3/api-docs/**").permitAll()
                .anyRequest().authenticated())
            // 인증 안 된 요청은 403 대신 401 로 응답(토큰 필요함을 명확히)
            .exceptionHandling(e -> e.authenticationEntryPoint(new HttpStatusEntryPoint(UNAUTHORIZED)))
            .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
Java · AuthUser.java (JWT ↔ Principal, 실제 코드 일부) 
// SecurityContext 의 principal + STOMP 세션의 Principal 을 겸한다(REST/WebSocket 공용)
public record AuthUser(Long userId, String email, List<Membership> memberships) implements Principal {

    public record Membership(Long tenantId, Role role) {}

    public boolean belongsToTenant(Long tenantId) {
        return tenantId != null && tenantIds().contains(tenantId);
    }

    // JWT 클레임 직렬화: Membership ↔ "tenantId:ROLE" 문자열 (예: "1:ACADEMY_ADMIN")
    public static String encode(Membership m) {
        String tenant = m.tenantId() == null ? "" : String.valueOf(m.tenantId());
        return tenant + ":" + m.role().name();
    }
}
흔한 오해: "JWT에 역할을 넣었으니 안전하다"—토큰은 서명 검증만 위변조를 막고, 내용은 누구나 디코딩해 볼 수 있습니다. 그래서 비밀번호 같은 민감정보는 절대 JWT에 넣지 않고, 만료 시간도 짧게 둡니다(이 프로젝트는 access 15분 + refresh 14일 — jwt.access-token-validity-seconds). 또한 WebSocket은 REST와 인증 시점이 다릅니다 — REST는 매 요청 검증하지만, STOMP는 CONNECT 프레임에서 1회만 검증하고 그 세션 동안은 그때 심어둔 Principal을 재사용합니다(StompAuthChannelInterceptor).

6. 실시간 위치 파이프라인 — Mock→실GPS 추상화

8. 알림 파이프라인 — 멱등성과 오탐 방지

한 줄 요약: 스케줄러가 같은 사건을 반복 확인해도 dedupKey로 1번만 발송하고, 연결 끊김 같은 순간 오탐은 유예시간(grace period)으로 걸러냅니다(연속 관측 카운트 방식 아님).
📊 연결 끊김 알림 판정 (실제 구현: grace 30초 + dedupKey)
Java · NotificationCommandServiceImpl.java (실제 코드) 
@Service
public class NotificationCommandServiceImpl implements NotificationCommandService {

    private final NotificationLogRepository notificationLogRepository;
    private final List<NotificationSender> notificationSenders;   // Log + WebSocket 병행 fan-out

    @Override
    @Transactional
    public void notify(NotificationType type, Long tenantId, Long studentId, String dedupKey, String message) {
        if (notificationLogRepository.existsByDedupKey(dedupKey)) {
            return; // 이미 발송된 이벤트 — 조용히 무시(멱등)
        }
        NotificationLog saved;
        try {
            saved = notificationLogRepository.save(NotificationLog.builder()
                    .tenantId(tenantId).studentId(studentId).type(type)
                    .dedupKey(dedupKey).message(message).build());
        } catch (DataIntegrityViolationException e) {
            return; // 동시 요청이 먼저 저장 — unique 제약이 최종 방어(경쟁 상태 대비)
        }
        notificationSenders.forEach(sender -> sender.send(saved));
    }
}

알림 유형(notification_log.type CHECK 제약, 실제 8종): BOARD_DONE·ALIGHT_DONE(승하차 완료, rideevent 발행)·SOS(발신+3분 미확인 에스컬레이션, sos 발행)·SCHEDULE_RESULT(시간변경 승인/반려, schedule 발행)·CONNECTION_LOST(location 발행)·ROUTE_RECOMMENDED(결석/시간변경으로 인한 노선 재계산, routing 발행) — 전부 DomainEventNotificationConsumer 하나가 7개 Kafka 토픽을 @KafkaListener로 소비합니다. APPROACH·NO_SHOW는 타입만 정의돼 있고 아직 발행하는 쪽이 없습니다(ETA·정류장 도착 감지가 필요해 후속 과제로 남음).

흔한 오해: "여러 번 관측해서 N회 이상이면 알림"이라고 생각하기 쉽지만, 이 프로젝트의 실제 방식은 카운트가 아니라 시간(grace period)입니다 — 최초 끊김 시각을 LocationSessionRegistry에 putIfAbsent로 고정해두고, 스케줄러가 그 시각과 지금을 비교해 유예시간이 지났는지만 봅니다. dedupKey가 그 고정된 시각을 포함하므로, 유예시간이 지난 뒤 스케줄러가 몇 번을 더 확인하든 최초 1번만 실제 알림이 나갑니다.

배포 관점 체크리스트

  1. 환경 분리(구현됨): application.yml의 local/prod 프로파일 — prod는 DB·Redis·Kafka·JWT secret 전부 ${ENV_VAR}로 주입, Flyway 시드(db/migration-local)도 prod엔 안 들어감.
  2. TLS(미구현, 운영 전 필수): 지금은 Nginx가 없어 TLS 종료 지점이 없습니다 — 운영 전환 시 Nginx 또는 클라우드 로드밸런서에서 Let's Encrypt 인증서로 HTTPS 종료.
  3. API 테스트/문서(구현됨): springdoc Swagger UI(/swagger-ui/index.html) — 로그인 후 accessToken을 Authorize에 넣으면 역할별 보호 API까지 한 화면에서 테스트 가능.
  4. 헬스체크: /actuator/health + postgres healthcheck(compose depends_on: condition: service_healthy)로 기동 순서 보장.
  5. 로깅·모니터링: 현재는 콘솔 로그(SLF4J)만 — 구조화 로그(JSON)·Prometheus/Grafana는 후속 과제. SOS·연결끊김 같은 안전 이벤트는 Kafka 이벤트 자체가 감사 추적점이 된다.
  6. 백업: PostgreSQL 정기 덤프 + pgdata 볼륨 스냅샷. 위치는 Redis TTL이라 백업 대상이 아니고, 승하차·SOS 기록은 법적 보관 요건 확인 필요.
