## 1. 배경

리포트가 세 축(확장성·유지보수성·개발용이성)을 관통하는 근본 원인 5개 중 1순위로 지목한 항목이다. 증상이 셋인데 뿌리가 하나다.

| | 증상 | 성격 | 대상 |
|---|---|---|---|
| **㉠** | `@PreAuthorize` **61개**에 역할 문자열 하드코딩 | 확장성 — 새 역할 추가 비용 | 컨트롤러 14개 |
| **㉡** | 인가 판정 메서드가 복붙으로 3중화 | 안전성 — 하나 놓치면 권한 우회 | 프로덕션 6곳 |
| **㉢** | 테넌트 격리가 `TenantGuard` / 인라인 두 갈래 | 안전성 — 정책 드리프트 | 프로덕션 2곳 |

**확정된 진행 순서: ㉡·㉢ (Phase 1) → ㉠ (Phase 2).**

이 순서를 택한 이유는 두 가지다. 첫째, ㉡·㉢ 이 실제 보안 구멍에 더 가깝다. 둘째, ㉠ 은 인증 구조 자체를 손대는 작업이라 **인가 동작을 고정해주는 테스트가 먼저 있어야 하는데**, 현재 그 지점의 커버리지가 희박해 ㉠ 을 먼저 하면 무엇이 깨졌는지 알 수 없다.

## 3. 확정된 설계 결정

### 3.1 배치 — 가드는 **소유 도메인**에 둔다 (승인됨)

| 새 컴포넌트 | 위치 | 형태 | 이유 |
|---|---|---|---|
| `GuardianAccess` | `student/access/` | **스프링 빈** (`StudentGuardianRepository` 주입) | 보호자 판정의 주인은 student 도메인 |
| `BusCrewGuard` | `bus/access/` | **static** (`TenantGuard` 와 동일 스타일) | `(Bus, AuthUser)` 만으로 판정되는 순수 함수 |

**기각한 대안**

- **`global/` 에 모으기** — `global` 이 `student` 도메인 Repository 에 의존하게 되어 계층이 역전된다. `global` 은 모든 모듈이 의존하는 바닥이라 거기서 특정 도메인을 참조하면 순환의 씨앗이 된다. **현재 순환 의존 0건**(tokensave `acyclicity = 1.0`)이 이 저장소의 최대 강점이므로 이를 깎는 선택은 피한다.
- **엔티티 판정 메서드** — `GuardianAccess` 는 Repository 가 필요해 애초에 불가능하다.

### 3.2 `access/` 라는 새 하위 패키지 (승인됨)

`reference.md` §3 표준 레이아웃에는 없는 패키지를 연다. **`query/` 에 넣을 수 없기 때문이다** — `GuardianAccess` 의 호출자가 전부 Command 서비스라 `attendance.command → student.query` 가 되고, 이는 **§7 이 금지한 "Command 가 Query 를 호출" 패턴을 새로 만드는 것**이다. 리포트가 routing 의 위반으로 지적한 바로 그 모양이라 같은 부채를 늘릴 수 없다.

`access/` 는 command 도 query 도 아닌 **정책(policy) 계층**이라 이 충돌을 피한다.

**함께 할 것**: `reference.md` §3 에 `access/` 를 정식 항목으로 추가한다. 리포트 D-3(표준 레이아웃이 서술이 아니라 희망사항)에 대한 부분적 답이기도 하다.

### 3.3 동작 보존 원칙

**Phase 1 은 순수 리팩터링이다. 관측 가능한 동작을 바꾸지 않는다.**

| 치환 | 동작 동일성 근거 |
|---|---|
| `requireGuardianOf` ×3 → `GuardianAccess` | 세 벌이 **메시지까지 바이트 단위로 동일**함을 직접 확인 |
| `requireAssignedCrew` ×3 → `BusCrewGuard` | 본문 동일. **단 rideevent 판만 메시지가 다름** → §4.2 에서 별도 처리 |
| 인라인 테넌트 검사 ×2 → `TenantGuard` | `resolveTenantId(admin, tenantId)` 는 tenantId 가 non-null 일 때 인라인과 분기 결과가 동일. 이 호출부는 **엔티티에서 꺼낸 값이라 null 불가** |

## 5. Phase 2 — ㉠ 개요 (Phase 1 완료 후 별도 설계)

조사 결과 **권장안은 (b) 메타 애너테이션 + (d) `RoleHierarchy` 기반 permission 파생** 조합이다. 상세 설계는 Phase 1 완료 후 착수한다.

### 5.1 환경 실측

| 항목 | 값 |
|---|---|
| Spring Boot | 4.1.0 |
| Spring Security | **7.1.0** (Boot BOM `spring-boot-dependencies-4.1.0.pom` 직독) |
| 메서드 시큐리티 | `SecurityConfig:41` `@EnableMethodSecurity` (옵션 없음 = `prePostEnabled=true`) |
| 커스텀 인가 빈 | **없음** — `AuthorizationManager`·`RoleHierarchy`·`PermissionEvaluator` 0개 |

### 5.2 핵심 구조 결정 — 테넌트는 애너테이션으로 올리지 않는다

`AuthUser.authorities()`(`:40~46`)는 `Membership(tenantId, role)` 에서 **`tenantId` 를 버리고 role 만** `ROLE_*` authority 로 올린다. 즉 `hasRole('ACADEMY_ADMIN')` 은 "어느 학원의 관리자인지"를 말하지 않는다.

이건 결함이 아니라 **의도된 2단 분리**다 (`AuthUser.java:20~22` 주석이 명시).

1. `@PreAuthorize` = "이 기능을 쓸 수 있는 **종류**의 사용자인가" (테넌트 무관)
2. `TenantGuard.resolveTenantId()` = "그 **학원 데이터**를 만질 수 있는가"

**결정: 이 분리를 유지한다.** 테넌트를 애너테이션으로 끌어올리려면 모든 엔드포인트가 `tenantId` 를 명시 인자로 받도록 시그니처를 고쳐야 하는데(현재 `TenantGuard` 는 null 이면 `primaryTenantId()` 로 기본값을 채운다), 이는 permission 간접층과 무관한 훨씬 큰 API 변경이다.

### 5.3 권장 방식

1. `RoleHierarchy` 빈 1개에 `ROLE_PLATFORM_ADMIN > ROLE_ACADEMY_ADMIN > student:manage …` 매핑 선언 → **역할→권한 표가 코드 한 곳**에 모인다
2. 8종 표현식을 8개 메타 애너테이션(`@RequiresStudentManage` 등)으로 정의 → 61곳은 기계적 치환
3. 이후 **역할 추가 = `RoleHierarchy` 빈 1파일 수정**
4. **JWT 토큰 포맷 불변** → 기존 발급 토큰 유효 (permission 을 서버 측에서 파생시키므로 `JwtTokenProvider` 무수정)

**메타 애너테이션을 고른 이유**: 표현식이 8종뿐이라 치환 비용이 낮고, 4개 후보 중 **유일하게 컴파일 타임 안전성**을 준다(애너테이션이 타입이라 오타 = 컴파일 에러). 빈 참조 SpEL(`@perm.can(...)`)은 빈 이름·메서드명 오타를 런타임에야 발견한다.

### 5.4 착수 전 확인할 리스크 2가지

- **`@WebMvcTest` 슬라이스 6개가 실제 `SecurityConfig` 를 import 해 진짜 인가를 탄다**(`@Import({SecurityConfig.class, ...})`). `RoleHierarchy` 빈이 슬라이스 컨텍스트에 안 들어가면 **허용 경로 200 단언이 먼저 깨진다**
- `SecurityAnnotationScanners.requireUnique` 때문에 **클래스 레벨 + 메서드 레벨 인가 애너테이션 중복은 거부**된다. 메타 애너테이션 `@Target` 에 `TYPE` 을 넣을지 신중히 결정할 것

|---|---|

## 6. 열린 결정 (착수 전 확정 필요)

### 6.1 퇴원 학생 처리 — **미결**

현재 **퇴원(`active=false`) 학생의 보호자도 결석신고·일정변경·위치변경을 정상적으로 낼 수 있다.** `active` 필터는 배차·시뮬레이션·로스터 쪽에만 있다(`RoutingCommandService:268`, `RoutePlanSimulationService:146`, `MockSimulationPlan:42`, `StudentRepository` 의 `…ActiveTrue` 메서드들). 보호자 요청 경로에는 없다.

결과적으로 위치변경 요청은 **접수는 되고 재배차에는 반영되지 않는 조용한 무효 요청**이 된다. 직전 커밋 `ded41c8`(H-1)이 배차 쪽에서 막은 것과 같은 계열로 보인다.

| 안 | 내용 | 평가 |
|---|---|---|
| **A (권장)** | 동작 보존만. 퇴원 필터는 별도 이슈로 분리 | 리팩터링과 버그 수정을 섞지 않아 원인 추적이 명확. **판정 지점이 1곳이 된 뒤에 고치면 고칠 곳도 1곳**이라 순서상 더 싸다 |
| B | `GuardianAccess` 에 `active` 필터를 넣어 퇴원 시 FORBIDDEN | 구멍은 즉시 막히나 기존 테스트 3건의 의미가 바뀌고 "리팩터링이 깨뜨린 것"과 "의도한 변경"이 섞인다 |
| C | `requireGuardianOf`(기존) / `requireActiveChildOf`(퇴원 제외) 둘 다 제공 | 정확하지만 호출부마다 판단이 필요해 범위가 커진다 |

### 6.2 `requireAssignedCrew` 메시지 통일 — **미결**

§4.2 참조. 권장 ⓐ(조회 문구로 통일)이나 사용자 노출 문구 변경이므로 확인 필요.

## 8. ※ 미확인

1. **테스트 실행 검증 없음** — 전역 규칙(Docker 임의 기동 금지)에 따라 `./gradlew test` 를 실행하지 않았다. "Docker 불필요"(§4.1) 판단은 해당 테스트들이 `new XxxService(mock, mock)` 로 생 객체를 만든다는 정적 근거에 기반한다.
2. **Phase 2 의 역할×기능 권한 매트릭스** — 조사는 완료했으나 이 문서에 옮기지 않았다. Phase 2 착수 시 **재수집이 필요하다**(세션 스크래치패드에만 존재).
3. **Spring Security 7.1 전용 변경사항** — context7 에 7.1 문서 세트가 없어 7.0 기준으로만 확인했다. 인용한 API 는 7.0 에서 GA 이며 7.1 제거 고지는 없다.
4. **`TenantGuard` 호출 누락 엔드포인트** — 호출이 23파일 30회인데, **호출해야 하는데 안 하는 곳**이 있는지는 별도 감사 대상이다. 이번 범위 밖.
5. **프론트엔드 영향** — Flutter 가 역할·권한을 어떻게 하드코딩했는지는 보지 않았다. Phase 2 의 실제 비용은 프론트를 포함하면 더 커질 수 있다.
