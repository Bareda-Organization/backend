## 사전 사실 (실측 — 이 값에 맞춘다)

| 항목 | 실측값 |
|---|---|
| `buildPlan` | **오버로드 2개**. 4-arg(로스터 직접 조회) → 5-arg(로스터 받음) 위임 |
| 5-arg 실행 순서 | ① `requireDepot` ② 정원 초과 검사 ③ `resolveStudentPoints` ④ `optimizeOrder` ⑤ `buildWaypoints` ⑥ `resolveRoute` ⑦ version 채번 ⑧ `save` |
| ETA 오프셋 | `DROPOFF`=1 (waypoint[0]이 depot) · `PICKUP`=0 |
| 정차 순서 | `DROPOFF`=`optimizeOrder` 결과 그대로 · `PICKUP`=역순 |
| `Student` 좌표 | 하원=`dropoffLat`/`dropoffLng`(직접 컬럼) · 등원=`boardingStop`(**여러 학생이 공유하는 `Stop` 참조**) |
| `Student` 변경자 | `assignBus(Bus)` · `assignStop(Stop)` · `updateDropoff(String, Double, Double)` |

### 외부 경로 API 호출 횟수 (요청 1건당)

`resolveRoute` 는 waypoint 가 상한을 넘으면 경계를 공유하며 쪼갠다. waypoint `W = 정차수 N + 1`(depot),
청크 진행폭 `maxWaypoints − 1 = 6` 이므로 **`호출 = ceil((W−1)/6) = ceil(N/6)`** — N=6→1회, 7→2회, 13→3회, **25(정원 상한)→5회**.

- `POST /simulate` = candidate 1회 계산 = `ceil(N/6)` 회. baseline 은 저장된 행을 읽기만 하므로 **0회**.
- `POST /simulate/apply` 도 `ceil(N/6)` 회 — `SimulationOutcome` 의 `PlannedRoute` 를 그대로 저장하기 때문.
  **재계산하면 2배(최대 10회)** 다. 구현에서 `outcome.candidate()` 를 반드시 재사용한다.
- `ADD` k명이면 `ceil((N+k)/6)` 회. FE-6 은 연속 호출을 디바운스한다.

```java

    /** 구간당 1000m·60s 고정 — 정차가 1개 줄면 델타가 정확히 −1000m/−60s 로 나온다. 외부 호출 없음. */

        final List<List<LatLng>> calls = new ArrayList<>();
        @Override public RouteResult route(List<LatLng> waypoints) {
            calls.add(List.copyOf(waypoints));
            int legs = waypoints.size() - 1;
            List<Double> legDurations = new ArrayList<>();
            for (int i = 0; i < legs; i++) legDurations.add(60.0);
            return new RouteResult(legs * 1000.0, legs * 60.0, legDurations, "[[37.5,127.0]]");
        }
```

> → **Step 1 특성 테스트에 이 분기 2개를 반드시 넣는다:** ① `pickupLat/Lng` 보유 학생은 그 좌표가 쓰인다
> ② `pickupLat/Lng` 가 null 인 학생은 기존대로 `boardingStop` 좌표가 쓰인다(회귀 방지).
> `BE-1` 시드가 두 경우를 모두 갖도록 학생을 섞어 두었으므로 통합 확인도 가능하다.

클래스 선언 — `package src.backend.routing.engine;` · `@Component` · 필드 3개(`RouteEngine routeEngine`, `MapRouteClient mapRouteClient`,
`int maxWaypoints`)를 생성자 주입하고 `maxWaypoints` 에는 `@Value("${routing.max-waypoints:7}")` 를 그대로 옮긴다. 클래스 javadoc —
*"노선 순수 계산. 저장·version 채번·권한 검사를 하지 않으므로 시뮬레이션(BE-4)과 실제 저장이 공유한다. 교체 후보가 아니라 concrete 클래스로 둔다(§11.3)."*

```java
    /** 저장하지 않고 노선을 계산한다. 정원 초과를 검사하지 않는다 — 시뮬레이션이 초과 상태도 보여줘야 하기 때문. */
    public PlannedRoute computeRoute(Bus bus, RouteDirection direction, Map<Long, LatLng> studentPoints) {
        LatLng depot = requireDepot(bus.getTenant());
        List<Long> optimizedOrder = routeEngine.optimizeOrder(depot, studentPoints);
        List<Long> stopOrder = direction == RouteDirection.DROPOFF ? optimizedOrder : reversed(optimizedOrder);
        List<LatLng> waypoints = buildWaypoints(depot, stopOrder, studentPoints, direction);
        RouteResult routeResult = resolveRoute(waypoints);
        List<Double> cumulative = cumulativeSeconds(routeResult.legDurationsS());
        int stopWaypointOffset = direction == RouteDirection.DROPOFF ? 1 : 0;
        List<LatLng> stopPoints = new ArrayList<>(stopOrder.size());
        List<Long> stopEtaSeconds = new ArrayList<>(stopOrder.size());
        for (int i = 0; i < stopOrder.size(); i++) {
            stopPoints.add(studentPoints.get(stopOrder.get(i)));
            stopEtaSeconds.add(Math.round(cumulative.get(i + stopWaypointOffset)));
        }
        return new PlannedRoute(List.copyOf(stopOrder), List.copyOf(stopPoints), List.copyOf(stopEtaSeconds),
                routeResult.totalDistanceM(), routeResult.totalDurationS(), routeResult.polyline());
    }

    /**
     * 학생 1명의 방향별 좌표. 없으면 null — 시뮬레이션이 override 로 덮어쓸 수 있어 개별 해석이 필요하다.
     *
     * ⚠️ PICKUP 은 <b>학생 자체 좌표(pickupLat/Lng)가 있으면 그것을 우선</b>하고, 없을 때만
     * 공유 정류장(boardingStop)으로 떨어진다(OVERVIEW 결정 D-K). 이 우선순위가 없으면
     * 학부모가 등원 위치를 바꿔도(BE-10 이 pickupLat/Lng 에 저장) 경로 계산은 계속 정류장을 읽어
     * <b>변경이 조용히 무효</b>가 된다. 반대로 Stop.lat/lng 를 고치면 같은 정류장을 쓰는
     * 다른 학생까지 함께 끌려가므로, Stop 은 절대 수정하지 않는다.
     */
    public static LatLng pointOf(Student student, RouteDirection direction) {
        if (direction == RouteDirection.PICKUP) {
            if (student.getPickupLat() != null && student.getPickupLng() != null) {
                return new LatLng(student.getPickupLat(), student.getPickupLng());
            }
            return student.getBoardingStop() == null ? null
                    : new LatLng(student.getBoardingStop().getLat(), student.getBoardingStop().getLng());
        }
        return (student.getDropoffLat() == null || student.getDropoffLng() == null) ? null
                : new LatLng(student.getDropoffLat(), student.getDropoffLng());
    }

    public LatLng requireDepot(Tenant tenant) { /* 기존 RoutingCommandService 구현 그대로 */ }

    // buildWaypoints · reversed · cumulativeSeconds · resolveRoute 는 private 으로 그대로 이동한다
}
```

**정원 초과를 예외로 죽이지 않는다**

- `RoutePlanComputer.computeRoute` 에 정원 검사가 없으므로 시뮬레이션은 초과 상태여도 **정상 응답**한다.
  비교 화면이 정원 때문에 통째로 죽으면 관리자가 "왜 안 되는지"를 볼 수 없다.
- 초과 여부는 **응답 하나로 자족**한다 — `candidate.stops().size() > seatCapacity`. FE-6 이 `GET /api/buses/{id}` 를 따로 부르지 않는다.
- `seatCapacity` 는 `baseline` 유무와 무관하게 **항상 채운다**(첫 계획이어도 초과 판정은 해야 한다).
- **저장 시점(`apply`)에는 정원 초과를 `INVALID_INPUT` 으로 거부**한다 — 기존 `buildPlan` 과 같은 규칙.
- `Snapshot.routePlanId`·`version` 은 candidate 에서 **항상 `null`**. `baseline` 이 없으면 `delta` 도 `null`.

**`StopView.label` 규칙** — `PICKUP` 이면 `student.getPickupAddress()`, 비어 있으면 `student.getBoardingStop().getName()`.
`DROPOFF` 면 `student.getDropoffAddress()`. **좌표 우선순위(D-K)와 같은 순서**다 — 좌표는 학생 자체 값을 쓰는데 라벨만 정류장명이면 화면이 어긋난다.
해당 값이 전부 `null`/공백이거나 학생 행을 못 찾으면 문자열 **`"좌표 지정"`** 을 쓰고 `lat`/`lng` 는 실제 좌표를 그대로 노출한다.
`MOVE` 된 학생의 `label` 은 **저장된 값 그대로**다(좌표만 변경안 값) — 화면은 baseline/candidate 의 좌표 차이로 이동을 인식한다.

```java
        if (overrides == null) {
            return;
        }
        for (StudentOverride o : overrides) {
            if (o.action() == StudentOverride.OverrideAction.REMOVE) {
                points.remove(o.studentId());
                continue;
            }
            if (o.lat() == null || o.lng() == null) {
                throw new BusinessException(ErrorCode.INVALID_INPUT,
                        o.action() + " 변경안에는 좌표가 필요합니다: studentId=" + o.studentId());
            }
            Student student = studentRepository.findById(o.studentId())
                    .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND,
                            "학생을 찾을 수 없습니다: " + o.studentId()));
            if (!student.getTenant().getId().equals(bus.getTenant().getId())) {
                throw new BusinessException(ErrorCode.FORBIDDEN);   // 타 학원 학생 끌어오기 차단
            }
            points.put(o.studentId(), new LatLng(o.lat(), o.lng()));
        }
    }
```

- [ ] **Step 3: `commitOverrides` 로 배정·좌표를 커밋한다**

D-K로 `Student` 가 등원 좌표를 자체 컬럼으로 갖게 됐으므로 **양방향 모두 좌표를 저장한다.** PICKUP `MOVE` 를 더 이상 거부하지 않는다.

```java
    /**
     * 변경안을 Student 에 커밋한다. 방향에 따라 저장 위치가 다르다 —
     * PICKUP 은 pickupLat/pickupLng(D-K), DROPOFF 는 dropoffLat/dropoffLng.
     * boardingStop 은 여러 학생이 공유하는 Stop 이라 절대 건드리지 않는다.
     */
    private void commitOverrides(Bus bus, SimulateRoutePlanRequest req) {
        if (req.overrides() == null) {
            return;
        }
        for (StudentOverride o : req.overrides()) {
            Student student = studentRepository.findById(o.studentId())
                    .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND,
                            "학생을 찾을 수 없습니다: " + o.studentId()));
            if (o.action() == StudentOverride.OverrideAction.REMOVE) {
                student.assignBus(null);
                continue;
            }
            student.assignBus(bus);   // ADD · MOVE 공통
            if (req.direction() == RouteDirection.PICKUP) {
                student.updatePickup(student.getPickupAddress(), o.lat(), o.lng());
            } else {
                student.updateDropoff(student.getDropoffAddress(), o.lat(), o.lng());
            }
        }
    }
```

> 좌표만 바꾸고 **주소 문자열은 기존 값을 그대로 넘긴다.** 관리자 화면은 지도에서 점을 찍을 뿐 주소를 입력하지 않는다 —
> 주소를 `null` 로 덮으면 `StopView.label` 이 `"좌표 지정"` 으로 퇴화한다. 역지오코딩은 이번 범위 밖이다.
> `updatePickup(String, Double, Double)` 은 `BE-2` 산출물이다 — 없으면 컴파일되지 않으니 선행 완료를 먼저 확인한다.

## 자체 점검

**(1) 요구 8 · P2 커버리지** — **요구 8**: "추가·수정·삭제"=`StudentOverride` 의 `ADD`/`MOVE`/`REMOVE`(Step 4),
"경로/시간/거리 비교"=`Snapshot.polyline` + `Delta.durationS` + `Delta.distanceM`(Step 6), "선택"=`POST /simulate/apply`(BE-5)가
배정 커밋 + 승인 + 배포까지 한 번에 수행. **P2**: 구현은 `BE-10` 이지만 **연산은 여기서 끝난다** — `BE-10` 은 학부모 요청을
`StudentOverride(studentId, MOVE, lat, lng)` 한 건으로 만들어 **`compare(busId, direction, serviceDate, overrides)`**(§4.5, `AuthUser` 없음)를
호출하고, 나온 `Delta` 를 `LocationChangeThresholds` 와 AND 비교(D-H)해 `APPLIED`/`REPLANNED`/`REJECTED` 를 정한다.
`simulate`·`compare`·`apply` 가 전부 `computeCore` → `RoutePlanComputer.computeRoute` 한 경로를 지나므로 기준이 갈라질 수 없다(D-I 충족).

**(2) 개정(2026-08-02)으로 처리한 항목**

**A** `compare(...)` 를 §4.5 그대로 노출하고 `simulate` 는 인가 후 `computeCore` 로 합류(Step 6). `SimulationOutcome` 은 "이 문서 밖으로 나가지 않는 BE-5 전용 타입"으로 명시.
**B** `RoutePlanComparison` 최상위 `seatCapacity` 를 Step 4의 record 선언과 Step 6c 의 `toComparison` 양쪽에 반영. 시뮬레이션은 무예외, `apply` 만 거부.
**C** PICKUP `MOVE` 거부 철회 — `pointOf` 등원 좌표 우선(Step 3), Step 1 특성 테스트 2건, `commitOverrides` 양방향 저장(BE-5 Step 3), `StopView.label` 을 `pickupAddress` 우선으로 변경.
**D** BE-4 Step 7 · BE-5 Step 5에 실제 `git commit` 명령 추가. **E** Step 3→3·3b·3c, Step 6→6·6a·6b·6c, BE-5 Step 2→2·3 으로 분할.

**(3) 개정하며 새로 발견한 모순**

1. **OVERVIEW §4.4 의 `RoutePlanComparison` record 선언 본문에는 `seatCapacity` 가 없다.** 바로 아래 산문에만
   *"최상위에 `int seatCapacity` 를 포함한다"* 로 적혀 있어 **컴포넌트 위치가 정해져 있지 않다.** 이 문서는 `delta` 다음
   **마지막 컴포넌트**로 확정했다(`RoutePlanComparison(baseline, candidate, delta, seatCapacity)`).
   §4.4 코드 블록도 같게 고쳐 두는 편이 안전하다 — 계약 문서가 자기모순이면 다음 에이전트가 다시 묻는다.
2. **§4.4 의 `StopView.label` 주석이 D-K 이전 기준이다.** *"정류장명(PICKUP) 또는 하차지 주소(DROPOFF)"* 라고만 적혀 있는데,
   `pickup_address` 가 생겼으므로 PICKUP 라벨은 `pickupAddress` → `boardingStop.name` 순이어야 한다(좌표 우선순위와 일치).
   이 문서는 그렇게 정했다. **§4.4 주석 갱신 필요.**
3. **`compare(...)` 는 인가를 하지 않으므로 `busId` 를 그대로 신뢰한다.** §4.5 가 *"인가는 호출자가 끝냈다"* 로 규정했으니 설계대로지만,
   `BE-10` 의 `LocationChangeCommandService` 가 **"그 학생의 보호자인가"에 더해 "그 학생이 그 버스에 배정돼 있는가"까지** 확인하지 않으면
   학부모가 임의의 `busId` 를 넣어 다른 학원 노선을 계산시킬 수 있다. `compare` 쪽에서는 막을 방법이 없다 — **`BE-10` 계획서에 이 검사가 있는지 확인 필요.**
4. **`autoAssign` 의 동작이 D-K 때문에 함께 바뀐다.** Step 3c 가 인라인 삼항을 `pointOf` 로 통일하므로, `pickupLat/Lng` 를 가진 학생은
   **자동 배차에서도** 새 좌표로 잡힌다. 의도한 결과지만 `BE-4` 범위를 넘는 부수효과라 명시해 둔다.
5. **`publishAndNotify` 는 `plan.getStops().get(0)` 을 무조건 참조한다** — 정차 0개면 `IndexOutOfBoundsException` 이다.
   `applySimulation` 은 그 앞에서 `computeCore` 가 "정차 0개" 를 `INVALID_INPUT` 으로 거르므로 안전하다.
