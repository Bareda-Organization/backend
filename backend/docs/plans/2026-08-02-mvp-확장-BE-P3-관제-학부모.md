## 전역 제약

- **Java 25**, **Spring Boot 4.1.0**. 웹 스타터는 `spring-boot-starter-webmvc`(구 `-web` 아님).
- 새 클래스는 전부 **`src.backend.*`** 하위(컴포넌트 스캔 루트). **`package-info.java` 를 만들지 않는다.**
- `spec`/`impl` 분리는 **"구현이 바뀔 가능성이 있는가"** 로만 판단한다. 이 문서의 신규 서비스는 전부 단일 구현이라 **concrete 클래스 하나**로 둔다(`repository` 만 Spring Data 관례대로 `repository/spec/` 인터페이스).
- gradle 명령은 전부 `backend/` 에서 실행한다.
- `ddl-auto: validate` 다 — 엔티티 필드는 **`BE-1` 이 만든 컬럼과 이름·타입이 정확히 맞아야** 앱이 뜬다.
- 도메인 이벤트는 `ApplicationEventPublisher.publishEvent(...)` 만 호출한다. `TransactionalDomainEventRelay` 가 AFTER_COMMIT 에 Kafka 로 릴레이한다.

  private User loadUserWithRole(Long userId, Long tenantId, Role required) {

### (1) 요구사항 커버리지

### (2) 소스를 읽다 발견한, 계획과 어긋나는 사실

1. **STOMP 인가 목록 추가는 필요 없다.** 지시에는 "필요하면 인가 목록 추가 단계를 넣어라"고 돼 있었으나, `StompAuthChannelInterceptor` 는 화이트리스트가 아니라 정규식 `^/topic/tenant/(\d+)/.*` 로 검사한다. `/topic/tenant/{tenantId}/bus-locations` 는 **이미 자동으로 걸린다** — `BE-8` 에서 이 파일을 수정하지 않는다.
2. **`DriveSessionRepository` 에 I-4 를 만족하는 메서드가 없다.** 기존 `findByBusIdAndDirectionAndServiceDateAndStatus` 는 상태를 인자로 받아 "진행 중"만 찾는다. I-4 는 종료된 세션도 거부하므로 `existsByBusIdAndDirectionAndServiceDate` 를 새로 추가해야 한다(`BE-10` Step 3).
3. **`RoutingCommandService.boardingPoint(Student)` 가 D-K 를 모른다.** 결정 D-K 로 `student.pickup_lat/lng` 가 생겼지만, 노선 계산의 좌표 해석기는 여전히 `boardingStop` 만 읽는다. 이대로면 학부모가 등원 위치를 바꿔 `REPLANNED` 로 재계산돼도 **엔진이 옛 정류장 좌표를 써 변경이 통째로 무효가 된다.** `BE-10` Step 5b 에서 "자체 좌표 우선"으로 고친다 — 이 메서드는 `buildPlan`·`autoAssign` 이 공유하므로 한 곳만 고치면 된다. **`BE-4` 의 시뮬레이션 엔진도 같은 우선순위를 써야** 비교와 재계산의 기준이 갈라지지 않는다(`BE-P2-엔진` 담당자 확인 필요).
4. **자동 적용의 계획 상태가 기존 흐름과 충돌한다.** 기존 replan(`RoutingCommandService.replanForStudent`)은 `RECOMMENDED` 만 만들고 관리자 승인을 기다리는데, D-H 는 무승인 자동 적용이라 그대로 두면 기사·선탑자 조회 API(`PUBLISHED` 만 노출)에 안 보인다. `republishForBus`(재계산→approve→publish)를 신설했다. 이때 **신청한 학부모 userId 가 `approvedBy`·`publishedBy` 에 남는데**, "누가 촉발했는지"를 남기려는 의도적 선택이다.
5. **배차 참조 무결성 결함은 `assign` 만이 아니다.** `BusCommandService.createBus` 도 같은 `loadUser` 를 쓴다(에러 메시지도 "기사를 찾을 수 없습니다"로 고정돼 선탑자엔 부정확하다). `BE-7` 에서 **생성 경로까지 함께 고친다.**
6. **`location_change_request` 컬럼 정의가 OVERVIEW 에 없다.** §3.1 은 "신규 테이블"이라고만 적어 `BE-1` 이 만든 컬럼을 확인할 수 없었다. `BE-10` Step 2 의 필드를 정본으로 가정했으니, 착수 전 `V1__init_schema.sql` 의 실제 컬럼과 **반드시 대조**해야 한다(`ddl-auto: validate` 라 불일치 시 기동 실패).
7. **`BusQueryServiceTest` 기존 테스트가 깨진다.** `getBus` 시그니처에 `date` 가 붙고 `BusResponse` 필드가 늘어 기존 6개가 컴파일 에러를 낸다. `BE-6` Step 1 에서 먼저 고친 뒤 진행한다.
8. **커밋 단계는 한 줄로만 뒀다.** OVERVIEW **§1.5** 가 *"모듈 계획서의 개별 단계에 커밋 명령을 반복해 적지 않는다"* 로 규약을 통일했으므로, 태스크마다 커밋 단계는 두되 **명령·형식은 반복하지 않고 태스크별 제목과 본문에 담을 "왜"만** 적었다.
9. **정원 초과 분기는 `MOVE` 단독으로는 거의 걸리지 않는다.** `RoutePlanComparison.seatCapacity`(OVERVIEW §4.4) 판정을 `BE-10` Step 6 의 4-a 로 넣었지만, 위치 변경은 정차 수를 늘리지 않으므로 **baseline 이 이미 정원을 넘긴 경우에만** 발동한다. 그래도 남긴 이유는 그 상태에서 좌표까지 바꾸면 초과가 고착되기 때문이다 — 정원 초과의 주 발생 경로는 `BE-5` 의 `ADD` 다.
