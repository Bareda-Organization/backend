# MVP 확장 — 백엔드 P2b: 계정 CRUD · 수동 매칭 (BE-12 ~ BE-14)

> **에이전트에게:** 공용 계약·결정은 [`docs/plans/2026-08-02-mvp-확장-OVERVIEW.md`](../../../docs/plans/2026-08-02-mvp-확장-OVERVIEW.md) 에만 있다. **그 문서를 먼저 읽고** 이 문서로 온다. 특히 **§4.2.1(실측 현황)** · **§4.6(DTO 계약)** · **D-M~D-P** · **I-6~I-9** 를 안 읽고 시작하면 이미 있는 API 를 다시 만든다.

- 작성일: 2026-08-02 · 담당: `BE-12` `BE-13` `BE-14` (OVERVIEW §5 의 P2·P3 구간, 요구 **A1·A2**)
- 전제: **`BE-2` 완료** — `Role.ATTENDANT`, `User.photoUrl`, `Student.photoUrl`·`Student.phone`, **`Student.active`** 존재.
- `BE-14` 는 추가로 **`BE-7` 완료**가 전제다(같은 `BusCommandService.assign` 을 고친다).
- Files 의 경로는 전부 `backend/` 기준이다.

## 전역 제약

- **Java 25**, **Spring Boot 4.1.0**. 웹 스타터는 `spring-boot-starter-webmvc`(구 `-web` 아님).
- 새 클래스는 전부 **`src.backend.*`** 하위. **`package-info.java` 를 만들지 않는다.**
- 이 문서의 서비스는 **전부 기존 concrete 클래스에 메서드를 더하는 것**이다. 새 서비스 클래스를 만들지 않는다 — `spec`/`impl` 분리 기준("구현이 바뀔 가능성")에 해당하지 않는다.
- `ddl-auto: validate` 다 — `Student.active` 는 **`BE-1` 이 만든 컬럼**과 이름·타입이 맞아야 앱이 뜬다. 이 문서는 **`V1__init_schema.sql` 을 열지 않는다.**
- gradle 명령은 전부 `backend/` 에서 실행한다.

### BE-12: 구성원 상세 · 수정 · 비밀번호 재설정 · 멤버십 해제 (요구 A1)

**목적:** 지금 `POST`(생성)와 `GET`(목록)뿐인 `/api/members` 에 **U·D 를 채워** 관리자가 학부모·기사·선탑자를 앱에서 끝까지 관리하게 한다(D-M).
**선행:** `BE-2`
**Files:**
- Create `src/main/java/src/backend/user/dto/UpdateMemberRequest.java` · `user/dto/ResetPasswordRequest.java` · `user/dto/MemberDetailResponse.java`
- Modify `src/main/java/src/backend/user/dto/MemberResponse.java` · `user/command/MemberCommandService.java` · `user/query/MemberQueryService.java` · `user/controller/MemberController.java`
- Modify `src/main/java/src/backend/user/repository/spec/UserTenantRoleRepository.java` · `bus/repository/spec/BusRepository.java` · `student/repository/spec/StudentGuardianRepository.java`
- Create Test `src/test/java/src/backend/user/command/MemberCommandServiceTest.java`

**Interfaces:**

- Produces: `MemberDetailResponse MemberQueryService.get(AuthUser, Long)` / `MemberResponse MemberCommandService.update(AuthUser, Long, UpdateMemberRequest)` / `void MemberCommandService.resetPassword(AuthUser, Long, ResetPasswordRequest)` / `void MemberCommandService.removeMembership(AuthUser, Long)`

> ⚠️ **이 태스크는 저장소에서 권한 사고가 나기 가장 쉬운 자리다.** 비밀번호를 남의 것으로 바꿀 수 있고, 역할을 올릴 수 있고, 자기 학원의 마지막 관리자를 지울 수 있다. Step 6·7·8 의 금지 규칙 4개는 **편의가 아니라 필수**다.

> ⚠️ **`User` 는 학원과 N:M 이다.** `PATCH /api/members/{id}` 로 이름·전화를 고치면 **그 사람이 속한 모든 학원에서 함께 바뀐다.** 이건 데이터 모델상 불가피하다(`app_user` 가 한 벌뿐이다). 학원별로 다른 이름을 갖게 하려면 `user_tenant_role` 에 표시명 컬럼이 필요한데, **이번 범위 밖**이다. Swagger 설명에 이 사실을 적어 관리자가 오해하지 않게 한다.

- [ ] **Step 4: `MemberDetailResponse` 를 만든다.** 정의는 **OVERVIEW §4.6** 이 유일한 출처다 — 필드를 지어내지 않는다.

- [ ] **Step 5: `MemberQueryService.get` 을 만든다.** 쿼리는 멤버십1 + 버스2 + 보호자1 = **4회 고정**이다.
  ```java
  @Transactional(readOnly = true)
  public MemberDetailResponse get(AuthUser admin, Long userId) {
      UserTenantRole membership = loadAccessibleMembership(admin, userId);
      Long tenantId = membership.getTenant().getId();
      List<Bus> asDriver = busRepository.findByDriverIdAndTenantId(userId, tenantId);
      List<Bus> asAttendant = busRepository.findByAttendantIdAndTenantId(userId, tenantId);
      List<StudentGuardian> guarded = studentGuardianRepository.findByGuardianId(userId);
      return MemberDetailResponse.of(membership, asDriver, asAttendant, guarded);
  }

  /** 요청자 학원의 구성원만 통과시킨다 — 여기가 이 태스크의 유일한 격리 지점이다. */
  private UserTenantRole loadAccessibleMembership(AuthUser admin, Long userId) {
      Long effectiveTenant = TenantGuard.resolveTenantId(admin, null);
      return userTenantRoleRepository.findByUserIdAndTenantId(userId, effectiveTenant)
              .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND, "이 학원의 구성원이 아닙니다"));
  }
  ```
  ⚠️ **`userRepository.findById` 로 시작하지 않는다.** 그러면 다른 학원 사용자도 찾아지고, 그 뒤에 붙이는 검사를 한 번이라도 빠뜨리면 **전 학원 계정 조회기**가 된다. **멤버십을 먼저 찾는 순서**가 격리를 구조적으로 보장한다.
  `guarded` 는 테넌트 필터가 없다 — `StudentGuardian.student.tenant` 로 걸러 넣는다(형제가 다른 학원일 수 있다).

- [ ] **Step 6: `update` — 금지 규칙 3개를 먼저 적고 그 다음에 갱신한다.**
  ```java
  @Transactional
  public MemberResponse update(AuthUser admin, Long userId, UpdateMemberRequest req) {
      UserTenantRole membership = loadAccessibleMembership(admin, userId);
      // ① 자기 자신은 이 경로로 못 고친다. 관리자가 스스로를 PARENT 로 바꾸면
      //    그 순간 화면에서 쫓겨나고 되돌릴 권한도 사라진다.
      if (userId.equals(admin.userId())) {
          throw new BusinessException(ErrorCode.INVALID_INPUT, "본인 계정은 이 화면에서 수정할 수 없습니다");
      }
      // ② 권한 상승 차단 — register 와 같은 규칙이다(BE-11 과 같은 결함군).
      if (req.role() == Role.PLATFORM_ADMIN) {
          throw new BusinessException(ErrorCode.INVALID_INPUT, "플랫폼 관리자로 변경할 수 없습니다");
      }
      User user = membership.getUser();
      // ③ 이메일은 로그인 ID다 — 바뀔 때만 중복 검사한다(자기 이메일 그대로면 통과해야 한다).
      if (req.email() != null && !req.email().equals(user.getEmail())) {
          if (userRepository.existsByEmail(req.email())) throw new BusinessException(ErrorCode.DUPLICATE_EMAIL);
          user.changeEmail(req.email());
      }
      user.updateProfile(req.name(), req.phone(), req.photoUrl());   // null 은 "그대로"
      if (req.role() != null && req.role() != membership.getRole()) membership.changeRole(req.role());
      return MemberResponse.of(membership);
  }
  ```
  `User` 에 `changeEmail`·`updateProfile`, `UserTenantRole` 에 `changeRole` 을 **엔티티 메서드로** 추가한다(세터를 열지 않는다).
  `updateProfile` 은 **전달된 값만** 덮는다: `if (name != null) this.name = name;` 식.
  ⚠️ **역할 변경은 `unique (user_id, tenant_id, role)` 제약에 걸릴 수 있다** — 같은 사람이 이미 그 역할을 그 학원에서 갖고 있으면(중복 멤버십) `DataIntegrityViolationException` 이 난다. 바꾸기 전에 `findByUserIdAndTenantId` 대신 `findByUserId` 로 훑어 중복이면 `CONFLICT` 로 돌린다.

  ```java
  @Transactional
  public void removeMembership(AuthUser admin, Long userId) {
      UserTenantRole membership = loadAccessibleMembership(admin, userId);
      if (userId.equals(admin.userId())) {
          throw new BusinessException(ErrorCode.INVALID_INPUT, "본인 계정은 해제할 수 없습니다");
  ```
