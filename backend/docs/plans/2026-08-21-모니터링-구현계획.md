## 1. 1차 · 버스 관제

### 1.A 백엔드 — 관제 데이터의 신뢰성

#### MON-1 · 버스 좌표 보관을 Redis TTL 로 전환 · **신규 발견**
- **증상 2건.**
  1. 기사 앱이 전송을 멈춰도 **마지막 좌표가 영구 잔존** — 관제 지도가 멈춘 버스를 계속 "여기 있음" 으로 표시. 만료·축출 수단 부재.
  2. 백엔드 재시작 시 **전 버스 좌표 소실** — 관제 지도가 빈 상태로 복귀.
- **근거.** `location/repository/impl/InMemoryBusLocationRepository.java:19~28` — `ConcurrentHashMap` 에 `put` 만 하고 TTL·제거 경로 전무.
  **대조군:** 학생 위치는 `location/repository/impl/RedisLocationRepository.java:35` 가 `tickMs * 3`(기본 9초) TTL 적용 → 자동 만료.
  **즉 학생 위치와 버스 위치가 비대칭**이며, 관제 화면이 보는 쪽이 만료 없는 쪽.
- **범위.** `RedisLocationRepository` 를 그대로 미러링해 `RedisBusLocationRepository` 신설.
  `BusLocationRepository`(spec) 계약은 불변 — 서비스 계층 수정 부재.
  조회에서 만료(=empty)면 관제 응답에 **"신호 없음"** 으로 구분해 반환.
- **부수 효과.** `docker-compose.prod.yml:114` 의 인스턴스 1개 제약 사유 **(2) 번이 해소**.
  ⚠ 단 **(1) `@Scheduled` 4개 중복 · (3) STOMP 세션 로컬 보관은 잔존**하므로 **인스턴스 증설은 여전히 금지**.
- **판단 필요.** TTL 값. 학생과 같은 `tick*3`(9초)이면 3초 보고 주기에서 2회 연속 누락 시 만료 — 관제 판정용으로 짧을 가능성.
  버스 보고 주기가 5초(`POST /api/locations/bus`)라 **별도 상수 도입**이 타당.
- **완료 조건.** 보고 중단 후 TTL 경과 시 `GET /api/locations/buses` 에서 해당 버스가 "신호 없음" 으로 구분 + 백엔드 재시작 후에도 유효 좌표 유지.

#### MON-2 · 위치 출처(origin) 실제 값 기록 · `= BG-2`
- **관제 관점 증상.** 상세 패널의 "단말/시뮬레이터" 표기가 **항상 단말** — 데모 Mock 좌표를 실 위치로 표시.
- **근거 (2026-08-21 재조사로 범위 축소).** 하드코딩은 **단말 보고 경로 한 곳뿐**이다 —
  `location/command/BusLocationCommandService.java:48` `reportSelf()` 와 `location/command/LocationCommandService.java:57` 이 `LocationOrigin.GPS` 고정.
  **서버 내부 Mock 경로는 이미 정직하다** — `location/source/MockBusLocationSource.java:57` 이 `ingest(..., LocationOrigin.MOCK)` 으로 실제 출처를 전달하고,
  `ingest()` 시그니처도 `origin` 을 받는다. 즉 **저장 계층은 이미 출처를 구분할 수 있고, 단말에서 올라오는 값만 수신 경로가 부재**하다.
- **범위.** 보고 DTO 에 `origin` 추가(미지정 시 `GPS`) → `reportSelf()` 가 `ingest()` 로 전달.
  `ingest()` 는 수정 불필요. **`BusLocationView` 는 이미 `origin` 필드 보유**라 응답 스키마 변경 부재.

  단말 보고만 관측하려면 `--app.location.mock.enabled=false` 로 기동한다(MON-1 검증에서 실제로 걸린 함정).
- **⚠ MON-1 과 같은 파일 수정** — `BusLocationCommandService`. 순차 진행.
- **완료 조건.** `MOCK` 으로 보고한 좌표가 관제 조회·STOMP push 양쪽에서 `MOCK` 으로 반환.

#### MON-8 · 스케줄러 4개의 생존 관측 · **가장 시급**
- **증상.** `@Scheduled` 4개가 **예외를 잡아 `log.warn` 만 남기고 계속 진행** — 판정 로직이 통째로 실패해도 앱은 정상 기동 상태를 유지하고, **알림이 안 나가는 것으로만 뒤늦게 드러남**.
- **근거.** `location/scheduler/ConnectionLossScheduler.java:29~33` 의 `try/catch` → `log.warn`. 나머지 3개도 동일 패턴.
  대상: `LocationSimulationScheduler`(위치 tick, 3초) · `ConnectionLossScheduler`(연결끊김, 10초) ·
  `ApproachNoShowScheduler`(근접·미승차, 15초) · `SosEscalationScheduler`(SOS 에스컬레이션, 30초).
- **왜 시급한가.** `SosEscalationScheduler` 는 **안전 기능**. 조용히 멈추면 3분 미확인 SOS 가 에스컬레이션되지 않으며 **관측 수단이 전무**.
- **범위.** 스케줄러별 **마지막 성공 시각·연속 실패 횟수**를 기록하고, 임계 초과 시 actuator health 를 `DOWN` 으로 내리는 커스텀 `HealthIndicator`.
- **완료 조건.** 스케줄러 하나를 인위적으로 실패시켰을 때 health 응답에 해당 스케줄러가 식별 가능한 형태로 노출.

#### MON-14 · Redis 장애 반경 축소 · **MON-1 리뷰에서 파생**
- **증상.** `spring.data.redis.timeout` 이 **local·prod·demo 어느 프로파일에도 미설정** — Lettuce 기본 명령 타임아웃 60초가 적용된다.
  Redis 가 죽는 경우(즉시 연결 거부)가 아니라 **응답만 지연되는 경우**, 요청 스레드가 최대 60초 점유된다.
  관제 화면이 3초 주기로 폴링하고 기사 앱이 5초 주기로 보고하므로 스레드 누적 속도가 빠르다.
- **MON-1 과의 관계.** 이 설정 부재는 MON-1 이전부터 존재했고 학생 좌표(`RedisLocationRepository`)가 이미 같은 조건이었다.
  **MON-1 이 만든 결함이 부재.** 다만 버스 좌표까지 Redis 로 옮기면서 **위치 실시간 경로 전체가 Redis 단일 장애점에 묶여 반경이 확대**됐다.
- **현재 거동(리뷰 실측).** Redis 예외가 그대로 전파돼 `GlobalExceptionHandler.handleUnexpected`(`@ExceptionHandler(Exception.class)`)가 500 응답.
  크래시·무한대기는 부재. 관제 조회는 부분 결과 없이 요청 전체가 실패.
- **⚠ 2026-08-21 실측 — 예상보다 결과가 무겁다.** Redis 를 정지시키고 관측한 결과,
  **`/actuator/prometheus` 스크레이프 자체가 타임아웃**되어 Prometheus 가 backend target 을 `down` 으로 표시하고
  **모든 지표가 조회 불가 상태**가 됐다(`context deadline exceeded`). Redis 대기로 Tomcat 스레드가 소진돼
  지표 엔드포인트를 서빙할 스레드가 남지 않은 것이다. Redis 복구 후 자동 회복(약 1~2분).
  → **관측이 가장 필요한 순간에 대시보드가 통째로 비는 형태다.** MON-14 는 견고성 항목이 아니라
    **관측의 전제 조건**으로 격상해야 한다.
- **⚠ MON-1 이 반경을 넓혔다(실측).** 같은 실험에서 `location-simulation` 스케줄러의 경과 게이지도 함께 증가했다.
  버스 좌표가 Redis 로 옮겨지면서(MON-1) 이 스케줄러도 Redis 에 의존하게 된 결과다.
- **범위.** (a) `spring.data.redis.timeout` 명시, (b) 조회 경로에서 Redis 실패 시 500 대신 축소 응답을 줄지 판단.
  **(b) 는 응답 스키마·프론트 처리와 얽히므로 별도 결정 필요.**
- **판단 필요.** 타임아웃 값. 학생·버스 양쪽에 함께 적용되므로 위치 경로 전체를 보고 정해야 한다.

#### MON-15 · 본문 파싱 실패가 500 으로 응답 · **MON-2 E2E 에서 발견**
- **증상.** 요청 본문의 **타입 불일치·잘못된 enum 값**이 400 이 아니라 **500** 으로 응답된다.
  `GlobalExceptionHandler` 에 `HttpMessageNotReadableException` 핸들러가 부재해 catch-all
  `@ExceptionHandler(Exception.class)`(`:48`)로 떨어진다.
- **실측(2026-08-21, 실 서버).**

  | 요청 본문 | 응답 | 처리 경로 |
  |---|---|---|
  | `{"busId":1,"lat":"abc","lng":127.0}` | **500** | 파싱 실패 → catch-all |
  | `{"busId":1,"lat":37.5,"lng":127.0,"origin":"BOGUS"}` | **500** | 동일 |
  | `{"busId":1,"lat":37.5}` (lng 누락) | 400 | `@NotNull` → `MethodArgumentNotValidException`(정상) |

- **MON-2 와의 관계.** **MON-2 가 만든 결함이 부재** — `lat:"abc"` 로도 재현되는 전역 갭이며 모든 엔드포인트가 대상이다.
  다만 MON-2 가 **5초 주기 호출 경로에 새 트리거(enum 파싱)를 추가**해 도달 가능성이 올라갔다.
- **모니터링 관점의 무게.** `handleUnexpected` 가 발생마다 **ERROR 레벨로 스택트레이스를 남긴다.**
  클라이언트가 잘못된 본문을 5초마다 보내면 ERROR 로그가 계속 쌓여, **MON-13 이 붙일 "로그 내 ERROR 발생률" 알람이 클라이언트 입력 오류에 반응**하게 된다.
  즉 이 항목을 두면 2차 알람의 신호가 오염된다.
- **범위.** `@ExceptionHandler(HttpMessageNotReadableException.class)` → 400 매핑.
  ⚠ **전 엔드포인트의 응답 코드가 바뀌는 전역 변경**이라 MON-2 에 묻어서 처리하지 않는다. 단독 판단 대상.
- **판단 필요.** 응답 메시지에 파싱 실패 상세를 얼마나 노출할지 — 필드명까지 줄지, 일반 문구로 막을지.

#### MON-9 · Kafka 소비 실패 관측
- **증상.** 컨슈머 예외가 삼켜져 **로그에만 남고 앱은 생존** — 이 저장소에서 **실제로 발생한 선례** 존재.
- **근거.** `PROJECT_MASTER_PLAN.md` §12.1 함정 3 — CHECK 제약 위반으로 알림 저장이 막혔으나 *"Kafka 컨슈머가 예외를 삼키고 로그만 남김, 앱 자체는 안 죽음"*.
- **범위.** 컨슈머 실패 건수 계측 + 소비 지연(lag) 관측. 재처리·DLQ 도입 여부는 별도 판단.

#### MON-10 · actuator 노출 범위 확장
- **범위.** `health` 외 `metrics`·`info` 추가 노출, `show-details` 를 인증 사용자 한정으로 완화.
- **⚠ 지킬 것.** `application.yml:91~92` 의 판단 유지 — **상세를 무인증으로 열면 DB URL·Redis 호스트가 노출**.
  nginx 의 `/actuator` 404 차단도 **유지**하고, 수집은 컨테이너 내부 또는 별도 경로로 처리.

#### MON-11 · 메트릭 수집
- **현재.** `micrometer-registry-*` 의존성 부재 → 지표 저장소 전무.
- **범위.** JVM·HTTP·DataSource 기본 지표 + 도메인 지표(버스 위치 보고 수신율·STOMP 세션 수·알림 발송 수).
- **판단 필요.** 전송 대상 — CloudWatch(기존 인프라 재사용) / Prometheus(EC2 1대에 추가 컨테이너, 메모리 여유 확인 필요).

#### MON-12 · 구조화 로그 + 요청 상관 id
- **현재.** CloudWatch Logs 로 6개 서비스 로그가 수집되나 **평문**이라 검색·집계 불리. 요청 단위 추적 수단 부재.
- **범위.** JSON 인코더 + MDC 상관 id(요청·STOMP 세션·Kafka 메시지 관통).

#### MON-13 · CloudWatch 알람
- **현재.** `docs/DEPLOYMENT.md:591` 명시대로 **알람 전무 · 장애 인지는 수동**.
- **범위.** EC2 CPU·메모리·디스크, 컨테이너 재시작, 백엔드 health `DOWN`, 로그 내 `ERROR` 발생률에 알람 부착.
- **선행.** MON-8(health 신뢰성) · MON-11(지표) 완료 후. 알람 대상이 먼저 존재해야 성립.

## 5. ⚠ 이 라운드에서 지킬 것

- **인스턴스 증설 금지.** MON-1 로 `docker-compose.prod.yml:114` 의 제약 사유 (2) 가 해소돼도 **(1) `@Scheduled` 중복 · (3) STOMP 세션 로컬 보관은 잔존**.
- **actuator 상세를 무인증으로 열지 않는다.** `application.yml:91~92` 의 판단(DB URL·Redis 호스트 노출)은 유효.
- **nginx 의 `/actuator` 404 차단을 풀지 않는다.** 수집은 내부 경로로.
- **MON-6 은 폴백을 지운 채 전환하지 않는다.** STOMP 끊김 시 관제가 정지하면 폴링보다 나쁨.
- **프론트 계약 변경 2건(MON-3·MON-4)은 프론트 대응 없이 배포 금지.**
- **`docker compose down` 시 `-v` 미부착.**
- **완료 판정은 실행 결과로만.** 각 항목의 완료 조건 재현 + `./gradlew test` 통과가 근거.
