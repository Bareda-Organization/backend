## 3. 작업 항목

### T1 · 기록 신뢰성

#### BG-1 · 승하차 순서·중복 서버 검증
- **증상.** 승차 기록 없는 하차 요청에 서버가 200 응답. 동일 학생·동일 세션 중복 승차도 통과.
- **근거.** `rideevent/command/RideEventCommandService.java:52~78` — 버스 존재·담당 선탑자·학생 존재·학원 일치만 확인, 직전 상태 미조회.
- **범위.** `RideEventCommandService.record()` 에 직전 이벤트 조회 + 전이 규칙 추가.
  `BOARD → ALIGHT|HANDOVER` 만 허용, 선행 `BOARD` 부재 시 `ErrorCode.CONFLICT`.
- **판단 필요.** 비교 기준을 **당일**로 할지 **운행 세션 단위**로 할지 — 세션 단위가 정확하나 `RideEvent` 에 `sessionId` 컬럼이 부재해 마이그레이션 동반.
- **완료 조건.** 선행 BOARD 없이 ALIGHT 요청 → 409 / 중복 BOARD → 409 / 정상 순서 → 200 을 단위 테스트로 고정.

#### BG-2 · 위치 출처(origin) 실제 값 기록
- **증상.** 기사 앱이 Mock 좌표를 보내도 서버가 전부 `GPS` 로 저장. 관제 화면의 "단말/시뮬레이터" 표기가 사실과 불일치.
- **근거.** `location/command/BusLocationCommandService.java:48` · `location/command/LocationCommandService.java:57` 이 `LocationOrigin.GPS` 하드코딩.
  enum `location/dto/LocationOrigin.java` 는 이미 존재하나 요청 DTO 가 미수신.
- **범위.** 보고 요청 DTO 에 `origin` 필드 추가(미지정 시 기본 `GPS`), 커맨드 서비스가 그대로 전달.
- **완료 조건.** `MOCK` 으로 보고한 좌표가 조회 응답에 `MOCK` 으로 반환.

#### BG-3 · 응답 시각의 타임존 포함 형식 전환
- **증상.** 서버가 `LocalDateTime` 을 그대로 직렬화해 9시간 편차 발생. 클라이언트가 절대 시각 산출 불가.
- **근거.** 응답 DTO 8종 — `sos/dto/SosEventResponse.java`(4곳) · `rideevent/dto/RideEventResponse.java`(3) ·
  `drivesession/dto/DriveSessionResponse.java`(3) · `schedule/dto/*`(각 2) · `routing/dto/RoutePlanResponse.java`(2) ·
  `notification/dto/NotificationResponse.java`(2) · `attendance/dto/AttendanceExceptionResponse.java`(2).
- **범위.** 응답 경계에서 `OffsetDateTime`(또는 `Instant`)으로 변환. **엔티티 컬럼 타입 변경 여부는 별도 판단** — 응답만 바꾸는 쪽이 마이그레이션 부담 부재.
- **⚠ 프론트 동시 변경.** 파싱 형식이 바뀌므로 단독 배포 금지.
- **완료 조건.** 전 응답의 시각 필드가 오프셋 포함 문자열로 반환.

### T2 · 승인 워크플로 완결

#### BG-4 · 시간 변경 승인의 실제 반영
- **증상.** 승인 API 가 200 을 주지만 운행 스케줄·명단에 미반영. 상태 필드만 전이.
- **근거.** `schedule/command/ScheduleCommandService.java:61` 이 `request.approve(admin.userId())` 만 호출.
  `routing` 의 replan 도 시간창 미반영이라 정차 순서가 동일하게 재생산됨(`PROJECT_MASTER_PLAN.md` §12.1 "알려진 MVP 한계").
- **범위 선택 2안.**
  - **(a) 최소안** — 승인 결과를 명단 조회(`AttendanceQueryService.getActiveRoster` 계열)가 읽도록 연결, 노선 재계산은 현행 유지.
  - **(b) 완전안** — `BG-19`(시간창 제약) 선행 필요. MVP 범위 초과.
- **권장.** (a). (b) 는 `BG-19` 와 함께 T6 로 이월.
- **완료 조건.** 승인된 시간 변경이 해당 날짜 명단·계획 조회에 반영됨을 E2E 로 확인.

#### BG-5 · 결석 반려 알림
- **증상.** 반려 시 학부모에게 통지 부재. 신청자가 결과를 확인할 수단 부재.
- **근거.** `attendance/event/` 에 `AttendanceApprovedEvent` 만 존재. `AttendanceCommandService:63` `reject()` 는 이벤트 미발행.
  대조군 — `schedule` 은 승인·반려 **양쪽** 다 `ScheduleResultEvent` 발행(`schedule/event/ScheduleResultEvent.java`).
- **범위.** `schedule` 방식을 이식 — `status` 를 담은 결과 이벤트 1종으로 통합하고 `DomainEventNotificationConsumer` 에 리스너 추가.
- **완료 조건.** 반려 후 `notification_log` 에 해당 행 저장 + 학부모 개인 큐 도달.

### T3 · 운영 조작 가능성

#### BG-6 · 배정 해제 수단
- **증상.** 버스에서 기사·선탑자·노선을, 학생에서 배정 버스를 **떼어낼 방법 부재**. `null` 전송은 "변경 없음"으로 해석.
- **근거.** `bus/command/BusCommandService.java:83~93` 이 `if (req.xxxId() != null)` 구조. 학생 `/assignment` 도 동일.
- **범위.** 명시적 해제 표현 도입. 요청 DTO 를 `Optional`·래퍼 객체·별도 `unassign` 필드 중 하나로 변경.
  **`null` 을 해제로 재해석하지 않음** — 부분 수정(PATCH)의 "미전송" 과 구분 불가해짐.
- **완료 조건.** 기사 해제 후 `GET /api/buses/{id}` 의 기사 필드가 null, 해당 기사가 다른 버스에 재배정 가능.

#### BG-7 · 진행 중 운행 세션 전용 조회
- **증상.** 기사·관리자 모두 **전체 운행 이력을 수신해 앱이 진행 중인 건을 선별**. 이력 누적에 비례해 응답 증가.
- **근거.** `drivesession/controller/DriveSessionController.java:91~104` 의 주석이 자체 명시 — *"'진행 중 세션'만 주는 전용 API 가 없어 전체 이력을 받아 앱이 고른다"*.
- **범위.** `GET /api/drive-sessions/bus/{busId}` 에 `status` 쿼리 파라미터 추가, 또는 `/active` 엔드포인트 신설.
- **완료 조건.** 진행 중 세션만 반환하는 호출 경로 확보 + 프론트가 전체 이력 수신을 중단.

### T4 · 인증·검증

#### BG-8 · 입력 검증 보강
- **증상 2건.**
  1. 비밀번호 길이·복잡도 제약이 **회원가입·회원생성에 부재** — 1글자 통과.
  2. 좌표에 위경도 범위 검증 **전무**.
- **근거.** `auth/dto/SignupRequest.java:16` · `user/dto/CreateMemberRequest.java:17` 이 `@NotBlank` 뿐.
  `user/dto/ResetPasswordRequest.java:14` 만 `@Size(min = 8)` 보유. `@DecimalMin`·`@DecimalMax` 는 전 소스 **0건**.
- **범위.** 비밀번호 제약을 `ResetPasswordRequest` 기준으로 통일. 좌표 DTO 에 위도 −90~90 · 경도 −180~180 범위 애너테이션 부착.
- **완료 조건.** 1글자 비밀번호 400 / 범위 밖 좌표 400.

#### BG-9 · 정류장 목록의 테넌트 격리
- **증상.** 인증된 임의 사용자가 **타 학원 정류장 이름·좌표 조회 가능**.
- **근거.** `route/controller/RouteController.java:61` `stops()` 가 `@AuthenticationPrincipal` 을 미수신.
  주석에 *"정류장은 개인정보가 아니다"* 라는 의도적 판단이 기재됨.
- **판단 필요.** 위 판단의 유지 여부. 정류장 좌표는 학생 승하차 지점과 근접하므로 **재검토 대상**.
- **범위.** 유지 시 → 이 항목 폐기 + 문서에 근거 명시. 변경 시 → `TenantGuard` 적용.

#### BG-10 · 서버 측 로그아웃·토큰 무효화
- **증상.** 유출된 토큰을 만료 전까지 차단 불가. 클라이언트는 로컬 저장소만 삭제.
- **근거.** `logout`·`revoke`·`blacklist` 문자열 전 소스 **0건**.
- **범위.** refresh 토큰 무효화 목록(Redis) + `POST /api/auth/logout`. access 토큰은 짧은 만료로 흡수.
- **완료 조건.** 로그아웃 후 동일 refresh 토큰의 재발급 요청 401.

### T5 · 규모·성능

- **완료 조건.** 목록 6종에 `page`·`size` 적용 + 관리자 승하차 조회에 `busId` 추가.

- **참고 해법.** `bus/query/BusQueryService.java:53` 이 이미 `findByAssignedBusIdInAndActiveTrue` 로 배치 조회 적용 — 동일 패턴 이식.

## 5. ⚠ 이 라운드에서 지킬 것

- **스키마 변경은 새 마이그레이션 파일로 추가.** `V1__init_schema.sql` 직접 수정 금지 — 2026-08-02 라운드의 예외 지침은 그 라운드 한정.
  대상은 `backend/src/main/resources/db/migration/V{n}__설명.sql`.
- **`docker compose down` 시 `-v` 미부착.** named volume 삭제 위험.
- **프론트 계약 변경 3건(BG-3·BG-7·BG-11)은 프론트 대응 없이 배포 금지.**
- **T6 항목에 착수 금지.** 범위 확장은 사용자 확정 후.
- **`BG-9` 는 코드 수정 전 결정 필요.** 현행 유지도 유효한 선택이며, 그 경우 근거를 문서에 명시하고 항목 폐기.
- **완료 판정은 실행 결과로만.** `./gradlew test` 통과 + 해당 항목의 완료 조건 재현이 근거. 코드 작성 자체는 완료 근거로 불충분.
