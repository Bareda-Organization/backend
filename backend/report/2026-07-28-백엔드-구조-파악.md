## 2. 런타임 아키텍처 — 요청이 흐르는 길

### 2.1 동기 REST 경로

```
HTTP 요청
  → CorsFilter (/api/** 만, app.cors.allowed-origins 화이트리스트)
  → JwtAuthenticationFilter        ← Authorization: Bearer 파싱 → SecurityContext에 AuthUser 주입
  → SecurityFilterChain 인가        ← /api/auth/**·/actuator/health·/ws/**·swagger 만 permitAll, 나머지 authenticated
  → @PreAuthorize (메서드 단위 역할 검사)
  → XxxController                   ← 요청 DTO 검증(@Valid)
  → XxxCommandService / XxxQueryService
        ├ TenantGuard.resolveTenantId(admin, requested)   ← 학원 격리 검증
        └ XxxRepository (Spring Data JPA)
  → ApiResponse<T> 로 감싸 응답
  (예외 발생 시 GlobalExceptionHandler → BusinessException/ErrorCode 매핑)
```

핵심 클래스 위치:

| 역할 | 파일 |
|---|---|
| 보안 체인 | `global/security/SecurityConfig.java` |
| JWT 발급·검증 | `global/security/JwtTokenProvider.java` (HMAC-SHA, access 15분 / refresh 14일) |
| 인증 필터 | `global/security/JwtAuthenticationFilter.java` |
| 테넌트 격리 | `global/tenant/TenantGuard.java` |
| 공통 에러 | `global/error/ErrorCode.java`, `GlobalExceptionHandler.java` |
| 감사 필드 | `global/common/BaseTimeEntity.java` (created_at/updated_at), `JpaAuditingConfig` |

`TenantGuard.resolveTenantId(admin, requested)`의 규칙이 이 시스템 권한 모델의 핵심이다.
- 플랫폼 관리자 → 어느 학원이든 가능하나 `tenantId`를 **반드시 명시**해야 한다(미지정 시 400).
- 학원 관리자 → 미지정이면 본인 소속 학원으로 자동 해석, 지정하면 소속 여부를 검증하고 아니면 403.

> **흔한 오해**: "`@PreAuthorize("hasRole('ACADEMY_ADMIN')")`가 붙었으니 권한 처리는 끝났다"고 생각하기 쉽다. 아니다. 역할 애너테이션은 "관리자인가"만 본다. **"어느 학원 관리자인가"는 서비스 계층의 `TenantGuard`가 봐야만** 걸러진다. 이 두 겹 중 하나라도 빠지면 다른 학원 데이터가 새어 나간다 — 실제로 이 프로젝트에서 가장 주의 깊게 봐야 하는 지점이다(§6 보안 감사 참조).

### 2.2 비동기 이벤트 경로 (Kafka)

```
CommandService (트랜잭션 안)
  → ApplicationEventPublisher.publishEvent(DomainEvent)
  → TransactionalDomainEventRelay  @TransactionalEventListener(AFTER_COMMIT)
  → DomainEventPublisher → KafkaEventPublisher.send(topic, key, event)
  → Kafka
  → @KafkaListener 소비자들
```

**AFTER_COMMIT 릴레이가 핵심 설계**다. 커밋 전에 Kafka로 쏘면 롤백된 사건의 알림이 나가는데, 이 릴레이가 그걸 막는다(`global/event/TransactionalDomainEventRelay.java`).

| rideevent | `HandoverCompletedEvent` | `handover-completed` | notification |

### 2.3 실시간 push 경로 (STOMP)

```
Kafka 소비자 (LocationPushConsumer / WebSocketNotificationSender)
  → PushTargetResolver 가 "이 사건을 누가 봐야 하나" 계산
  → 개인: convertAndSendToUser(userId, "/queue/location" | "/queue/notifications")
     테넌트: convertAndSend("/topic/tenant/{tenantId}/location" | "/notifications")
```

- 엔드포인트: `/ws/location` (`WebSocketConfig`), 브로커 프리픽스 `/topic`·`/queue`, 앱 프리픽스 `/app`, 사용자 프리픽스 `/user`.
- WebSocket 핸드셰이크는 `SecurityConfig`에서 `permitAll` — 대신 **STOMP CONNECT 프레임에서 `StompAuthChannelInterceptor`가 JWT를 검증**한다. 네이티브 WS 클라이언트가 임의 헤더를 못 붙이는 경우가 많아 내린 결정이며 주석에 근거가 남아 있다.
- SUBSCRIBE 인가는 `/topic/tenant/{id}/**` 패턴에만 적용해 소속 학원인지 확인한다(`TENANT_TOPIC_PATTERN`). 개인 큐는 Spring이 세션별 목적지로 재작성하므로 추가 검사가 불필요하다는 판단.

### 3.2 관찰

1. **`tenant_id`가 12개 테이블에 물리 컬럼으로 존재**한다(`app_user`·`stop`·`route_plan_stop`·`student_guardian` 제외). 격리는 DB 제약이 아니라 **애플리케이션 계층(`TenantGuard` + 리포지토리 쿼리의 `tenantId` 조건)** 에서만 강제된다. 즉 `findById`만 부르고 tenantId를 안 보는 코드가 하나라도 있으면 그게 곧 구멍이다.
2. **인덱스가 단 2개**뿐이다 — `idx_ride_tenant_student(tenant_id, student_id, occurred_at)`, `idx_sos_status_occurred(status, occurred_at)`. `notification_log(tenant_id, student_id)`, `drive_session(bus_id, service_date)`, `route_plan(bus_id, service_date, status)` 등 실제 조회 패턴을 받는 인덱스가 없다. 데모 데이터량에서는 문제가 드러나지 않는다.
3. **enum이 varchar + CHECK 제약**으로 구현돼 있다(Hibernate가 생성한 DDL을 그대로 채택). enum 상수를 추가하면 반드시 새 마이그레이션으로 `DROP/ADD CONSTRAINT` 해야 하며, V3~V5가 정확히 그 사례다. 이 규율이 Flyway 전환(2026-07-20)으로 구조적으로 강제된 상태다.
4. `app_user`에 `tenant_id`가 없고 `user_tenant_role`로 N:M을 푼 것은 **한 사람이 여러 학원에 다른 역할로 소속**될 수 있게 한 의도적 설계다. 대신 "이 사용자의 소속 학원"을 알려면 항상 조인이 필요하다.
5. 소프트 삭제 컬럼(`deleted_at` 등)이 전무하다. 학생 전학·기사 퇴사 같은 이력 보존 요구가 생기면 스키마 변경이 필요하다.

## 5. 계층 패턴과 spec/impl 분리 실태

`reference.md` 규칙은 "구현이 바뀔 가능성이 있는가"로만 인터페이스 분리를 판단한다. 실제 적용 현황:

| 구분 | 적용 위치 | 판단 |
|---|---|---|
| repository `spec/` 인터페이스만 (impl 없음) | 15개 모듈 전부 | Spring Data JPA가 구현을 만들어주므로 정상 |
| repository `spec/` + `impl/` | `location` 만 (`InMemory` 2종, `Redis` 1종) | Redis↔InMemory 교체가 실재 → 규칙에 부합 |
| service `spec/` + `impl/` | `notification` 만 | 나머지 14개는 구체 클래스 단독 |
| 포트/어댑터 | `routing/engine/{spec,impl}`, `routing/infrastructure/{spec,impl}` | `RouteEngine`, `MapRouteClient`(OSRM↔Naver) |
| 평면 배치 인터페이스 | `location/source/` (`LocationSource` + 구현 4종이 같은 패키지) | spec/impl 하위 패키지 미사용 |

핵심 교체 포인트 3곳:
- `MapRouteClient` — `OsrmMapRouteClient` ↔ `NaverMapRouteClient`, `routing.provider` 설정으로 전환(현재 기본값 `naver`).
- `RouteEngine` — `HeuristicRouteEngine`(sweep 방위각 정렬 + nearest-neighbor + 2-opt) + `BusAssigner`/`SweepAssigner`.
- `NotificationSender` — `LogNotificationSender`(로그 스텁) / `WebSocketNotificationSender`(실제 STOMP push).

> **주의**: `NotificationSender` 구현 중 실제 외부 발송(FCM/APNs/SMS)은 **하나도 없다**. 알림은 DB `notification_log` 저장 + WebSocket push + 로그 출력까지다. "알림 기능 완료"를 앱 푸시 완료로 오해하지 않도록 구분이 필요하다.

### 6.1 High

#### H1. 회원가입 API로 누구나 PLATFORM_ADMIN 계정을 만들 수 있다 (권한 상승)

- 위치: `auth/dto/SignupRequest.java:19`, `auth/command/AuthCommandService.java:50-62`, 진입점 `global/security/SecurityConfig.java:60`
- 근거:

  ```java
  // SignupRequest.java:19 — role 을 클라이언트가 그대로 지정한다
  @NotNull @Schema(example = "PARENT") Role role

  // AuthCommandService.java:50-53 — 화이트리스트도 승인 절차도 없다
  ```

- 영향: **인증 없이 POST 한 번으로 최고 권한 계정이 생성된다.** `role: "PLATFORM_ADMIN"` 이면 전 학원 데이터에 접근하는 전역 관리자가 되고, `role: "ACADEMY_ADMIN"` + 임의 `tenantId` 면 남의 학원 관리자가 된다. 이 시스템이 다루는 데이터가 **미성년자의 실시간 위치와 SOS 신고**라는 점에서 §6의 다른 어떤 항목보다 우선한다. `@NotNull` 검증은 "값이 있는가"만 보지 "이 값을 요구할 자격이 있는가"는 보지 않는다 — 이 구분이 핵심이다.
- 도달 가능성: 완전히 열려 있다. Swagger(M1)가 `SignupRequest.role` 필드를 그대로 문서화하고 있어 정찰조차 필요 없다.
- 권고: 세 가지 중 하나. ①`signup` 은 `PARENT`/`STUDENT`/`DRIVER` 만 허용하고 관리자류는 서버에서 거부(가장 작은 변경), ②관리자 계정은 `MemberController`(관리자 인증 필요)로만 생성, ③초대 토큰 기반 가입. **MVP·데모 단계라도 이건 그대로 두면 안 된다** — 데모 URL이 외부에 노출되는 순간 바로 악용 가능한 형태다.

> 이 항목은 첫 조사에서 놓쳤다가 감사 과정에서 잡힌 건이다. `auth` 모듈의 인증 로직(`AuthQueryService` 의 login/refresh)만 보고 **가입 경로(`AuthCommandService`)를 확인하지 않은 것이 원인**이다. "인증(authentication)"만 보고 "계정이 어떻게 생기는가"를 안 본 셈이다.

### 6.2 Medium

#### M1. Swagger/OpenAPI가 프로파일과 무관하게 무인증 공개

#### M2. JWT 서명키 기본값이 소스에 박혀 있고, 누락돼도 조용히 기동한다

- 위치: `src/main/resources/application.yml` — `jwt.secret: ${JWT_SECRET:local-dev-secret-change-me-please-32bytes-minimum-length}`
- 영향: prod 배포 시 `JWT_SECRET` 환경변수를 빠뜨리면 앱이 **에러 없이** 저 공개된 문자열로 토큰에 서명한다. 저장소를 본 사람은 누구나 임의 사용자·임의 역할의 access 토큰을 위조할 수 있다. 실패가 조용하다는 점이 핵심 위험이다.
- 권고: prod 프로파일에서는 기본값을 제거해(`${JWT_SECRET}`) 미설정 시 기동 실패하게 만든다. "안 되면 안 뜨는 것"이 "되는 척하는 것"보다 안전하다.

#### M3. refresh 토큰을 무효화할 수단이 없다

- 위치: `auth/query/AuthQueryService.java:53-67`, `auth/controller/AuthController.java`(엔드포인트 3개 = signup/login/refresh)
- 근거: `refresh()` 는 토큰 파싱 → 타입 확인 → `userRepository.findById` → 재발급이 전부다. 서버 측 저장소·블랙리스트·jti 검증이 없고, **로그아웃 API 자체가 없다**.
- 영향: 유출된 refresh 토큰은 유효기간 14일(`refresh-token-validity-seconds: 1209600`) 동안 무제한으로 access 토큰을 찍어낼 수 있고 회수 수단이 없다. 사용자 비활성화·탈퇴 개념도 스키마에 없어(`app_user` 에 상태 컬럼 없음) 계정 차단으로도 막을 수 없다.
- 참고(완화 요인): `refresh()` 가 재발급마다 `encodeMemberships()` 로 DB에서 역할을 다시 읽는다. 따라서 **역할 회수는 다음 refresh 시점에 반영**된다. 역할이 토큰에 영구 고정되는 최악의 형태는 아니다.
- 권고: Redis 가 이미 인프라에 있으므로 `jti` 화이트리스트/블랙리스트를 얹는 비용이 낮다.

#### M4. 테넌트 검증 관용구가 두 갈래로 갈라져 있다

- 위치:
  - A안 `TenantGuard.resolveTenantId(...)` — `bus`·`student`·`route`·`routing`·`user`·`location`·`notification`·`drivesession`·`rideevent` (18개 파일)
  - B안 수기 검사 — `sos/command/SosCommandService.java:87`, `attendance/command/AttendanceCommandService.java:80`, `schedule/command/ScheduleCommandService.java:85`
- 근거(B안, 세 곳이 동일):

  ```java
      throw new BusinessException(ErrorCode.FORBIDDEN);
  ```

- 영향: 현재 두 관용구의 판정 결과는 같아서 **지금 뚫린 구멍은 아니다**. 문제는 미래다 — 테넌트 정책이 바뀌어 `TenantGuard` 를 고치면 이 세 곳은 조용히 옛 규칙으로 남는다. 격리 로직이 한 곳에 모여 있지 않다는 것 자체가 리스크다.

#### M5. DB 레벨 참조무결성이 절반만 있다

- 위치: `db/migration/V1__init_schema.sql`
- 근거: FK 제약이 걸린 테이블은 `bus`·`route`·`route_plan_stop`·`stop`·`student`·`student_guardian`·`user_tenant_role` 7개뿐이다. **`ride_event`·`sos_event`·`attendance_exception`·`schedule_change_request`·`drive_session`·`notification_log`·`route_plan` 7개 테이블에는 FK가 하나도 없다** — `student_id`, `tenant_id`, `bus_id` 가 전부 맨 `bigint` 다.
- 이유(추정 아님, 코드로 확인): 이 7개는 엔티티가 연관관계 매핑(`@ManyToOne`) 대신 **ID 값만 필드로 들고 있다**. Hibernate가 DDL을 생성했으므로 매핑이 없으면 FK도 안 생긴다.
- 영향: 애플리케이션 계층 버그로 잘못된 `tenant_id` 가 들어가도 DB가 잡아주지 않는다. §3.2에 적었듯 격리가 애플리케이션 단일 방어선인데, 그 방어선 뒤에 안전망이 없는 구조다.
- 권고: 새 마이그레이션으로 FK를 추가한다. 다만 기존 데이터 정합성 확인이 선행돼야 하므로 즉시 조치보다는 계획 항목이다.

#### M6. 사람(User)을 참조할 때만 학원 소속을 검증하지 않는다

- 위치: `bus/command/BusCommandService.java:98-101`(`loadUser`, 호출부 `createBus:52`·`assign:70`), `student/command/StudentCommandService.java:163-166`(`loadUser`, 호출부 `addGuardian:132`)
- 근거: 같은 클래스 안에서 **사물은 검증하고 사람은 검증하지 않는다.**
  ```java

  private Route loadRouteInTenant(Long routeId, Long tenantId) {
      ...
      if (!route.getTenant().getId().equals(tenantId)) {
          throw new BusinessException(ErrorCode.INVALID_INPUT, "노선이 이 학원 소속이 아닙니다");
      }
  }

              .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND, "기사를 찾을 수 없습니다"));
  ```

  `StudentCommandService` 도 동일하다 — `loadBusInTenant`·`loadStopInTenant` 는 검증하는데 보호자를 얹는 `loadUser` 만 `findById` 뿐이다.
- 영향: 학원 관리자가 **타 학원 소속 사용자를 자기 학원 버스의 기사로, 또는 자기 학원 학생의 보호자로 지정**할 수 있다. 일단 지정되면 그 사람은 이후 소유권 검사(`bus.getDriver().getId().equals(...)`, `findByGuardianId(...)`)를 정상 통과하므로 **그 시점부터 합법적으로 남의 학원 학생 위치·승하차 기록을 조회한다.** §6.4에 적은 "IDOR 없음"은 *관계가 올바르게 맺어졌다는 전제*에서 성립하는데, 그 관계를 맺는 입구가 열려 있는 셈이다.
- 도달 가능성: 관리자 신뢰 경계 안이라 H1보다 낮다. 기사 배정은 대상이 어딘가에서 `DRIVER` 역할을 이미 가져야 실효가 있지만(기사 API는 `@PreAuthorize` 로 역할을 본다), **보호자 연결은 그런 제약도 없다** — 임의 사용자를 남의 자녀 보호자로 붙이면 곧바로 `/children` 조회가 열린다.
- 권고: `loadUser` 에 "이 userId 가 해당 tenant 에 (기사면 DRIVER 로) 소속돼 있는가"를 `UserTenantRoleRepository` 로 확인하는 조건을 추가한다. 이미 옆에 `loadRouteInTenant` 라는 정확한 본보기가 있다.

### 6.4 확인했으나 문제 없던 항목 (실측)

- **IDOR 없음.** `/children` 계열은 클라이언트가 보낸 `studentId` 를 믿지 않고, `studentGuardianRepository.findByGuardianId(parent.userId())` 로 **서버가 자녀 목록을 유도**한 뒤 그 ID로만 조회한다(`RideEventQueryService:57-68`, `LocationQueryService:53-59`, `NotificationQueryServiceImpl:31-42`). `/me` 계열도 `findByUserId(student.userId())` 로 본인만 잡는다. **단서**: 이 방어는 "보호자–학생 관계가 올바르게 맺어져 있다"는 전제 위에서만 성립한다. 관계를 맺는 입구(M6)는 검증이 없다.
- **기사 권한 검사 존재.** `/bus/{busId}` 계열은 전부 `bus.getDriver().getId().equals(driver.userId())` 를 확인한다(`LocationQueryService:65`, `RideEventQueryService:74`, `DriveSessionQueryService:46`). `getRoster` 는 한 발 더 나가 `session.getDriverId().equals(driver.userId())` 로 **본인이 시작한 운행**만 허용한다.
- **STOMP 인가가 실제로 걸려 있다.** `StompAuthChannelInterceptor` 가 CONNECT에서 JWT를 검증하고, SUBSCRIBE에서 `^/topic/tenant/(\d+)/.*` 패턴을 잡아 `isPlatformAdmin() || (hasRole(ACADEMY_ADMIN) && belongsToTenant(...))` 를 요구한다. 발행 목적지를 전수 조사한 결과 브로드캐스트 토픽은 `/topic/tenant/{id}/location` 과 `/topic/tenant/{id}/notifications` **두 개뿐**이고 나머지는 전부 `convertAndSendToUser` 개인 큐다. 즉 인가 대상이 빠짐없이 덮여 있다. `/topic/bus/{busId}` 같은 미보호 토픽은 존재하지 않는다.
- **클래스 레벨 `@PreAuthorize` 사용.** `StudentController:36`, `BusController:34` 는 클래스 전체에 `@PreAuthorize("hasAnyRole('ACADEMY_ADMIN', 'PLATFORM_ADMIN')")` 를 건다. 메서드별 애너테이션 개수만 세면 "누락"으로 보이지만 실제로는 전 엔드포인트가 덮여 있다.
- **사용자 열거(user enumeration) 불가.** 이메일 없음/비밀번호 불일치 모두 동일한 `ErrorCode.INVALID_CREDENTIALS` 로 응답한다(`AuthQueryService:46,48`).
- **예외 응답에서 내부 정보 누출 없음.** `GlobalExceptionHandler:48-53` 의 catch-all이 스택트레이스는 로그에만 남기고 클라이언트에는 고정 메시지만 준다. `AccessDeniedException` 을 catch-all보다 먼저 잡아 403이 500으로 뒤바뀌는 흔한 실수도 이미 막아뒀다.
- **비밀번호 해시**는 `BCryptPasswordEncoder`. 401(미인증)/403(권한부족) 구분도 `HttpStatusEntryPoint` 로 명시 처리.
- **입력 검증**: 컨트롤러 `@RequestBody` 에 `@Valid` 가 붙어 있고, 위반 시 첫 필드 에러만 반환한다.
- **CORS 기본값이 "닫힘"이다.** `${app.cors.allowed-origins:}` 가 미설정이면 허용 origin 목록이 빈 배열이 되어 전부 차단된다. 설정 누락이 "전면 허용"이 아니라 "전면 차단"으로 떨어지는 것은 좋은 기본값 선택이다 — M2(JWT 시크릿)가 정반대 방향인 것과 대비된다.
- **JWT 구조**: HS256 서명, access 15분 / refresh 14일 만료 분리, 토큰 타입 클레임(`isAccessToken`/`isRefreshToken`)으로 refresh 토큰을 access 자리에 쓰는 오용을 차단. 구조 자체는 양호하며 문제는 키 관리(M2)와 폐기 수단(M3)뿐이다.

### 7.3 위반·불일치

아래 `CH*` 2건은 "취향 차이"가 아니라 reference.md 에 문장으로 못박힌 규칙을 실제로 어긴 건이다. `C1~C7` 은 규칙 위반이라기보다 모듈 간 일관성 문제다.

#### CH1. [High] Command 가 다른 모듈의 Query 서비스를 직접 주입한다 — reference.md §7 위반

reference.md §7은 "**Command는 Query를 호출하지 않는다**"고 명시한다. CQRS-lite 구조에서 쓰기 경로와 읽기 경로를 갈라놓는 것이 이 규칙의 목적인데, 한 곳이 이를 가로지른다.

```java
// routing/command/RoutingCommandService.java
import src.backend.attendance.query.AttendanceQueryService;   // 19행
...
private final AttendanceQueryService attendanceQueryService;  // 60행
```

두 겹으로 규칙을 넘는다 — ①Command→Query 방향 위반(§7), ②모듈 경계를 넘어 다른 모듈의 내부 서비스를 직접 참조(§6의 모듈 간 결합 최소화). 다른 13개 모듈은 이런 참조가 0건이라, 이 한 곳만 예외다.

배차 계산에 출결 정보가 필요한 것 자체는 정당한 요구다. 규칙을 지키면서 같은 일을 하려면 ①`attendance` 가 제공하는 조회용 포트(인터페이스)를 `routing` 이 의존하거나, ②출결 스냅샷을 이벤트/DTO 로 받아 넘기는 형태가 된다. **다만 이 위반은 "지금 무언가 고장나 있다"는 뜻이 아니라 "attendance 의 조회 로직이 바뀌면 routing 이 같이 깨진다"는 결합 비용의 문제다** — 긴급도는 낮고 중요도는 높은 항목으로 읽는 게 정확하다.

#### CH2. [Medium] 이벤트 이름 3개가 과거형 규칙을 어긴다 — reference.md §14 위반

reference.md §14는 "**Event는 과거형으로 작성한다**"고 규정한다. 도메인 이벤트는 "이미 일어난 사실"을 알리는 것이므로 이름만 봐도 명령(Command)과 구분돼야 한다는 취지다.

| 파일 | 판정 |
|---|---|
| `drivesession/event/ApproachEvent.java` | ❌ 과거형 아님 → `BusApproachedEvent` 류 |
| `drivesession/event/NoShowEvent.java` | ❌ 과거형 아님 → `StudentNoShowedEvent` 류 |
| `schedule/event/ScheduleResultEvent.java` | ❌ 과거형 아님 → `ScheduleDecidedEvent` 류 |
| `attendance/event/AttendanceApprovedEvent.java` | ✅ |
| `rideevent/event/StudentBoardedEvent.java` | ✅ |
| `drivesession/event/HandoverCompletedEvent.java` | ✅ |
| 나머지 8개(`LocationUpdatedEvent`·`SosTriggeredEvent`·`RoutePlanPublishedEvent` 등) | ✅ |

`*/event/` 아래 18개 파일 중 인프라 3개(`DomainEvent`·`DomainEventPublisher`·`TransactionalDomainEventRelay`)를 뺀 **이벤트 클래스 15개 기준으로 12개가 규칙을 지키고 있고 3개만 벗어났다.** 이름만 바꾸는 작업이지만 Kafka 토픽명과 묶여 있을 수 있으므로, 토픽 상수까지 같이 확인한 뒤 한 번에 정리하는 편이 안전하다.

#### C1. [Medium] 엔티티 패키지 이름이 `entity` / `domain` 두 갈래

13개 모듈이 `entity/` 를 쓰는데 `notification` 만 `domain/NotificationLog.java`·`domain/NotificationType.java` 다. `routing` 은 `domain/`(LatLng·GeoMath 같은 값객체)과 `entity/`(RoutePlan·RoutePlanStop, JPA)를 **역할로 구분**해서 쓰므로 나름의 규칙이 있는데, `notification` 은 JPA 엔티티를 `domain` 에 넣어 그 구분을 깬다. → `notification/domain/` 을 `entity/` 로 옮기면 규칙이 "JPA 엔티티=entity, 순수 값객체=domain" 으로 깔끔하게 통일된다.

#### C2. [Medium] `notification` 만 서비스에 spec/impl 을 적용 — 규칙 기준 과잉 분리

`NotificationCommandService`/`NotificationQueryService` 는 인터페이스 + `...Impl` 구조인데, 하는 일은 다른 13개 모듈의 CommandService/QueryService와 성격이 같다(로그 저장, 조회). 구현이 교체될 근거가 코드상 없다 — 실제 교체 지점은 서비스가 아니라 `NotificationSender`(3구현)다. reference.md의 "구현이 바뀔 가능성이 있는가" 기준을 그대로 적용하면 **서비스 분리는 되돌리는 게 맞고, `infrastructure/{spec,impl}` 은 그대로 두는 게 맞다**.

#### C3. [Medium] 포트/어댑터 배치 방식이 세 가지

- `routing/engine/{spec,impl}` — 하위 패키지 분리
- `notification/infrastructure/{spec,impl}` — 하위 패키지 분리
- `location/source/` — **평면 배치**. `LocationSource`(포트)와 `MockLocationSource`·`PhoneGpsSource`·`DriverGpsSource`·`MockBusLocationSource`(구현 4종)가 같은 패키지에 섞여 있다.

셋 다 "구현 교체가 실재하는 포트"라는 점에서 성격이 같은데 배치만 다르다. Phase 8에서 Mock→실 GPS 를 갈아끼울 때 가장 자주 열게 될 패키지가 하필 평면 배치라, `location/source/{spec,impl}` 로 맞추는 것이 일관성·가독성 양쪽에 이득이다.

**추가 실측**: 프로젝트 전체에서 `infrastructure/` 디렉토리를 가진 곳은 `global`·`notification`·`routing` **3곳뿐이다**. reference.md §3·§13은 외부 연동을 `infrastructure/` 아래에 두라고 규정하는데, `location` 은 외부(단말 GPS) 연동 지점을 갖고 있으면서도 `infrastructure/` 패키지가 **아예 없고** `source/` 라는 모듈 고유 이름을 쓴다. 즉 C3은 "spec/impl 을 안 나눴다"보다 **"외부 연동을 어디에 두는가라는 상위 규칙 자체가 location 에서만 다르게 적용됐다"**가 더 정확한 진단이다. 정리한다면 `location/infrastructure/{spec,impl}` 로 옮기는 것이 규칙에 가장 충실하다 — 다만 Phase 8 작업과 정면으로 겹치는 패키지이므로, **Phase 8 착수 직전이 아니라 착수 시점에 같이 하는 편이 충돌이 적다**.

#### C4. [Low] `user/service/spec`, `user/service/impl` 이 빈 디렉토리로 남아 있다

`.java` 파일이 0개다. 리팩터링 중 파일만 옮기고 디렉토리를 지우지 않은 흔적으로 보인다. Git은 빈 디렉토리를 추적하지 않으므로 로컬 워킹트리에만 있는 잔재일 가능성이 높다.

#### C5. [Low] enum 배치 위치가 세 곳으로 흩어짐

`user/entity/Role.java`, `routing/domain/RoutePlanStatus.java`·`RouteDirection.java`, `notification/domain/NotificationType.java`, **`location/dto/LocationOrigin.java`**. 특히 마지막 것은 DB에 저장되는 도메인 개념인데 `dto` 에 있다. C1을 정리할 때 같이 규칙을 정해두면 좋다.

#### C6. [Low] `RouteResult` 가 포트 패키지(`routing/infrastructure/spec/`)에 있다

포트 인터페이스(`MapRouteClient`)의 반환 타입이라 물리적으로 가까운 건 이해되지만, 성격은 DTO다. 회색지대에 가깝다.

#### C7. [Low] `notification/NotificationThresholds.java` 가 모듈 루트에 평면 배치

하위 패키지 없이 모듈 루트에 놓인 유일한 클래스다.

#### 회색지대 2건 (위반으로 단정하지 않음)

- **`MemberController` 가 다른 모듈의 엔티티 enum 을 API 파라미터 타입으로 쓴다.** `user/controller/MemberController.java:21` 이 `src.backend.user.entity.Role` 을 import 해서 `:54` 의 `@RequestParam Role role` 로 받는다. "엔티티를 컨트롤러에 노출하지 않는다"는 규칙의 문자적 위반은 아니다(같은 모듈 내부이고, 노출되는 건 enum 값 문자열뿐이다). 다만 enum 배치 규칙(C5)을 정리할 때 이 지점이 같이 걸린다.
- **`global/push/PushTargetResolver.java` 가 표준 모듈 구조 밖에 있다.** `global/` 아래의 공용 유틸이라는 점에서 위치 자체는 납득되지만, `global` 하위 다른 패키지(`security`·`response`·`exception`·`infrastructure`)와 달리 `push` 는 도메인 성격이 섞여 있다. 알림 채널을 실제로 붙일 때(§10 권고) 이 클래스가 `notification` 쪽으로 갈지 `global` 에 남을지 자연히 결정된다 — 지금 손댈 필요는 없다.

- **Flyway ↔ 엔티티 정합성 테스트 없음**: `ddl-auto: validate`가 앱 기동 시에만 잡아준다.

검증은 대부분 **curl E2E 수동 검증**으로 대체돼 있다(마스터플랜 §12.1에 각 Phase별 검증 로그가 상세히 남아 있음). 데모 단계에선 합리적 선택이지만, 회귀 방지 자산으로는 남지 않는다.

> 참고: 마스터플랜에 `attendance`·`schedule`·`sos`·`drivesession`은 "전용 테스트 파일은 만들지 않음(선례를 따름)"이라고 명시적으로 기록돼 있다. 즉 커버리지 공백은 사고가 아니라 **의식적으로 내린 결정**이다.

## 9. 설정 · 인프라

- **스택**: Spring Boot 4.1.0 / Java 25 toolchain / Gradle. 웹 스타터는 신형 `spring-boot-starter-webmvc`.
- **의존성 특이점**: `spring-boot-starter-webclient`(webflux 아님 — Boot 4에서 분리됨), `spring-boot-starter-flyway` + `flyway-database-postgresql`, `springdoc-openapi-starter-webmvc-ui:3.0.3`(Jackson 3 라인), jjwt 0.12.6.

- **docker-compose**: postgres 16, redis 7, apache/kafka 3.9.0, backend. `frontend` 서비스는 `profiles: ["frontend"]`로 기본 실행에서 제외.

### 워킹트리 상태 (참고)

`frontend/` 디렉토리가 **삭제되어 스테이징된 상태**다(Next.js 데모 33개 파일). docker-compose의 frontend 서비스는 profile로 비활성화돼 있다. 즉 현재 저장소는 **백엔드 단독 프로젝트로 재편되는 과도기**에 있으며, 새 프론트엔드 작업을 준비 중인 것으로 읽힌다. `backend/docs/*.html`, `application.yml`, 계획 문서 3종도 미커밋 수정 상태다.

## 10. 종합 평가와 권고

### 잘 되어 있는 것

1. **이벤트 발행이 AFTER_COMMIT으로 통일**돼 있다. 롤백된 트랜잭션의 알림이 나갈 수 없는 구조다.
2. **`notification_log.dedup_key` UNIQUE 하나로 멱등성을 확보**했다. SOS 3분 에스컬레이션 폴링처럼 중복 발송 위험이 큰 로직도 별도 방어 코드 없이 안전하다.
3. **포트/어댑터가 실제로 값을 하는 곳에만 적용**됐다(위치 소스, 지도 API, 경로 엔진, 알림 발송). 단순 CRUD에는 불필요한 인터페이스를 만들지 않아 파일 수가 부풀지 않았다.
4. **역할별 조회 4갈래 패턴**이 6개 모듈에 동일하게 반복돼, 새 모듈을 붙일 때 따라 쓸 템플릿이 명확하다.
5. **결정과 함정이 문서에 축적**돼 있다(마스터플랜 §12에 Kafka consumer group 함정, `@Lob` → oid 함정, enum CHECK 제약 함정 등이 원인·해결까지 기록). 이 수준의 의사결정 로그는 흔치 않다.

### 다음 착수점에 대한 의견

마스터플랜은 "Phase 8(Mock→실 GPS)"을 유일한 잔여 과제로 잡고 있지만, **Phase 8은 코드가 아니라 법적 선행요건에 막혀 있다**(플래그는 이미 준비 완료). 그렇다면 그 사이에 무엇을 할 것인가에 대한 의견은 이렇다.

1. **#1(H1)은 다른 어떤 항목보다 먼저다.** 현재는 로컬 개발 환경이라 실질 피해가 없지만, 이 상태로 외부에 한 번이라도 노출되면 그 시점에 이미 늦는다. 수정 자체는 `AuthCommandService.signup` 에 역할 화이트리스트를 넣는 작은 작업이라, 비용 대비 효과가 압도적이다.
2. 그다음 실질적 가치가 큰 것은 **#5 Kafka 통합 테스트**다 — 이 시스템의 기능 대부분이 이벤트 파이프라인을 타는데, 그 파이프라인이 지금 회귀 안전망 없이 수동 검증에만 의존하고 있다.
3. **#9 컨벤션 정리는 서둘러 할 이유가 없다.** 동작에 영향이 없고, `location` 관련 항목은 Phase 8에서 어차피 그 패키지를 다시 열게 되므로 그때 같이 하는 편이 충돌이 적다.

### 이 보고서의 한계 (분명히 밝혀둠)

- **정적 분석만 수행했다.** 앱을 기동하거나 요청을 실제로 보내보지 않았다(로컬 인프라 기동은 사용자 확인이 필요한 사항이라 요청하지 않았다). 따라서 H1·M6 은 **코드상 도달 가능한 경로**로 확인한 것이지, 실제 HTTP 요청으로 재현한 것은 아니다. 배포 전이라면 이 두 건은 실제 요청으로 한 번 재현해보는 것을 권한다.
- **테스트를 실행하지 않았다.** §8의 테스트 현황은 파일·클래스 실측이며 통과 여부가 아니다.
- **첫 조사에서 H1 을 놓쳤다.** 인증 로직(`AuthQueryService` 의 login/refresh)만 보고 계정이 만들어지는 경로(`AuthCommandService.signup`)를 확인하지 않은 것이 원인이다. 감사 단계에서 잡아 §6.1에 반영했으나, "인증을 봤다"와 "계정 생성 경로를 봤다"는 다른 일이라는 점을 기록해둔다.
