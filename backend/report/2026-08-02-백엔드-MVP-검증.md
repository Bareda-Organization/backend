## 3. 발견 사항

### ✅ H-1 (High) — **수정 완료 (2026-08-02)** · I-9 위반: 퇴원 학생이 시뮬레이션·배차·배포 노선에 다시 들어간다

> **수정 결과** — `applyOverrides`·`commitOverrides` 두 곳에 `student.isActive()` 검사를 넣어 `ADD`·`MOVE` 대상이 비활성이면 `INVALID_INPUT`(400)으로 거부하고, `REMOVE` 는 그대로 허용한다(빼는 것은 언제나 안전하다).
> 회귀 테스트 3건 추가 — `compare_addOverrideOnInactiveStudent_throwsInvalidInput` · `compare_removeOverrideOnInactiveStudent_isAllowed` · `applySimulation_addOverrideOnInactiveStudent_throwsInvalidInputAndDoesNotAssignBus`. 전체 **193건 통과**.
> 런타임 재확인: ② simulate+ADD **400** · ③ apply+ADD **400** · ④ simulate+REMOVE **200** · ⑤ 활성 학생 ADD **200**(정상 기능 유지). DB 실측상 퇴원 학생이 든 새 노선은 생성되지 않았다.
> 부수 확인 — 퇴원 처리가 발행하는 재계획 이벤트로 만들어진 `version 2` 계획에서 그 학생이 정확히 빠졌다.
>
> 아래는 수정 전 원본 기록이다.

**위치**
- `routing/query/RoutePlanSimulationService.java:136-142` (`applyOverrides`)
- `routing/command/RoutingCommandService.java:258-272` (`commitOverrides`)

**원인** — 두 곳 모두 override 로 지목된 학생을 `studentRepository.findById` 로 직접 꺼내 **테넌트만 검사하고 `isActive()` 를 보지 않는다.** `computeCore` 가 `getActiveRoster`(활성 필터 적용)로 만든 명단에, `applyOverrides` 가 그 필터를 거치지 않은 학생을 **뒤에서 주입**하는 구조다.

**재현 — 실제로 재현했다** (학원 관리자 토큰 하나면 성립)

```
① DELETE /api/students/3           → active=false (assignedBusId=1 유지)
② GET  /api/students               → 박도윤 빠짐 ✅ (여기까진 정상)
③ POST /api/route-plans/simulate   {"busId":1,"direction":"DROPOFF",
     "overrides":[{"studentId":3,"action":"ADD","lat":37.5061,"lng":127.0299}]}
   → 200. candidate.stops = [(3,박도윤), (1,김민준), (2,이서연)]   ← 퇴원생 포함
④ POST /api/route-plans/simulate/apply  (같은 body)
   → 200. 계획 id 3 / version 3 / status PUBLISHED
```

**DB 실측 결과**

```
 plan | version |  status   | sid |  name  | active
    3 |       3 | PUBLISHED |   3 | 박도윤 | f      ← 비활성인데 배포된 노선의 정차
    3 |       3 | PUBLISHED |   1 | 김민준 | t
    3 |       3 | PUBLISHED |   2 | 이서연 | t
```
학생 3의 `bus_id` 도 1로 (재)배정됐다.

**실제 피해가 나는 지점** — 조회 화면은 `getActiveRoster` 를 쓰므로 퇴원생이 안 보이지만, **계획의 `stops` 를 직접 읽는 경로**에서 새어 나온다. 특히 `DriveSessionCommandService.checkSession` 이 `plan.getStops()` 를 순회하며 `ApproachEvent`·`NoShowEvent` 를 발행한다(코드 확인) — 즉 **퇴원한 학생의 보호자에게 "곧 도착"·"미승차" 알림이 발송된다.**

**권장 수정** — 두 곳에서 `findById` 직후 `student.isActive()` 를 검사해 `ADD`·`MOVE` 대상이 비활성이면 `INVALID_INPUT` 으로 거부한다. `REMOVE` 는 비활성이어도 허용해야 한다(빼는 건 언제나 안전). 회귀 테스트도 없으므로 함께 추가한다.

> 참고: 이 구멍은 **I-3(미저장)과는 무관**하다. 시뮬레이션 자체는 아무것도 저장하지 않는 것이 런타임으로 확인됐고, 저장은 `apply` 에서만 일어난다.

**보조 구멍(파급 제한적)**
- `PATCH /api/students/{id}/assignment` 로 비활성 학생에게 버스·정류장을 배정할 수 있다(화면엔 안 나타남)
- `confirmAutoAssign` TOCTOU — `autoAssign` 직후 학생을 퇴원시키고 `confirm` 하면 비활성 학생이 든 계획이 승인·배포된다

### 🟡 M-1 (Medium) — `POST /api/buses` 로 만든 버스는 승하차 기록이 영구히 불가능하다

`CreateBusRequest` 에 `attendantId` 필드가 **없어** 새로 만든 버스는 항상 `attendant_id IS NULL` 이다. 그 상태에서 `POST /api/ride-events` 는 I-2(담당 선탑자 본인만) 때문에 **전부 403** 이 된다. 관리자가 `PATCH /{id}/assignment` 로 선탑자를 따로 붙이기 전까지 그 버스는 "반쯤 죽은" 상태다.

I-1 본문이 *"버스 생성 API가 선탑자 없이도 생성 가능해야 하므로 스키마 제약을 걸지 않는다"* 고 스스로 허용한 예외라 **위반은 아니다.** 다만 생성 직후 무엇을 더 해야 하는지 API 응답·Swagger 어디에도 안내가 없다.

> 시드·로컬 DB 실측은 100% 충족(`attendant_id IS NULL` 0건)이고, **API 로 선탑자를 떼어낼 수는 없다**(`assign` 은 `attendantId != null` 일 때만 동작).

---

### 🟡 M-2 (Medium) — `POST /api/members` 가 `STUDENT` 역할을 막지 않는다

`MemberCommandService.register` 는 `PLATFORM_ADMIN` 만 거부한다. 결정 **D-N** 은 *"학생은 로그인 계정(`User`)을 만들지 않는다 — 쓰지도 않을 계정을 만들면 비밀번호가 걸린 유령 계정만 늘어난다"* 고 규정하고 Swagger 설명도 "학생은 여기서 만들지 않는다"고 적혀 있는데, **코드가 이를 강제하지 않는다.**

---

### 🟡 M-3 (Medium) — 컨트롤러 권한 테스트 공백

`@PreAuthorize` 를 고정하는 MockMvc 테스트가 없는 컨트롤러: `/api/route-plans/simulate`·`/simulate/apply`, `/api/location-change-requests/**`, `/api/buses/**`, `/api/students/**`, `/api/locations/children/buses`. 서비스 단 인가 테스트만 있어 **누가 애너테이션을 지워도 190개 테스트가 그대로 통과한다.**

---

### 🟢 L-1 ~ L-4 (Low)

- **L-1** 같은 버스에 `IN_PROGRESS` 세션이 2건 공존 가능. 중복 방지 가드가 `(bus, direction, date)` 단위라 등원·하원이 동시에 진행 중이 된다(런타임 재현). 버스 한 대가 등·하원을 동시에 할 수는 없다
- **L-2** `PATCH /api/route-plans/{id}/publish` 를 **구버전 행**에 걸 수 있어 같은 bus·direction 에 `PUBLISHED` 가 복수 생기고, `DriveSessionCommandService.start` 의 `.findFirst()` 가 낡은 계획을 집을 수 있다
- **L-3** `PATCH /api/members/{id}` 로 버스에 배정된 `DRIVER` 의 역할을 바꾸면 `bus.driver_id` 가 DRIVER 아닌 사람을 가리키게 된다
- **L-4** `CreateMemberRequest` 에 `photoUrl` 이 없어 구성원 생성 시 사진을 못 넣는다(생성 후 `PATCH` 필요). 유실은 아니다
- **L-5** 시드의 `route_plan`(4200m/900s)이 리터럴이라 엔진 실계산값(~4618m)과 달라, `simulate` 를 빈 override 로 부르면 아무것도 안 바꿨는데 `delta +657m` 로 보인다. **시드 아티팩트지 코드 결함은 아니지만**, Swagger 로 처음 만져보는 사람이 오해한다
- **L-6** I-7 의 blocker 테스트가 기사 케이스만 고정. 선탑자·보호자 blocker 는 미고정

## 4. 런타임 E2E — 기능 실패 0건

시드 초기화 후 실제 HTTP 호출 36단계. 전부 기대대로였다.

| 시나리오 | 결과 |
|---|---|
| S1 선탑자 하루(`/buses/me` → 세션 → 명단 → 기록) | ✅ 명단 3/3에 `photoUrl` 존재 |
| **D-K 좌표 우선순위** | ✅ 김민준 `lat=37.5002`(학생 자체 좌표) — 정류장 A(`37.5010`) 아님. 자체 좌표 없는 이서연만 정류장으로 폴백 |
| S2 기사 권한 경계 | ✅ 승하차 기록 **403**, 운행 시작·위치 보고 **200**(D-J 유지) |
| S3 관제 종합 응답 | ✅ 한 응답에 버스+기사+선탑자+`plans[].polyline`(7점)+`stops`(3)+`roster`+보호자 |
| S4 시뮬레이션 3종 | ✅ REMOVE `stopCount -1`, ADD `+1`, `seatCapacity` 채워짐 |
| **I-3 미저장** | ✅ simulate 6회 후에도 `route_plan` 1건 유지 |
| S5 학부모 | ✅ 자녀 버스만, 자녀 승하차만(같은 버스 타 학생 미노출) |
| **S6 크로스 테넌트 격리** | ✅ **8/8 전부 403** (가온 선탑자→한빛 자원 7건, 한빛 관리자→가온 버스 1건) |
| S7 플랫폼 관리자 | ✅ `?tenantId=1` 200, 생략 시 400(설계상 정상) |

지도 API는 실제 NCP 키로 동작 확인 — 위치 변경 4분기(APPLIED·REPLANNED·BLOCKED·REJECTED) 전부 재현.
