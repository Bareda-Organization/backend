# Swagger 최신화 점검 보고

- 작성일: 2026-08-01
- 범위: 백엔드 컨트롤러 14개 / REST 엔드포인트 68개 전수 + `OpenApiConfig` · `SecurityConfig` · `application.yml` · `build.gradle` · `docs/API_SPEC.md`
- 방법: 에이전트 4대 병렬 정적 대조(코드 ↔ 애너테이션 ↔ 시드 ↔ 프론트 호출부 ↔ 사양 문서). 앱을 기동한 `/v3/api-docs` 실측은 하지 않음(Docker 필요)
- **코드는 수정하지 않았다. 보고만 한다.**

## 0. 한 줄 결론

**Swagger 는 "낡은" 게 아니라 "비어 있다"** — 엔드포인트 68개 중 Swagger UI 에 설명 한 줄이라도 뜨는 것은 **0개**이고, 붙어 있는 `@Operation` 18개는 전부 MVP 그룹 태깅 전용이라 문서로서 기능하지 않는다.

## 2. 핵심 발견 (심각도 High)

### H1. Swagger UI 에 표시되는 설명이 0줄이다 — 이번 점검의 근본 결론

`@Operation(summary)` 과 `@ApiResponse` 가 저장소 전체에 하나도 없다. 그 결과 68개 엔드포인트 전부가 **메서드명(`operationId`)만 노출**된다 — `tenant`, `children`, `me`, `list` 같은 이름만 보이고 무슨 API 인지 알 수 없다.

컨트롤러에는 한글 Javadoc 이 촘촘히 달려 있지만 **Swagger 에 렌더링되지 않는다.** `backend/build.gradle:51` 에 `springdoc-openapi-starter-webmvc-ui:3.0.3` 만 있고 Javadoc 을 OpenAPI 로 옮겨주는 `therapi-runtime-javadoc` 이 없기 때문이다. 즉 **"코드에는 설명이 있는데 문서에는 없는" 상태**이며, 이 한 가지가 아래 Med 지적 대부분의 원인이다.

파생 문제:
- springdoc 은 `@PreAuthorize` 를 렌더링하지 않으므로 **68개 전 엔드포인트의 역할 제한이 UI 에 안 보인다.** 5계층 권한 제품에서 상시 리스크.
- 이름이 비슷한 API 를 구분할 수 없다. 예: `LocationController` 의 `GET /bus/{busId}`(= 그 버스에 탄 **학생들의** 위치, `LocationView`) 와 `GET /buses`(= **버스의** 위치, `BusLocationView`) 가 설명 없이 나란히 노출된다.

### H2. `00. MVP 사용 API` 태그가 스스로 한 주장을 지키지 못한다

`OpenApiConfig.java:40-41` 의 태그 설명은 *"실제로 쓰는 API만 모은 묶음 — 새 프론트엔드가 호출할 대상"* 이라고 단정한다. 그러나 양방향으로 어긋난다.

## 4. 컨트롤러별 주요 지적 (Med 이하 요약)

**공통 반복 항목 — `tenantId` 쿼리 파라미터 (7곳)**
`MemberController:53`, `StudentController:57`, `ScheduleController:78`, `LocationController:89,109`, `AttendanceController:78`, `SosController:84`, `RouteController:48`, `BusController:60`, `DriveSessionController:80`, `RoutingController:104`, `NotificationController:48` 이 모두 `required=false` 로 "선택" 표시되지만, `TenantGuard.java:23-27` 에 따라 **플랫폼 관리자에게는 필수**다(생략 시 400 "tenantId가 필요합니다"). 시드의 `platform@school.com` 으로 Try-it-out 하면 그대로 400 이 난다. 프론트도 이 함정을 코드 주석으로 감당 중(`notification_feed_controller.dart:183`).

**상태 전이 409 미문서화 (3곳)**
`ScheduleController:52,60` (`ScheduleChangeRequest.java:69-80`), `AttendanceController:52,60` (`AttendanceException.java:69-79`), `SosController:51,59` (`SosEvent.java:71-83`) — 이미 처리된 요청을 다시 승인/반려하면 409. 특히 SOS 는 "확인 없이 바로 종료"가 반드시 실패하는데(`OPEN→ACKNOWLEDGED→RESOLVED` 단방향) 어디에도 안내가 없다.

**WebSocket 실시간 채널이 Swagger 에서 완전히 보이지 않는다**
`LocationSocketController` 는 `@MessageMapping` 이라 springdoc 이 스캔하지 않는다. 실제 채널은 핸드셰이크 `/ws/location` + 전송 목적지 **`/app/location`** + `/topic/tenant/{tenantId}/notifications` + `/user/queue/notifications`(`WebSocketConfig.java:39,44`, `WebSocketNotificationSender.java:34-44`)이고 프론트는 알림 2개를 실제 구독한다.
다만 **문서가 없는 게 아니다** — `docs/API_SPEC.md:1785-1879`(§16)에 상세히 정리돼 있다. 공백은 "Swagger 에서 거기로 가는 길이 없음"이므로 `OpenApiConfig` info description 에 한 줄 + 링크면 충분하다.

**`attendance` 와 `rideevent` 의 경계가 태그 설명만으로 구분되지 않는다**
Attendance 는 `targetDate` 기반 **사전 신고**(승인 워크플로), RideEvent 는 `occurredAt` 기반 **사후 탑승 기록**이다. 둘을 잇는 고리는 `AttendanceApprovedEvent`(승인 시 당일 명단 스킵)인데 어느 태그에도 없다.

**응답 DTO 의 `@Schema` 비대칭**
요청 DTO 에는 `@Schema` 가 꼼꼼한데 응답 DTO 에는 거의 없다(`BusResponse`, `RouteResponse`, `TenantResponse`, `MemberResponse`, `TokenResponse`, `StudentDetailResponse` 등). 특히 `StudentDetailResponse` 는 `student` 를 중첩 객체로 감싼 구조라 오해 소지가 큰데 설명이 없다.

**null 의 의미가 문서에 없다**
`UpdateStudentAssignmentRequest.java:9-10` — null 은 "배정 해제"가 아니라 **"변경 안 함"** 이다(`StudentCommandService.java:100-107` 이 `!= null` 일 때만 갱신). 현재 API 에 배정 해제 수단이 없다는 뜻이기도 하다.

**`auto-assign` 의 미문서화 동작 2가지**
① `RoutingCommandService.java:154-159` 는 좌표 없는 학생을 에러 없이 `excludedStudentNames` 로 조용히 제외하는데, 같은 파일 `:340-342` 의 `generate` 는 같은 상황에서 **400 을 던진다**(두 API 동작이 정반대). ② `:166` 이 `assignCapacity` 가 아니라 `bus.getSeatCapacity()`(물리 좌석)를 쓴다.

**시드에 데이터가 없어 항상 빈 결과인 조회 API**
`ride_event`, `notification_log`, `schedule_change_request` 는 `V2__seed_data.sql` 의 INSERT 대상 8테이블에 없다. 해당 조회 API 는 Swagger 시연 시 항상 `[]` 이고, schedule 의 approve/reject 는 선행 POST 없이는 항상 404 다.

**형식 일관성 (Low)**
- `SosController.java:29` 의 `"13. SOS"` 만 `NN. 한글명(영문)` 패턴을 벗어남 → `"13. 긴급(SOS)"` 로 통일 권장

- `application.yml:85` 주석이 접두사를 `"0. "` 라 적었으나 실제는 두 자리(`"00. "`/`"01. "`)
- `OpenApiConfig.java:26` 주석이 MVP 태그 사용 컨트롤러를 5개로 열거하나 실제는 6개(Bus 누락)

- `AttendanceController.java:44` 는 생성 API 인데 `@ResponseStatus` 없이 **200** 을 반환한다(`ApiResponse.ok(...)`). 201 이 아님이 문서에 없음

## 5. 점검했고 **문제 없던** 항목

- **`@Tag` 번호 체계 01~14 — 중복·결번 없음.** 메서드 `@Operation(tags={…})` 8곳도 클래스 `@Tag` name 과 문자열이 한 글자도 다르지 않아 오타로 인한 유령 태그가 없다
- **유령 API·미문서화 API 없음.** `docs/API_SPEC.md` 부록 A(1884~1958행) 68행과 실제 컨트롤러 엔드포인트 68개가 1:1 일치. HTTP 메서드·경로변수명까지 동일
- **프론트가 호출하는 REST 경로 전부 실존.** 계약이 깨진 곳 없음
- **응답 DTO ↔ 엔티티 매핑 정합.** `RideEventResponse`(13필드)·`BusLocationView`(6)·`LocationView`(6)·`NotificationResponse`(6)·`AttendanceExceptionResponse`(9)·`SosEventResponse`(11) 모두 `from()` 과 일치, 누락·유령 필드 없음
- **id·좌표 example 대부분 시드와 정확히 일치.** `driverId=3`(박기사), `routeId=1`, `tenantId=1`(한빛학원), `busId=1`(3호차), `studentId=1`(김민준), `stopId=1`, 좌표 3종 모두 맞음. enum example(`BOARD`, `DRIVER`, `ABSENCE`)도 실존 값
  - ⚠️ **단, 이 정합성은 시퀀스 전제 위에서만 성립한다.** 시드가 시퀀스 기반이라 `docker compose down`(컨테이너 제거) 없이 `stop`/`start` 로 재기동하면 id 가 밀려 example 이 전부 어긋난다. CLAUDE.md 의 "볼륨 없는 postgres → 매번 Flyway 재구성" 운용을 지켜야 유효하다
- **부분 갱신·결석 제외 등 Javadoc 서술이 구현과 일치** (`BusCommandService.java:69-74`, `DriveSessionQueryService.java:67`)
- **2026-07-29 배차 최적화 검증 보고서와 `@Operation` 이 어긋난 곳 없음** — 단, 어긋날 수 없는 이유가 "정확해서"가 아니라 설명 자체가 없어서다. ⚠️ 향후 `auto-assign` 에 summary 를 넣을 때 그 보고서의 한계 L1(정원↔클러스터 크기 미조정)·L2(버스 간 거리 불균형)를 함께 적지 않으면, **그 순간 문서가 틀린 주장을 하게 된다**

### 6-1. 6번에 대한 보충

`build.gradle` 에 아래를 추가하면 이미 잘 쓰여 있는 한글 Javadoc 이 Swagger 설명으로 자동 반영된다. 엔드포인트 68개에 `summary` 를 손으로 다는 것보다 압도적으로 싸고, 이후 Javadoc 만 관리하면 되므로 재드리프트도 덜하다.

implementation 'org.springdoc:springdoc-openapi-starter-common:3.0.3'

## 7. 이번 점검의 한계

- **앱을 기동하지 않았다.** `/v3/api-docs` 실물 JSON 을 받아 보지 않았으므로, springdoc 이 런타임에 스키마를 어떻게 병합하는지(특히 제네릭 `ApiResponse<T>` 래퍼의 전개)는 검증 대상이 아니었다. 실물 확인이 필요하면 `docker compose up -d postgres redis kafka` 후 `./gradlew bootRun` 이 선행돼야 한다
- Try-it-out 실패 5건은 **코드·스키마·시드 정적 대조로 판정**했고 실제 HTTP 호출로 재현하지는 않았다. 다만 보호자 연결 500 건의 전제(unique 제약 + 시드 중복 행)는 마이그레이션 파일에서 직접 확인했다
- `@PreAuthorize` 는 애너테이션 값만 읽었고 SpEL 평가나 메서드 내부 추가 검증까지 전부 추적하지는 않았다(주요 서비스는 확인)
