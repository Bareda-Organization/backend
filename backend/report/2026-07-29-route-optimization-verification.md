# 배차 최적화 실측 검증 — 다중 버스·상이 정원

- 일자: 2026-07-29
- 질문: **경로 제안이 실제로 학생 승하차지·버스 가용 인원수·경로를 토대로 최적화되는가**
- 방법: 로컬 DB(`school-bus-postgres-1`)에 **통제된 테스트 데이터를 직접 주입**하고 `POST /api/route-plans/auto-assign` 실 응답을 알고리즘 예측·완전탐색 최적해와 대조
- **코드는 수정하지 않았다.** 검증만 했다.

## 요약

| # | 검증 항목 | 판정 |
|---|---|---|
| **V1** | 버스별 **정원 상한**을 지키는가 | ✅ 지킨다 |
| **V2** | **총 정원 초과** 시 거부하는가 | ✅ 거부한다 (명확한 메시지) |
| **V3** | 승하차지 **위치 기반 클러스터링**인가 | ✅ depot 기준 방위각으로 묶는다 |
| **V4** | 버스 내 **방문 순서 최적화**가 실제로 개선하는가 | ✅ **naive 대비 56% 단축, 최적해와 0.03% 차이** |
| **V5** | 등원/하원 **양방향** 동작 | ✅ 하원은 등원의 역순(대칭성 활용) |
| **L1** | 버스 **정원과 클러스터 크기를 맞추는가** | ❌ **안 맞춘다** — 아래 참조 |
| **L2** | 버스 간 **운행거리 균형**을 맞추는가 | ❌ 안 맞춘다 |

**한 줄 결론**: 최적화는 **실제로 작동한다.** 정원은 하드 제약으로 지켜지고, 위치 기반으로 묶이며, 버스 안에서의 방문 순서는 사실상 최적이다. 다만 **"어느 버스에 몇 명을 태울지"는 최적화 대상이 아니다** — 방위각 순으로 자른 뒤 버스 id 순서대로 좌석수만큼 채울 뿐이라, 큰 버스가 넓은 지역을 맡게 되는 우연이 그대로 결과가 된다.

## 알고리즘이 주장하는 것 (소스 확인)

`SweepAssigner`(`routing/engine/impl/SweepAssigner.java`) — **버스 배정**
1. 총원 > 총 정원이면 `Optional.empty()` → 400
2. depot 기준 **방위각**(`GeoMath.bearingDegrees`)으로 학생 정렬
3. 버스를 **파라미터 순서대로**(= `RoutingCommandService:143` 에서 `Bus::getId` 정렬) 순회하며 좌석수만큼 순차로 채움

`HeuristicRouteEngine`(같은 패키지) — **방문 순서**
- sweep = 결정적 초기 순서(타이브레이커)만 제공
- 실제 경로는 **nearest-neighbor** 로 구성 → **2-opt** 로 개선 (최대 1000 pass)
- 거리 함수는 Haversine(외부 호출 0). 실도로 거리·ETA 는 순서 확정 후 `MapRouteClient` 1회 호출

## 테스트 케이스 1 — 정원이 서로 다른 버스 3대

**한빛학원(tenant 1)은 기사앱 점검용으로 손대지 않고, 가온에듀(tenant 2)에 구성했다.**

- depot: `37.4980, 127.0276`
- 버스 3대, **정원을 일부러 다르게**: `4석` / `6석` / `3석` = 총 13석
- 학생 12명을 depot 기준 **방위각 15°~340°** 에 800m 반경으로 균등 배치
  (승차 정류장과 하차지를 같은 좌표로 둬서 두 방향 모두 예측 가능하게 함)

### 사전 예측

알고리즘대로라면 방위각 순으로 잘라 버스 id 순서대로 채우므로:

| 버스(id 순) | 정원 | 예측 |
|---|---|---|
| 3 | 4 | 15°, 40°, 65°, 100° |
| 8 | 6 | 130°, 160°, 190°, 220°, 250°, 280° |
| 9 | 3 | 310°, 340° (남은 2명) |

### 실제 응답 (`POST /api/route-plans/auto-assign`, PICKUP)

```
버스 3  정차 4곳  거리 3500m  소요 1016s  학생 [7, 8, 9, 10]
버스 8  정차 6곳  거리 7529m  소요 1975s  학생 [11,12,13,14,15,16]
버스 9  정차 2곳  거리 3815m  소요 1205s  학생 [18, 17]
```

학생 id ↔ 방위각 매핑(DB 확인): `7=15° 8=40° 9=65° 10=100° 11=130° … 17=310° 18=340°`

→ **예측과 완전히 일치한다.** V1·V3 확인.

### 정원 초과 (V2)

학생 2명을 추가해 14명(> 13석)으로 만들고 재요청:

```
결과: 거부
메시지: 전체 정원(13명) 초과: 대상 14명
```

정원은 **하드 제약**이다. 조용히 넘치거나 일부를 버리지 않는다.

### 하원 (V5)

```
버스 3  정차 4  거리 5600m  학생 [10, 9, 8, 7]
버스 8  정차 6  거리 5762m  학생 [16,15,14,13,12,11]
버스 9  정차 2  거리 2365m  학생 [17, 18]
```

등원의 **역순**이다. `RoutingCommandService:360` 주석("대칭거리에서 depot 고정 최적경로를 뒤집어도 총거리는 동일")대로 동작한다. 실도로 거리가 방향별로 다른 건 정상 — 일방통행·회전 제약 때문이다.

## 테스트 케이스 2 — 방문 순서 최적화 (V4)

케이스 1의 학생들은 **같은 반경의 원 위**에 있어 방위각 순서가 곧 최적 경로였다. 순서 최적화가 실제로 일하는지는 이걸로 알 수 없어, **방위각 순서가 명백히 나쁜** 배치를 따로 만들었다.

- 버스 1대(6석), 학생 6명
- 방위각은 10°→85° 로 단조 증가시키되 **반경을 1600m ↔ 300m 로 교대** → 방위각 순으로 가면 안팎을 왕복하게 된다

| 순서 | 총 이동거리(Haversine, depot 출발 open-path) |
|---|---|
| 방위각 정렬(naive) | **8,159m** |
| **엔진(NN + 2-opt)** | **3,578m** |
| 완전탐색 최적해(6! = 720) | **3,577m** |

엔진이 낸 순서: `가까운 3개(85°→55°→25°) → 먼 3개(10°→40°→70°)`
완전탐색 최적해: `25°→55°→85° → 70°→40°→10°` (거울상)

→ **naive 대비 56% 단축, 완전탐색 최적해와 0.03% 차이.** 순서 최적화는 확실히 작동하며 이 규모에서는 사실상 최적이다.

## 발견한 한계 — 개선 여지 (지금 고장은 아니다)

### L1. 버스 정원과 클러스터를 맞추지 않는다

방위각으로 자른 뒤 **버스 id 순서대로** 채우므로, 어느 버스가 어느 지역을 맡을지는 **버스 id 순서라는 우연**이 정한다.

케이스 1 결과가 그대로 보여준다:

| 버스 | 정원 | 담당 방위각 폭 | 실도로 거리 |
|---|---|---|---|
| 3 | 4석 | 15°~100° (**85°**) | 3,500m |
| 8 | 6석 | 130°~280° (**150°**) | **7,529m** |
| 9 | 3석 | 310°~340° (30°) | 3,815m |

정원이 큰 버스가 우연히 **넓은 부채꼴**을 맡아 운행거리가 2배 이상 벌어졌다. 학생 수는 정원대로 맞지만 **기사 부담은 안 맞는다.**

### L2. 버스 간 운행거리 균형이 없다

L1 의 결과다. 총 거리 합을 줄이거나 최장 노선을 줄이는 목적함수가 **없다**. sweep 은 "겹치지 않게 나눈다"까지만 한다.

### 개선하려면

- **버스를 정원 내림차순으로 순회**하면 큰 버스가 먼저 채워져 조금 나아지지만 근본 해결은 아니다
- 제대로 하려면 클러스터 경계를 정할 때 **거리 비용을 목적함수에 넣어야** 한다(예: capacitated k-means → sweep 대신)
- **MVP 범위에서는 지금으로 충분하다** — 정원이 지켜지고 지역별로 묶이면 실무상 배차는 성립한다. 위 표를 관리자 화면에 그대로 보여주면(버스별 거리·인원) **관리자가 눈으로 보고 수동 조정할 근거**가 된다
