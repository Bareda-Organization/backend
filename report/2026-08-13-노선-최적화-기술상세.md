# 노선 최적화 — 노선 설정 방식과 알고리즘 (쉬운 설명)

> 작성 2026-08-13 · 기준 브랜치 `feat/mvp-deployment` · 근거는 전부 실제 코드 실측(`backend/src/main/java/src/backend/routing/`)

---

## 0. 한 줄 요약

**"어느 버스에 누구를 태울지"는 방위각으로 부채꼴처럼 잘라 정하고(Sweep), "어떤 순서로 돌지"는 직선거리 기준 근사 알고리즘(nearest-neighbor + 2-opt)으로 정한 다음, 확정된 순서에 대해서만 외부 지도 API를 한 번 불러 실제 도로 거리·ETA를 채우는 구조.**

---

## 1. 용어 정리 — "노선"이 두 가지 의미로 쓰임

혼동이 가장 잦은 지점이라 먼저 가름.

| 모듈 | 대상 | 성격 | 설명 |
|---|---|---|---|
| `route/` | `Route` · `Stop` | 사람이 등록하는 **마스터 데이터** | 정류장 이름·좌표를 관리자가 CRUD 로 등록. 알고리즘 개입 없음 |
| `routing/` | `RoutePlan` · `RoutePlanStop` | 서버가 계산하는 **하루치 운행 계획** | 이 문서가 다루는 대상. 자동 계산·버전 관리·승인·배포 |

즉 **"노선 최적화"의 산출물은 `Route` 가 아니라 `RoutePlan`**. `RoutePlan` 은 (버스 1대 × 방향 1개 × 운행일 1일)당 1건이며, 재계산할 때마다 `version` 을 올린 **새 행**으로 쌓임.

또 하나 중요한 전제 — **최적화 단위는 정류장이 아니라 학생 1명**. `RoutePlanStop` 은 `studentId` 를 들고 있고, 정차 좌표는 학생별로 해석됨(§4).

---

## 2. 전체 파이프라인 6단계

관리자가 "자동 배정" 버튼을 눌렀을 때 서버 안에서 벌어지는 흐름.

1. **명단 확정** — `ActiveRosterReader` 가 활성 학생 중 그날 **승인된** 결석·휴원자를 뺀 "오늘 실제 태울 명단"을 만듦. (신청·반려 상태는 제외 사유가 아님)
2. **좌표 해석** — 학생마다 방향별 좌표를 뽑음. 좌표가 없는 학생은 자동배정에서는 `excludedStudentNames` 로 빠지고, 단일 버스 생성(`/generate`)에서는 400 으로 거부.
3. **버스 배정 (Sweep)** — `SweepAssigner` 가 학생을 버스별로 나눔. 여기까지가 "누구를 어느 차에".
4. **방문 순서 최적화 (NN + 2-opt)** — `HeuristicRouteEngine` 이 버스 한 대의 명단을 받아 도는 순서를 정함. **직선거리(Haversine)만 사용 → 외부 호출 0회.**
5. **실도로 경로 조회** — 순서가 확정된 뒤에야 `MapRouteClient`(네이버 Direction 15 기본, OSRM 대체)를 호출해 실제 도로 거리·소요시간·polyline 획득.
6. **저장·상태전이** — `RoutePlan` 을 `version+1` 새 행으로 저장 → `APPROVED` → `PUBLISHED`. 배포돼야 기사·선탑자 앱에 노출.

**4번과 5번의 분리가 이 설계의 핵심.** 순서를 정하는 과정에서는 후보 순서를 수백~수천 번 비교하는데, 그때마다 지도 API 를 부르면 호출 수가 폭발함. 그래서 **비교는 공짜인 직선거리로, 최종 확정 1개만 유료 API 로** 채우는 방식.

> 비유 — 여행 코스를 짤 때 지도 위에 자로 직선을 그어 대충 순서를 잡고(공짜), 순서가 정해진 뒤 내비게이션에 한 번만 찍어 실제 소요시간을 확인하는 것과 같음.

## 3. 알고리즘 ① 버스 배정 — Sweep (방위각 정렬)

**한 줄 요약: 학원을 중심에 두고 시계 방향으로 훑으면서(sweep), 버스에 좌석 수만큼 순서대로 담는 방식.**

`SweepAssigner.java:24`

1. 전체 인원 > 전체 좌석 합이면 즉시 실패(빈 결과 → 400 "전체 정원 초과").
2. 학원(depot) 기준으로 각 학생 좌표의 **방위각**(0°=정북, 90°=정동)을 구해 오름차순 정렬. → `GeoMath.bearingDegrees`
3. 버스를 **id 오름차순**으로 순회하며 `seatCapacity` 만큼 앞에서부터 잘라 담음.

```java
// SweepAssigner — 정렬 후 순차 절단이 전부
List<Long> sortedStudentIds = studentPoints.entrySet().stream()
        .sorted(Comparator.comparingDouble(e -> GeoMath.bearingDegrees(depot, e.getValue())))
        .map(Map.Entry::getKey)
        .toList();
```

**왜 방위각인가** — 학원 기준으로 같은 방향에 사는 학생끼리 자연스럽게 묶임. 피자를 부채꼴로 자르는 것과 같은 발상이라, 한 버스가 동서남북을 헤집고 다니는 배정이 나오지 않음. 계산이 단순하고 **결과 설명이 쉬움**("이 차는 북쪽 담당")이 실무 채택 이유.

**반영하는 제약은 좌석 수 하나뿐**. 시간창(몇 시까지 도착), 버스 간 부하 균등, 기사 배정 여부, 학생별 우선순위는 **미반영**. 그래서 정원이 넉넉하면 1호차에 전원이 몰릴 수 있음(실제로 E2E 검증에서 6명 전원이 bus1 에 배정된 사례가 기록돼 있음).

## 4. 알고리즘 ② 방문 순서 — Sweep → nearest-neighbor → 2-opt

**한 줄 요약: 가까운 곳부터 욕심껏 이어 붙여 초안을 만든 뒤(NN), 꼬인 구간을 뒤집어 펴는(2-opt) 2단 구성.**

`HeuristicRouteEngine.java:29`

### 1단계 — sweep 정렬 (초기 순서 고정)

방위각 순으로 후보 목록을 정렬. 여기서는 **순서를 정하는 게 아니라 "동률일 때 누가 먼저인지"를 결정적으로 고정**하는 용도. 이게 없으면 `Map` 순회 순서에 따라 같은 입력이 매번 다른 노선을 뱉을 수 있음.

### 2단계 — nearest-neighbor (그리디 초안)

학원에서 출발해 **현재 위치에서 가장 가까운 미방문 학생**을 계속 골라 이어 붙임. 계산량 O(n²).

```java
LatLng current = depot;
while (!remaining.isEmpty()) {
    // remaining 중 current 에서 최단 거리인 학생을 골라 tour 에 추가
}
```

한계 — 눈앞의 최단만 보므로, 마지막에 혼자 멀리 떨어진 학생이 남아 크게 되돌아가는 경로가 나오기 쉬움.

### 3단계 — 2-opt (구간 반전 개선)

경로에서 **두 지점을 잡아 그 사이 구간을 통째로 뒤집었을 때** 총거리가 줄면 채택. 더 이상 줄지 않을 때까지 반복(방어적 상한 1000 pass).

- 지그재그로 교차하던 경로가 펴지는 효과. 실뜨기에서 꼬인 줄을 한 번 뒤집어 푸는 것과 같음.
- **구간 내부 간선은 뒤집어도 길이가 같으므로, 바뀌는 두 경계 간선만 비교**하면 됨 → 비교 1회가 O(1).
- 학원(depot)을 인덱스 −1 의 가상 노드로 취급하는 **open-path 2-opt**. 출발점은 고정, 도착점은 자유.
- 매 교환마다 총거리가 엄격히 줄어들어 반드시 수렴. `MAX_TWO_OPT_PASSES = 1000` 은 부동소수 오차 대비 안전장치.

### 이 알고리즘의 성격

| 항목 | 값 |
|---|---|
| 문제 종류 | open-path TSP(외판원 문제, 시작점 고정·종료점 자유) |
| 해의 품질 | **최적해 보장 없음** — 지역 최적(local optimum)에 수렴하는 근사 |
| 거리 함수 | Haversine 직선거리(지구 반지름 6,371km) — 도로·일방통행·신호 미반영 |
| 외부 호출 | **0회** |
| 검증 | 단위 테스트 4건(빈 입력 / 단일 지점 / 순열 보존 / 지그재그 대비 총거리 개선) |

## 5. 등원과 하원 — 뒤집기 트릭

**한 줄 요약: 계산은 항상 "학원에서 출발"로 한 번만 하고, 등원은 그 결과를 뒤집어 씀.**

`RoutePlanComputer.java:43`

| 방향 | 실제 운행 | 내부 처리 |
|---|---|---|
| `DROPOFF`(하원) | 학원 출발 → 학생들 하차 | 최적화 결과 그대로. waypoint = `[학원, 정차1, 정차2, ...]` |
| `PICKUP`(등원) | 학생들 승차 → 학원 도착 | 최적화 결과를 **역순**으로. waypoint = `[정차1, ..., 학원]` |

근거는 **대칭 거리에서 경로를 뒤집어도 총거리가 같다**는 성질. 덕분에 알고리즘을 두 벌 만들 필요가 없음.

**좌표를 어디서 읽는지가 방향마다 다름** (`RoutePlanComputer.pointOf`):

- `PICKUP` → 학생 본인 좌표(`pickupLat/Lng`)를 **우선**, 없을 때만 공유 정류장(`boardingStop`)
- `DROPOFF` → `dropoffLat/Lng` 만. 없으면 null

우선순위가 뒤집히면, 학부모가 등원 위치를 바꿔도 계산은 계속 정류장을 읽어 **변경이 조용히 무효**가 됨. 반대로 `Stop.lat/lng` 를 고치는 방식은 같은 정류장을 쓰는 다른 학생까지 함께 끌려가므로 금지.

**ETA 기준점** — 구간별 소요시간을 누적해 정차마다 채움. `DROPOFF` 은 학원 출발 시각 기준(첫 정차 ETA > 0), `PICKUP` 은 **첫 승차 지점 출발 기준**이라 첫 정차 ETA 가 0.

## 6. 외부 지도 API 계층 — 포트 하나에 어댑터 둘

`MapRouteClient` 인터페이스(port) 하나에 구현체 2개. `routing.provider` 설정으로 **한 개만** 주입됨(`@ConditionalOnProperty`).

| 구현체 | 활성 조건 | 특징 |
|---|---|---|
| `NaverMapRouteClient` | `routing.provider=naver` (**기본값**) | NCP Direction 15. 실키 E2E 검증 완료 |
| `OsrmMapRouteClient` | `osrm` 또는 설정 자체가 없을 때 | 공개 데모 서버, 키 불필요 |

실키 검증에서 드러난 함정이 코드 주석에 그대로 남아 있음 — 그대로 옮기면:

1. 경유지 상한은 실제 **5개**(start+goal 포함 총 7개). `routing.max-waypoints: 7` 초과 시 `RoutePlanComputer.resolveRoute` 가 **경계를 공유하는 구간으로 쪼개 여러 번 호출한 뒤 병합**.
2. `option` 미지정 시 NCP 기본값이 `traoptimal` 이라 코드가 기대하는 `trafast` 키가 응답에 없어 파싱 실패 → 반드시 명시.
3. 같은 정류장 학생이 인접하면 좌표가 연속 중복되는데 NCP 가 "출발지와 도착지가 동일합니다" 400 으로 거부 → **호출 전 연속 중복을 접고, 접힌 구간은 leg 0초로 되살려 인덱스 복원**.
4. waypoints 구분자 `|` 는 `URI.create()` 로는 예외 발생 → `UriComponentsBuilder.encode()` 경유 필수.
5. NCP 는 구간별 소요시간을 주지 않아 **직선거리 비율로 안분해 근사**. (OSRM 은 실제 leg 값 제공)

즉 **총거리·총시간은 실측, 정차별 ETA 는 네이버 사용 시 근사값**이라는 점이 실무상 유의점.

## 7. request → 처리 → response (자동 배정 예)

```
POST /api/route-plans/auto-assign
{ "tenantId": 1, "direction": "PICKUP", "serviceDate": "2026-08-13" }
```

1. **Controller** `RoutingController.autoAssign` — `@CanManageRoutePlans` 로 관리자 인가.
2. **Service** `RoutingCommandService.autoAssign`
   1. `TenantGuard.resolveTenantId` 로 테넌트 격리 확인
   2. `BusRepository.findByTenantId` → id 오름차순 정렬
   3. `computer.requireDepot(tenant)` — **학원 좌표 미설정이면 다른 어떤 검사보다 먼저 실패**
   4. `ActiveRosterReader.forTenant` → 명단
   5. 좌표 해석(실패자는 `excluded` 목록으로)
   6. `BusAssigner.assign` → 버스별 학생 묶음
   7. 버스마다 `HeuristicRouteEngine` → `MapRouteClient` → `RoutePlan(status=RECOMMENDED)` 저장
3. **Repository** `RoutePlanRepository.save` — `version` 은 같은 (버스, 방향) 최신값 +1
4. **Response** `plans[]`(계획 id·거리·시간·정차 목록) + `excludedStudentNames[]`

이 시점에 **학생 배정(`student.assigned_bus`)은 아직 바뀌지 않음**. `POST /auto-assign/confirm` 에 계획 id 를 넘겨야 배정 커밋 + 승인 + 배포가 한 번에 일어남.

### 계층 매핑

| 계층 | 클래스 | 책임 |
|---|---|---|
| Controller | `RoutingController` | 인가 애너테이션, DTO 변환만 |
| Command Service | `RoutingCommandService` | 오케스트레이션(명단→알고리즘→API→저장), 트랜잭션 |
| Query Service | `RoutingQueryService` · `RoutePlanSimulationService` | 조회·비교. **아무것도 저장하지 않음** |
| 순수 계산 | `RoutePlanComputer`(concrete) | 저장·인가 없이 계산만. 시뮬레이션과 실제 저장이 **공유** |
| 전략 포트 | `RouteEngine` · `BusAssigner` | 교체 가능한 알고리즘 |
| 인프라 포트 | `MapRouteClient` | 외부 HTTP 어댑터 |
| Repository | `RoutePlanRepository` | 최신 version 조회·저장 |

`RoutePlanComputer` 를 별도로 뽑은 이유가 실무적으로 중요 — **시뮬레이션(미저장 비교)과 실제 생성이 같은 계산 코드를 타야** 화면에서 본 숫자와 저장된 숫자가 갈라지지 않음.

## 8. 상태 전이와 버전

```
DRAFT (POST /generate)
RECOMMENDED (자동배정·재계산·시뮬레이션 채택)
        └→ APPROVED (PATCH /{id}/approve)
                └→ PUBLISHED (PATCH /{id}/publish)  ← 여기서부터 기사·선탑자에게 노출 + 알림 발송
```

- 상태 검사는 엔티티 안(`RoutePlan.approve` / `publish`)에서 수행 → 잘못된 전이는 409.
- **재계산은 기존 행 UPDATE 가 아니라 `version+1` 새 행 INSERT.** 같은 버스·방향에 여러 버전이 쌓이는 게 정상이며, 이력 추적과 롤백 근거가 됨.
- 기사 조회 API 는 `PUBLISHED` 만 노출. 승인 전 초안은 보이지 않음.

## 9. 자동 재계산(replan) — 이벤트로 굴러감

`RoutingReplanEventConsumer` 가 Kafka 토픽을 구독해 **영향받는 버스만 국소 재계산**.

| 토픽 | 트리거 | 동작 |
|---|---|---|
| `attendance-approved` | 결석 승인 | 해당 학생 배정 버스 재계산 |
| `schedule-result` | 일정 변경 승인(반려는 무시) | 동일 |
| `student-assignment-changed` | 배정 버스 변경 | **이전 버스·새 버스 둘 다** 재계산(동일하면 1회) |
| `student-dropoff-changed` | 하차지 변경 | 해당 버스 재계산 |

- **"그 버스의 최신 계획의 운행일 == 이벤트 날짜"일 때만** 재계산. 무관한 날짜의 계획을 건드리지 않기 위함.
- 재계산 실패(명단 0명·정원 초과·API 오류)해도 **기존 계획을 그대로 두고 로그만 남김** — 운행 중 노선이 사라지는 사고 방지.
- 알림 모듈이 같은 `schedule-result` 토픽을 구독하므로 **consumer group 을 반드시 분리**(같은 그룹이면 메시지를 나눠 갖는 경쟁 소비가 되어 한쪽이 이벤트를 놓침).
- 학부모 위치 변경(P2)만 예외적으로 승인 단계 없이 `republishForBus` 로 재계산→승인→배포까지 직행.

## 10. 시뮬레이션 — "보여주기는 관대, 저장은 엄격"

`POST /simulate` 는 변경안(`overrides`: ADD·MOVE·REMOVE)을 얹어 다시 계산하고 **현재 최신 계획 vs 변경안**을 비교해 돌려줌. **어떤 행도 저장하지 않음.**

| 상황 | `/simulate` | `/simulate/apply` |
|---|---|---|
| 정원 초과 | 그대로 보여줌(화면이 판단) | **400 거부** |
| 좌표 없는 학생 | 조용히 제외 | 동일 |
| 퇴원(비활성) 학생 추가 | 거부 | 거부(쓰기 경로에서 재검사) |

`apply` 는 화면이 계산한 결과를 받지 않고 **`overrides` 만 받아 서버가 다시 계산**. 클라이언트가 보낸 거리·순서를 그대로 믿으면 조작된 노선이 DB 에 들어감. 대신 직전 시뮬레이션 결과를 재사용해 **지도 API 를 두 번 부르지 않도록** 설계돼 있음.

## 11. 초보자가 자주 오해하는 지점

1. **"최적화 = 최단 경로 보장"** → 아님. NN+2-opt 는 **근사 휴리스틱**이라 이론상 최적해와 차이가 있을 수 있음. 정확한 최적해(exact TSP)는 학생 수가 늘면 계산 시간이 폭발해 실무에서 쓰지 않음. "충분히 좋은 답을 즉시"가 목표.
2. **"지도 API 가 순서를 정해준다"** → 아님. 순서는 전부 자체 계산이고, 지도 API 는 **이미 확정된 순서**의 실도로 거리·시간·경로선만 채움. 이 오해를 하면 "API 를 바꾸면 노선이 좋아진다"는 잘못된 결론으로 감.
3. **"auto-assign 하면 배정이 바뀐다"** → 아님. `confirm` 전까지는 제안일 뿐이고 `student.assigned_bus` 는 그대로.
4. **"노선을 고치면 기존 계획이 수정된다"** → 아님. 항상 새 version 행. 목록에 여러 버전이 보이는 건 버그가 아님.
5. **"정류장 좌표를 옮기면 그 학생만 옮겨진다"** → 아님. `Stop` 은 여러 학생이 공유하므로 같은 정류장 학생 전원이 끌려감. 개인 위치 변경은 `student.pickupLat/Lng` 로.
6. **"직선거리로 최적화했으니 도로 기준으로도 최적"** → 아님. 강·고가·일방통행이 많은 지역에서는 직선 기준 순서가 실도로에서 뒤집힐 수 있음. 현재 구조가 감수하는 알려진 trade-off.

## 12. 현재 미반영(향후 확장 여지)

- 시간창(TW) — "몇 시까지 도착" 제약 미반영
- 버스 간 부하 균등 — 정원만 볼 뿐 균등 분산 로직 부재
- 기사 배정 여부·근무시간·보험 만료 미반영
- 같은 정류장 학생 병합 — 좌표 중복을 API 호출 직전에 접을 뿐, 알고리즘은 학생 단위 유지
- 교통 상황 반영 재계산 — 계산 시점의 `trafast` 1회 조회가 전부, 운행 중 갱신 없음
- 네이버 경유지 상한(7) 초과 시 구간 분할 병합이라, **분할 경계에서 전역 최적과 미세하게 어긋날 가능성**
